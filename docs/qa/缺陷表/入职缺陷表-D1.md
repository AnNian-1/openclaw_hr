## D-003

标题：[入职] HCM DB 与 stub-state 候选人不同步（张三 vs 测试员）  
级别：P2  
Agent / Skill：hcm-backend / seed.py（对照 stub-state）  
过程标签：`过程/假成功`（O-14 对盘风险）

发生了什么：首轮 `GET /api/candidates` 返回 6 人含「张三」(zhangsan, status=onboarding)，但 `stub-state/` 下无 zhangsan 目录；`stub-state` 有「测试员」(ceshiyuan)，HCM DB 无。两数据源候选人集合不一致，O-14 假成功查进度若引用错误数据源会对不上。  
期望：HCM DB 与 stub-state 候选人集合一致，或文档明确两数据源分工，避免 Agent 引用错误数据源。  
复现：
1. `curl -sS http://localhost:8000/api/candidates` → 含张三（zhangsan）
2. `ls stub-state/` → 无 zhangsan，有 ceshiyuan
3. 对比两数据源候选人集合

证据：首轮 HCM DB 6 人 = [郭超 / 雷武 / 李四 / 李鑫 / 张磊 / 张三]；stub-state 6 人 = [郭超 / 雷武 / 李四 / 李鑫 / 张磊 / 测试员]。删 `hcm.db` 全量重 seed 后 HCM DB = [测试员 / 郭超 / 雷武 / 李四 / 李鑫 / 张磊]，与 stub 同步，张三消失。  
是否稳定：偶发（疑为旧 seed 残留；重 seed 后未复现）

## D-004

标题：[入职/网关] 控制台 XIAOMI_API_KEY 降级提示（环境实际有值）  
级别：P3  
Agent / Skill：gateway / secret 加载器

发生了什么：OpenClaw 控制台聊天区顶部提示「⚠️ 密钥加载器降级 —— 环境变量 XIAOMI_API_KEY 缺失或为空，运行时已回退到上次正常快照」。但读 `/proc/<openclaw node PID>/environ` 确认进程环境**实际有** `XIAOMI_API_KEY`（有值，已打码）。[openclaw.yaml](../../.openclaw-hr/config/openclaw.yaml) 第 550 行 `xiaomi.apiKey` 配置 `source: env, id: XIAOMI_API_KEY`。  
期望：环境变量有值时不应提示降级；或提示更准确（如「快照校验失败」而非「环境变量缺失」）。  
复现：
1. `source env.sh; cd ~/.openclaw-hr; openclaw gateway run`
2. 浏览器打开 `http://127.0.0.1:18790/`，填 gateway token 登录
3. 观察聊天区顶部系统提示

证据：进程 67240 environ 含 `XIAOMI_API_KEY`（有值，已打码）；重启 gateway 后启动日志**无降级 warning**，`agent model: xiaomi/mimo-v2.5-pro` 正常加载。前端提示因 browser agent 中断未最终截图验证。  
是否稳定：每次（首轮 gateway 启动后出现；重启后 gateway 层无 warning）

## D-006

标题：[HCM] seed.py 增量导入不还原已存在记录  
级别：P3  
Agent / Skill：hcm-backend / seed.py

发生了什么：O-06 / O-02 / O-03 测试改动了郭超的 contract / account 数据。测完跑 `python seed.py` 还原，但 seed.py 跳过已存在记录（输出「⏭ 跳过 郭超 — 已存在」），改动未还原。需删 `hcm.db` 全量重 seed 才能还原。  
期望：seed.py 提供 `--reset` / `--force` 选项重置已存在记录，或文档说明还原需删 DB。  
复现：
1. `PUT /api/candidates/{id}/prep/contract` 改 contract data
2. `cd backend && python seed.py`
3. 观察：跳过已存在，改动仍在

证据：seed.py 输出「跳过 郭超 — 已存在」；`GET /api/candidates/1` 仍显示改动。删 `hcm.db` 后 seed 全量重导，郭超 5 节点全 completed 原值。  
是否稳定：每次（seed.py 逻辑固定）

## D-007

标题：[环境] background job + `exec uvicorn` 启动失败  
级别：P3  
Agent / Skill：部署 / run_in_background

发生了什么：用 `source env.sh; ...; exec uvicorn main:app` 在 run_in_background 模式启动 HCM 后端，job 失败（exit -1，日志空）。改用直接 `uvicorn main:app`（不 exec）成功。  
期望：`exec` + run_in_background 组合应可工作，或文档避免该用法。  
复现：
1. Shell `run_in_background=true`，command 含 `exec uvicorn main:app --port 8000`
2. job failed exit -1，日志空
3. 改用 `uvicorn main:app`（无 exec）成功

证据：job-85dc557f failed exit -1 日志空；job-bc46cb8f（无 exec）成功，`curl 8000/api/health` → `{"ok":true,"service":"hcm"}`。  
是否稳定：每次（`exec` + run_in_background）
