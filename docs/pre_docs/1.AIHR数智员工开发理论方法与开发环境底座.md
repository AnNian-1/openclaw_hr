## §1 从堆功能到设计系统

### 1.1 一个对照实验：两位开发者的三种结局

公司给两位开发者下了同一个需求：做一个 AI HR 数字员工，把招聘、入职这些重复、繁琐的工作接过去。两人手里工具一样——都是 **OpenClaw**。

**OpenClaw（官网 https://openclaw.ai）是什么？**
一个 Agent-first 的多通道 Gateway：一个常驻进程，对外接入飞书、Slack、邮件等多种渠道，对内统一管理大量内置工具、Skill、记忆引擎和自动化机制，专门用来搭建工业级的数字员工。

> 本课学员已经会用它的基础功能（建 Agent、装 Skill、用记忆系统），但"会单点"和"会设计系统"之间隔着一道坎。

**第一位开发者（反例）**：
- 拿到需求当天就动手。打开 OpenClaw，建了一个 Agent，开始装 Skill——解析简历的、发邮件的、查日历的，一个接一个。
- 两周后能跑出点东西：丢一份简历进去，Agent 能解析、能打分。
- 但需求方一追问："能不能把这周收到的 80 份简历批量处理一遍，按岗位 JD 排个序？"——就卡住了。
- **症结**：Skill 是齐了，可从来没有一个人想过：这些 Skill 之间怎么串、简历数据存在哪、谁来调度这一整套流程。想加一个新功能，往往要把已经接好的拆掉重接。
- **三个月后的结果**：一堆互相不认识的脚本，即"所谓的数字员工"。

**第二位开发者（正例）**：
- 拿到需求没有马上碰 OpenClaw，他先做了三件事：
  1. 把"AI HR 数字员工"这个模糊需求，拆成具体工作事项——招聘要做 JD、筛简历、约面试，入职要发 Offer、走流程。
  2. 对照 OpenClaw 的能力，逐项想清楚每件事用什么来做。
  3. 画了一张系统架构图——系统由几个 Agent 组成、各管哪一摊、彼此怎么协作、哪些环节必须留给人审批。
- 到第二周他才开始动手。
- **三个月后**：交付一个分工清晰、能持续扩展的系统：加一个新场景，是往既定架构里填一块，不是推倒重来。

**核心差异**：第二位开发者把"开发"这件事往前挪了一步——他在动手之前，先做了设计。

> 这门课要解决的，就是怎么把一个模糊的"做个 AI 数字员工"的需求，设计成一个清晰、可扩展、能工业级落地的 Agent 系统。

> 这套"从业务场景到 Agent 系统"的设计流程是可复用的——之后你做 AI 客服、AI 财务助理、任何一种数字员工，都能照着走。

### 1.3 设计方法论总纲：能力盘点 → 业务分析 → 系统架构 → 开发计划

**四步路径**（固定顺序，链式依赖）：

```
能力盘点  →  业务分析  →  系统架构  →  开发计划
   §2         §3          §4         §5
```

**为什么是这四步，而且顺序不能乱？**

- 没有先盘点能力，做业务分析时就判断不了"这件事到底能不能技术落地"。
- 没有做业务分析，系统架构就是凭感觉拍脑袋。
- 没有架构，开发计划根本无从拆起。
- 四步是一条链，缺一环，后面就接不住。

**最常见的误区**：拿到需求，第一步就去配 Skill。

- 为什么会犯？因为 OpenClaw 把"建 Agent、装 Skill"做得太顺手——顺手到让人把"动手"等同于"装功能"。
- 但配 Skill 是一个开发动作，不是设计动作。在还没想清楚"这个系统该有几个 Agent、各管什么"之前装下的 Skill，大概率装错了地方，后面还得拆。
- **设计阶段动的是脑子和图纸，不是 OpenClaw 的配置。**

**四步的输入、动作、产出**：

| 步骤 | 输入 | 做什么 | 产出 | 对应章节 |
|---|---|---|---|---|
| 能力盘点 | OpenClaw 的能力清单 | 搞清楚做定制化开发时，能操作哪些系统 | 一张七抓手能力图谱 | §2 |
| 业务分析 | 模糊的业务需求 | 拆成具体工作事项，逐项映射到 OpenClaw 能力 | 业务与技术对位表 | §3 |
| 系统架构 | 一堆分散的场景技术需求 | 剥离、归并这些需求，推导出系统架构 | 系统架构方案 | §4 |
| 开发计划 | 系统架构方案 | 拆成有依赖关系的阶段，每阶段配检查点 | 开发计划表 | §5 |

> **关键设计哲学**：每一步都有一个明确的、能拿在手里的产出。设计过程不是"在脑子里想想"，而是会沉淀出实实在在的文档。

### 1.4 微缩示例：一句话需求走一遍四步

**假设需求**：HR 提了一句话："想要个简历筛选助手。"

**走一遍四步**：

1. **能力盘点**——OpenClaw 能解析文档（DOCX、PDF）、能让大模型按一套标准给文本打分、能把结果写进文件或表格。筛简历需要的能力，基本都现成。

2. **业务分析**——拆开"筛简历"：
   - 具体动作：拿到一批简历文件，对照岗位 JD，给每份简历打一个分，排序，输出一份候选人清单。
   - 边界要剥出来："最终淘汰谁、谁进面试"不属于这个助手的职责，那是人的决定。

3. **系统架构**——就这一个场景，架构很轻：
   - 一个 Agent 就够了，不需要拆成多个。
   - 要不要审批门？只给简历排序、不发 Offer、不动用人决定，可以不要。
   - 产出物是一份评分结果文件。

4. **开发计划**——分三步走：
   - 第一步：先把"单份简历解析加打分"跑通。
   - 第二步：加上批量处理。
   - 第三步：加排序和清单输出。
   - 每一步都定一个能判断"做完了没有"的验收标准。

> 哪怕只是个"简历筛选助手"，四步走完，你也清楚了它该有几个 Agent、要不要审批、产出什么、第一步先做什么。
> 需求越大、越复杂，这套四步法省下的返工就越多。

### 1.5 主线案例：小慧上线后的工作一幕

**主角**：AI HR 数字员工"小慧"，完整方案。

**它工作时的一幕**：
- HR 在对话框里发一句"帮我筛一下这周收到的简历"。
- 几分钟后，小慧回过来一份结果——一个按岗位匹配度排好序的候选人清单，每位候选人附一个评分和一句评分理由。
- 点开其中一位，是一份 HTML 格式的候选人画像，里面有技能雷达图、关键经历摘要。
- **整个过程，HR 没有打开任何一份原始简历文件，也没有手动给任何人打分。**

> 这一幕需要说明清楚：它是 openclaw-ai-hr 课程三期全部走完之后的成品形态。
> **这一期（Lesson 1）只做到两件事**——设计出小慧应该长什么样，以及搭好开发它的环境。
> 把小慧真正建出来、让它能干活，是 Lesson 2 和 Lesson 3 的内容。

> 把这一幕放在方法论的开头，是为了让你心里有一个明确的目标：后面所有的能力盘点、业务分析、架构设计，都是为了让这一幕能真实发生。设计方法论不是纸上谈兵的流程，它通向一个具体的、能干活的数字员工。

## §2 能力盘点：定制化开发的七大抓手

### 2.1 什么是"开发者抓手"

四步法的第一步是能力盘点。盘点之前要先回答一个问题：**盘点的对象到底是什么？**

**两层划分**：
- **基础功能的实现**：Agent 运行时是怎么跑起来的、记忆系统在底层怎么存取数据——这些是 OpenClaw 内部的事，你用它，但一般不去改它。
- **开发者抓手**：做定制化开发时，你真正动手操作的七大系统。**能力盘点盘的，就是这七个抓手。**

> **类比**：学一门编程语言时，你的"抓手"是它的语法、标准库、工具链；你不需要读解释器源码。那是"底层实现"。做 Agent 系统设计也一样：盯紧这七个抓手就够了，不必陷进运行时和记忆系统是怎么实现的。

**七大抓手速查表**：

| 抓手 | 一句话定位 |
|---|---|
| md 文档系统 | 用 markdown 文件定义 Agent 的身份、规范、工作流 |
| Skill 系统 | OpenClaw 原生的能力包，给单个 Agent 加技能 |
| MCP 系统 | 标准化的外部工具协议，接入 OpenClaw 生态之外的工具 |
| 插件系统 | 给 OpenClaw Gateway 本身装新的功能模块 |
| Channel 系统 | 接收不同消息平台消息的入口，是数字员工的"门" |
| Lobster 工作流 | 可恢复、带审批检查点的工作流引擎 |
| 多 Agent 系统 | 一个 Gateway 挂多个 Agent，分工协作 |

### 2.2 设计阶段的常见陷阱

**最容易走偏的，就是一头扎进底层实现**。

- 例如纠结"OpenClaw 的记忆系统底层用的是 SQLite 还是别的引擎"——这问题对设计一个 HR 数字员工没有任何帮助。
- 设计阶段你只需要知道"记忆这个能力存在、能用、大概是什么形态"，不需要知道它怎么实现。
- 把精力花在抓手的组合上，不要花在抓手的内部构造上。

### 2.3 抓手与系统设计决策的对应关系

**七大抓手不是平铺的七个知识点**。它们各自对应系统设计中的一类决策：

| 抓手 | 系统设计中对应的决策 |
|---|---|
| md 文档系统 | 定义"这个 Agent 是谁、按什么规矩工作" |
| Skill 系统 + MCP 系统 | 定义"这个 Agent 会做什么" |
| 插件系统 + Channel 系统 | 定义"整个系统怎么扩展、消息从哪里进来" |
| Lobster 工作流 | 定义"多步流程怎么编排、哪个环节要留给人的审批" |
| 多 Agent 系统 | 定义"系统由几个 Agent 组成、它们怎么协作" |

> 到了四步法的第三步（系统架构，§4），你会看到架构方案要确定的几个要素——几个 Agent、怎么调度、要不要工作流、人设怎么写——几乎逐一对应这些抓手。
>
> 换句话说，盘点抓手不是为了"知道有这些东西"，而是为了在设计架构时，每一个设计决策都能落到一个具体的抓手上。

### 2.4 md 文档系统：用文档定义身份与工作流

**它回答什么**：怎么定义"这个 Agent 是谁、按什么规矩工作"。

**OpenClaw 用一组 markdown 文件来定义一个 Agent 的身份、规范和工作流**。

> 不是写在代码里，不是填在结构化的配置项里，而是写在普通的 .md 文本文件里。

每个 Agent 都有一个 workspace（工作目录），workspace 里放着这样一套文档。两份核心：
- **SOUL.md**——Agent 的"人设档案"。写清它是谁、负责什么、边界在哪。
- **AGENTS.md**——Agent 的工作规范。写做事的规则、流程约定。

除此之外，OpenClaw 在创建 Agent 时会在 workspace 里生成 IDENTITY.md、USER.md、TOOLS.md 等脚手架文件。设计阶段最需要你亲手去写、去定制的，是 SOUL.md——它直接决定一个子 Agent 的行为基调。

#### 2.4.1 文档如何进入 Agent 的上下文

**文档要能定义行为，关键在于它怎么"生效"**。

当一个 Agent 接到任务、要做出回应时，OpenClaw 会把这套文档加载进 Agent 的上下文（context）——也就是说，文档的内容会作为 Agent "思考"时的背景信息，和用户当前的消息一起，喂给底层的大模型。

> 所以 SOUL.md 里写下的"你只做评分排序、不做最终淘汰"这句话，会实际进入模型的输入，实际约束 Agent 的行为。

**关键认知**：md 文档不是注释，不是给人看的说明文档——它是 Agent 行为的直接来源。改一句 SOUL.md，Agent 下一次回应的依据就变了。

> **文档即配置，文档即行为**。

#### 2.4.2 一个重要机制：脚手架文档的幂等生成

OpenClaw 在创建 Agent 时生成那套脚手架文件，行为是幂等的、只补缺失：
- 如果 workspace 里已经有一份 SOUL.md，创建过程会保留它、不覆盖。
- 如果 workspace 是空的，才写入一份通用的默认模板。

**这个行为决定了一个正确的操作顺序**：
- ✅ 正确：先把定制好的 SOUL.md 放进 workspace，再创建 Agent。
- ❌ 错误：先创建再写，会先吃到一份不含任何业务信息的默认模板，还得再覆盖一次。

> 这条顺序在 §6 实际搭多 Agent 骨架时会用到。

#### 2.4.3 一份招聘子 Agent 的 SOUL.md 长什么样

```markdown
# 你是谁
你是"招聘小慧"，AI HR 数字员工小慧团队里负责招聘环节的子 Agent。

# 你负责什么
- 解析候选人简历，提取关键信息
- 对照岗位 JD，给每份简历打分并写明评分理由
- 输出按匹配度排序的候选人清单

# 你的边界
- 你只做评分和排序。是否淘汰某位候选人、谁进入面试，由人类 HR 决定。
- 你不与候选人直接沟通，不发送任何对外邮件。
- 评分理由必须可追溯到简历原文，不允许臆测。
```

这份文档里没有一行代码。它就是几段中文说明。但请注意"你的边界"那一段——尤其"你只做评分和排序，是否淘汰由人类 HR 决定"这一句。

> **这不是一句客套话，它是一条合规红线**：对应的是《个人信息保护法》对"自动化决策"的要求——对个人有重大影响的决策，不能完全交给算法。
>
> 把这条红线写进 SOUL.md，意味着从 Agent 的"人设"这一层，就把合规约束钉死了。
> 设计一个 HR 数字员工，类似这样的边界还有不少，它们都该在 SOUL.md 里显式写出来。

#### 2.4.4 为什么是文档，而不是代码或配置

| 方式 | 怎么做 | 主要问题 |
|---|---|---|
| **md 文档（OpenClaw 的选择）** | 把身份、规范写进 .md 文本文件 | 文档会占用上下文空间；是软约束不是硬隔离 |
| 硬编码 persona | 把"你是谁、你的边界"写死在代码里 | 改一次要改代码、重新部署；业务方完全无法参与 |
| 结构化配置文件 | 用 JSON/YAML 的配置项表达 persona | persona 是大段自然语言，硬塞进键值对很别扭 |

**对比硬编码**：persona 写进代码，每改一次都要动代码、重新部署，HR 业务方根本碰不了。而 md 文档是纯文本，业务方能读、能提意见、能直接参与修订——这对一个要贴合业务的数字员工很关键。

**对比结构化配置**：persona 的内容大多是大段自然语言描述，把它塞进键值对形式的配置项里非常别扭。而 md 文档天然适合写大段说明。更重要的是，这套文档最终是要喂给大模型读的——自然语言正是大模型最擅长处理的输入形态。**用文档，等于用模型最顺的方式跟它沟通。**

> **本节事实出处**：本节关于 md 文档系统的事实，来自 OpenClaw v2026.5 能力图谱（Agent 架构部分），以及阶段 A 多 Agent 骨架搭建实验记录（`exp-stage-a-multi-agent.md`）中对脚手架文件幂等生成行为的实测。

#### 2.4.5 两个局限

设计时要心里有数：

1. **文档会占用上下文**。每个 Agent 的文档都会加载进上下文，文档写得越长，留给实际对话的上下文空间就越少。所以 SOUL.md 要精炼——写清职责和边界，不堆废话。

2. **文档是软约束，不是硬隔离**。SOUL.md 里写"不发送对外邮件"，是在人设这一层约束 Agent 的行为倾向。但要做到这个 Agent 在物理上根本没有发邮件的能力，得靠工具权限（Tool Policy）把发邮件的工具从这个 Agent 上摘掉。

> **一句话总结**：文档定义意图，权限做强制。两者配合，约束才真正可靠。

### 2.5 Skill 系统与 MCP 系统：两条能力扩展路径

md 文档定义了 Agent 是谁、按什么规矩工作。下一个问题是：当一个 Agent 能力不够——它需要做某件 OpenClaw 没有内置的事——该怎么补？

**两条补能力的路径**：Skill 系统和 MCP 系统。
- Skill 是 OpenClaw 原生的能力包。
- MCP 是一套标准化的外部工具协议。

**两条路径解决的是同一个问题"能力不够怎么补"，区别在于补进来的能力以哪种形态存在**。

> **类比**：装一个 Skill，像 OpenClaw 装一个为它量身定做的扩展——这个扩展懂 OpenClaw 的规矩。接一个 MCP server，像是插一个标准接口的外设——MCP 是 AI 工具界的通用接口，谁遵守这个标准都能插上。

#### 2.5.1 Skill 系统：OpenClaw 原生能力包

**一个 Skill 就是一个能力包**，它的核心是一份 SKILL.md 文件——**用 frontmatter 声明这个 Skill 做什么、怎么触发、依赖哪些环境**。给一个 Agent 装上一个 Skill，这个 Agent 就多一项技能。

> **frontmatter 机制说明**：SKILL.md 顶部用 YAML 风格的元数据块（以 `---` 分隔）声明 Skill 的元信息（例如触发关键词、所需环境变量、依赖的工具或 API 密钥等），正文则详细描述具体的能力语义。OpenClaw 解析 Skill 时，先读 frontmatter 决定是否加载、再读正文作为大模型理解 Skill 用法的提示。**这种"声明 + 文本"的混合形态正是 OpenClaw 原生 Skill 与代码类扩展的本质区别**。

**设计阶段要知道四件事**：

1. **生态规模大**：OpenClaw 的 Skill 生态相当成熟——公开注册的 Skill 上万个，经过筛选的优质 Skill 也有五千以上。HR 场景常用的能力——简历解析、收发邮件、日历调度——几乎都有现成 Skill，不用自己写。

2. **加载有优先级**：Skill 可以放在多个位置，OpenClaw 按六级优先级加载，高优先级胜出。最高的是 Agent 自己 workspace 里的 skills 目录，最低的是系统自带的 bundled skills。这意味着你可以在某个 Agent 的 workspace 里放一个同名 Skill，覆盖掉全局的版本。

   > **Skill 六级加载优先级设计意义**：这套优先级机制让"**全局通用能力 → 项目特定能力**"的覆盖链条天然成立。如果某 HR 数字员工需要定制版的"邮件 Skill"（比如加上本公司邮件签名、报销口径），工程师**不必去改全局 Skill 的代码**，只要在某个 Agent 的 workspace 里放一份同名 SKILL.md，就能用局部版本覆盖全局版——既保留全局默认、又支持局部定制。这一架构决策使 OpenClaw 在多团队、多数字员工的场景下保持配置层的简洁。

3. **可以按 Agent 配白名单**：可以给每个 Agent 配一个 skills 白名单，控制它只能用哪些 Skill——这是给 Agent 做能力约束的手段之一。

4. **兼容 Claude Code 格式**：OpenClaw 能直接加载 Claude Code 格式的 skill，生态是打通的。

   > **"生态打通"的实操含义**：用户原本为 Claude Code 写的 skill（同样基于 SKILL.md frontmatter 机制）**可以直接迁移到 OpenClaw**，不必重新包装或改写。这意味着 HR 数字员工可以从既有 AI 编程助手的 skill 生态中**直接复用**——例如文档解析、邮件处理、日历调度这些通用能力，Claude Code 社区已有的优质 Skill 可零成本平移到 OpenClaw 上使用，**显著降低了冷启动成本**。

**容易踩的坑**：Agent 的 skills 白名单，非空时是**替换语义**，不是合并语义。

- 也就是说，如果你给某个 Agent 配了 `skills: ["github"]`，它就只有 github 这一个 Skill，默认配置里那些 Skill 全都不在了。
- 想做"在默认基础上再加一个"，必须把默认的那些也一列全。
- **这个语义如果想错了，会发现 Agent 莫名其妙少了一堆能力。**

#### 2.5.2 MCP 系统：跨应用的开放工具协议

**MCP 的全称**是 Model Context Protocol（模型上下文协议）。它是一个开放标准，由 Anthropic 在 2024 年 11 月提出，目的是统一"AI 应用怎么连接外部工具和数据源"这件事。

**它解决的问题，业界叫"N×M 问题"**：
- 有 N 个 AI 应用、M 种外部工具，如果每个应用都为每种工具单独写一套对接，要写 N×M 套，越加越乱。
- MCP 的做法是定一个统一标准——工具方按标准实现一个 MCP server，AI 应用方按标准做一个 MCP client，两边就能对接。
- **类比**：MCP 之于 AI 应用，相当于 USB-C 之于电子设备——一个通用接口，省掉为每种组合定制连线。
- 目前 Anthropic、OpenAI、Microsoft、Google 等都在自己的产品里支持 MCP。

> **N×M 问题的细节推演**：以 HR 场景举例，假设公司有 5 个 AI 助手场景（招聘筛选、入职办理、培训推送、绩效评估、行政答疑），同时已经采购了 6 类企业内部系统（招聘 ATS、人事 ERP、考勤系统、薪酬系统、IT 工单系统、企业微信后台）。在 MCP 出现之前，每个场景都要为每类系统做定制对接，工程师要写 `5 × 6 = 30` 套适配代码，且每新增一个场景或一类系统都要联动改 30 处。MCP 把这套星形问题变成"两次单点"——每类系统实现一次 MCP server（6 次）、每个 AI 应用实现一次 MCP client（5 次），加起来只有 **11 次对接**。新增场景或系统的边际成本从 N 或 M 降到 **1 次**——这就是 USB-C 类比的工程价值。

**OpenClaw 内置了 MCP 系统**（由 `openclaw mcp` 命令族管理 MCP 配置）。这意味着你可以把任何一个 MCP server 接进 OpenClaw——这个 server 可能是别的团队写的、用别的语言实现、本来是给别的 AI 应用用的，只要它遵守 MCP 协议，OpenClaw 的 Agent 就能调用它暴露出来的工具。

#### 2.5.3 两条路径的选用边界

| 维度 | Skill 系统 | MCP 系统 |
|---|---|---|
| 本质 | OpenClaw 原生的能力包 | 跨应用的开放工具协议 |
| 适合接什么 | OpenClaw 生态里现成的能力、或自己写的 OpenClaw 专属能力 | 已经有 MCP server 的外部工具或数据源 |
| 生态范围 | OpenClaw 自己的 Skill 生态，上万个现成 Skill | 任何遵守 MCP 标准的 server，不限于 OpenClaw 生态 |
| 什么时候选它 | HR 常见动作（简历解析、邮件、日历）几乎都有现成 Skill，**优先选** | 要接的是公司内部已有 MCP server 的系统（如内部招聘系统、人事系统） |

**给一个务实的建议**：做 HR 数字员工时，绝大多数能力——文档解析、收发邮件、日历调度、信息检索——在 OpenClaw 的 Skill 生态里都有成熟的现成 Skill，**优先用 Skill**。

只有当你要接入的是公司内部某个系统、而它恰好已经提供了 MCP server 时，走 MCP 才是更短的路。

> 不要为了用 MCP 而用 MCP——选哪条路径，取决于你要的那个能力，以哪种形态现成存在。

### 2.6 插件系统与 Channel 系统：功能增强与多平台接入

Skill 和 MCP 扩展的是单个 Agent 的能力。还有两个抓手，扩展的是另外两个层次的东西——插件系统和 Channel 系统。
- 插件系统：给 OpenClaw Gateway 本身装新的功能模块。
- Channel 系统：数字员工接收不同消息平台消息的入口。

> **一个改的是 Gateway 的能力，一个改的是 Gateway 的"门"**。

**三个层次要分清楚**——这是初学者最容易混的地方：

| 抓手 | 作用层次 | 决定什么 |
|---|---|---|
| Skill 与 MCP | 扩展的是单个 Agent 的能力 | 决定这个 Agent 会做什么 |
| 插件 | 扩展的是整个 Gateway 的能力 | 是系统级功能，所有 Agent 都受影响 |
| Channel | 扩展的是消息从哪里进来 | 是数字员工对外的入口 |

#### 2.6.1 插件系统：给 Gateway 装功能模块

**插件是 Gateway 级别的功能模块**。装一个插件，整个 Gateway 多一项系统级能力，这项能力不针对某一个 Agent，而是对整个系统生效。

**一个具体的认识**：本课后面要讲的几个能力，本身就是以插件形式存在的：
- Lobster 工作流引擎：插件
- 可观测相关的 Prometheus 指标采集、OpenTelemetry 数据导出：插件

所以"装插件"不是边角操作——它是给 OpenClaw 这个底座本身加东西。

正因为插件作用在 Gateway 这一层，它要提醒一个边界：
- 插件是受信任的系统级代码，装插件的影响面比装 Skill 大得多。
- 装一个 Skill，最多让某个 Agent 多一项技能；装一个插件，是给整个 Gateway 加了一段会一直运行的代码。
- 所以对插件的来源要更谨慎，OpenClaw 也建议把信任的插件显式登记进允许清单，避免来路不明的插件被自动加载。
- **设计阶段选用插件，要把它当成"给系统底座做改动"来对待。**

#### 2.6.2 Channel 系统：数字员工的入口

**Channel 是数字员工和真人之间的通道**。HR 在飞书里给小慧发一句话，这句话要进入 OpenClaw，靠的就是飞书 Channel。

OpenClaw 内置支持十二个以上的 Channel——飞书、Slack、Microsoft Teams、Discord、iMessage、Telegram、WhatsApp 等等。

- 一个 Gateway 可以同时挂多个 Channel，意味着同一个数字员工能从多个平台同时接收消息。
- Channel 还和多 Agent 系统相关：*当一个系统挂了多个 Agent，"消息从哪个 Channel、哪个群、哪个人来"，正是决定这条消息路由到哪个 Agent 的依据之一*。
  - 用 HR 场景举例：同样是飞书群消息，群 A 里的"招聘需求收集表"机器人对应招聘 Agent；群 B 里的"IT 设备申请"机器人对应入职 Agent。**Channel 提供身份信息，Router 基于身份做分诊**——这就是 Channel 与多 Agent 系统的真正耦合点。

**关于 Channel，本课要交代两点**：

**第一**，本课不实际接入 Channel。这一期搭的是一个纯命令行（CLI）的开发环境，飞书集成放在 Lesson 3。但即便这一期不接，设计阶段也必须清楚 Channel 的定位——因为"数字员工从哪里接任务"是系统架构的一部分。**做架构设计时要为这个入口预留位置，哪怕这一期暂时空着。**

**第二**，邮件**不是**一个内置 Channel。

- 你可能以为"邮件"和"飞书"一样，是 OpenClaw 的一个 Channel。其实不是——OpenClaw 收发邮件走的是 Skill 路径（有专门的邮件类 Skill）。
- 设计 HR 数字员工时常常要发录用通知、面试邀约，涉及邮件，这时候要记得：**邮件能力来自 Skill，不是来自 Channel**。
- 把这个区分记清楚，架构图才不会画错。

### 2.7 Lobster 工作流引擎：可恢复的审批工作流

前面四个抓手——md 文档、Skill、MCP、插件、Channel——解决的是"一个 Agent 是谁、会什么、从哪接消息"。

但一个 HR 数字员工要做的事，往往不是单步动作，而是一条多步流程：起草 Offer、等审批、发放 Offer。流程里还有一个绕不开的环节——某些步骤不能让 AI 单独拍板。这就要用到第六个抓手：**Lobster 工作流引擎**。

**Lobster** 是 OpenClaw 内置的工作流引擎（以插件形式提供）。它解决的问题是：把一串多步操作编排成一条流程（pipeline），并且支持在中间某一步"停下来等人审批"，人审批之后能从断点继续。

**三个关键能力**：

1. **流程可编排**——把"AI 起草、人审批、继续执行"这样的多步操作串成一条 pipeline。
2. **审批点可暂停**——执行到审批节点时停住（halt），不继续往下跑。
3. **暂停后可恢复**——人审批之后，凭一个令牌让流程从断点继续，而不是从头重跑。

这三件事合起来，技术上叫 **HiTL（Human-in-the-Loop，人在回路）**——在一个自动化流程里，把关键决策点显式地留给真人确认。

> HR 场景里，发放 Offer、核准薪资这类**不可逆的高风险决策**，不能交给 AI 全自动完成，必须有人在回路。Lobster 就是实现这套机制的现成底座。

#### 2.7.1 approval checkpoint 与 resumeToken 怎么工作

一条 Lobster workflow 由若干 step 组成。普通的 step 执行一个命令。而审批 step（approval checkpoint）不执行命令，它做的事是"把流程拦下来"。

**整个机制运转流程**：

1. 流程跑到审批 step，状态从 `ok` 变成 `needs_approval`，整条流程暂停——审批 step 之后的所有步骤一律不执行。
2. 暂停的同时，Lobster 返回一个 `resumeToken`。
3. 这个 `resumeToken` 是理解 Lobster 的关键，需要重点说明。它**不是一个简单的"yes/no 凭证"**。
4. 把它做 base64 解码，里面是一段 JSON，JSON 里有一个 `stateKey` 字段，指向一条被持久化保存下来的流程状态记录。
5. **换句话说，resumeToken 是"取回整个暂停现场的钥匙"——它能找回流程停在哪一步、之前几步产出了什么数据、待审批的内容是什么。**

**为什么要做成这样？** 因为审批是异步的。HR 主管可能正在开会，可能已经下班，明天才来批这份 Offer。这就要求：
- 流程的暂停状态必须存得住。
- 这个令牌隔多久拿出来都能恢复，恢复时从断点接着跑、不是从头重来。
- **这是工业级审批流程的硬要求——审批人不可能时刻在线**。resumeToken 指向持久化状态，正是为了满足这一点。

人做出决策后，用 `resume` 命令带上这个 token：
- 参数 `--approve yes`：流程从断点继续、跑完剩下的步骤。
- 参数 `--approve no`：流程终止，状态变成 `cancelled`。

> **批准和拒绝，是同一个命令的两种参数。**

#### 2.7.2 HR Offer 审批流怎么跑

本课在阶段 A 的环境搭建里，真实跑通了一个最小的 Offer 审批 workflow，文件名是 `hr-offer-approval.lobster`。它由三个 step 组成：

| Step | 职责 |
|---|---|
| `draft` | AI 起草 Offer，产出一份候选人 Offer 的数据 |
| `gate` | 审批门。把待审的内容连同审批问题一起亮出来："HR 主管，是否批准这份 Offer 进入下一步发放流程？" |
| `issue` | 批准之后才执行的发放动作 |

**真实运行样态**：
- 跑一次 workflow，状态停在 `gate`，**`issue` 步骤没有执行**。
- 返回的 `requiresApproval` 里带着：审批问题、待审的候选人数据、那个 resumeToken。
- 也就是说——AI 已经起草好了 Offer，但它没有发，它停在审批点等人。

**批准之后的状态**：
- `status` 回到 `ok`，输出里出现"Offer 已批准，进入正式发放流程"——这正是 `issue` 步骤的输出。
- 审批之前，`issue` 一直没有跑；批准之后，它才执行。
- 如果 HR 主管给的是 `--approve no`，流程状态会变成 `cancelled`，`issue` 步骤直接跳过——Offer 发不出去。

> **这一幕的关键**，不是"AI 会起草 Offer"——会起草不稀奇。关键是"AI 在没人点头的时候，绝不会把 Offer 发出去"。
>
> 审批门把"发放 Offer"这个不可逆的动作，从自动化流程里物理性地隔离了出来，交回给人。
> 而 resumeToken 保证了隔离之后还能无缝接回——**这才是 Lobster 对 HR 数字员工的价值所在**。

#### 2.7.3 对比纯脚本与状态机，以及 Lobster 的局限

要实现"多步流程加审批"，Lobster 不是唯一选择。把它和两种自动手的方案对比：

| 方案 | 能不能做 | 代价 |
|---|---|---|
| **Lobster 工作流** | 能 | **开箱即用**，审批与恢复机制现成 |
| 纯脚本（shell / Python） | 能串流程，但难做可恢复审批 | 要自己写状态持久化、自己设计令牌机制 |
| 自己实现状态机 | 能 | 要自己定义状态、转移、持久化，工程量不小 |

**对比纯脚本**：你完全可以用一个脚本把这些步骤串起来。但脚本要实现"跑到一半停下、等一个外部审批、隔天还能从断点恢复"，就得自己写状态持久化、自己设计一套令牌机制——而这正是 Lobster 现成提供的。**纯脚本适合无审批环节的一次性流程。**

**对比状态机**：自己实现一个状态机来管"待审批、已批准、已拒绝"这几个状态，也能做。但状态机要自己定义状态、定义转移规则、做持久化，工程量不小。Lobster 把"审批"这个最常见的状态机模式，做成了开箱即用的一个步骤类型。

> **所以 Lobster 的价值，不在于"能把流程串起来"——脚本也能串。它的价值在于：把"可暂停、可恢复的审批"这个工业级的麻烦事，做成了现成的能力。**
>
> **设计 HR 数字员工时，凡是涉及不可逆决策的环节，都该想到用 Lobster，而不是自己造一遍轮子。**

**最后说两个局限，设计和实操时要避开**：

1. **不要用 inline pipeline 写带实际命令的流程**。Lobster 支持在命令行里直接写一行 pipeline，但这种写法在命令带空格、带中文、带引号时非常脆弱。真实的、带实际命令的 workflow，应该写进一个 `.lobster` 文件。写进文件还有额外好处——能版本管理、能复用，而审批流程本来就该是可复用的资产。

2. **dry-run 通过不代表真跑能过**。Lobster 的 dry-run 只校验 pipeline 的解析，不真正执行命令。dry-run 干净，真跑仍可能在执行环节出错。

### 2.8 多 Agent 系统：从单体助手到分工团队

七个抓手里最后一个，也是分量最重的一个——**多 Agent 系统**。它回答的是系统设计中最顶层的问题：**这个系统，到底该由几个 Agent 组成**。

先看不用多 Agent 会怎样。一个 HR 数字员工要同时干招聘、入职、培训、绩效、行政五摊业务。如果把这五摊全塞进一个 Agent，会出三个问题：

1. **上下文互相污染**——招聘的简历筛选对话，和绩效的反馈评估对话，挤在同一个 Agent 的记忆里，互相干扰。
2. **权限无法分级**——招聘 Agent 本不该有权限去改绩效数据，但单个 Agent 没办法按业务领域切分权限。
3. **无法独立演进**——想给招聘加一个新 Skill，会牵连到其他四个领域，改动影响面失控。

**OpenClaw 的解法是多 Agent 系统**：
- 一个 Gateway 下挂多个 Agent，每个 Agent 有自己独立的工作目录和状态目录。
- 请求进来后，由 Multi-Agent Routing 决定交给哪个 Agent 处理。
- **本课主线案例小慧，就是这样一个多 Agent 系统**——它由 6 个子 Agent 组成：招聘、入职、培训、绩效、行政五个业务 Agent，外加一个总控 Router。
- 对外它是"一个数字员工小慧"，对内它是一支分工的团队。

#### 2.8.1 隔离与路由：多 Agent 怎么各管一摊

多 Agent 系统能成立，靠两件事：**隔离，和路由**。

##### 隔离

每个子 Agent 有三样东西各自独立：

| 资源 | 作用 |
|---|---|
| **workspace（工作目录）** | Agent 读写的文件放这里。招聘 Agent 处理简历，绩效 Agent 处理评估数据，两者的文件物理隔开 |
| **agentDir（状态目录）** | 存这个 Agent 的会话历史、记忆、身份 |
| **session store（会话存储）** | 存会话记录 |

> **必须记住的铁律**：绝不复用 agentDir。如果两个 Agent 共用一个 agentDir，A 的对话记忆会污染 B，身份也会冲突。
>
> 每个 Agent 用一套自己专属的目录，是多 Agent 隔离的根基。
> 前面说的"上下文互相污染"问题，正是靠这套物理隔离从根上解决的。

##### 路由

由 **Multi-Agent Routing** 负责。它有两条主要通路：

1. **Channel 路由**：系统接了飞书、Telegram 等 Channel 时，按"消息从哪个群、哪个人来"分发到对应 Agent。
2. **本地工作流模式**：没有 Channel 的环境——本课这一期就是纯命令行环境，没有接 Channel，用的是 OpenClaw 的本地工作流模式：Agent 与 Agent 之间，靠一个叫 `agentToAgent` 的工具来通信。

> **两种路由的工程含义不同**：
> - **Channel 路由**依赖消息平台侧的身份信息（用户 ID、群 ID）做分发判定，分发依据在"消息来源侧"；
> - **agentToAgent 路由**是 Agent 之间互相转发，分发依据在"Agent 调用关系侧"。
>
> 这两种通路既独立、又可组合：例如一个飞书消息先被 Channel 路由到 Router，Router 再用 `agentToAgent` 转发给招聘 Agent——这种**双层路由**的组合让系统在多消息源 + 多业务 Agent 的真实生产场景下保持清晰。

> **关于 `agentToAgent`，有一个设计上的安全默认值得知道**：它**默认是关闭的**。
>
> OpenClaw 把"跨 Agent 调用"当作一件需要谨慎对待的事——一个 Agent 能调用另一个 Agent，必须显式开启，并且配一个白名单，明确哪些 Agent 允许被调用。
>
> 这是为了避免出现不受控的、随意的跨 Agent 调用关系。
> **设计多 Agent 系统时，"哪些 Agent 之间允许通信"本身就是一个要明确的架构决策。**

#### 2.8.2 消息在 Agent 之间流转的一幕

多 Agent 系统最难凭空想象的，是"消息在 Agent 之间到底怎么流转"。把它具体讲一遍。

**设想小慧已经上线**，HR 在对话框里发了一句"帮我筛一下这周的简历"。这条消息进入系统后，在几个 Agent 之间是这样一步步流转的：

1. **总控 Router 接收，并判断领域**。消息先到 Router。Router 自己不筛简历——它的职责是"看一眼这个请求属于哪个 HR 领域"。"筛简历"这件事，落在招聘领域。Router 判断完，得出结论：这个任务该交给招聘子 Agent。

2. **Router 把任务转给招聘 Agent**。Router 调用 `agentToAgent` 工具，把这个任务转发给 recruitment 子 Agent。这一步能成有个前提——`agentToAgent` 已经开启，且 recruitment 在允许调用的白名单里。

3. **招聘 Agent 处理**。任务进入 recruitment 自己独立的会话通道。招聘 Agent 在它自己的上下文里干活——解析简历、对照 JD 评分、排序——用的是它自己 workspace 里的文件、它自己装的 Skill。整个处理过程中，它碰不到绩效 Agent 或别的 Agent 的数据。

4. **招聘 Agent 把结果回报给 Router**。处理完，招聘 Agent 通过 `agentToAgent` 把结果——一份排好序的候选人清单——回传给 Router。注意：Router 自己也得在白名单里，因为它是子 Agent 回报的合法目标。

5. **Router 把结果交回给 HR**。

这一幕里，HR 全程只跟 Router 一个对象打交道，体验上就像在跟"一个小慧"对话。但消息背后是两个 Agent 的协作——**Router 负责分发，招聘 Agent 负责干活**。

> 这就是"从单体助手到分工团队"的实际含义：对外是一个数字员工，对内是一支各司其职的团队。

#### 2.8.3 对比单 Agent 全包与 ClawTeam

多 Agent 不是唯一的组织方式。把它和另外两种放在一起对比：

| 方式 | 形态 | 适合什么 |
|---|---|---|
| 单 Agent 全包 | 一个 Agent 干所有事 | 业务简单、单一领域的小场景 |
| **多 Agent 系统** | 多个常驻 Agent，按业务领域分工 | **常驻的、多领域的数字员工——本课的选择** |
| ClawTeam | 临时拉起一支多 Agent 突击队，跑完即散 | 一次性的批量突击任务 |

**对比单 Agent 全包**：一个 Agent 干所有事，最简单。但它就是本节开头说的那三个问题——上下文污染、权限无法分级、无法独立演进。业务一复杂就撑不住。HR 数字员工有五大业务模块，单 Agent 显然不够。

**对比 ClawTeam**：ClawTeam 也是多个 Agent，但它的形态是"临时拉起一支突击队做一个项目，跑完就解散"。它适合一次性的批量突击任务——比如某天要并行处理 200 份简历，临时拉起 8 个 worker，跑完即散。而 HR 数字员工是一个**常驻服务**：6 个子 Agent 像公司里 6 个固定岗位，长期在线、各管一摊。所以小慧用的是 OpenClaw 原生的多 Agent 系统（常驻），不是 ClawTeam（临时）。

> **一句话区分**：常驻团队用多 Agent 系统，临时突击用 ClawTeam。

> **架构决策延伸：什么时候应该用 ClawTeam 包装多 Agent 系统?**
> - 项目周期 < 1 周、任务可并行拆解、跑完不需长期复用——用 ClawTeam。
> - 业务每日有例行工作、需要保留会话上下文与历史记忆、需要按业务领域稳定分工——用多 Agent 系统。
>
> 误用 ClawTeam 来做"常驻 HR 数字员工"会出现两个工程问题：
> 1. **上下文丢失**——ClawTeam 解散时 Agent 的记忆随之清空，HR 第二天问同一件事，数字员工会失忆。
> 2. **权限断裂**——临时团队无法承载稳定的权限分级与审计链。
>
> 本课选多 Agent 系统，正是因为 HR 是带状态的持续服务。

#### 2.8.4 两个局限

1. **`agentToAgent` 默认关闭，要显式开启加白名单**。配置时要小心——白名单配漏了，Agent 之间通不了；配得太开，又失去了"受控通信"的意义。**哪些 Agent 之间允许通信，是要在架构里想清楚的。**

2. **多 Agent 不是免费的**。每个 Agent 都要一套独立的 workspace、agentDir、session store，这是实打实的隔离成本。所以 **Agent 的数量应该由业务领域决定**——HR 有五大业务模块，就是 5 个业务 Agent 加 1 个 Router——而不是越多越好。**Agent 拆得过细，管理成本会反过来吃掉分工带来的好处。**

## §3 业务分析：场景拆解与逐项映射

### 3.1 业务目标分析：开发任何 Agent 系统的第一步

上一章我们盘点了 OpenClaw 定制化开发的 7 大抓手——md 文档、Skill、MCP、插件、Channel、Lobster 工作流、多 Agent。这是你做 Agent 系统开发时手里握着的"牌"。

但拿到一个真实需求——比如"给公司做一个 AI HR 数字员工"——第一步并不是挑牌出牌。**第一步是业务目标分析**。

这一节先讲清楚什么是业务目标分析、为什么它不能跳过，以及在动手之前要先定下来的"总方向"。

#### 3.1.1 三个基础问题

业务目标分析，指的是在碰任何技术之前，先把三个问题答清楚：
1. **服务什么场景**——这个系统用在什么业务里、谁来用、在什么情况下用。
2. **解决什么问题**——这个场景里，使用者真正的痛点是什么、现在是怎么做的、哪里慢、哪里容易出错。
3. **做成什么样算成功**——交付物是什么、达到什么标准才算这个系统"做对了"。

这件事你其实并不陌生。做过软件项目就知道，拿到一个开发任务，没人会一上来就敲代码——总是先做需求分析、理清楚要做什么，再画架构图、定技术方案，最后才动手。Agent 系统开发是同一套逻辑。

> "业务目标分析"对应的就是软件工程里的需求分析：它是整个开发流程的第一道工序，不是可做不可做的前戏。

**区别只在于**：传统软件的"功能"是确定的输入输出，而 Agent 系统的"能力"是一组可以被组合、被编排的工具——就是上一章那 7 个抓手。正因为可组合的方式太多，在动手组合之前先想清楚业务目标，反而更重要。**牌越多，乱出牌的代价越大。**

#### 3.1.2 跳过业务分析会做出什么样的系统（反面教材）

设想两个开发者拿到同一个需求："给公司做一个 AI HR 数字员工。"

**开发者甲**（跳过业务分析，直接动手）：
- 他的理解是"HR 数字员工 = 一堆 HR 相关的能力"。
- 打开 ClawHub（OpenClaw 的 Skill 市场），搜 `resume`、`HR`、`interview`，看到简历解析 Skill 就装、看到日历调度 Skill 就装、看到邮件 Skill 就装。
- 两周后他有了十几个能单独跑的脚本和 Skill。

**开发者乙**（先做业务分析）：
- 他花了半天时间搞清楚：这家公司 HR 团队最大的痛点是什么、每天的工作怎么流转、哪些环节适合自动化、哪些必须人来定。
- 两周后他还没装几个 Skill，但他有一份清晰的系统设计。

三个月后：
- 甲的"系统"是这样的：十几个 Skill 各装各的，没有统一的任务入口（用户不知道该跟谁说话），没有分工（所有能力挤在一个 Agent 里互相干扰），没有协作（简历解析的结果没法自动流给评分环节）。每个 Skill 单独 demo 都能跑，但合起来不是一个系统，是一堆零件。想加一个新功能，得在一堆纠缠的脚本里找地方塞。这样的东西无法工业级落地。

> 这就是跳过业务分析最典型的陷阱：**被工具牵着走**。看到一个 Skill 能用就装一个，需求被悄悄偷换成"装尽量多的 HR 相关 Skill"。
>
> 技术本该是业务分析的产物——先想清楚要解决什么，再决定用什么；而不是反过来，先看手上有什么工具，再拼凑出一个"系统"。

**一句话**："能跑"不等于"成体系"。单点 demo 能跑，是 OpenClaw 生态成熟的功劳；成体系，才是开发者设计能力的体现，也正是这门课要教的东西。

#### 3.1.3 AI HR 数字员工的总方向：辅助，不是替代

业务目标分析里，最高层、要最先定下来的，是**总方向**——这个系统整体上要把业务带到哪里去。具体功能可以边做边调，但总方向定错了，后面全是返工。

本课的主线案例，是给一家 **200-500 人规模**的公司做一个 AI HR 数字员工，我们给它起名叫"小慧"。小慧的总方向是：**用 AI 承接 HR 的一部分工作，目标落在三个点上**：

| 方向 | 含义 | 例子 |
|---|---|---|
| **提效** | 同样的事，做得更快 | 一周 30 份简历的初筛，从人工 3-5 小时压缩到几十分钟 |
| **提质** | 做人工做不到、或做不好的事 | 给每个候选人生成一张可视化画像（能力雷达图、经历时间线）——人工基本不做 |
| **降本** | 把重复劳动从人力成本里释放出来 | 高频的员工政策答疑，由数字员工 7×24 承接 |

这里必须把一条边界说在前面，它会贯穿整门课：

> **AI HR 数字员工是"辅助"，不是"替代"。**

HR 工作里有大量"对人有重大影响"的决策——简历的最终淘汰、Offer 发不发、要不要解雇——这些在法律上明确要求由人来做（《个人信息保护法》第 24 条规定，个人有权拒绝仅由自动化决策做出的、对其有重大影响的决定）。

所以小慧的总方向准确说是：**AI 接住"可以自动化的部分"，把 HR 从重复劳动里解放出来，让人专注在判断和决策上**。

> 不是"造一个不需要 HR 的系统"——那个方向既不合法，工程上也做不出来。
>
> 总方向定成"辅助"，后面所有的架构设计才有正确的落点。

### 3.2 AI HR 场景拆解：HR 到底做哪些工作

总方向定了——小慧要辅助 HR，做到提效、提质、降本。

但"辅助 HR 的工作"还是一个模糊的大词。你没法对一个大词做技术设计。**业务目标分析的第二步，就是拆解**：把"HR 的工作"这个大场景，拆成一个个具体、可观察、可判断的工作事项。

> **为什么必须拆？** 因为"HR 工作"这四个字无法映射到任何技术，但"筛简历""排面试时间""回答员工的年假问题"这种具体动作可以。
>
> 拆解就是在**大场景和技术能力之间架一座桥**——桥的这头是模糊的业务目标，那头是 7 个开发者抓手，中间需要一层"具体工作事项"才接得上。

#### 3.2.1 HR 的六大模块工作全图

拆 HR 工作，不能靠拍脑袋想——想出来的清单一定是残缺的。要拆得完整，得基于 HR 行业的真实 SOP（Standard Operating Procedure，标准作业流程）。

HR 是一个成熟了几十年的职能，它的工作早已被行业归纳成六大模块。下表是把这六大模块和每个模块下的真实工作事项摊开的结果：

| 模块 | 典型工作事项（节选） |
|---|---|
| **招聘 Recruitment** | JD 撰写发布、渠道运营、简历收发、简历初筛、人才画像比对、人才库维护、候选人沟通、面试调度、面试通知、面试纪要、Offer 制作发放、Offer 跟进 |
| **入职 Onboarding** | 合同准备、资料收集、账号设备申请、政策介绍、Buddy 匹配、入职培训、试用期跟进 |
| **培训发展** | 需求调研、计划制定、内容生成、实施记录、效果测评、发展路径设计 |
| **绩效管理** | 目标（OKR / KPI）设定、周期评估、360 反馈、面谈纪要、改进跟踪 |
| **薪酬福利** | 薪资核算、调薪审批、社保公积金、个税申报、福利申请、离职结算 |
| **员工关系与行政** | 需求对接、会议安排、会议纪要、HR Helpdesk、内部通知、劳动争议、考勤异常、离职面谈、档案管理、数据看板 |

六个模块加起来有 30 多个子项。这张图本身就是一个重要产出——**它告诉你 HR 这个场景的完整边界**。后面判断"小慧该做哪些、不做哪些"，全部以这张图为底。漏掉一个模块，就漏掉了一类需求。

> 这里先埋一个伏笔：**六大模块不会机械地对应到六个子 Agent**。比如薪酬模块牵涉金税四期、社保公积金、个税申报，是强合规、强外部系统对接的领域，本课主线不为它单独设一个 Agent——具体怎么归并，是第 4 章的事。
>
> 这一章先把"全图"拆完整，"怎么归并成系统"留到下一章。

#### 3.2.2 把一条招聘流程念出来

"工作事项"听起来还是有点抽象。我们挑招聘模块，把一条真实的招聘流程从头到尾念一遍——你会看到，每一个箭头之间，都是一件具体的、HR 真的会坐下来做的事：

```
业务部门提出招聘需求
    （要 3 个 Python 高级开发，填一张《招聘需求表》，写明职级、薪酬带宽、审批链）
  → HR 撰写 JD
    （按"职位名称 / 岗位职责 / 任职要求 / 薪酬待遇 / 工作地点 / 企业情况"六要素写）
  → 多渠道发布（智联招聘、BOSS 直聘、拉勾、猎聘……）
  → 收简历（一个职位平均会收到约 180 份投递）
  → 简历初筛
    （从 180 份里筛出值得面试的——业界"投递→面试邀约"的转化率约 3%）
  → 面试调度（协调面试官和候选人的时间，多轮面试时尤其繁琐）
  → 面试（按 8 个维度打分，用 STAR 行为面试法追问）
  → Offer
    （面试通过率约 27%；Offer 须符合劳动合同法对试用期的规定）
  → 入职（候选人接受 Offer，转 入职模块）
```

念完这条流程，你会有两个体感：
1. **第一**，HR 工作是由一连串具体动作组成的，不是"管人事"这一团模糊的东西。
2. **第二**，每个动作的"可自动化程度"差别很大——"写 JD""筛简历"这种有明确输入输出的事，AI 能接得很好；而"决定录用谁"这种判断，要留给人。**这个差别，正是下 1 节"逐项映射"要回答的问题。**

> 注：上面流程里的数字（180 份投递、3% 投递→面试转化、27% 面试→Offer 转化）是 HR 行业的公开基准数据（来源 Jobvite 2024 等行业报告）。后面做小慧的招聘看板时，会用它们作为对照基线。

#### 3.2.3 拆到能映射技术为止

拆解这件事，真正的难点不在"拆不拆"，而在拆到多细才合适。这是拆解方法里最容易把握不准的地方，要专门讲清楚。

**判断标准只有一条**：**拆到每一项都能直接回答"用什么技术做"为止**。

比如"简历初筛"就是一个合适的颗粒度——
- 它足够具体，你能立刻想到"解析简历文件 + 用 LLM 按 JD 评分"；
- 它又足够完整，是一件 HR 真的会作为一个任务来做的事。
- 再往上一层（"招聘"）太粗，再往下一层（"读取 PDF 的第二页"）太细。

所以这一节的产出，不是"一张全图"就完事——**而是一张拆到"工作事项"颗粒度的清单，清单里每一项都站在"马上能讨论用什么技术"的位置上**。

> ❌ 拆得太粗，没用。"招聘"是一个词，但它没法映射到任何具体技术——你不能对"招聘"装一个 Skill。
> ❌ 拆得太细，也没用。"在 BOSS 直聘后台点击'发布'按钮"是一个动作，但这种颗粒度已经掉进了 UI 操作细节，对系统设计没有意义，还会让你的清单膨胀到无法管理。

### 3.3 逐项映射：每个 HR 事项怎么用 OpenClaw 做

上一节把 HR 场景拆成了一张工作事项清单。业务目标分析的第三步——也是最后一步——是**逐项映射**：拿着清单，一项一项判断这件事能不能用 OpenClaw 做、**用什么做**、**AI 能做到哪一步**。这一步做完，业务分析就从"HR 在做什么"，落到了"我们的系统要用什么技术做什么"。

**映射不是随便对一对，每个工作事项都要回答三个固定的问题**：

1. **用什么 OpenClaw 能力**——对应 7 个开发者抓手里的哪一个或哪几个。
2. **用现成的还是自己写**——ClawHub 上有现成 Skill、OpenClaw 有内置工具，就优先用；涉及合规边界、或者没有现成方案的，就手写。
3. **AI 能做到哪一步、哪一步必须人来做**——这一问**最关键**，它直接决定了后面架构里"人工审批点"设在哪。

#### 3.3.1 HR 事项 × OpenClaw 能力对位表

把工作事项清单逐项过一遍三个问题，就得到下面这张对位表。它是业务分析阶段最核心的产出物——下游的架构设计、开发计划，都建立在它之上。

表里的能力名称（office-to-md、fastio、Lobster 等）都是 OpenClaw v2026.5 真实存在的 Skill 或内置工具：

| HR 工作事项 | 用什么 OpenClaw 能力 | 现成 / 手写 | AI 做到哪一步 |
|---|---|---|---|
| **简历解析（PDF / DOCX）** | office-to-md Skill | **现成** + 手写中文字段提取 prompt | 全自动 |
| **简历评分排序** | LLM 评分任务 | **手写**完整评分 Pipeline（含合规过滤层） | AI 评分排序，最终淘汰由人工 |
| **候选人画像** | image_generate + matplotlib | **现成**图表 + 手写报告排版 | 全自动 |
| **人才库语义检索** | fastio Skill + Memory LanceDB | **现成** + 手写 HR 字段 schema | 全自动 |
| **面试调度** | Sub-agent 协调（本集 CLI 入口） | **手写**调度规则 | AI 出推荐时段，人确认 |
| **面试纪要** | faster-whisper（含说话人分离） | **现成** ASR + 手写总结 prompt | 全自动出初稿 |
| **入职审批流程** | Lobster 工作流（HiTL） | **现成**引擎 + 手写审批分支 | AI 跑流程，每个审批点人批 |
| **培训物料生成** | LLM 任务 + image_generate | **手写** PPT→手册→测试题 Pipeline | 全自动出初稿 |
| **HR Helpdesk 答疑** | Memory Wiki + RAG | **现成** + 手写 RAG 编排 + HiTL 升级 | 常规问题全自动，复杂的升级人工 |
| **HR 月报** | Cron + code_execution（pandas / plotly） | **现成** + 手写报告 Pipeline | 全自动 |
| **定时调度（如季度绩效触发）** | OpenClaw Cron CLI | **现成** | 全自动 |

> 表中 **HiTL（Human-in-the-Loop，人在回路）** 指的是：在自动化流程中插入"必须由真人确认"的节点，AI 跑到这里会停下来等人批准。后面第 4 章会专门讲它怎么落进架构。

**看完这张表，有三个结论值得记下来**：

1. **大部分事项有现成方案，但不是装上就完**。office-to-md、fastio、faster-whisper 这些 Skill 解决了"读文件""存数据""转语音"这类通用能力，但 HR 业务的特殊性——中文简历的字段、HR 专属的评分维度、公司的政策口径——都得靠手写部分补上。**整体下来，小慧大约 60% 用现成能力、40% 是手写**。这个比例不是凑出来的，是逐项映射时"现成/手写"那一列累加的结果。

2. **越靠近合规边界，越要手写**。简历评分这种事，为什么不直接用一个现成的"打分 Skill"？因为评分要绝对避开年龄、性别、院校排名这些敏感特征（这是法律红线），**合规过滤层必须自己掌控**，不能交给一个看不见内部逻辑的现成 Skill。

3. **"AI 做到哪一步"这一列，藏着架构信息**。凡是写着"人确认""人批""升级人工"的行，未来都是**一个 HiTL 审批点**。映射做对了，架构里该设几个审批点、设在哪，就已经浮出来了。

#### 3.3.2 拆开看三个事项怎么落地

对位表是浓缩的。挑三个事项，把"OpenClaw + 对应能力怎么解决这个问题"展开讲清楚，你就能体会到映射不是填表格，是真的想清楚了实现路径。

**事项一：简历初筛**

这件事拆成一条小流水线：
1. 先用 `office-to-md` Skill 把 PDF / DOCX 格式的简历转成结构化的 Markdown 文本（这是现成能力）；
2. 再让 LLM 拿着这份文本和岗位 JD 做比对评分，按"技能匹配度""经验匹配度"等维度打分并给出文字理由（这是手写的评分 Pipeline，里面有一层合规过滤，强制不让年龄、性别、毕业院校进入评分特征）；
3. 最后把评分结果写成一份结构化文件存起来，供后续排序和生成画像用。

> **一句话**：office-to-md 解析 + LLM 按 JD 评分（含合规过滤）+ 结果落盘。

**事项二：入职审批流程**

新员工入职要走"合同准备 → IT 账号 → 设备申请 → Buddy 匹配"等一串步骤，其中有几步必须 HR 主管点头才能继续。

这件事映射到 Lobster 工作流引擎：
- 把整个入职流程编排成一条 pipeline，在需要审批的地方放一个 `approval` 节点。
- AI 跑到审批节点会暂停（halt），把待审内容连同一个恢复令牌一起交出来。
- 等 HR 主管批准后，流程凭令牌从断点继续。

> AI 负责把流程跑顺，人负责在关键节点拍板——**这正是 HiTL**。

**事项三：HR Helpdesk 答疑**

员工问"年假还剩几天""报销发票丢了怎么办"这类高频问题，映射到 Memory Wiki 加 RAG（检索增强生成）：
- 把公司的 HR 政策文档灌进 Memory Wiki 知识库。
- 员工提问时先检索出相关的政策原文。
- 再让 LLM 基于原文作答并附上出处。
- 常规问题这样就能自动答完；
- 遇到复杂的、涉及个人隐私的、或者政策没覆盖的，自动升级给真人 HR。

> **RAG 保证答案有据可查，HiTL 升级机制保证边界问题不乱答**。

#### 3.3.3 AI 不能单独做的事（合规红线清单）

对位表的最后一列里，反复出现"由人工""人批""升级人工"。把这些单独拎出来，就是一份 **AI 不能单独做的事的清单**。这不是 OpenClaw 能力不足，而是**法律和工业级标准的硬性要求**：

| 必须由人做最终决定的事项 | 为什么 |
|---|---|
| **简历的最终淘汰** | 个保法第 24 条 + GDPR 第 22 条：个人有权拒绝纯自动化的重大影响决定 |
| **Offer、调薪、解雇决定** | 同上，且涉及劳动合同法的合规审查 |
| **绩效的最终定级** | AI 只能聚合多方反馈，定级是对人的重大影响决定 |
| **背景调查的结论** | 结论直接影响录用，须人工判断 |

> 这条边界有过血的教训。2023 年起诉、至今仍在进行的 Workday Mobley 集体诉讼里，Workday 自己披露有约 **11 亿份求职申请被 AI 拒绝**——核心争议点就是"AI 自动拒绝候选人、没有人工复核"。这类设计在今天已经是明确的法律风险。

**但要分清楚一件事**：
> "AI 不能单独做最终决定" **不等于** "AI 不参与"。

以简历初筛为例，AI 照样做解析、做评分、做排序、生成画像——它把 30 份简历整理成一份有理有据的排序清单，HR 拿着这份清单做最终录用判断。**AI 把人从重复劳动里解放出来，人专注在那个"不能交出去的决定"上。**

对系统设计来说，这一列的意义是：**凡是"必须人做"的事项，在架构里都对应一个 HiTL 审批点**。映射阶段把这些事项标出来，第 4 章设计架构时，Lobster 审批节点该放在哪，就是照着这份清单落子。

> **诚实地标出 AI 的边界，本身就是架构设计的一部分。**

### 3.4 业务分析方法论小结

第 3 章走完了一套完整的业务目标分析。回到这一章开头那个问题——拿到一个"做个 AI 数字员工"的需求，第一步该做什么？

答案现在很明确：**第一步不是配 Skill，是做业务分析**。而业务分析本身有固定的三步。

#### 3.4.1 三步回顾

| 步骤 | 做什么 | 产出物 | 对应小节 |
|---|---|---|---|
| **① 确定总方向** | 想清楚系统服务什么场景、解决什么问题、做成什么样算成功，并定下整体方向 | 一句话总方向（如小慧：AI 辅助 HR，提效、提质、降本） | §3.1 |
| **② 拆解工作事项** | 基于行业真实 SOP，把大场景拆成具体的工作事项清单，拆到能映射技术的颗粒度 | HR 六模块工作全图 + 工作事项清单 | §3.2 |
| **③ 逐项技术映射** | 给每个工作事项回答三个问题：用什么能力、现成还是手写、AI 做到哪一步 | HR 事项 × OpenClaw 能力对位表 | §3.3 |

> **三步是有顺序、有依赖的**：没有总方向，拆解会拆偏；没有拆解，映射无从下手。每一步都有一个书面的产出物——这一点很重要，下一章第 4.3 节会专门讲为什么中间产出必须落到纸面上。

**有一个常见误区要纠正**：

很多人觉得"业务分析"是写文档、走流程的虚活，真本事在写代码。恰恰相反——三步里没有一步是空谈，每一步都在为技术决策做准备。
- 总方向决定架构往哪走，
- 拆解决定系统有哪些功能，
- 映射直接产出"用什么技术"。

> **业务分析做得越扎实，后面写代码越不返工。**

#### 3.4.2 这套方法不止用于 HR

这套三步法最大的价值，是它**和 HR 无关**——它是一套通用的"从业务场景到技术方案"的分析方法。换一个完全不同的业务，方法一字不改。

> **举例：假设公司下次要做的是一个 AI 客服数字员工**：
>
> - **第①步 确定总方向**：AI 辅助客服团队，提效（高频问题自动答）、提质（回答口径统一）、降本——和小慧的总方向是同一个句式。
> - **第②步 拆解工作事项**：基于客服行业的真实 SOP 拆——售前咨询、订单查询、物流追踪、售后工单、退换货处理、投诉升级……拆到工作事项颗粒度。
> - **第③步 逐项技术映射**：售后工单解析用 `office-to-md`，常见问题答疑用 Memory Wiki + RAG，退款审批用 Lobster 工作流挂 HiTL 审批点——映射的三个问题原样套用。

你会发现，连用到的 OpenClaw 能力都高度重合。**这正是这套方法论的价值所在**：学会它，以后做任何 Agent 系统——AI 客服、AI 财务助理、AI 法务助手——**前期分析都不用从零摸索**。

> 这门课交付给你的，首先是这套可迁移的分析方法，其次才是 HR 这一个具体案例。

## §4 系统架构：从场景到六要素

### 4.1 关键转变：场景分析是分散的，系统开发是整体的

第 3 章结束时，我们手里有一张"HR 工作事项 × OpenClaw 能力对位表"。很自然的下一个念头是：照着这张表，一项一项做下去——简历初筛写一个，面试纪要写一个，HR Helpdesk 写一个。

> 这个念头是错的。它会把你带回第 3.1 节那个开发者甲的结局，只不过是"升级版"。这一节要讲清楚的，是从业务分析进入系统开发时，**一个必须完成的认知转变**：
>
> **场景分析的产物是分散的，系统开发面对的是整体的**。两者中间隔着一道坎，迈不过去，再好的对位表也做不出工业级系统。

#### 4.1.1 一张清单不是一个系统

先看清楚"清单"和"系统"到底差在哪。

| 维度 | 业务分析的产物：对位表 | 系统开发的目标：一个系统 |
|---|---|---|
| **形态** | 一张清单——若干并列的工作事项 | 一个整体——多个部件协同运转 |
| **关系** | 每项独立，互不相干 | 部件之间有分工、有协作、有调用关系 |
| **入口** | 没有入口的概念，就是一份列表 | 有统一入口——用户对一个对象说话 |
| **基础设施** | 不涉及 | 共享一套日志、权限、调度、可观测 |

**对位表是一份地图**——它标清了"HR 这片地方有哪些事、每件事用什么技术"。但地图不是房子。你不会把地图上标的每个地点单独盖一座小屋，然后管这堆小屋叫"一座建筑"。

如果照着对位表逐项开发，你会得到 11 个互不相干的脚本：用户要记住 11 个入口、面对 11 套各自的输出格式、11 处重复写的权限判断和日志代码。每个脚本单独看都没问题——毕竟它们都经过了第 3 章扎实的映射分析——但合起来，**它依然不是一个系统**。

> **业务分析做对了，不代表可以直接照着清单动手**。这是最关键、也最容易被忽略的一点。

#### 4.1.2 关键动作：剥离与归并

既然不能照着清单逐项做，正确的下一步是什么？**是在动手之前，先对这张清单做两个动作——剥离和归并**。

**1. 剥离**

是把每个场景里的"技术需求"，从"业务故事"里剥出来。

举个例子，"简历初筛""面试纪要""HR 月报"这三件事，业务上毫不相干——一个属于招聘、一个属于面试、一个属于行政。但如果只看它们的技术需求，会发现一条共性：**三件事都要"调 LLM 处理文本 + 把结果写成一份文件"**。剥掉业务外壳，技术骨架露出来了。

**2. 归并**

是把剥离出来的技术需求按类聚到一起。归并有两个方向：

| 归并方向 | 做法 | 用途 |
|---|---|---|
| **按业务领域归并** | 把对位表里的事项按"招聘 / 入职 / 培训 / 绩效 / 行政"归类 | 归完一看，每一类事项的量和内聚度，就提示了"这个系统该分几个 Agent、各管哪一摊" |
| **按共性基础设施归并** | 把所有场景都要用的东西（日志、权限分级、定时调度、可观测）抽出来 | 它们不属于某一个场景，是整个系统的**公共底座** |

这两个动作做完，散落的清单会重新组织成有结构的东西：**几类业务、一套公共底座**。

> **系统架构的轮廓，就是在剥离和归并之后浮现出来的——它不是凭空设计的，是从对位表"重新整理"出来的。**

这里要点出一件事，它会在下一节的架构方案里得到印证：
> **剥离归并不是把 6 个 HR 模块机械地映射成 6 个 Agent**。
>
> 第 3.2 节埋过的伏笔——薪酬模块——就是例子：薪酬强合规、强外部系统对接，归并时不会单独成为一个 Agent，它的少量可自动化事项会挂到别的 Agent 下。
>
> **归并是带着工程判断重新组织，不是照抄模块清单**。

### 4.2 从场景需求到系统架构：架构六要素

上一节说，对清单做完剥离和归并，系统架构会"浮现"出来。但"浮现"不能靠感觉——**你需要一组固定的问题，能把"剥离归并后的需求"稳定地转成"一份架构"**。

**这个方法是：架构设计 = 回答六个问题**。把这六个问题答完，你手里就有了系统架构。我们把这六个问题叫**架构六要素**。

#### 4.2.1 架构六要素与归并结果的对应关系

| 要素 | 是什么 | 怎么从场景推出来 | OpenClaw 里对应什么 |
|---|---|---|---|
| **① Agent 数量与分工** | 系统拆成几个独立 Agent，各管哪块业务 | 按业务领域归并对位表，看每类的量与内聚度 | 多 Agent 系统（每个 Agent 独立 workspace、独立 agentDir） |
| **② 调度模式** | 用户请求进来后，怎么分发到对应 Agent；Agent 之间怎么协作 | 看"谁是入口""谁调用谁" | Multi-Agent Routing（路由分发）+ Agent 间通信 |
| **③ 工作流** | 哪些多步骤流程需要中途暂停、等 人审批 | 对位表里标"人批""人确认"的事项 | Lobster 工作流引擎（HiTL 审批 + 可恢复） |
| **④ hooks** | 哪些事件发生时要自动触发动作 | 找"一旦发生 X 就应该自动做 Y"的场景 | hooks（生命周期事件钩子） |
| **⑤ 人设** | 每个 Agent 是谁、负责什么、边界在哪 | 每个 Agent 的业务领域 + 第 3 章定的合规边界 | 每个 Agent 一份 SOUL.md（人设档案） |
| **⑥ 落盘物** | 每个场景跑完，给用户留下什么持久化的文件 | 看每个工作事项的"交付物" | JSON / HTML 报告 / 审计日志等磁盘文件 |

> **一句话对应**：按业务领域归并的结果 → ① 要几个 Agent、各管什么；按"谁调用谁"的协作关系 → ② 用什么调度模式；对位表里标了"人批"的事项 → ③ 哪些步骤要走审批工作流；需要自动触发的事件 → ④ 配哪些 hooks；每个 Agent 的角色定位 → ⑤ 人设怎么写；每个场景跑完要交付什么 → ⑥ 产出哪些落盘物。

**六个要素不是孤立的清单，它们互相咬合**：
- 定了几个 Agent（①），才谈得上 Agent 之间怎么调度（②）；
- 调度里有审批需求，才需要工作流（③）。

把六个问题依次答完，一份结构完整的架构就成形了。

**这里专门解释两个容易陌生的概念**：

- **调度模式**：当系统里有多个 Agent，必须有人决定"用户这句话该交给谁处理"——这个分发机制就是调度。
- **人设**：在 OpenClaw 里，一个 Agent 的身份不是写死在代码里的，而是写在一份叫 SOUL.md 的文档里——它定义这个 Agent 是谁、负责什么、不能做什么。比如招聘 Agent 的 SOUL.md 里会明确写"只做简历评分和排序，最终淘汰由人工决定"，**把第 3 章那条合规红线从架构阶段就钉进 Agent 的身份里**。

#### 4.2.2 落盘物长什么样（最容易讲虚的那个要素）

六要素里，"落盘物"最容易被讲虚——一句"产出一些文件"就带过。但它恰恰是学员最该有具体画面的一个，因为**落盘物是系统"价值"的载体**：

> 用户感知到小慧有用，不是因为后台调了多少次 LLM，而是因为他收到了一份能打开、能看、能转发的东西。

**落盘物**，指的是系统运行后产出的、**持久化保存在磁盘上**的文件。它和"运行时在内存里转一圈就没了的中间数据"相对——**落盘物是留得下来、给得出去的成果**。

**小慧的落盘物，具体长这样**：

**第一种，简历评分结果，是一份 JSON 文件**。

招聘 Agent 筛完一份简历，产出的不是一句"这个候选人不错"，而是一份**结构化的 JSON**，里面有：
- 候选人标识
- 与 JD 的总匹配度评分
- 各维度的分项得分（技能、经验、教育等）
- 一段说明"为什么是这个分"的评分理由文字
- 评分时间
- 用的是哪一版 JD

> 它是结构化的，所以能被程序读取——后续的排序、生成画像、汇总看板，都从这份 JSON 取数。

**第二种，候选人画像，是一个 HTML 文件**。

同一个候选人，除了给程序看的 JSON，还要有一份**给人看的画像**。它是一个 HTML 文件，里面有：
- 能力雷达图
- 工作经历时间线
- 技能词云
- 与 JD 的匹配度对比

HR 用浏览器打开就能看，也可以直接转发给业务部门——这就是第 3.1 节说的"提质"：给每个候选人做一张可视化画像，是人工基本不做的事。

**第三种，审计日志，是一条一条的决策记录**。

系统每做一个动作，就往审计日志里写一条记录，每条记录回答五个问题：
- **谁**（哪个 Agent、受哪个用户指令）
- **何时**
- **做了什么**（具体操作）
- **依据什么**（用了哪些数据 / 哪一版规则）
- **结果是什么**

> 审计日志不是可选项——《个人信息保护法》要求自动化决策可追溯、可解释，候选人有权要求系统说明"为什么是这个结果"。没有审计日志，系统就达不到工业级标准。

**把这三种落盘物放在一起看**，你会明白为什么"落盘物"要作为一个独立的架构要素：
- **JSON** 保证数据能在系统内部流转
- **HTML** 保证价值能交付到用户手里
- **审计日志** 保证整个系统经得起合规追溯

> **设计架构时如果不把落盘物明确列出来，做出来的系统很可能"跑是跑通了，但什么都没留下"**。

#### 4.2.3 架构不是一次定死的（要诚实承认的局限）

最后要诚实说明一点局限：**用六要素推导出来的，是第 1 版架构，不是终版**。

开发过程中，架构几乎一定会被调整：
- 可能实测发现某个 Agent 职责太重，要拆成两个；
- 可能发现某两个 Agent 总是互相调用，不如合并；
- 可能某个落盘物的字段在真实业务里不够用，要补。

> **这是正常的——架构是活的，会随着开发和真实数据不断迭代。**

但"架构会变"绝不是"不用先设计"的理由。两者的关系是：

- **没有第一版架构，开发就没有起点**——你不知道先建哪个 Agent、各模块怎么对接，只能边写边猜，这就退回了开发者甲的老路。
- **有了第一版架构，后续的每一次调整都是"修订"**——在一个已知的结构上做局部改动，影响范围清楚、改动可控。

> **所以正确的心态是：认真做第一版架构，同时接受它会被修订**。六要素给你的是一个扎实的起点和一套调整时的参照系，不是一份不许动的圣旨。

### 4.3 规范中间节点的产出

到这里，业务分析（第 3 章）和架构推导（4.1 至 4.2 节）的方法都讲完了。回头看整个过程，它并不是"分析完直接就有了一个能跑的系统"——中间产生了几样东西：一张业务-技术对位表、一份架构方案。它们**不是最终的可运行系统，是开发流程里的中间产出**。

这一节讲一件容易被忽略、但直接决定系统能不能落地的事：

> **这些中间产出必须规范化**。

听起来像是流程管理的虚活，其实是工程问题——**中间产出不规范，下游开发根本接不住**。

**为什么接不住？** 因为系统开发是分阶段、分人的。
- 做业务分析的人，和做架构的人，可能不是同一个；
- 做架构的人，和写代码的人，往往也不是同一个；
- **哪怕全程是你一个人，三个月后的你也接不住三个月前那个只存在脑子里的结论**。

> **中间产出如果只在脑子里、只靠口头说一句，信息会在每一次传递中流失**。
>
> **口头传递等于信息丢失——这是系统开发里最隐蔽的成本。**

#### 4.3.1 系统开发的三个中间节点

把一个 Agent 系统从需求做到上线，中间有三个关键节点，每个节点都必须产出一份明确的、书面的产出物：

| 中间节点 | 产出物 | 这份产出物回答什么 | 本课对应 |
|---|---|---|---|
| 业务分析 | 业务-技术对位表 | 这个系统要做哪些事、每件事用什么技术 | §3.3 的对位表 |
| 架构设计 | 系统架构方案 | 系统由哪些部件组成、怎么协作、产出什么 | §4.4 的架构方案 |
| 开发计划 | 带检查点的阶段计划 | 按什么顺序开发、每阶段做完的标志是什么 | 第 5 章的开发计划 |

**这三个节点是一条接力链**：
> 业务分析的产出物是架构设计的输入，架构设计的产出物是开发计划的输入，开发计划的产出物是写代码的输入。
>
> **链条上任何一环的产出物含糊，下一环就得回头补——要么回去问，要么凭猜测往下做。**

把这一点说具体些。假设架构方案里写"系统有 6 个 Agent"，但没写清楚"为什么是 6 个、每个管什么、为什么薪酬没单独成一个 Agent"。拿到这份方案去写开发计划的人，就无法判断该先开发哪个、各 Agent 之间的依赖是什么——他只能回头找写架构的人重新讲一遍。**这一来一回的成本，本可以靠一份写清楚的产出物省掉。**

#### 4.3.2 一份合格的中间产出物长什么样

"规范"不是把文档写得花哨。一份合格的中间产出物，要满足四个标准：

1. **书面化**——它是一份独立的文档，不在脑子里，不在聊天记录里翻找。能被打开、被引用、被存档。
2. **结构化**——用表格、清单、架构图来组织，不是一大段散文。结构化的信息一眼能定位，散文得通读才能提取。第 3 章的对位表、第 4 章的六要素表，都是结构化的范例。
3. **可追溯**——每个结论都能查到依据。架构里"为什么是 6 个 Agent"，要能追回到业务分析里"按业务领域归并的结果"；"为什么招聘 Agent 只做评分不做淘汰"，要能追回到对位表里那条合规红线。**可追溯，下游才信得过，也才改得动。**
4. **下游能直接用**——下一个节点的人拿到它就能开工，不需要回来追问。**这是检验前三条是否做到位的最终标准**。

> 这四条不用死记。它们其实就指向一个朴素的判断：
>
> **把这份产出物交给一个没参与过分析的人，他能不能照着往下做？**
>
> **能，它就合格；不能，它就还停留在"你自己心里清楚"的状态。**

接下来 §4.4 会给出小慧的系统架构方案，第 5 章会给出开发计划——这两份文档本身，就是"规范的中间产出物"的范例。

### 4.4 AI HR 数字员工系统架构方案

前面三节讲了从场景到架构的方法——剥离归并、回答六要素、规范产出。这一节是方法的产出物本身：

> **把 AI HR 数字员工"小慧"的系统架构方案完整摆出来**。

这份方案有双重身份：
- 它既是本课主线案例的架构定稿，后面第 5 章的开发计划、Lesson 2 的开发实战都以它为蓝本；
- **它本身又是第 4.3 节说的"规范的中间产出物"的一个范例**——你会看到它是表格化的、每个结论都能往回追溯。

> 本方案基于 OpenClaw v2026.5.12 stable。

#### 4.4.1 小慧的架构六要素定稿

| 架构要素 | 小慧的方案 |
|---|---|
| **① Agent 数量与分工** | 6 个常驻子 Agent：招聘、入职、培训、绩效、行政 5 个业务 Agent + 1 个总控 Router。每个独立 workspace + 独立 agentDir |
| **② 调度模式** | Multi-Agent Routing 负责把请求分发到对应 Agent；Agent 之间用 `agentToAgent` 通信。本集为 CLI 入口，飞书 Channel 入口留待 Lesson 3 |
| **③ 工作流** | Lobster 工作流引擎承接 HiTL 审批：入职流程、Offer 审批、调薪审批等关键决策点，AI 跑流程、人卡审批点 |
| **④ hooks** | 5 个 bundled hooks（会话记忆、命令日志等）+ 1 个自写 hook（如"候选人投递 → 自动触发评分"） |
| **⑤ 人设** | 每个子 Agent 一份 SOUL.md 定义领域职责与边界。如招聘 Agent 写明"只做评分排序，最终淘汰由人工" |
| **⑥ 落盘物** | JSON（简历评分结果）/ HTML（候选人画像、HR 月报）/ 审计日志（每次决策一条：谁、何时、做了什么、依据、结果） |

##### 系统架构总图：小慧的六个 Agent

```
                ┌─────────────────────────────────────┐
                │          AI HR 数字员工 "小慧"        │
                └──────────────────┬──────────────────┘
                                   │
                ┌──────────────────┴──────────────────┐
                │            总控 Router              │  ← 唯一入口，判断领域并分发
                └──────────────────┬──────────────────┘
                                   │
        ┌──────────────┬───────────┼───────────┬──────────────┐
        │              │           │           │              │
   招聘 Agent   入职 Agent   培训 Agent   绩效 Agent   行政 Agent
        │              │           │           │              │
        └──────────────┴───────────┼───────────┴──────────────┘
                                   │
        ┌──────────────────────────┴──────────────────────────┐
        │              工业级公共底座                          │
        │  可观测（Prometheus + OpenTelemetry）              │
        │  / 权限分级（Per-Sender Tool Policy 三档）         │
        │  / 定时调度（Cron）                                 │
        │  / 事件触发（hooks）                                │
        │  / 审计日志                                         │
        └────────────────────────────────────────────────────┘
```

##### 为什么是这 5 个业务 Agent

它们对应 HR 工作里**内聚度最高、可自动化空间最大**的五个领域：招聘、入职、培训、绩效、行政。每个子 Agent 有自己独立的 workspace（工作目录）和独立的 agentDir（状态目录，存会话历史与记忆）——**物理隔离**，招聘的简历对话不会污染绩效的反馈数据，权限也能按领域分别收紧。

##### 为什么薪酬模块没有独立 Agent

这正是第 3.2 节埋下、第 4.1 节点过的伏笔。

HR 工作全图里明明有六大模块，归并成系统却只有五个业务 Agent——**因为归并是带工程判断的重新组织，不是模块清单的机械照抄**。

薪酬牵涉金税四期、社保公积金、个税申报，是强合规、强外部系统对接的领域，本课主线不为它单独建一个 Agent；薪酬里少量可自动化的审批类事项（如调薪审批），走 Lobster 工作流挂在绩效 Agent 下处理。

> **架构方案敢于和模块清单不一致，并把理由写清楚——这本身就是"可追溯"的体现。**

#### 4.4.2 每个子 Agent 的能力配置

六要素定的是系统的"骨架"。再往里看一层，是每个业务子 Agent 各自的能力配置——也就是它要用哪些 OpenClaw 抓手、哪些现成、哪些手写。这张表直接对应第 3 章对位表的归并结果：

| 子 Agent | 负责领域 | 主要能力配置 |
|---|---|---|
| **招聘 Agent** | 简历筛选、人才库、面试 | `fastio` + `office-to-md` + `paddleocr` + **手写**评分 Pipeline + `sessions_spawn` 批量并行 |
| **入职 Agent** | 新员工入职全流程 | Lobster 工作流（HiTL 审批，多步串联）+ **手写** onboarding 分支 |
| **培训 Agent** | 培训物料生成 | LLM 任务 + Skills + **手写**"PPT → 讲师手册 → 测试题"Pipeline |
| **绩效 Agent** | 绩效评估、360 反馈 | Standing Orders + Cron 季度触发 + **手写** 360 反馈聚合 |
| **行政 Agent** | HR Helpdesk、会议纪要 | Memory Wiki + RAG + `faster-whisper` + **手写** Helpdesk 编排 |
| **总控 Router** | 接收请求、判断领域、分发 | Multi-Agent Routing + Per-Sender Tool Policy（三档权限） |

> 把两张表对照着看：上面那张是"系统骨架"，下面这张是"每个 Agent 的肌肉"。
>
> 骨架来自六要素，肌肉来自对位表——架构方案不是凭空设计的，每一格都能往回追溯到第 3 章和第 4 章的分析。
>
> **书面化、结构化、可追溯，这份方案本身就是第 4.3 节那四条标准的一个范例。**

#### 4.4.3 一个任务在系统里怎么流转

架构表是静态的。要真正理解这套架构，最好的方式是跟着一个任务，看它在系统里走一遍。下面这一幕，描述的是小慧设计完成后的工作方式——**一个 HR 任务从接收到返回的完整路径**。

**设想场景**：HR 主管对小慧说一句话："帮我筛一下这周收到的简历。"

接下来发生的事：

1. **总控 Router 接收**。Router 是整个系统的唯一入口，所有请求先到它这里。HR 主管不需要知道"该找招聘 Agent 还是入职 Agent"——他只跟小慧说话，面对的是一个统一的对象。

2. **判断领域**。Router 读懂这句话，判断它属于"招聘"领域的任务。这一步就是第 4.2 节说的调度——决定这个请求该交给谁处理。

3. **转交子 Agent**。Router 通过 `agentToAgent` 通信，把任务路由给招聘子 Agent。**Router 自己不处理业务，它只做分发和回收**。

4. **子 Agent 调用能力处理**。招聘 Agent 接到任务，开始干活：
   - 用 `office-to-md` 把这周收到的简历文件解析成文本，
   - 用手写的评分 Pipeline 按 JD 给每份简历打分（评分时合规过滤层强制不让敏感特征进入），
   - 份数多时还会用 `sessions_spawn` 批量并行处理。

5. **产出落盘物**。处理完，招聘 Agent 生成两样落盘物：
   - 一份排好序的候选人评分结果 JSON，
   - 每个候选人一篇 HTML 画像，
   - 写到磁盘。

6. **回报结果**。招聘 Agent 把"处理完成 + 落盘物路径"回报给 Router，Router 再回复 HR 主管："已筛完，候选人排序和画像在这里。"

**这一幕里有两条贯穿全程的隐线**：

- **其一，审计日志全程在记**——每一步是谁做的、何时、做了什么、结果如何，都落进日志，事后可追溯、可解释；Prometheus 同时记录这次任务消耗了多少 token。
- **其二，HiTL 审批随时可能介入**——如果这个任务不是"筛简历"而是"给张三发 Offer"，流程走到发放那一步会被 Lobster 拦下，halt 在审批点，等 HR 主管批准后才继续。**AI 把流程跑顺，人在关键处拍板**。

> 这套"统一入口 Router + 业务子 Agent 分工 + 工业级公共底座"的结构，**不只是属于 HR**。
>
> 换一个业务——AI 客服、AI 财务助理——子 Agent 的领域会变，但三层结构不变、六要素这套填法不变、任务流转的路径不变。
>
> **所以这份架构方案对你的价值，不只是"小慧长这样"，而是一个可以照着填的参照模板**。
>
> 第 5 章，我们就把这份架构方案，转化成一份可执行的开发计划。

## §5 开发计划：阶段化与检查点

### 5.1 从架构方案到开发计划

架构方案回答的是"系统由什么组成"——6 个子 Agent、调度模式、工作流、hooks、人设、落盘物，六个要素一张图说清。

但拿着这张图还不能直接开工：它没有告诉你**先做哪一块、后做哪一块**，也没有告诉你**每一块做到什么程度算完成**。把架构方案变成可执行的建造过程，靠的是开发计划。

#### 5.1.1 两份文档的分工

这是两份独立的文档，各自回答一个不同的问题。

| 维度 | 架构方案 | 开发计划 |
|---|---|---|
| **回答的问题** | 系统由什么组成 | 按什么顺序造、怎么验收 |
| **描述的对象** | 系统的静态结构 | 系统的建造过程 |
| **核心内容** | 6 子 Agent、调度、工作流、hooks、人设、落盘物 | 阶段划分、阶段依赖、检查点、验收标准 |
| **盖楼类比** | 建筑设计图 | 施工组织计划 |
| **产出阶段** | §4 已完成 | §5 本章产出 |

**架构方案**描述的是系统的**静态结构**——它由哪些部件组成、部件之间什么关系。它回答的问题是**"做什么"**。

**开发计划**描述的是系统的**建造过程**——按什么顺序把这些部件造出来、每一步怎么确认做对了。它回答的问题是**"按什么顺序做、怎么验收"**。

> **可以盖楼来理解两者的分工**：架构方案像一张建筑设计图：画清楚楼有几层、每层什么功能、承重墙在哪、水电管线怎么走。
> 开发计划像一份施工组织计划：先挖地基、再浇筑框架、然后砌墙、最后装修，每一道工序完成都要验收合格才进下一道。
>
> 两份文档缺一不可——**只有设计图没有施工计划，工人到了工地不知道从哪下手；只有施工计划没有设计图，按部就班盖出来的不是想要的那栋楼**。

#### 5.1.2 为什么不能跳过开发计划直接动手

AI HR 数字员工"小慧"不是一个几十行的小脚本。它是 6 个子 Agent，加上调度模式、Lobster 工作流、hooks、权限分级、可观测——**拆开来是几十个技术点**。

对着架构图直接开工，会撞上三个具体问题：

1. **第一，开发会失去顺序**。几十个技术点之间没有"先做谁"的指引，开发者很容易东一榔头西一棒槌：今天觉得简历评分有意思就去配评分 Skill，明天想起来还没装监控就回头搭 Prometheus。每一块单独看都在推进，合起来却拼不成一个系统。

2. **第二，会踩空依赖**。技术点之间存在硬依赖关系。招聘子 Agent 要真正跑起来，前提是 Gateway 在运行、LLM Provider 已经配好、招聘 Agent 自己的 workspace 和 agentDir 已经建好。**如果顺序反了——先开发招聘子 Agent 再回头搭环境——招聘子 Agent 根本没法验证，因为它依赖的东西还不存在**。开发顺序必须尊重技术依赖，这不是可选项。

3. **第三，进度变得不可判断**。开发到一半，有人问"还差多少、哪些做完了、哪些没做"，如果答不上来，说明开发处在一种模糊状态里。没有阶段、没有检查点，进度就只能凭感觉估计，而凭感觉估计的进度往往严重失真。

#### 5.1.3 开发计划的核心：阶段划分与检查点，不是排期表

关于开发计划，最常见的误解是把它等同于一张"哪天做完什么"的排期表（甘特图）。排期表有它的用处，但它**不是开发计划的核心**，而且排期恰恰是最容易变的那部分——

> 人手调整、优先级变化、突发问题，任何一个都会让日期失准。**把开发计划做成一张排期表，计划很快就会和现实脱节。**

真正不变、真正构成骨架的是另外两样东西：

**1. 阶段之间的依赖顺序**。地基永远排在业务单元前面，业务单元永远排在集成前面。这个顺序由技术依赖决定，不由日历决定——无论项目排期怎么调整，"先搭环境再开发 Agent"这个顺序都不会变。

**2. 每个阶段"做完的标志"**。一个阶段到底完成没有，要有**一条可判定的标准**，不能凭感觉说"差不多了"。这条标准就是**验收标准**，它让"做完"变成一件可以客观确认的事。

> **所以开发计划的核心可以归结成一句话**：把整个开发工作切成若干个有依赖关系的阶段，再给每个阶段配上可判定的检查点。
>
> **日期是附属信息，阶段和检查点才是骨架。**

### 5.2 阶段划分、检查点与验收标准

开发计划的核心是阶段划分加检查点。本节把它落到 AI HR 数字员工这个具体项目上——这套系统的开发计划怎么切阶段、检查点长什么样、为什么这样做。

> 本节内容基于本项目的完整实施计划，那是一份已经按此执行的真实开发计划，不是纸面推演。

#### 5.2.1 怎么切阶段：按"地基 → 单元 → 集成 → 验收"的依赖链

切阶段的依据不是工作量平均，而是**技术依赖**。一个阶段要么不依赖别的阶段、要么只依赖已经完成的阶段——顺着这条线，整个开发自然分成四类阶段。

| 阶段类型 | 含义 | 本项目对应的阶段 |
|---|---|---|
| **地基类** | 系统跑起来的前提条件 | 阶段 A 搭基础环境（独立 profile、Gateway、可观测、Lobster、多 Agent 骨架、权限）<br>阶段 B 准备真实数据资产（简历库、JD 库、HR 政策 Wiki、月报历史数据） |
| **单元类** | 一个一个独立的业务功能模块 | 阶段 C 招聘、阶段 D 入职、阶段 E 培训、阶段 F 绩效与行政 |
| **集成类** | 把分散的单元拼成一个整体 | 阶段 G 开发总控 Router，用 Multi-Agent Routing 把 4 个业务子 Agent 加上行政模块编排成统一的"小慧"，再叠加三档权限 |
| **验收类** | 在接近真实的条件下检验整个系统 | 阶段 H 跑 8 个端到端 HR 业务场景，从"上午集中筛简历"到"三种角色同时找小慧"，验证系统真实可用 |

**依赖关系说明**：

- **地基阶段**（A、B）不依赖任何业务功能，但所有业务功能都依赖它们。
- **业务单元阶段**（C、D、E、F）之间没有依赖——招聘子 Agent 的开发不需要等入职子 Agent。所以这 4 个阶段**可以并行开发**。
- **集成阶段**（G）必须等单元阶段基本完成才能开始——没有子 Agent，无所谓编排。
- **验收阶段**（H）排在最后，它依赖前面所有阶段。

**这四类阶段串起来就是开发的主干**：
> **地基（A、B）→ 业务单元（C、D、E、F 并行）→ 集成（G）→ 验收（H）**

每一类只依赖它前面的那一类，依赖关系是单向的，**不存在环**。

#### 5.2.2 检查点：让"做完"变成可判定的事

每个阶段都要有一个检查点，回答一个问题：**这个阶段到底完成了没有**。

**检查点不是一句"差不多了"，而是一组可以逐条客观判定的条件**。每个条件都能用一条命令、一个输出、一个事实来确认真假，不依赖任何人的主观判断。**一个阶段的所有检查点条件全部为真，这个阶段才算完成；只要有一条为假，就是没完成——没有"基本完成"这种中间状态。**

以**阶段 A（基础环境）的验收检查点**为例，它具体长这样：

1. `openclaw doctor` 跑完没有 Errors（实测结果是 `Plugins Errors: 0`）；
2. Gateway 的 `/health` 端点返回 `{"ok":true,"status":"live"}`，HTTP 状态码 200；
3. `openclaw agents list` 里能看到 6 个 HR 子 Agent（recruitment、onboarding、training、performance、er-admin、router）全部就位；
4. Lobster 跑通一个含审批检查点的最小工作流，并能用 resumeToken 恢复；
5. 三档权限的解析验证通过，不同身份算出的有效工具集确实不同；
6. 所有配置文件落盘到独立 profile 目录 `~/.openclaw-hr/`。

**这组条件的共同特点**：**每一条都能直接验真伪**。

- "doctor 有没有 Errors"是看输出里那个数字是不是 0，不是问感觉；
- "6 个子 Agent 在不在"是看 agents list 的列表，数得出来。

**检查点把"阶段完成"从一个模糊判断，变成了一道可以照着核对的清单——这正是检查点存在的意义**。

> §6 的环境搭建实操，做的就是逐条满足阶段 A 的这些检查点。

#### 5.2.3 为什么不一口气做完再测：阶段化与一次性交付的对比

既然最后还有一个验收阶段 H，为什么不干脆把 A 到 G 全部做完，到 H 一次性测完？这种"一口气做完再测"的方式（工程上叫**一次性集成**）听起来省事，实际风险很大。

**一次性集成的问题在于缺陷被推迟暴露**：
- 如果阶段 A 的环境有一个配置错误，而你直到阶段 H 才测，那么 C、D、E、F、G 五个阶段全部是在一个有问题的地基上开发的。
- 这个错误暴露时，已经有大量代码建立在它之上，回头修的代价远大于在阶段 A 当场修。
- **缺陷发现得越晚，修复成本越高——这是软件工程里被反复验证的规律**。

**阶段化开发的做法相反**：每个阶段结束就用检查点验一次，缺陷在产生它的那个阶段就被拦下，不让它流到下游。代价是每个阶段多花一点验收时间，但换来的是问题不累积。

**与阶段化常被混淆的还有另外两种做法**：

| 做法 | 问题 |
|---|---|
| **纯排期表驱动** | 计划只有日期没有检查点，"5 月 20 日完成阶段 C"，但"完成"没有可判定标准，到了日期就宣布完成，缺陷照样流到下游 |
| **完全不设阶段** | 边做边改——灵活，但项目一旦变大，没有阶段就没有进度坐标，也没有验收节点 |

> **阶段化不排斥灵活，它只是要求**：无论怎么调整，**阶段的依赖顺序和每个阶段的检查点要保住**。

**对比一张表**：

| 对比维度 | 阶段化 + 检查点 | 一次性集成 | 纯排期表 |
|---|---|---|---|
| 缺陷暴露时机 | 产生它的阶段当场 | 拖到最终验收 | 拖到下游 |
| "完成"的判定 | 检查点逐条核对 | 无中间判定 | 按日期，无标准 |
| 修复成本 | 低（就地修） | 高（已被依赖） | 高（已流到下游） |
| 适用场景 | 多模块、有依赖的系统 | 极小的一次性脚本 | 不推荐单独使用 |

#### 5.2.4 这套阶段划分的局限（要诚实承认）

阶段划分是开发的骨架，但它**不是一经定下就不许动的铁律**。诚实地说，它有几处局限，开发中需要正视。

1. **阶段划分本身会被修订**。本课用的这份实施计划是 v2 版本——它是在 v1 基础上吸收了五处反馈后改出来的。这说明阶段划分不是一次定稿，开发过程中发现某个阶段切得太大、或两个阶段其实该合并，就要回头调整。**计划服务于开发，不是开发迁就计划。**

2. **并行阶段的检查点需要额外协调**。C、D、E、F 四个业务单元阶段并行开发，但集成阶段 G 依赖它们全部达到各自的检查点。这意味着 **G 的启动时间由四个并行阶段里最慢的那个决定——有明显的木桶效应**。计划并行能省总时长（这套计划并行后总耗时约 15 天，比串行减半），但并行阶段的进度必须统一盯，否则一个阶段拖后腿，集成就卡住。

3. **检查点的松紧需要把握**。检查点定得太松，会放过本该拦下的缺陷；定得太严，会在不影响下游的小问题上卡住进度。**阶段 A 的检查点里，"doctor 无 Errors"是硬条件**（Errors 会真的让系统出问题），而"doctor 报了若干 Warnings"则被判定为可接受——比如它会警告检测到两个 state 目录，但那恰恰是 profile 隔离的预期现象。**哪些条件是硬的、哪些可放行，需要结合实际判断，不是越严越好。**

### 5.3 AI HR 数字员工开发计划表

把前两节的方法落成一张可以直接查的表。

下面这张开发计划表，就是 AI HR 数字员工"小慧"从零到验收的完整骨架——**8 个阶段**，每个阶段标明它属于哪一类、做什么、产出什么、用什么标准验收。

> 这张表是本期方法论的最终产出物之一：做其他 Agent 系统（AI 客服、AI 财务助理等）时，套用同一套"地基 → 单元 → 集成 → 验收"的分类和检查点思路，就能产出对应的开发计划表。

#### 5.3.1 8 阶段开发计划表

| 阶段 | 类型 | 主要内容 | 关键产出 | 验收标准 | 预估工期 |
|---|---|---|---|---|---|
| **A 基础环境** | 地基 | 独立 profile、Gateway、可观测、Lobster、多 Agent 骨架、三档权限、LLM Provider | 一套隔离的、工业级的 OpenClaw 开发环境 | doctor 无 Errors；Gateway `/health` 返回 live；6 子 Agent 就位；Lobster 跑通含 resume；三档权限验证通过；配置落盘 `~/.openclaw-hr/` | **1-2 天** |

| **C 招聘子 Agent** | 业务单元 | 简历批量解析评分、候选人画像、人才库语义检索、面试纪要 | 招聘子 Agent | 跑通 20+ 份真实简历，产出排序结果与 HTML 画像 | **5-7 天** |

> **阶段 C、D、E、F 是四个互不依赖的业务单元，并行开发**。并行后整体工期约 15 天，相比串行接近减半。

#### 5.3.2 里程碑：4 个进度核对节点

8 个阶段之上还有 **4 个里程碑**。里程碑是比阶段更粗的进度坐标——它把若干个阶段的完成捆成一个有业务意义的节点，用来回答"项目整体走到哪了"。

| 里程碑 | 完成标志 | 此时系统能证明什么 |
|---|---|---|
| **M1 地基就绪** | 阶段 A + B 完成 | 隔离环境、Lobster 引擎、真实数据资产全部备好 |
| **M2 单 Agent 可用** | 阶段 C 完成 | 招聘子 Agent 能跑真实简历，产出超越人工的 HTML 画像 |
| **M3 数字员工成型** | 阶段 C、D、E、F + G 完成 | "小慧"5 个子 Agent 加总控 Router 编排完整 |
| **M4 工业级验收** | 阶段 H 完成 | 8 个真实 HR 场景端到端跑通，有录制素材 |

#### 5.3.3 这张表怎么用

- **判断进度**：任何时刻，对照"已完成阶段"和检查点，能精确说出项目走到哪个里程碑、距下一个里程碑还差哪几个阶段。

## §6 环境搭建实操（阶段 A）

### 6.1 环境搭建总览：要搭什么、为什么

方法论四步——能力盘点、业务分析、系统架构、开发计划——到这里已经走完。开发计划的第一个阶段是**阶段 A 基础环境**。

从本节起进入动手环节，先把这个环境的整体面貌看清楚：它由哪些部件组成、为什么必须在开发任何业务功能之前先把它搭起来。

看清全景之后，§6 后面三节再逐步动手。

#### 6.1.1 开发环境的 10 个组成

AI HR 数字员工的开发环境不是"装好 OpenClaw"这一件事，而是 **10 个组成部件**。按职责分成三组：

**第一组，地基与底座（组成 1-5）**——这是环境跑起来的最底层。

| # | 组成 | 含义 |
|---|---|---|
| 1 | **环境检查** | 确认实操机的 OS 版本、Node 运行时版本、是否已有 OpenClaw、端口是否空闲。动手前先摸清现状 |
| 2 | **独立 profile** | 为本课创建一个隔离的工作目录 `~/.openclaw-hr/`，与机器上原有的 OpenClaw 完全分开 |
| 3 | **OpenClaw 安装** | 把 OpenClaw v2026.5.12 stable 装进这个独立 profile，不碰用户原有版本 |
| 4 | **Gateway** | OpenClaw 的服务进程。本课的 HR profile 用独立端口 18790，配 auth token 保护 |
| 5 | **可观测** | 给数字员工装上"仪表盘"：Prometheus 暴露指标端点、OpenTelemetry 推送链路数据 |

**第二组，编排能力（组成 6-7）**——这是让数字员工从"单个助手"变成"分工系统"的能力。

| # | 组成 | 含义 |
|---|---|---|
| 6 | **Lobster 工作流引擎** | 可恢复的审批工作流。AI 跑流程、流程在审批点暂停等真人批准、批准后从断点恢复 |
| 7 | **多 Agent 骨架** | 把"小慧"拆成 6 个常驻子 Agent（招聘、入职、培训、绩效、行政、总控 Router），每个独立隔离，用 Multi-Agent Routing 分发请求 |

**第三组，安全与接入（组成 8-10）**——这是工业级落地必须有的部分。

| # | 组成 | 含义 |
|---|---|---|
| 8 | **权限分级** | 按身份给不同的人配不同的工具权限。HR 主管能用全套工具，普通员工只能查政策 |
| 9 | **hooks** | 事件触发底座。某个生命周期事件发生时自动做事，让数字员工脱离"人不发指令就不动"的被动状态 |
| 10 | **LLM Provider** | 配置数字员工实际使用的大模型。本课用国内可用的 DeepSeek 等模型 |

> 这 10 个组成对应开发计划里阶段 A 的 10 个子步骤（A.1 到 A.10）。
> §6 后面三节按这个顺序动手：6.2 搭组成 1-5，6.3 搭组成 6-7，6.4 搭组成 8-10。

#### 6.1.2 为什么开发前要先搭这套地基

开发计划那一节讲过一条规则：**地基阶段排在业务单元阶段前面，因为所有业务功能都依赖地基**。这套环境就是地基本身。

把它具体化：
- **招聘子 Agent 要跑起来**，得先有 **Gateway 在运行**（没有服务进程，Agent 无处挂载）、得先配好 **LLM Provider**（没有模型，Agent 收到消息也无法思考）、得先有**自己独立**的 workspace 和 agentDir（没有隔离的工作目录，多个 Agent 会互相污染）。
- 这些前提哪一个缺失，招聘子 Agent 都没法验证。
- **环境不是"可以晚点补"的配套，它是业务开发能不能开始的硬门槛**。

这也是为什么阶段 A 要有一组严格的验收检查点——只有这套地基逐条通过检查，后续阶段才有立足之地。

> **先搭环境、再开发业务，不是流程上的讲究，是技术依赖决定的硬顺序**。

#### 6.1.3 为什么要用独立 profile 隔离（最容易被忽略，但最重要）

这一步最容易被忽略，但它是整套环境的**安全前提**。

学员的机器上多半已经有一个在用的 OpenClaw——可能是日常工作配好的，有自己的配置、Agent、会话历史。

**本课要**：
- 装一个新版本（v2026.5.12）
- 改大量配置
- 新建 6 个子 Agent
- 启用一堆插件和 hooks

> **如果这些操作都写进同一个 OpenClaw profile**，结果就是 HR 课的折腾会**改坏用户原本在用的环境**——版本被覆盖、配置被冲掉、Agent 列表被搅乱。

**独立 profile 就是为了隔离这个风险**：

做法是给本课单独开一个工作目录 `~/.openclaw-hr/`，所有配置、状态、Agent、会话都落在这个目录里，和用户原有的 `~/.openclaw/` 物理分开。

**切换到这个独立 profile 有两条路**：
1. 设置 `OPENCLAW_STATE_DIR` 和 `OPENCLAW_CONFIG_PATH` 两个环境变量。
2. 用 OpenClaw 自带的 `--profile` 选项。

两种方式效果等价，§6.2 会实际演示。

> **记住这条原则**：在一台已经装了 OpenClaw 的机器上做新项目，**第一件事就是开独立 profile**。
>
> **不隔离 = 拿用户正在用的环境做实验，这是工业级开发不能接受的**。

### 6.2 实操：独立 profile、Gateway 与可观测

从这一节开始动手。本节对应开发环境 10 个组成里的前 5 个——环境检查、独立 profile、OpenClaw 安装、Gateway、可观测——也就是**阶段 A 的子步骤 A.1 到 A.5**。

每一步都给出真实命令、真实截图和验证方法，路上遇到的坑也照实写出来。

> 实操机是一台 **Mac mini M4**(macOS 26.4.1,Node v24.14.0,npm 11.9.0)。开始前先约定一件事：本节所有命令都在本课的独立 profile 环境里执行,不碰机器上原有的 OpenClaw。
>
> **机型选择的隐含意义**:Mac mini M4 是 Apple Silicon 架构,与 Intel x86 架构在底层二进制兼容性上存在差异。这一选择意味着:
> 1. **依赖安装路径不同**——`node_modules/.bin/` 下的二进制已是为 arm64 架构编译的版本,迁移到 x86 机器时需要重装。
> 2. **命令差异较小**——本课用到的所有命令(`openclaw config set` / `find` / `git clone` 等)都是跨平台标准命令,跨平台迁移成本很低。
> 3. **macOS 版本敏感性**——原 PDF 提示 26.5 上有 WebSocket 兼容问题,本机是 26.4.1,正处于安全区。

#### 第一步：检查实操机环境（A.1）

**动手前先摸清现状**——不靠假设，先把事实查清楚。要确认四件事：操作系统版本、Node 运行时版本、机器上是否已有 OpenClaw、端口是否空闲。

```bash
sw_vers                    # 查 macOS 版本
node --version             # 查 Node 版本
npm --version              # 查 npm 版本
which openclaw             # 原有 openclaw 二进制位置
openclaw --version         # 原有 openclaw 版本
```

**实测结果**：macOS 26.4.1、Node v24.14.0、npm 11.9.0。

**为什么先看 macOS 版本**：
- OpenClaw v2026.5.12 在 **macOS 26.5** 上有一个已知的 WebSocket 兼容问题(**编号 `#82037`**)——表现为 Gateway 启动后 /health 端点偶发超时、Channel 连接断流。
- 如果实操机是 macOS 26.5 及以上,需降级使用 **v2026.5.7** 来规避(注意 v2026.5.7 与本课锁定版本 v2026.5.12 stable 在配置 schema 上**不完全兼容**,需同步调整若干 patch 与 hook 命令)。
- **26.4 及以下则可以安全使用 v2026.5.12 stable**。
- 这台机器是 26.4.1,落在安全区,所以本课锁定 v2026.5.12 stable。
- Node 24.14.0 也满足 OpenClaw 要求的 **Node ≥ 22.16 或 24**。

> **小贴士:版本号判读**:OpenClaw 用的版本号格式是 `vYYYY.M.PATCH`。`v2026.5.12` 表示 2026 年第 5 个月发布的第 12 个 patch 版本(`stable` 后缀表明已通过发布流程),`v2026.5.7` 则是同月第 7 个 patch。在降级规避 bug 时,选**同月第几 patch** 是兼容性判断的常用做法——跨月降级往往带 schema 变化风险更大。

接着查机器上原有的 OpenClaw 和端口占用：

```
openclaw --version          # 2026.4.15
# 端口方面，OpenClaw 默认 gateway 端口 18789 和我们准备用的 18790 都空闲
```

**这台机器已经装了一个 OpenClaw 2026.4.15**，位于 `~/.npm-global/bin/openclaw`——这是用户日常在用的版本，**本课全程不碰它**。端口方面，OpenClaw 默认 gateway 端口 18789 和我们准备用的 18790 都空闲，本课的 HR Gateway 就占用 18790。

**这一步的验证**：拿到三组确定的事实——
- OpenClaw 版本锁 v2026.5.12
- Gateway 端口用 18790
- 原有环境是 2026.4.15 不可触碰

后面每一步都建立在这三个事实上。

#### 第二步：创建独立 profile（A.2）

6.1 讲过为什么要隔离。这一步把隔离落地——给本课单独建一个工作目录 `~/.openclaw-hr/`。

```bash
mkdir -p ~/.openclaw-hr/{config,state,workspace,agents,sessions,memory,hooks,plugins,install,logs}
```

这条命令一次性建出 profile 的目录骨架：

| 目录 | 用途 |
|---|---|
| `config` | 放配置文件 |
| `state` | 放运行状态 |
| `workspace` | 放 Agent 的工作文件 |
| `agents` | 放 Agent 状态 |
| `sessions` | 放会话存储 |
| `memory` | 放记忆数据 |
| `hooks` | 放 hooks 文件 |
| `plugins` | 放插件文件 |
| `install` | 放本地安装的 OpenClaw |
| `logs` | 放日志 |

**所有本课产生的东西都落在这个目录里，与用户原有的 `~/.openclaw/` 物理分开。**

光建目录还不够，还要让 OpenClaw 知道"用这个 profile"。做法是写一个环境变量文件 `~/.openclaw-hr/env.sh`（权限设为 600，因为里面会有 token）：

```bash
export OPENCLAW_STATE_DIR=$HOME/.openclaw-hr
export OPENCLAW_CONFIG_PATH=$HOME/.openclaw-hr/config/openclaw.yaml
export OPENCLAW_GATEWAY_TOKEN="<32字节随机串，用 openssl rand 生成>"
export OPENCLAW_HR_BIN=$HOME/.openclaw-hr/install/node_modules/.bin/openclaw
alias openclaw-hr="$OPENCLAW_HR_BIN"
```

**隔离的原理就在前两个变量**：
- `OPENCLAW_STATE_DIR` 把 OpenClaw 的状态根目录切到 `~/.openclaw-hr/`。
- `OPENCLAW_CONFIG_PATH` 指定独立的配置文件。
- 每次开新终端，先 `source ~/.openclaw-hr/env.sh`，这个终端就进入了 HR profile。

**一个值得知道的便利项**：实测发现 OpenClaw v2026.5.12 自带一个 `--profile <名字>` 选项，`openclaw --profile hr config file` 会直接把 state 和 config 隔离到 `~/.openclaw-hr/` 下，效果和上面手动设环境变量完全等价。

**两种方式都能用**：
- 环境变量方式更显式、便于在脚本里固化。
- `--profile` 方式更简洁。

> 本课后续命令以**环境变量方式**为准。

**这一步的验证**：profile 目录骨架就位 + env.sh 写好，`source` 后 `echo $OPENCLAW_STATE_DIR` 能打印出 `~/.openclaw-hr` 即说明 profile 切换生效。

#### 第三步：把 OpenClaw 装进独立 profile（A.3）

环境锁定的版本是 v2026.5.12。动手装之前，先确认这个版本号在 npm 上真实存在——又一次"零假设"。

```bash
npm view openclaw versions --json    # 确认 2026.5.12 真实存在且无 -beta 后缀

cd ~/.openclaw-hr/install
npm init -y
npm install openclaw@2026.5.12       # 实测约 added 447 packages
```

**为什么不用 `npm install -g`**：全局安装会覆盖用户机器上原有的 OpenClaw 2026.4.15。本地目录安装把 v2026.5.12 的二进制装在 `~/.openclaw-hr/install/node_modules/.bin/openclaw`，和全局的 `~/.npm-global/bin/openclaw` 是两个不同的文件，**互不影响**。

**这一步的验证**：截图对比了两个 profile——
- HR 课的是 2026.5.12（位于 `~/.openclaw-hr/install/...`）
- 用户原有的是 2026.4.15（位于 `~/.npm-global/bin/openclaw`）

版本号不同、二进制路径不同，证明本地安装没有污染用户全局环境。**隔离铁律在这一步真正落地**。

#### 第四步：配置并启动 Gateway（A.4）

Gateway 是 OpenClaw 的服务进程。配置它分三件事：**写配置项、跑体检、启动进程**。

先写 Gateway 的四个配置项。OpenClaw 不需要手写配置文件，用 `config set` 命令逐条写入：

```bash
openclaw config set gateway.port 18790 --strict-json
openclaw config set gateway.mode local
openclaw config set gateway.auth.token \
  --ref-provider default --ref-source env --ref-id OPENCLAW_GATEWAY_TOKEN
openclaw config set gateway.auth.mode token
chmod 700 ~/.openclaw-hr        # 先收紧 profile 目录权限
openclaw doctor --fix --non-interactive --no-workspace-suggestions
```

**第三条值得专门说一句**：`gateway.auth.token` 没有直接写明文 token，而是配成一个"环境变量引用"（SecretRef）——它告诉 OpenClaw"token 的值去环境变量 OPENCLAW_GATEWAY_TOKEN 里取"。**这样配置文件里不含明文密钥，真正的 token 值只待在权限 600 的 env.sh 里**。这是工业级配置的安全惯例。

**配置写完，跑一遍体检命令 `openclaw doctor --fix` 修复环境**：

> `doctor --fix` 会扫描环境并自动修复能修的问题：建好缺失的 session 存储目录、自动禁用缺第三方依赖的 skill、重建插件注册表。
> 截图里最关键的一行是 **`Plugins Errors: 0`**——插件加载零错误，这是阶段 A 检查点的硬条件。

**这一步有两个坑必须知道**：

- **坑一：`doctor` 默认是交互式的，而且跑得慢**。不加参数它会弹交互提示等你回答，所以要加 `--non-interactive --no-workspace-suggestions` 让它一气跑完。**即便如此，`doctor` 跑完仍要 90 秒以上**，看到它"卡着"不要中断，耐心等。

- **坑二：`doctor` 会报"检测到多个 state 目录"的警告**。它发现机器上同时有 `~/.openclaw`（用户原有）和 `~/.openclaw-hr`（本课的），提示"可能切分会话历史"。
  - **这条警告要忽略**——两个 state 目录正是我们刻意做的隔离，是预期现象，不是错误。
  - **区分"硬错误"和"可忽略警告"是看懂 doctor 输出的关键**。

体检通过，启动 Gateway：

```bash
nohup openclaw gateway run --port 18790 > ~/.openclaw-hr/logs/gateway.log 2>&1 &
echo $! > ~/.openclaw-hr/gateway.pid
```

**为什么用 `gateway run` 而不是 `gateway start`**：
- OpenClaw 有两种启动方式——
  - `gateway start` 会把 Gateway 注册成系统级开机服务（macOS 的 launchd），
  - `gateway run` 只是前台运行一个进程。
- 本课用 `gateway run` 配 `nohup` 后台化，**遵守"不修改系统级配置"的约束，不往用户系统里塞开机项**。

**这一步的验证**：启动日志出现 `[gateway] ready`，然后用 `curl` 打 `/health` 端点确认服务活着：

```bash
unset http_proxy https_proxy all_proxy HTTP_PROXY HTTPS_PROXY ALL_PROXY
curl -s --noproxy '*' http://127.0.0.1:18790/health
# 返回 {"ok":true,"status":"live"}
```

无 token 访问应被拒：

```bash
curl -s --noproxy '*' http://127.0.0.1:18790/api/diagnostics/prometheus
# 带 token 访问 —— 应返回指标
curl -s --noproxy '*' -H "Authorization: Bearer $OPENCLAW_GATEWAY_TOKEN" \
  http://127.0.0.1:18790/api/diagnostics/prometheus
```

> **坑三**：本机若配了 HTTP 代理，访问本地 Gateway 会被拦。这台实操机配了 `http_proxy`（给别的服务用的），`curl` 访问 `127.0.0.1:18790` 时请求被代理拦截，返回 HTTP 502。
> **如果你的机器也配了 HTTP 代理**，访问本地 Gateway 前要么 `unset` 掉所有 proxy 变量、要么给 curl 加 `--noproxy '*'`。没配代理的机器可以忽略这条。

> **坑四**：启动日志里的 `gateway.auth.token is inactive` 是已知告警。它表示 token 环境变量已配但 secrets surface 未激活。**本课是 loopback（只接受本机连接）+ 纯 CLI 模式，这条告警不影响使用，可忽略**；下集接入飞书 Channel 时才需要重新处理。

> 还要记住：`gateway run` 启的是前台进程，它会**随终端会话关闭或系统重启而消失**。每次接着做实验前，先确认 Gateway 还活着（`ps -p $(cat ~/.openclaw-hr/gateway.pid)`），没了就重新启动。

#### 第五步：启用可观测——Prometheus 与 OpenTelemetry（A.5）

HR 数字员工"小慧"上线后会 7×24 运转，每一次 LLM 调用都在烧 token、产生成本。没有可观测体系，就没人知道这个月小慧花了多少钱、哪个子 Agent 最耗 token。

> **A.5 就是给它装上"仪表盘地基"**。

可观测用两个 OpenClaw 原生诊断插件——`@openclaw/diagnostics-prometheus` 和 `@openclaw/diagnostics-otel`，用 `openclaw plugins install` 装进 HR profile。

装好并重启 Gateway 后，确认两个插件处于 `enabled` 状态，再验证 Prometheus 端点：

```bash
# /health 端点公开（无需 token）
curl -s --noproxy '*' http://127.0.0.1:18790/health
# → {"ok":true,"status":"live"}

# 无 token 访问 Prometheus —— 应被拒
curl -s --noproxy '*' http://127.0.0.1:18790/api/diagnostics/prometheus

# 带 token 访问 Prometheus —— 应返回指标
curl -s --noproxy '*' -H "Authorization: Bearer $OPENCLAW_GATEWAY_TOKEN" \
  http://127.0.0.1:18790/api/diagnostics/prometheus
```

**为什么故意测两种状态**：
- `/health` 端点是公开的（心跳检测用），
- 但 `/api/diagnostics/prometheus` 含 token 用量、成本这类**敏感数据**，必须受保护。
- 截图证明了这道权限边界——**无 token 访问返回 `Unauthorized`，带 token 访问才返回 Prometheus 文本格式的指标**。
- **一拒一放，证明端点既能工作、又受 auth 保护**。

> **一个要讲清的时序问题**：
>
> 此刻带 token 访问只返回了一条 exporter 自身的计数指标，synthesis 列的 4 个核心 LLM 指标（token 数、成本、请求耗时等）还看不到。
>
> **这不是 bug**——Prometheus 的 counter 类指标在第一次对应事件发生前**不会出现**。`openclaw_llm_tokens_total` 必须等真实发起过一次 LLM 调用、消耗过 token 才会被创建。
>
> **所以这 4 个核心指标的验证要留到 A.10 配好大模型、实际调用一次之后**。
>
> **装好监控不等于立刻有业务数据，指标是被业务行为"喂"出来的。**

接着配 OpenTelemetry（OTel）的 OTLP 推送参数。OTel 是业界统一的**可观测协议**，把指标、链路、日志推给任意兼容的后端。用 `config set` 逐条写入：

```bash
openclaw config set diagnostics.enabled true
openclaw config set diagnostics.otel.enabled true
openclaw config set diagnostics.otel.endpoint "http://127.0.0.1:4318"
openclaw config set diagnostics.otel.protocol "http/protobuf"
openclaw config set diagnostics.otel.serviceName "openclaw-hr"
openclaw config set diagnostics.otel.sampleRate 1.0 --strict-json
openclaw config set diagnostics.otel.flushIntervalMs 10000 --strict-json
openclaw config set diagnostics.otel.captureContent false --strict-json
openclaw gateway restart
```

**几个配置项的取值要解释清楚**：

- **endpoint 是 `http://127.0.0.1:4318`**——4318 是 OTLP/HTTP 的**标准端口**。本课没有部署真实的 OTel collector，这里配的是"指向哪推"的地址，下集接 Grafana 或 Jaeger 时换成真实地址即可。这是"**配置就绪、collector 待接入**"的状态。

- **`sampleRate` 设 1.0**——HR 场景请求量不大，**全采样能确保每次 LLM 调用都被追踪到**，不丢数据。高并发系统才会调低采样率省成本。

- **`captureContent` 设 false**——这关系到**隐私红线**。HR 数字员工处理的是简历、薪资、绩效，全是敏感个人信息，可观测数据绝不能带出消息原文。不导出原文是 OpenClaw 的默认行为，这一步本想把它显式固化进配置——但这个 key 本身藏着一个坑，见下面的坑五。

> 数值和布尔类型加 `--strict-json`——不加的话 `sampleRate`、`flushIntervalMs` 这类值会被当成字符串写入。
>
> **`--strict-json` 的工程原理**:OpenClaw 配置加载管线默认按字符串解析所有 config set 的值,**仅当显式传 `--strict-json` 时才尝试 JSON 反序列化**。这导致两个常见病:
> 1. **类型错位**——`sampleRate 1.0` 不加标记会被存为字符串 `"1.0"`,运行时按 `Float` 解析时直接报错;
> 2. **隐式安全风险**——把对象塞进字符串会导致整段 key 被吞掉。
>
> **凡是要写真值/对象/数组,务必加 `--strict-json`**。判断标准很简单:`allow`、`deny` 这类数组值是 JSON 数组,数字与布尔同理;纯字符串 key(如 mode "local")则不用加。

> **坑五**：`config set` 只做轻量校验，无效的配置 key 也能被它写进去。
>
> 上面第 8 条 `captureContent` 就是一个例子：`config set` 接受了它，截图里 `config get diagnostics` 也确实显示了这个字段。但实测后来发现，v2026.5.12 的配置 schema 并不收录 `captureContent` 这个 key——它是个"**未识别 key**"。
>
> 它能写进去而**不立即报错**，会潜伏到某个对配置校验严格的命令（比如 6.3 会用到的 `openclaw sessions`）才暴露出来。
>
> **届时用 `openclaw doctor --fix` 清理即可**。

> **这一条引出一个判断方法**：OpenClaw 插件真实支持的配置字段，要以**配置 schema 和实测**为准，`config set` 写得进去**不代表这个 key 合法**。

**这一步的验证**：`config get diagnostics` 能读出写入的 OTel 字段（endpoint、protocol、serviceName、sampleRate、flushIntervalMs 等），说明可观测配置已落盘。配合前面 Prometheus 端点的一拒一放，**A.5 的可观测地基就绪**。

> **至此 A.1 到 A.5 全部完成**。回看这一节做了什么：摸清环境、隔离 profile、装好 OpenClaw、跑通 Gateway、装上可观测——**开发环境最底层的 5 个组成已经就位**。

### 6.3 实操：Lobster 工作流与多 Agent 骨架

本节对应开发环境的第 6、7 个组成——**Lobster 工作流引擎和多 Agent 骨架**，也就是阶段 A 的 **A.6 和 A.7**。这两项让 OpenClaw 具备两项关键能力：
- 在审批点暂停的工作流
- 把"小慧"拆成分工子 Agent 的骨架

> **本节事实出处**：本节关于 Lobster 的事实，来自阶段 A 的 Lobster 工作流实验记录（`exp-stage-a-lobster.md`）——其中真实跑通了 `hr-offer-approval.lobster` 的暂停、批准、拒绝三条路径。终端截图即该实验的真实运行结果。

#### 6.3.1 Lobster 工作流引擎（A.6）

入职、Offer 审批是 HR 数字员工最典型的"高风险决策点"。AI 可以自动整理材料、起草 Offer，但"是否真的发 Offer"必须由人类点头。这要求工作流引擎能做到三件事：
- 把流程编排成 pipeline
- 执行到审批点能暂停
- 暂停后能凭令牌恢复

**Lobster 就是 OpenClaw 内置的这套引擎**。A.6 跑一个最小工作流，验证这条链路。

#### 步骤一：确认 Lobster 插件与调用入口

动手前先搞清楚 Lobster 怎么调用——**不靠猜测，先确认**。

```bash
plugins list | grep -i lobster        # 确认 lobster 插件 enabled
node ~/.openclaw-hr/npm/node_modules/@clawdbot/lobster/bin/lobster.js --help
```

**关于路径**：`@clawdbot/lobster` 的 `bin/lobster.js` 具体在哪，取决于这个底层包在你 profile 里的安装位置。找不到时用 `find ~/.openclaw-hr -name lobster.js -path '*@clawdbot*'` 定位即可。下文命令里的路径以本次实操机的实际位置为准。

**这里要分清两层**：
- `lobster` 在 OpenClaw 里注册成一个 **agent tool**——它不是 openclaw 的 CLI 子命令，直接敲 `openclaw lobster` 不存在。
- OpenClaw 的 `@openclaw/lobster` 插件底层依赖一个独立包 `@clawdbot/lobster`，这个包自带 `bin/lobster.js` 命令行入口，可以直接在终端跑工作流。

**为什么本课用底层 CLI 而不是 agent tool**：
- 让 agent 去调用 lobster 工具，需要 agent 能"思考"，也就是需要 **LLM Provider**——而那要到 A.10 才配。
- `@clawdbot/lobster` 的 CLI 是**确定性执行**的（同样输入必得同样输出，不依赖 LLM），不配模型就能完整跑通"运行 → 暂停 → 恢复"链路。
- 它跑出的结果结构和 agent 调用工具时拿到的是同一套，**所以 CLI 验证的结论对 agent 路径同样成立**。

**验证**：截图确认 Lobster 插件 `enabled`、版本 2026.5.12，底层 `@clawdbot/lobster` CLI 可用，`--help` 列出了 `run` 和 `resume` 两个核心命令。

#### 步骤二：构造最小工作流并验证执行计划

构造一个最小工作流：一步操作产出数据，加一个审批门。它的结构正是 HR 审批场景的最小骨架。

```bash
LOBSTER=~/.openclaw-hr/npm/node_modules/@clawdbot/lobster/bin/lobster.js
node "$LOBSTER" run --dry-run --mode tool \
  "exec --json \"echo 入职申请-张三-后端工程师-期望薪资28K\" | approve --prompt HR主管是否批准这份Offer进入下一步发放流程\""
```

这条 pipeline 用 `|` 连两段：
- `exec` 是第一步操作（模拟"AI 起草好一份 Offer 申请"），
- `approve` 是审批门（执行到这里会拦住、等人决定）。
- `--dry-run` 只校验和打印执行计划、不真正执行。

**为什么先 dry-run**：
- 审批门一旦真跑会产生一个有状态的待审批流程，
- dry-run 能在不产生副作用的前提下先确认写法无误。

**为什么用 `--mode tool`**：
- tool 模式输出一个机器可解析的 JSON 结构，稳定、好记录。

**验证**：截图里 Lobster 把 pipeline 正确解析成 `exec + approve` 两个 stage，`approve` 被识别为审批门。计划无误。

#### 步骤三：真跑工作流——从 inline pipeline 到 .lobster 文件

去掉 `--dry-run` 真跑时，这里撞上了一个真实的坑。

**坑一：inline pipeline 对带空格、带中文的命令极其脆弱**。

> 上一条 pipeline 真跑时连续报错：`exec` 要么抱怨"没拿到命令"，要么把命令和参数按空格拆错。
> 原因是 pipeline 字符串经过 shell、lobster CLI、pipeline 解析器**三层处理**，参数里再带空格和中文，引号配对几乎必错。
>
> **`--dry-run` 能过不代表真跑能过**——dry-run 只校验解析，不真正执行 `exec`。

正确做法是改用 workflow 文件——这也更贴近真实场景：HR 审批流程本就该写成可复用、可版本管理的文件。在 profile 的 workspace 里写一个 `hr-offer-approval.lobster`：

```yaml
name: hr-offer-approval
steps:
  - id: draft
    run: echo '{"candidate":"张三","role":"后端工程师","salary":"28K"}'
  - id: gate
    approval: HR 主管，是否批准这份 Offer 进入下一步发放流程？
    stdin: $draft.stdout
  - id: issue
    run: echo 'Offer 已批准，进入正式发放流程'
    when: $gate.approved
```

三个 step：
- `draft`（AI 起草 Offer，产出 JSON）
- `gate`（审批门，接上一步输出）
- `issue`（批准后才执行的发放动作，靠 `when: $gate.approved` 条件控制）

然后真跑：

```bash
node "$LOBSTER" run --mode tool --file ~/.openclaw-hr/workspace/hr-offer-approval.lobster
```

**验证——这是 A.6 的核心**。

截图里 `status` 不是 `ok` 而是 `needs_approval`：流程在 `gate` 步骤停住了，`issue` 步骤没有执行。**AI 不会在没人点头时擅自发 Offer。**

返回的 `requiresApproval` 里带着四样东西：
- 审批问题
- 待审数据（张三的 Offer 详情）
- 人类可读的预览
- 以及一个 `resumeToken`。

**这个 resumeToken 是理解"可恢复"的关键**。

> 把它做 base64 解码，里面是一个含 `stateKey` 的 JSON——`stateKey` 指向一条**被持久化保存下来的流程状态记录**。
>
> **所以 resumeToken 不是简单的"yes/no 凭证"，而是"取回整个暂停现场的钥匙"**。
>
> 这意味着审批可以隔很久再处理：HR 主管下班了、明天再来批，**流程状态不丢，恢复时从断点继续而不是从头重跑**。

#### 步骤四：用 resumeToken 恢复——批准与拒绝两条路径

拿上一步返回的 `resumeToken`，用 `resume` 命令恢复流程。批准用 `--approve yes`：

```bash
node "$LOBSTER" run --mode tool --file ~/.openclaw-hr/workspace/hr-offer-approval.lobster > /tmp/lob-run.json
TOKEN=$(python3 -c "import json;print(json.load(open('/tmp/lob-run.json'))['requiresApproval']['resumeToken'])")
node "$LOBSTER" resume --mode tool --token "$TOKEN" --approve yes
node "$LOBSTER" resume --mode tool --token "$TOKEN" --approve no
```

> **小提示**：`resume` 必须带 `--token`，且要用当次运行返回的**最新 token**——每次跑工作流会生成新的 `stateKey`，旧 token 对应的状态可能已被消费。提取 token 时直接用 Python 读文件最稳，别为了绕引号去拼花哨的脚本。

**批准后**：
- `status` 回到 `ok`，
- `output` 里出现 `Offer 已批准，进入正式发放流程`——这正是 `issue` 步骤的输出。
- **审批前它一直没执行，批准后才跑。**

**拒绝后**：
- `status` 变成 `cancelled`，
- `output` 是空数组——`issue` 步骤完全没有执行。
- **HR 主管不批，Offer 就发不出去。**

**验证**：批准和拒绝是同一个 `resume` 命令的两种参数，分别得到：
- `status: ok`（流程走完）
- `status: cancelled`（流程终止）

两条路径合起来，**证明了一个完整的可恢复审批闭环**：流程能在审批点暂停、人类决策后能凭 token 恢复或终止。

> 这就是 **HR 审批"人在回路"的技术底座**。

#### 6.3.2 多 Agent 骨架（A.7）

一个 HR 数字员工要同时干招聘、入职、培训、绩效、行政五摊业务。如果都塞进一个 Agent，会出现：
- 上下文互相污染
- 权限无法分级
- 无法独立演进

三个问题。

**OpenClaw 的解法是多 Agent**——一个 Gateway 下挂多个 Agent，每个有独立的 workspace 和 agentDir，请求由 Multi-Agent Routing 分发。

**A.7 搭的是骨架占位**：6 个 Agent 的定义、隔离、路由通路，**它们的实际业务能力留到 Lesson 2 再填**。

#### 步骤五：借鉴参考项目 openclaw-agents

`openclaw-agents` 是一个"一键 setup 多 Agent"的开源套件，它把 9 个分工的 AI 研究 Agent 配成一个协作团队。

- 本课不直接用它的 9 个 Agent（那是论文写作场景），
- 而是借鉴它组织多 Agent 的方式：
  - 一份 `agents.yaml` 清单登记所有 Agent、
  - 每个 Agent 一个独立 workspace 加一份身份文件、
  - 支持无 channel 的纯 CLI 协作模式。

**裁剪一点**：参考项目的安装脚本没有给每个 Agent 显式指定 `agentDir`，靠自动生成。**本课的铁律是"绝不复用 agentDir"**，所以每个 Agent 都显式指定——比参考脚本更严格。

**验证**：`clone` 成功，仓库里能看到 `agents.yaml` 清单、`setup.sh` 安装脚本和 `.agents/` 目录。**借鉴的是"怎么组织"，不是"组织成什么"**。

#### 步骤六：写 HR Agent 清单与隔离骨架

借鉴 manifest 驱动的思路，先写一份 HR 专属的 Agent 清单 `hr-agents.yaml`，再给 6 个子 Agent 各准备一套隔离目录：

```bash
cd ~/.openclaw-hr/workspace
git clone https://github.com/shenhao-stu/openclaw-agents
for a in recruitment onboarding training performance er-admin router; do
  mkdir -p ~/.openclaw-hr/workspace-$a ~/.openclaw-hr/agent-dirs/$a
done
```

清单里每个 Agent 登记 id、显示名、领域、职责、workspace、agentDir 等字段。**6 个子 Agent 对应 HR 的 6 个领域**：

| Agent ID | 领域 |
|---|---|
| `recruitment` | 招聘 |
| `onboarding` | 入职 |
| `training` | 培训 |
| `performance` | 绩效 |
| `er-admin` | 行政 |
| `router` | 总控 |

> **注意每个 Agent 的 workspace 和 agentDir 路径各不相同**。

**为什么每个 Agent 要独立 workspace 和 agentDir**：

> workspace 是 Agent 的工作目录，agentDir 存的是它的**会话历史、记忆、身份**。
> 两个 Agent 共用一个 agentDir，**会话记忆就会互相污染**。
> 所以 **"绝不复用 agentDir"是骨架阶段就要钉死的铁律**。

每个 Agent 还各写一份 `SOUL.md`——它的"人设档案"，写清这个 Agent 是谁、负责哪个 HR 领域、边界在哪。比如招聘 Agent 的 SOUL.md 明确写"只做评分排序，最终淘汰由人工决定"——**这是个保法的合规红线，从骨架阶段就钉进人设**。

**一个要记住的顺序**：

> 实测发现 `openclaw agents add` 会给 Agent 的 workspace 自动生成一套**脚手架文件**，包括 `SOUL.md`。
>
> 它的生成是"**幂等、只补缺失**"——workspace 里已经有 SOUL.md 就保留不覆盖，空 workspace 才写默认英文模板。
>
> 所以正确顺序是：**先写好 HR 人设的 SOUL.md，再 agents add**。
>
> 反过来会先吃到默认模板，得再覆盖一次。

**验证**：截图里一个 `for` 循环逐个检查 6 个 Agent 的三类资源——workspace、agentDir、SOUL.md，**6 行全部 OK**，隔离骨架就位。

#### 步骤七：用 agents add 注册 6 个子 Agent

把 6 个子 Agent 逐个注册进 OpenClaw，每个显式指定独立的 workspace 和 agentDir：

```bash
openclaw agents add recruitment \
  --non-interactive \
  --workspace ~/.openclaw-hr/workspace-recruitment \
  --agent-dir ~/.openclaw-hr/agent-dirs/recruitment

# onboarding / training / performance / er-admin / router 同样命令逐个执行
```

**为什么必须加 `--non-interactive`**：

- `agents add` 默认是交互式的，会逐项弹提示问 workspace、model 等。
- 脚本化或演示必须加这个参数；
- 而它一旦加上，就强制要求同时给 `--workspace`（少了它非交互模式直接报错）。

**为什么显式 `--agent-dir`**：

- 落实"绝不复用 agentDir"铁律，路径自己定、可控可审计。

**验证**：`config get agents.list` 读出配置里的 Agent 列表，6 个 HR 子 Agent 每个的 `workspace` 列和 `agentDir` 列都不一样，**两两不撞，隔离落实**。

> **坑二：`openclaw agents delete <id> --force` 会连 workspace 整个目录一起删掉**。
>
> 实验中为了演示一次干净的注册，先 `delete --force` 删掉再重建，结果发现它把 `workspace-router/` 整个目录连同手写的 HR SOUL.md 一起删了——`delete` 说明里的 "prune workspace/state" 是真的。
>
> **workspace 里有手写文件时，删之前务必先备份**。
> 这一条到 Lesson 2 各 Agent 装满业务代码后尤其重要。

#### 步骤八：验证 agents list 显示 6 个子 Agent

```bash
openclaw agents list
```

**验证**：列表里一共 **7 个 Agent**——
- `main` 是 OpenClaw 原有的默认 Agent（本课不用它跑 HR 业务），
- 下面 6 个是新建的 HR 子 Agent。
- 每个子 Agent 显示独立的 **Workspace** 和 **Agent dir**，
- **`Routing rules: 0`** 说明还没配路由——这是预期的，路由在下一步配。

**这一步验收的是阶段 A 检查点里那条"6 个子 Agent 都在 agents list 里"**。

#### 步骤九：配置 Multi-Agent Routing

让请求能路由到对应子 Agent。OpenClaw 的多 Agent 路由有多条通路，本课没有飞书 Channel，用的是基于 CLI 的 **Local Workflow 模式**——Agent 之间靠 `agentToAgent` 工具通信：

```bash
openclaw agents list
openclaw config set tools.agentToAgent.enabled true
openclaw config set tools.agentToAgent.allow \
  '["recruitment","onboarding","training","performance","er-admin","router"]' --strict-json
openclaw gateway restart
```

**为什么启用 `agentToAgent`**：
- HR 数字员工的设计是"用户跟总控 router 说话，router 判断业务领域后转给对应子 Agent"。
- 这个"转发"动作靠的就是 `agentToAgent` 工具，它默认是关的（**OpenClaw 的安全默认：跨 Agent 调用必须显式开启**）。

**为什么要 allow 白名单**：
- 明确列出"这 6 个 Agent 之间允许互相路由，此外不行"，避免不受控的跨 Agent 调用。

> **坑三：照抄开源项目的配置格式会写出当前版本不认的写法**。
>
> 参考项目 `openclaw-agents` 里 `agentToAgent.allow` 用的是 `{from, to}` 对象数组格式，但 v2026.5.12 实测加官方文档确认，现在是简单的 **Agent ID 字符串数组**。这是版本差异——**借鉴开源项目的组织思路可以，具体配置字段格式必须以当前版本的实测或官方文档为准**。

**验证**：`config get tools.agentToAgent` 显示 `enabled: true` 加 6 个 Agent ID 的白名单，gateway 重启后 `/health` 正常。

#### 步骤十：验证路由通路与 session 隔离

**配好了不等于路由真的通**。用 CLI 直达路由真实发两条消息，向 `recruitment` 发一条、向 `onboarding` 发一条：

```bash
openclaw agent --agent recruitment -m "测试路由：这条消息应进入 recruitment 子 Agent 的独立 session" --timeout 30 --json
openclaw agent --agent onboarding -m "测试路由：这条消息应进入 onboarding 子 Agent 的独立 session" --timeout 30 --json
openclaw sessions --agent recruitment
openclaw sessions --all-agents
```

> **坑四：此处会撞上 6.2 埋下的潜伏问题**。
>
> 第一次跑 `openclaw sessions` 直接报错退出：`diagnostics.otel: Unrecognized key: "captureContent"`。
>
> 这正是 6.2 配可观测时写进去的那个**未识别 key**——`config set` 当时接受了它，但 `openclaw sessions` 这类读配置严格的命令把它当**致命错误**拒绝运行（而 `openclaw agent` 命令只打一行警告照常执行，**同一份无效配置不同命令的容忍度不同**）。
>
> 按 OpenClaw 提示用 `openclaw doctor --fix` 清掉无效 key（它会自动留备份），`sessions` 命令随即恢复正常。

发消息命令返回了 `harness "codex" is not registered` 的中止——**这是预期的、正常的**。

> 6 个子 Agent 在骨架阶段还没配 LLM Provider，OpenClaw 给它们带的默认 harness 还没注册，于是 turn 在调模型处中止。
>
> **A.7 验证的是"路由通路对、session 隔离对"，不是"agent 能对话"**——对话能力是 A.10 配完模型之后的事。

看 `sessions --agent recruitment` 的输出才是关键：**消息确确实实进了 `agent:recruitment:main` 这个 recruitment 专属的 session lane**。

**验证**：
- `sessions --all-agents` 显示 **7 个独立的 session store**。
- 发给 recruitment 的消息落在 **`agent:recruitment:main`**，
- 发给 onboarding 的落在 **`agent:onboarding:main`**——
- **两个完全不同的 lane、两个不同的 session id，互不串扰**。

> 这是路由隔离的**决定性证据**：发给谁就进谁的 lane。

**至此 A.6 和 A.7 完成**。这一节让环境长出了两项能力——
- 可在审批点暂停的 Lobster 工作流，
- 以及 6 个物理隔离、可路由的常驻子 Agent。

### 6.4 实操：权限分级、hooks 与 LLM Provider

本节对应开发环境最后三个组成——**权限分级、hooks、LLM Provider**，也就是阶段 A 的 **A.8 到 A.10**。

这三项都属于"安全与接入"——让数字员工从"谁来都一样"走向"按身份分权"，从"人不发指令就不动"走向"事件来了自动响应"。

#### 6.4.1 工业级权限分级（A.8）

一个 HR 数字员工会同时面对三种身份的人：
- **HR 主管**要导花名册、批量处理简历，需要"重武器"；
- **业务部门负责人**只看自己部门的招聘进度，能查不能改；
- **普通员工**只问年假、报销这类 Helpdesk 问题。

> 如果三种人调用同一套工具，就会出安全问题（普通员工能执行命令 = 服务器门大开）和合规问题（业务负责人能改简历评分 = 数据可篡改）。

**A.8 给"小慧"配上按身份分权的能力。**

OpenClaw 把这件事拆成两个机制：
- **Per-Sender Tool Policy**——按"发消息的人是谁"分权
- **Per-Agent Tool Policy**——按"请求交给哪个子 Agent"分权

#### 步骤一：实测真实的 Tool Policy schema

> 知识库 synthesis 给的 per-sender 配置结构标注了"推断、待验证"。**动手前必须先确认真实结构——不照搬未验证的内容**。

OpenClaw 自带一条命令能打印**权威的配置 JSON Schema**：

```bash
openclaw config schema > /tmp/oc-schema.json
grep -c 'perSender'        /tmp/oc-schema.json   # synthesis 推断的 key
grep -n 'toolsBySender'    /tmp/oc-schema.json   # 实测的真实 key
```

> **坑一：知识库标了"推断"的内容实测两处都错**。
>
> - `grep -c 'perSender'` 结果是 **0**——synthesis 推断的 `perSender` 这个 key 在真实 schema 里**根本不存在**。
> - 真实的 key 叫 `toolsBySender`，而且数据形态也不同：
>   - synthesis 推断它是数组 `[{sender, allow, deny}]`，
>   - 实测是一个对象 map `{ "<sender-key>": {allow, alsoAllow, deny} }`——**sender key 直接做对象的键**。

> **知识库里标了"推断 / 待验证"的内容，引用前必须用 `config schema` 实测。**

**验证**：`config schema` 输出是 OpenClaw 校验配置时用的那份权威 schema，比任何文档都准。**实测确认了真实 key 是 `toolsBySender`**，后面所有配置全部基于这个事实。

#### 步骤二：摸清 toolsBySender 的配置层级

`toolsBySender` 在 schema 里出现在多个位置，**配错层级就不生效**。归类后是三层：

| 层级 | 配置路径 | 作用范围 |
|---|---|---|
| **全局层** | `tools.toolsBySender` | 所有 Agent 共享一套 sender 权限表 |
| **per-agent 层** | `agents.list[].tools.toolsBySender` | 单个子 Agent 的 sender 权限表 |
| **channel 层** | `channels.<feishu/...>.toolsBySender` | 某个 channel 内的 sender 权限表 |

**验证**：channel 层有 22 个位置，它们都要求**先有 channel（飞书等）**。本课没有飞书 channel，所以 per-sender 用全局层 `tools.toolsBySender` 配置——这也决定了本课 per-sender 的验证边界（见步骤四）。

#### 步骤三：摸清 sender key 格式与工具组清单

配权限表还差两块拼图：**sender key 写什么格式，allow / deny 里填的工具名有哪些**。

**sender key 是带前缀的字符串**，匹配时从最精确到最宽松逐级尝试：

```
channel:<channelId>:<senderId>    ← 最精确
id:<senderId>
e164:<手机号>
username:<用户名>
name:<显示名>
*
```

**两条关键规则**：
1. **先命中先用**——多个 sender key 都能匹配同一个发件人时,按"最精确→最宽松"的顺序逐级尝试,首个匹配的就生效;
2. 同一个工具同时出现在 `allow` 和 `deny` 里,**`deny` 永远赢**(安全默认,拿不准就拒)。

**工具名填进 allow / deny 时**，既可以填单个工具（如 `exec`），也可以填整组。**OpenClaw v2026.5.12 有 11 个核心工具组**，其中和 HR 场景最相关的几个：

| 工具组 | 包含能力 | 备注 |
|---|---|---|
| `group:runtime` | `exec`/`process`/`code_execution` | **权限最危险的一组** |
| `group:fs` | 文件读写 | |
| `group:memory` | 检索记忆库 | Helpdesk 查政策靠它 |
| `group:sessions` | 含批量并行 `sessions_spawn` | |
| `group:media` | 含画雷达图的 `image_generate` | |

此外 `*` 通配代表全部。

> **11 个工具组的设计意义**:把上百个零散工具按功能聚合成"组",在权限配置上提供了三个层次的工程价值:
> 1. **配置最小化**—— 一行 `deny: ["group:runtime"]` 即可禁掉所有"能跑 shell"的工具;
> 2. **语义清晰**——配置可读性极高,审计者一眼能看出"这个 Agent 不给执行类工具";
> 3. **新工具自动归类**——OpenClaw 新增工具时按其能力自动归入对应组,**无需手动重新配置 deny 列表**,这是 OpenClaw 跨版本兼容性的重要保障。
>
> **工程实践**:受限 Agent 用 deny、不用 allow 白名单,本质上是利用了"组"的减法特性——只扣掉危险组,业务组(group:memory、group:web 等)自动保留。

> **小提示**：工具名填错（比如把 `web_search` 写成 `websearch`）不会致命报错，只会被当成"未知条目"打一行 warning 然后忽略——**结果是配了个"看着生效、实际是空"的假权限**。
>
> 所以工具名必须用真实的，下一步会用 `config validate` 兜底校验。

#### 步骤四：配置三档 Per-Sender Tool Policy

**用真实的 `toolsBySender` 结构，把 HR 三档权限写进配置**。先准备一份 patch 文件 `/tmp/hr-persender.patch.json5`：

```json5
{
  tools: {
    toolsBySender: {
      "name:HR主管":   { allow: ["*"] },                  // 高权限 · 全工具
      "name:业务负责人": {
        allow: ["group:memory","group:web","read","sessions_list","sessions_history"],
        deny:  ["group:runtime","write","edit","apply_patch"]
      },                                                    // 中权限 · 只读
      "name:普通员工":   { allow: ["group:memory"],
                          deny:  ["group:runtime","group:fs","browser","cron"]
      },                                                    // 低权限 · 仅 Helpdesk
      "*":               { deny: ["*"] }                    // 兜底 · 未知身份全锁
    }
  }
}
```

然后用 `config patch` 一次性写入并校验：

```bash
openclaw config patch --file /tmp/hr-persender.patch.json5 --dry-run   # 先 dry-run
openclaw config patch --file /tmp/hr-persender.patch.json5             # 真正写入
openclaw config validate                                              # 校验配置合法
```

**为什么用 `config patch` 而不是 `config set`**：

- 三档权限是一个**嵌套结构**（4 个 sender key，每个挂 allow/deny 数组），
- `config set` 一次设一个路径要敲十几条命令。
- `config patch` 读一个 JSON5 文件一次性原子写入。

**为什么先 `--dry-run`**：

- patch 会真改配置文件，dry-run 先报告"会改几处"，确认无误再真写。

**三档怎么对应 HR 业务**：

| 身份 | 权限 |
|---|---|
| HR 主管 | 放全部工具 |
| 业务负责人 | 只给检索、看文件、看进度类工具，**明确禁掉执行和写文件** |
| 普通员工 | 只给检索政策库的能力 |
| `*` 兜底 | "白名单 + 默认拒绝"——没明确授权的身份一律全锁 |

> **本课 per-sender 的边界（诚实标注）**：
>
> sender key 这里用 `name:` 前缀（按显示名匹配），因为本课没有飞书 channel，没有真实的飞书用户 ID。
>
> **三档权限表已写入、已通过 `config validate` 校验**，这是"**配置就绪**"。
>
> 但"按身份发消息 → 命中对应档 → 工具被过滤"的完整端到端验证需要 channel，**留待下集接入飞书后补做**。
>
> 生产环境上线飞书后，把 `name:HR主管` 换成 `id:ou_<真实飞书ID>` 即可，结构不变。
>
> **本课"权限分级确实生效"的完整证据，由下面的 per-agent 提供**。

#### 步骤五：配置三档 Per-Agent Tool Policy

per-agent 按"请求交给哪个子 Agent"分权，配置位置是 `agents.list[].tools`，**不依赖 channel**。

> **这里有一个关键的工程决策——不能用 `config patch`**。

> **坑二：`config patch` 对数组是整体替换，不是合并**。
>
> `config patch` 的合并规则是"对象递归合并，数组和标量替换"。
>
> `agents.list` 本身是一个数组——用 `config patch` 提交含 `agents.list` 的 patch，**会把整个数组替换掉**，A.7 建好的 6 个 HR 子 Agent **全部丢失**。
>
> 正确做法是用 `config set` 的方括号索引路径，只定位到数组某个元素的某个字段，**单点写入**。

`agent` 在 `agents.list` 里的索引（实测确认）：
- `[0]` main
- `[1]` recruitment
- `[2]` onboarding
- `[3]` training
- `[4]` performance
- `[5]` er-admin
- `[6]` router

逐个写入四个 agent 的 tool policy：

```bash
# 受限 agent · er-admin —— deny 危险工具
openclaw config set 'agents.list[5].tools.deny' \
  '["group:runtime","write","edit","apply_patch","browser"]' --strict-json
# 受限 agent · performance —— deny 执行与写
openclaw config set 'agents.list[4].tools.deny' \
  '["group:runtime","write","edit","apply_patch"]' --strict-json
# 高权限 agent · router —— allow 全部
openclaw config set 'agents.list[6].tools.allow' '["*"]' --strict-json
# 高权限 agent · recruitment —— allow 宽工具集
openclaw config set 'agents.list[1].tools.allow' \
  '["group:memory","group:web","group:fs","group:sessions","group:media"]' --strict-json
openclaw config validate
```

**三档怎么对应子 Agent**：

| 子 Agent | 权限策略 |
|---|---|
| `router`（总控） | 要先"看见"所有工具才能正确分诊路由，**给全集** |
| `recruitment`（招聘） | 要批量处理简历，**给文件读写、批量并行、画图等宽工具集**，但不给 `group:runtime` |
| `performance`（绩效）、`er-admin`（行政） | 处理绩效数据和员工关系，是"**能查能算但不该改不该跑命令**"的典型，用 `deny` 精确禁掉危险工具 |

**为什么受限 agent 用 deny 不用 allow 白名单**：

- `deny` 是在默认能力上做**减法**，只扣掉危险工具、不影响业务工具，配置最小。

**验证**：
- 四条 `config set` 全部写入成功，
- `config validate` 通过，
- 写后 `config get agents.list` 确认 7 个 agent **一个不少**——
- `config set` 方括号索引确实是单点写入，没有发生数组替换。

#### 步骤六：验证权限分级确实生效（这是 A.8 的核心）

**必须真实证明"权限被分级了"**。

Agent 真跑工具需要 LLM Provider（A.10 才配），但"工具能不能被调用"**本质上**由 OpenClaw 的 `tool-policy` 管线决定，与 LLM 无关。

**所以换一条不需要 LLM 的路**：直接调用 OpenClaw 生产代码里算 agent 工具集的那个函数 **`applyFinalEffectiveToolPolicy`**，对每个 agent 算出"过滤后的有效工具集"。

> **`applyFinalEffectiveToolPolicy` 函数说明**:这是 OpenClaw 生产代码中的**工具权限管线最终聚合函数**——它在请求一个 Agent 实际调用工具前,把 per-sender policy、per-agent policy、channel-level policy、group 工具组展开等多个层级的策略**全部叠加**,最终输出该发件人向该 Agent 发起请求时可用的具体工具列表。直接从这条管线取证意味着**绕开了 LLM、绕开了 Channel、绕开了真实业务调用**,但得到的"有效工具集"与生产运行时**完全等价**——这是工业级权限测试的常用方法(称为"**policy-as-code 验证**"或"**离线权限断言**")。

写一个 Node 脚本，构造一组探针工具（10 个），对 7 个 agent 各算一次有效工具集：

```bash
node /tmp/verify-peragent-policy.mjs
```

**验证——这是 A.8 的硬证据**。

> 同样的 10 个探针工具，喂给不同 agent，算出**不同的有效工具集**：
> - 没配 policy 的 `main` 和 `allow:["*"]` 的 `router` 都是 **10**（高权限拿全集）；
> - `recruitment` 用 allow 白名单算出 **6**（白名单外的 runtime、browser 进不来）；
> - `performance` 是 **4**（runtime、文件写被 deny 拦掉）；
> - `er-admin` 是 **3**（额外把 browser 也禁了）。
>
> **受限 agent 配的 deny 里写了什么、结果里就少了什么，一一对应**。
>
> **10 / 6 / 4 / 3 四个不同的数字**，就是"权限分级确实生效"的可测量证据。

> **坑三：per-sender 和 per-agent 在同一条管线里叠加，验证一层必须排除另一层**。
>
> 验证脚本第一版所有 agent 工具数都是 **0**——因为脚本没传 sender 身份，per-sender 解析命中了步骤四配的兜底键 `"*": { deny: ["*"] }`，把工具全锁了，per-agent 那层的差异根本没机会显现。
>
> 解决办法是给脚本传 `senderName: 'HR主管'`，命中 per-sender 高权限档放行，per-agent 的分级才显出来。
>
> **这个对照顺带间接验证了一件事**：per-sender 兜底配置不只是通过了 schema 校验，**它在解析管线里确实会执行**。

#### 6.4.2 事件触发底座 hooks（A.9）

到这里，"小慧"的能力都是"人发指令 → Agent 响应"的被动模式。而真实的 HR 数字员工需要在某些生命周期事件发生时自动做事——

- 候选人投递简历就自动评分
- 会话结束就自动存记忆

**这就是 hooks 系统**。

计划里事件触发用"**5 个 bundled hook + 1 个自写 hook**"，A.9 先把 5 个官方 bundled hook 启用并验证，它们是后续自写 hook 的**底座**。

#### 步骤七：摸清 OpenClaw 自带的 5 个 bundled hook

```bash
openclaw hooks list
```

**验证**：v2026.5.12 自带正好 **5 个 hook**，Source 列全部是 **`openclaw-bundled`**（平台内置标识，意味着这 5 个 hook 是 OpenClaw 官方维护的、与二进制版本一起发布）：

| Hook | 触发事件 | 干什么 |
|---|---|---|
| `boot-md` | Gateway 启动 | 启动时跑 workspace 下的 `BOOT.md` |
| `bootstrap-extra-files` | agent 引导 | 按路径注入额外文件到引导上下文 |
| `command-logger` | 命令事件 | 把命令事件写进集中审计日志 |
| `compaction-notifier` | 会话压缩前后 | 压缩开始和结束时发可见提示 |
| `session-memory` | 会话重置命令 | `/new`、`/reset` 时把上下文存进记忆 |

> **小提示**：`hooks list` 表头会显示 `5/5 ready`。
>
> 但 **`ready` 不等于 `enabled`**——`ready` 只表示"依赖满足、可被加载",一个 hook 究竟生效没有要看下一步的状态字段。两者是不同的状态机:
> - **`ready=true`**: hook 文件已注册、依赖项齐备;
> - **`enabled=true`**: hook 配置上启用,且经 Gateway 实际加载进进程;
> - **`disabled=true`**: 配置上明确禁用。
>
> 三者共同决定 hook 实际是否介入事件分发。

#### 步骤八：看清每个 hook 的真实启用状态

```bash
openclaw hooks list --json | python3 -c '...提取 disabled / enabledByConfig / loadable...'
```

**验证**：`--json` 拿到结构化字段后能看清——**5 个 bundled hook 全部 `disabled=false`、`enabledByConfig=true`、`loadable=true`**。

这里有个关键事实：

> **v2026.5.12 的 5 个 bundled hook 默认就是启用状态**，不像插件那样需要先 install 再 enable。

既然默认就启用，为什么还要做下一步的"启用"？

> 因为"**默认启用**"是**隐式的**、**不写在配置文件里的**——换一台机器、换一个人接手，**看不到任何痕迹**。
>
> 对工业级系统，事件触发底座是**审计链路的一部分**，必须显式落到配置文件。

#### 步骤九：把 5 个 hook 显式写进配置

启用命令是 `hooks enable`，一次启用一个，用 shell 循环把 5 个全部启用：

```bash
for h in boot-md bootstrap-extra-files command-logger compaction-notifier session-memory; do
  openclaw hooks enable $h
done
```

执行后看一眼配置文件里写进去了什么：

```bash
sed -n '298,318p' ~/.openclaw-hr/config/openclaw.yaml
```

**验证**：

> config 文件里多了一个 `hooks` 段，结构是 `hooks.internal.enabled`（总开关）下挂 `entries`，每个 hook 一条 `{ enabled: true }`。
>
> 总开关很关键——Gateway 只在"**至少一个 hook 启用**"时才加载 internal hooks 子系统，`hooks enable` 第一次执行会自动把它打开。
>
> **这一步把"启用意图"从隐式的平台默认，变成了配置文件里可见、可复现、可审计的记录**。
>
> **`hooks.internal.enabled` 总开关的设计哲学**:这是 OpenClaw 的"零成本关闭 hooks 系统"机制——把 `enabled: false` 写进去,整个 internal hooks 子系统都不加载,既节约内存,又避免不必要的 hook 监听带来的性能损耗。设计上:
> - **`enabled: false`** → 整个 internal 子系统不加载,所有 hook 不生效;
> - **`enabled: true` + `entries: [{}]`** → 子系统加载,但没有任何 hook 注册(等于"开了门但没人值班");
> - **`enabled: true` + `entries: [{name: "session-memory", enabled: true}]`** → 子系统加载且该 hook 启用。
>
> 这种**总开关 + 逐项开关**的两段式设计,让"批量关闭 hooks"只需一行配置变更(对比"逐个禁用 5 个 hook 要改 5 处")。

#### 步骤十：确认配置被 Gateway 热重载

改了配置、Gateway 已经在跑，新配置怎么生效？**常规思路是"改配置就重启服务"**。看 Gateway 日志，答案不一样：

```bash
grep -E '(Enabled hook|hot reload applied \(hooks)' /tmp/openclaw/openclaw-2026-05-15.log
```

**验证**：

> 每启用一个 hook，日志里都出现一行 `config hot reload applied`——
> **Gateway 监测到配置文件变化，自动把 hook 配置热重载进来了，完全不需要手动重启**。
>
> 原因是 OpenClaw 的配置热重载默认是 **hybrid 模式**：能热应用的直接热应用。
>
> **对要求高可用的数字员工，这意味着事件触发底座可以在线调整**——新增或临时关闭一个 hook，不用中断正在服务的 Gateway。

#### 步骤十一：确认每个 hook 绑定的触发事件

```bash
for h in boot-md command-logger session-memory compaction-notifier bootstrap-extra-files; do
  openclaw hooks info $h | grep -E "Ready|Events:"
done
```

**验证**：

> `hooks enable` 只改了配置，要确认 hook 真的加载、绑上了事件，得看 `hooks info` 的 `Events:` 字段。
>
> 5 个 hook 全部 `Ready`，且各自绑定了明确事件：
> - `boot-md` 绑 `gateway:startup`
> - `command-logger` 绑 `command`
> - `session-memory` 绑 `command:new` 和 `command:reset`
> - `compaction-notifier` 绑 `session:compact:before/after`
> - `bootstrap-extra-files` 绑 `agent:bootstrap`
>
> **OpenClaw 内部维护一张"事件 → hook"分发表**，某个事件发生时，监听它的 hook 被依次调用。

#### 步骤十二：触发验证与运行时确认

前面都是静态确认（配置写对、hook 加载、事件绑定）。要进一步证明 hook 会真的跑，得制造一个事件再看痕迹。尝试用本地 tui 连上 Gateway、发一个 `/new` 命令来触发 `command` 事件，结果发现 `command-logger` 该写的审计日志文件没有出现。

> **这是工具事件模型决定的边界，不是实验疏漏**。
>
> 查证源码和官方文档确认：`command` 事件由"**从消息通道（Telegram、WhatsApp 等）发来的、带 slash 命令的消息**"触发，而本地 tui 的 `/new` 是 **TUI 客户端自己的会话切换动作**，不走 Gateway 的命令事件分发。
>
> **本课的 HR profile 没有接入任何消息通道，所以无法在本集制造这个事件**。
>
> `command-logger`、`session-memory` 这两个 hook 验证到"已加载 + 已绑定触发事件 + 被运行中的 Gateway 热重载"为止——**完整端到端触发留待后续接入消息通道后补**。

另外，验证 HR Gateway 时 tui 默认连的是 `ws://127.0.0.1:18789`（OpenClaw 默认端口），而 HR Gateway 在 18790——**必须显式 `--url ws://127.0.0.1:18790 --token "$OPENCLAW_GATEWAY_TOKEN"`**，否则会连错 profile。

**把能拿到的硬证据收成一处**：

```bash
openclaw hooks check
```

**验证**：

> **三条互相独立的证据收口**——
> 1. `hooks check` 显示 **`Total hooks: 5 / Ready: 5`**；
> 2. Gateway 日志里 `config hot reload applied (hooks*)` 出现多次，证明 hook 子系统**进了运行中的 Gateway 进程**；
> 3. `command-logger` 的文档示例确认 `command` 事件来源是消息通道。
>
> 结论：**5 个 bundled hook 在运行中的 Gateway 里确实是活的**，事件触发底座就绪。
>
> 后续自写"候选人投递 → 自动评分"的 hook，只要照 `hooks.internal.entries` 的结构注册、绑一个事件，就能挂进同一套分发管线。

## 附录 D:HR 数字员工"小慧"上线工作一幕

> 此节把开篇 §1.5 提到的一幕完整还原——这是 OpenClaw AI HR 数字员工"小慧"上线后**正常运转的状态**,本课三期的最终成品形态。

**HR 的输入**:
- 对话框里发一句"帮我筛一下这周收到的简历"。

**小慧的响应**(几分钟后):
- 一份按岗位匹配度排好序的候选人清单。
- 每位候选人附:**评分**(分值) + **评分理由**(一句话文本)。
- 点开候选人中的某一位,看到一份 **HTML 格式的候选人画像**,包含:
  - **技能雷达图**(可视化展示能力维度)
  - **关键经历摘要**(从简历原文提炼)
  - **匹配度分析**(与 JD 的对比)

**这个过程的"AI 端"完整流转**:
1. HR 消息进入飞书 Channel(本期不接,Lesson 3 接) → Channel 路由到 Router。
2. Router 判断领域(招聘) → `agentToAgent` 转发到 recruitment 子 Agent。
3. 招聘 Agent 用 `office-to-md` 解析简历 → 手写评分 Pipeline 按 JD 评分(含合规过滤) → 批量并行(`sessions_spawn`)→ 生成 JSON + HTML 落盘。
4. `agentToAgent` 回报 Router → Router 回复 HR(整链路审计日志全程记录)。

**这个过程的"人端"感受**:
- HR 全程**没有打开任何一份原始简历文件**。
- HR **没有手动给任何人打分**。
- HR 看到的是一份结构化、可点开、可决策的清单。
- 招聘 Agent **不会擅自淘汰任何候选人**(§3.3.3 合规红线)。
- 整套系统的 token 消耗通过 Prometheus 可观测(§6.2)。

**这一幕的"为什么"**(回到方法论):
| 设计要素 | 小慧端的体现 |
|---|---|
| md 文档(§2.2) | 招聘 Agent 的 SOUL.md 明确"只做评分排序,淘汰由人定" |
| Skill + MCP(§2.3、§2.5) | 用了 office-to-md、fastio、faster-whisper 等现成 Skill |
| 插件(§2.6) | Lobster 让入职流程可暂停、Prometheus 给 AI 算账 |
| Channel(§2.7) | 飞书 Channel 是 HR 的入口(Lesson 3 才接) |
| 多 Agent 系统(§2.8) | 6 个子 Agent 分工,HR 只与 Router 对话 |
| 架构六要素(§4.2) | 候选人画像 HTML、评分 JSON、审计日志三类落盘物 |
| 阶段化 + 检查点(§5.2) | 这是 8 个阶段全部跑完的最终交付 |

> **设计方法论的承诺**:这一刻证明 §1 立下的目标——"构建一个清晰、可扩展、工业级落地的 Agent 系统"——**从设计原则落到了真实的工作流**。
>
> 后续 Lesson 2 会在 A.10 LLM Provider 配好之后,把这一刻在实操中真正实现出来。
