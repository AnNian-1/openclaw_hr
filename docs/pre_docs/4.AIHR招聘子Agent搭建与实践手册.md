## §0 数据资产与字段契约

开发前先确认数据资产就位，并把字段契约钉死。

```bash
# 确认 inbox 有 28 份简历
ls inbox/ | wc -l          # → 28

# 确认字段标准存在（数据契约的成文形式）
ls candidate-profile-schema.md
```

`candidate-profile-schema.md` 定义候选人画像的 6 组字段：基础信息、教育背景、工作经历、技能、评估、来源与跟进。**解析照它产出、画像照它渲染、评分维度来自它 §8、合规黑名单来自它 §9。契约必须先定义、后开发。**

> 若要造自己的测试数据，避开两个坑：① 有标识作用的字段（尤其姓名）必须唯一；② 反面样本的缺陷要藏进正文，绝不能在标题/注释里剧透。

## §1 工业四步操作模板（通用）

后面五个能力全部走这四步，先给通用模板：

```bash
# ① 建 Skill：标准一层布局
#   skills/<name>/
#   ├── SKILL.md        （必需：frontmatter + 渐进式披露正文，≤500 行）
#   ├── scripts/        （可执行脚本，被执行不进上下文）
#   ├── references/     （详细文档，按需加载）
#   └── evals/          （评测场景）

# ② 改核心 md 文档（先 Read 看清，再精确字符串替换插入，不整文件覆盖）
#   TOOLS.md   —— 加"做什么 / 什么时候用 / 调用要点"
#   AGENTS.md  —— 加"调用时机 / 嵌进工作流哪一步"
#   SOUL.md    —— 若涉及价值观或边界，补一条硬边界

# ③ 改配置（即使确认"无需改动"也不能省，必须主动确认）
$OPENCLAW_HR_BIN config get 'agents.list[1].tools'   # recruitment 工具权限（含 group:runtime）
$OPENCLAW_HR_BIN skills check --agent recruitment     # allowlist 状态（Blocked by allowlist: 0）

# ④ 调用测试：三个测试
#   A 验证加载：skills info <name> --agent recruitment  → ✓ Ready / Visible to model: yes
#   B 发自然任务（不点名 Skill），验证 Agent 自己选中
#   C 验证脚本真跑：让 Agent 贴回脚本输出，再独立复跑对比逐字符一致
```

**SKILL.md frontmatter 模板**：

```yaml
---
name: parsing-resumes          # 动名词，小写+连字符（不是 resume-parser）
description: <第三人称、写给 AI 看、含 what + when + 与相邻 Skill 的区别>
metadata:
  openclaw:
    requires:
      bins: ["node"]           # 显式声明依赖二进制
---
```

> **建完 Skill 第一件事永远是 `skills info` 验证被识别**——标准一层布局 + 合法 frontmatter 的 Skill 当场被扫到、无需重启 gateway。

## §2 简历解析：parsing-resumes + auditing-extraction

### 2.1 格式转换（用现成 Skill）

```bash
# PDF/DOCX 先用 office-to-md-v2 转 Markdown（注意：需先把它的嵌套目录布局修正成标准一层才会被加载）
$OPENCLAW_HR_BIN agent --local --agent recruitment \
  -m "请用 office-to-md skill 解析 inbox/resume-tech-02-林雨桐-算法工程师.pdf，转成 Markdown。完成后告诉我输出路径和转换统计。"
```

- DOCX 格式保留度好于 PDF（DOCX→HTML→MD 保留标题层级、表格；PDF 只提取纯文本）。
- Markdown 简历本身就是结构化文本，不用转换，Agent 直接读。

### 2.2 建 parsing-resumes Skill

目录布局：

```
parsing-resumes/
├── SKILL.md                       # frontmatter + 渐进式披露正文（约 57 行）
├── scripts/
│   └── validate_profile.js        # 候选人 JSON 校验器（确定性把关）
├── references/
│   └── field-extraction.md        # 字段级抽取细则
└── evals/
    └── eval-cases.md              # 4 个评测场景
```

**正文写死的 4 条硬规则**：

1. 只抄原文有的，原文没有的字段留空——绝不编造。
2. 绝不抽取合规红线字段（年龄、性别、婚育、户籍、民族、健康）。
3. 软推断字段必须显式标注（`industry` 要带 `industry_inferred: true`）。
4. 派生字段按客观数据计算（`total_experience_years` 按起止时间累加），不取简历自述值。

**校验脚本先单独验证（隔离变量）**：

```bash
node skills/parsing-resumes/scripts/validate_profile.js /tmp/baseline-林雨桐.json   # exit 0
node skills/parsing-resumes/scripts/validate_profile.js /tmp/bad-profile.json        # exit 1（含 age/gender）
```

`validate_profile.js` 校验：JSON 能否解析、必需字段组齐不齐、合规红线字段是否零出现（递归扫描）、派生字段与工作经历是否自洽。退出码 0 通过 / 1 不通过。

### 2.3 调用测试（B + C）

```bash
# 测试 B：发不点名 Skill 的自然任务
$OPENCLAW_HR_BIN agent --local --agent recruitment \
  -m "inbox/resume-tech-03-郑凯文-前端开发.md 这份简历需要处理成结构化候选人数据，给评分环节用。"

# 测试 C：验证脚本真跑（让 Agent 贴回输出，再独立复跑对比）
$OPENCLAW_HR_BIN agent --local --agent recruitment \
  -m "用 parsing-resumes skill 的校验脚本，校验 parsed/resume-tech-05-刘佳怡-测试工程师.json。把脚本的完整输出原样贴给我。"
node skills/parsing-resumes/scripts/validate_profile.js parsed/resume-tech-05-刘佳怡-测试工程师.json
```

### 2.4 双 Claude 迭代（真实暴露的两个问题）

| 验收点 | 迭代前 | 迭代后复测 |
|---|---|---|
| `total_experience_years` 按起止时间算 | 取自述值 2 | 3.6（脚本按 2021-07~2025-03 累加） |
| `industry` 带 `industry_inferred` 标志 | 漏标注 | 两段经历均带 `"industry_inferred": true` |

**两条迭代动作**：① SKILL.md 正文补硬规则（派生字段按起止时间算、软推断字段必须带标志）；② `validate_profile.js` 增两条校验（累加月数比对 `total_experience_years`，偏差超 1 年报错；产出 `industry` 必须同时带 `industry_inferred: true`）。

> **堵幻觉偷懒**：复测撞上 Agent 回复"刚才已处理过、文件已存在"但 `ls` 确认根本不存在。修正——任务里显式声明"该文件目前不存在，不要假设它已存在" + 要求贴回可核验产物。

### 2.5 建 auditing-extraction Skill（真实性核对）

`parsing-resumes` 保证"形状对"，`auditing-extraction` 保证"内容真"。

```
auditing-extraction/
├── SKILL.md                     # 正文 55 行
├── scripts/
│   └── audit_extraction.js      # 真实性核对器（逐字回溯）
├── references/
│   └── audit-method.md
└── evals/
    └── eval-cases.md
```

`audit_extraction.js` 输入两个文件（parsed JSON + 简历原文 Markdown），先做文本归一化（去空白、统一全半角括号、统一连字符），再按三类字段三套标准核对：

- **硬提取字段**（name/phone/email/target_position/expected_salary/school/company/起止时间）——值必须在原文逐字符找到出处，找不到 = 疑似编造。
- **软推断字段**（`industry`）——不核对出处，核对是否带 `industry_inferred: true` + 推断依据（公司名）是否在原文。
- **派生字段**（`total_experience_years`/`job_count`）——核对计算依据是否成立。

产出可追溯率 + 逐字段核对报告 `audited/<简历名>.audit.json`，退出码 0（全部可追溯）/ 1（有对不上或漏标注）/ 2（文件缺失）。

**调用测试**：

```bash
# 测试 B：核对 §2.3 留下的林雨桐产出（迭代前 industry 没带 _inferred）
$OPENCLAW_HR_BIN agent --local --agent recruitment \
  -m "parsed/resume-tech-02-林雨桐.json 准备进评分环节了。进评分前请核对真实性——确认每个字段都真来自简历原文。发现问题要具体指出是哪个字段。"

# 测试 C：验证能抓出"编造的硬字段"（篡改样本：expected_salary 改成原文没有的 30K-40K、school 改成浙江大学）
$OPENCLAW_HR_BIN agent --local --agent recruitment \
  -m "parsed/resume-tech-03b-郑凯文-test.json 准备进评分环节。进评分前请核对真实性。如果有字段对不上原文，明确告诉我是哪个字段。不要自己修，只核对并报告。"
```

> **两个脚本 bug（单独验证阶段抓出）**：① 带括号的值要分"主体 vs 补充"——防"核心值假、补充词真"（"30K-40K（月薪）"里"月薪"真但"30K-40K"假）；② 脚本路径推导不靠"调用方在标准目录"的假设——改为从简历原文路径向上两级定位 workspace 根。

## §3 评分 Pipeline：三层三个 Skill

评分 Pipeline = 合规过滤 + 8 维评分 + 数字回核，一层一个 Skill，顺序固定、缺一层不能上线。

### 3.1 第一层 · filtering-sensitive-fields（合规过滤）

```
filtering-sensitive-fields/
├── SKILL.md                    # 正文 56 行
├── scripts/
│   └── filter_sensitive.js     # 递归删除 + 自检
├── references/
│   └── sensitive-fields.md     # 敏感字段清单 + 法律依据
└── evals/
    └── eval-cases.md
```

`filter_sensitive.js` 三件事一气做完：① `stripRecursive` 递归物理删除黑名单字段（顶层 + `education` 子层 + `work_experience` 数组）；② 剥离后递归重扫，用词干匹配（`FORBIDDEN_STEMS`）找残留，残留任何一个退出码 1 绝不放行；③ 产出脱敏 JSON + 剥离清单。

黑名单 `FORBIDDEN_KEYS` 中英文键名都列入，法律依据写明来源（schema §9 + 就业促进法 26-30 条 + 个保法第 28 条）。退出码：0 通过（自检剩余 = 0）/ 1 自检未通过 / 2 文件问题。

**脚本先单独跑 4 个评测场景**：

```bash
# 场景 1：含多敏感字段的张磊画像 → 5 个敏感字段全删、自检 0
node skills/filtering-sensitive-fields/scripts/filter_sensitive.js profiles/profile-张磊-full.json /tmp/s1.json   # exit 0
# 场景 4：黑名单覆盖不到的字段 → 自检词干匹配兜住、绝不放行
node skills/filtering-sensitive-fields/scripts/filter_sensitive.js /tmp/case-applicantbirthdetail.json /tmp/s4.json  # exit 1
```

**调用测试 B**（任务里显式声明"文件不存在" + 要求贴回脚本输出）：

```bash
$OPENCLAW_HR_BIN agent --local --agent recruitment \
  -m "profiles/profile-周晓峰-full.json 准备进评分环节了。scoring/clean-周晓峰.json 这个文件目前不存在、不要假设它已存在。请现在处理，把脱敏后的评分输入产出到那个路径。处理时把用到的脚本的完整输出原样贴给我。"
```

**事后核验**（不信 Agent 文字汇报）：① `ls` 确认文件落盘；② 独立复跑脚本，两份脱敏 JSON `sort_keys` 后 `diff` 逐字节一致；③ 残留检查——基线漏掉的 `education.school_tier` 这次被递归剥掉。

> **关键设计**：删的是画像副本（`structuredClone`），原始画像保留敏感字段供 HR 统计；自检用 `process.exit(1)` 不用可被优化掉的 `assert`。

### 3.2 第二层 · scoring-candidates（8 维评分）

这个 Skill 有**两个脚本**：

```
scoring-candidates/
├── SKILL.md                  # 正文 57 行
├── scripts/
│   ├── score_candidate.js    # 单份 8 维评分（含固定 prompt + 评级切分）
│   └── batch_rank.js         # 批量评分 + 排序（含重试 + 失败标记）
├── references/
│   └── scoring-method.md
└── evals/
    └── eval-cases.md
```

`score_candidate.js` 把基线不稳定点全部钉死：① 8 维度写成 `DIMENSIONS` 常量；② 固定评分 prompt 写死（合规红线声明 + 可解释要求 + 只评分不淘汰 + 维度权重指引）；③ 评级切分 `ratingOf()` 用脚本固定区间，**覆盖 LLM 自填的评级字母**（哪怕 LLM 填了 B，脚本按综合分重算盖掉）；④ 强制产出 `dimension_scores`（不是漂移的 `dimensions`）；⑤ `extractJson` 尾逗号容错 + 解析失败重试，`callDeepseek` 3 次重试指数退避。

`batch_rank.js` 用 `require` 复用 `score_candidate.js` 的评分函数（不抄两遍）：每份最多评 3 次，3 次全失败**显式标记"待人工处理"绝不静默丢弃**，全部评完按综合分降序排序，每人标"建议动作"不标淘汰。

**脚本先单独跑评测**：

```bash
# 场景 1 单份（张磊）：8 维齐全、dimension_scores 命名正确、综合分归到 C(待定)、硬伤空、exit 0
# 场景 2+3 批量（张磊+王浩然+周晓峰）：降序排序，周晓峰硬伤被抓出 hard_issues、建议动作不淘汰、exit 0
```

> `concerns` vs `hard_issues` 边界：`hard_issues` 只装三类（经历时间矛盾/学历存疑/自相矛盾）；薪资过高、期望城市不符归 `concerns`。

**调用测试 B**（周晓峰脱敏 JSON 评分，验证抓硬伤）：

```bash
$OPENCLAW_HR_BIN agent --local --agent recruitment \
  -m "scoring/clean-周晓峰.json 需按 jds/jd-bigtech-后端开发工程师.md 评分。/tmp/agent-score-周晓峰.json 目前不存在、不要假设。请现在评分，结果写到那个路径。把用到的脚本的完整输出原样贴给我，并说明有没有硬伤。"
```

### 3.3 第三层 · auditing-numbers（数字回核）

```
auditing-numbers/
├── SKILL.md                  # 正文 57 行
├── scripts/
│   └── audit_numbers.js      # extract + verify + adjudicate + apply 四步合一
├── references/
│   └── audit-method.md
└── evals/
    └── eval-cases.md
```

> **边界判断**：`number_audit.py` 只做前三步，"最小替换对精确修正"在 `score_pipeline.py` 里。Skill 化时把四步合一（否则得到一个半截 Skill）。

`audit_numbers.js` 四步：① **extract**（正则 `NUM_PATTERN` 扫所有"数字+单位"）；② **verify**（归一化后子串匹配，三态）；③ **adjudicate**（大模型判定，3 次重试 + JSON 容错，多次失败显式抛错退出码 1）；④ **apply**（最小替换对 `bad_span`→`good_span` 精确修正，每处留 `text_before`/`text_after` 快照）。

**CLI 签名钉死铁规则**：`audit_numbers.js <评分结果json> <候选人原简历md> [输出json]`——**只接两个数据参数，不留 JD 参数位**（JD 是串台来源，连传进来的入口都没有）。

**脚本先单独跑 4 个评测**：

```bash
# 场景 1（张磊回核前 + 原简历）：抽取 26 个数字、存疑 7、判定 2 处虚构精确修正（58万笔/秒→12.8 万 TPS）、exit 0
# 场景 3（基准只能是原简历）：同一"58万"片段，用原简历当基准判 false（会被判虚构），用 JD 当基准判 true（漏判）——证明基准只能是原简历
# 场景 4（大模型不可用）：monkey-patch 断网，3 次重试后显式抛错退出码 1，绝不静默当"无虚构"放行
```

**调用测试 B**（张磊回核前评分结果做交付前核对）：

```bash
$OPENCLAW_HR_BIN agent --local --agent recruitment \
  -m "scoring/results/score-张磊-回核前.json 是张磊的评分结果，准备交给 HR。交付前要确认评分文字里引用候选人简历的数字都是真的。张磊原简历在 inbox/resume-tech-01-张磊-后端开发.md。/tmp/agent-audit-张磊.json 目前不存在、不要假设。请现在处理，把用到的脚本的完整输出原样贴给我。"
```

> **跨语言移植坑**：`NUM_PATTERN` 单位部分是可选组，允许零宽匹配。Python `re.finditer` 每次必前进，但 node `RegExp.exec` 配全局 flag 遇零宽匹配 `lastIndex` 不前进会死循环——脚本手动 `lastIndex++` 跳过。

## §5 人才库检索：ingest / search / explain 三 Skill

一条流水线的三个 Skill，产物一环接一环：`ingesting-talent-pool` 产出 `talent-pool.json` → `searching-talent-pool` 产出 `search-<锚点>.json` → `explaining-similarity`。

> **流水线型 Skill 的 description 必须写清"我在流水线哪个位置"**（第几环、上下游是谁），否则 Agent 会选错。

### 5.1 ingesting-talent-pool（入库）

```
ingesting-talent-pool/
├── SKILL.md                       # 正文 58 行
├── scripts/
│   └── ingest_talent_pool.py      # parse + embed 两阶段，226 行
├── references/
│   └── ingest-pipeline.md
└── evals/
    └── eval-cases.md
```

- **两阶段**：`parse`（简历→结构化数据）+ `embed`（结构化数据→向量），含断点续跑。
- **每人存 5 个向量**：1 整体 + 4 维度（教育/经历/技能/行业），由 `build_dim_texts()` 拼各段文本。整体向量是单独 embed 一段完整摘要（不是 4 维求平均）。
- **依赖两个 API Key**：`DEEPSEEK_API_KEY`（抽取）+ `DASHSCOPE_API_KEY`（embedding）。
- **产物固定**落 `talent-pool/talent-pool.json`。

```bash

python3 skills/ingesting-talent-pool/scripts/ingest_talent_pool.py all
```

**调用测试 B**（先删 `talent-pool.json` 备份到 /tmp、保留 `parsed-all.json`）：

```bash

  -m "人才库向量库文件 talent-pool/talent-pool.json 目前不存在（不要假设它已存在）。28 份候选人的结构化数据 parsed-all.json 已抽好，你只需重新做向量化那一步、把人才库建起来。建好后把入库脚本打印的关键信息原样贴给我。"
```

> **踩坑 · AGENTS.md 12000 字符注入上限**：五个能力工作流写满后字符数顶到 12010、末尾被静默截断（只在 `agent --local` 启动日志打一行 `truncating` 警告）。修正——删掉末尾 OpenClaw 默认模板的无业务价值样板（"Make It Yours"、指向不存在文件的 "Related"）腾出约 180 字符。**核验超限以运行时 `truncating` 日志为准，不看本地 `python3 len()`（两者差约 15 字符）。**

### 5.2 searching-talent-pool（检索）

`description` 写死真实性纪律：`all computed by real vector cosine similarity, never by LLM ranking`。

```bash
diff talent-pool/search.py skills/searching-talent-pool/scripts/search_talent_pool.py   # search IDENTICAL

# 三种跑法：--like 按候选人 / --jd 按 JD / --compare-keyword 加关键词对照
python3 talent-pool/search.py --like 张磊 --topn 5
```

检索取锚点向量与库内每人算余弦相似度排 Top N，4 个维度向量分别算维度相似度。以库内已有候选人为锚点时约 88 毫秒（省掉锚点转向量那一步）；换新 JD 当锚点要多一次 embedding 往返。

> **关键词 vs 向量**：`--compare-keyword` 是混合能力入口。生产推荐向量粗排 + 关键词精筛（硬条件学历/年限/城市）。朴素词重叠率会把财务经理排进 Top 5，BM25 能缓解通用词误召回但仍读不懂"Java 后端"≈"大数据开发"的语义。

### 5.3 explaining-similarity（解释）

`description` 写死防串台：`the dimension similarity scores are computed upstream and passed through verbatim — the LLM only organizes wording, it never re-ranks or invents scores`。

```bash
diff talent-pool/explain.py skills/explaining-similarity/scripts/explain_similarity.py   # explain IDENTICAL

# 跑法：--search 指向检索结果 JSON
python3 talent-pool/explain.py --search talent-pool/search-张磊.json
```

**调用测试 C 核心验收点**：逐个核对 Agent 解释里出现的每个数字（0.79、0.744、0.713……）——全部能在 `search-张磊.json` 的 `dim_similarity` 找到原值，没有一个是大模型编的新分数；解释还诚实标出差异维度（"差异在行业背景""技术栈方向完全不同"）。

> **架构级防串台**：算分是裁判、解释是解说员，两个 Skill 物理分开——大模型在解释这一步根本拿不到重算分的权限。更彻底的做法：让大模型只输出带占位符的文字（"经历维度相似度 {{exp}}"），真实分数由代码模板填进去。

## §6 面试纪要：TTS 造音频 → 转写分离 → 结构化纪要

三段链路：TTS 造模拟录音 → **FunASR + CAM++ 转写 + 说话人分离**（一体化一次推理）→ LLM 结构化纪要 + 数字回核。

> **环境前置**：TTS 用 `tts-say.sh`（在 `interview/scripts/`）；转写/说话人分离用 **FunASR**（在 `playground/2.step_B_recruitment/playground/1.step_6_arc/`），conda 环境 `funasr_me`。**faster-whisper + 基频阈值分离保留为演示专用降级方案**（见 §6.3b），生产请用 §6.3 的 FunASR。
>
> **理论选型分析**：见 `3.AIHR §8.1`——为什么换 FunASR、它怎么跳过 HuggingFace 认证墙、CAM++ 怎么"自动决定几个说话人"、三跑 v1/v2/v3 怎么 100% 一致。

### 6.3 FunASR + CAM++ 转写 + 说话人分离（推荐方案）

**为什么换 FunASR**：pyannote 有 HuggingFace 认证墙（需 token + 接受协议 + 国内下载受阻），whisper-派生的英文侧模型在中文场景也不够稳。FunASR (Paraformer-zh) + CAM++ 是 ModelScope 上的 MIT 开源方案，国内直下载、零 token、一次推理同时输出字幕 + `speaker_A/B` 标签。理论分析见 `3.AIHR §8.1`。

**环境前置**：

```bash
# 1. conda 虚拟环境（也可改用 venv / 系统 Python，按 README §2 自行决定）
conda create -n funasr_me python=3.10 -y
conda activate funasr_me

# 2. PyTorch：自动检测 GPU/CPU
#    有 NVIDIA 卡: pip install torch torchaudio --index-url https://download.pytorch.org/whl/cu121
#    没 GPU:        pip install torch torchaudio --index-url https://download.pytorch.org/whl/cpu
# 3. 锁 NumPy 1.x（torch 2.2.2 ABI 要求）：pip install "numpy<2"
# 4. 装 FunASR + ModelScope
pip install funasr modelscope
# 第一次跑会自动从 ModelScope 下载 Paraformer-zh / VAD / PUNC / CAM++ 四个模型到 ./models
```

详见 `playground/1.step_6_arc/README-funasr-setup.md`（安装命令、模型列表、故障排查表都齐）。

**调用**（CPU / GPU 自动检测走默认）：


### 6.3b faster-whisper + 基频阈值分离（演示专用降级方案）

> **本节保留作"上一版实现"**：如果不想安装 FunASR 环境、或只有 TTS 双音色录音（面试官女声、候选人降基频）做演示，faster-whisper + 基频阈值分离仍然能跑。**但生产面试请用 §6.3 FunASR**。

```bash

# 片段 26 · 面试官 13 · 候选人 13 · F0 阈值 126Hz
```

## 附录：踩坑速查表

| # | 踩坑 | 现象 | 修正 |
|---|---|---|---|
| 1 | Skill 目录嵌套 / 外层 SKILL.md 缺 frontmatter | `skills list` 里没有它（如 `office-to-md-v2`） | 用标准一层布局 `skills/<name>/SKILL.md`，建完立即 `skills info` 验证 |
| 2 | 确定性规则只放 references/ | Agent 漏标 `industry_inferred`、派生字段取自述值 | 硬规则写进 SKILL.md 正文 + 校验脚本强制把关 |
| 3 | Agent 幻觉"已处理过"偷懒 | 回复文件已存在但 `ls` 没有 | 任务显式声明"文件不存在" + 要求贴回可核验产物 |
| 4 | 核对带括号值半真半假 | "30K-40K（月薪）"里假的 30K-40K 被放过 | 硬字段核对整串命中或去括号主体命中，补充词不单独放行 |
| 5 | 脚本路径依赖调用方目录深度 | /tmp 临时文件算出 `/audited` 根路径写入失败 | 从简历原文路径向上定位 workspace 根 |
| 6 | 合规自检用 assert | Python `-O` 模式静默移除、合规闸消失 | 用 `process.exit(1)` 硬失败语句 |
| 7 | 评测样本走错路径 | 黑名单太全，`birthYear` 走了删除路径，自检没被测到 | 用 `applicantbirthdetail`（黑名单没有、词干 birth 能匹配）才测到自检 |
| 8 | 数字回核用 JD 当基准 | JD 里查到"58万" → 漏判虚构 | CLI 签名不留 JD 参数位 |
| 9 | JS 全局正则零宽匹配 | node `RegExp.exec` lastIndex 不前进死循环 | 零宽匹配时手动 `lastIndex++` |
| 10 | 子串匹配合规校验只测一面 | 只测负向会误报、只测正向不知能否抓真违规 | 正向（不误报）+ 负向（能抓出）两面都测 |
| 11 | AGENTS.md 超 12000 字符 | 末尾静默截断，只在启动日志打 truncating | 删默认模板无业务样板腾空间；以运行时日志为准 |
| 12 | tts-local-cli command 用 `~` | `spawn ENOENT` | 写绝对路径 |
| 13 | 不配置直接 infer tts convert | 卡 30 秒试外网 | 先配置 + 显式带 `--local` |
| 14 | DeepSeek 请求被代理拦截 | 国内直连服务被本机 HTTP 代理拦 | 调用前 `unset http_proxy ...` |
| 15 | FunASR 环境装 CPU 版 torch 但有 NVIDIA 卡 | `cuda.is_available()` 报 False，funasr 强制走 CPU、慢 4× | 重装 `pip install torch torchaudio --index-url https://download.pytorch.org/whl/cu121`；先 `pip uninstall -y torch torchaudio` 避免 ABI 残留 |
| 16 | FunASR 装 torch 2.2.2+cu121 后跑推理报 `RuntimeError: Numpy is not available` | torch 用 NumPy 1.x ABI 编译，env 装的是 2.x | `pip install "numpy<2"`（锁 1.26.x） |
| 17 | FunASR 模型下到一半 404 | VAD 模型 ID 写错（`speech_fsmn_vad_zh-cn-16k-common` 已更名为 ...-pytorch） | 改 ID 为 `iic/speech_fsmn_vad_zh-cn-16k-common-pytorch`；其他三个 ID 同理以 `-pytorch` 结尾 |
| 18 | FunASR 多说话人场景说话人对错（基频阈值不奏效） | 多人音高不可控，F0 分离只对 TTS 双峰够用 | 改用 `transcribe_funasr.py` 的 CAM++ 模式，**自动**决定说话人数量 |
| 19 | transcribe_funasr.py 故意报 `device=cpu` 但 GPU 显存空闲 | 用户在 v1 装机时装过 CPU 版 torch，新装 CUDA 后 `cuda.is_available()` 仍然 False | 走 15 重装；或加 `--device cpu` 显式走 CPU（明确可控降级） |
