## §0 一句话主旨：从架构方框到能跑的子 Agent

Lesson 1 的产物是**设计**——七抓手能力盘点、6 子 Agent 架构图、开发计划、工业级开发环境。但架构图上"招聘子 Agent"那个方框，此刻只是一个空占位：它被指定负责招聘，可它**还不会解析一份简历、不会评一个分、不会出一张画像**。

本集要做的就是把这个方框填实：把"招聘子 Agent"从架构图上的一个名字，变成一个能跑通真实简历的子 Agent。从这一集起不再画图、不再规划，而是真正动手开发。

> **交付定位**：不是 demo 级玩具，而是有合规过滤层、有字段级真实性核对、有数字回核机制、有可视化画像、能做语义检索、能出结构化纪要的**工业级版本**。它不锁定星桥科技的岗位——换成自己业务的 JD 和简历，一样能跑。

## §1 招聘 5 能力全链路：解析 → 评分 → 画像 → 检索 → 纪要【目前需要补充的是：收发邮件的能力】

招聘子 Agent 要接手 HR 的三件苦活（筛简历、找相似的人、整理面试纪要），靠的是**五个能力串成的一条链**：


| 能力    | 一句话定义               | 输入             | 输出                    | 章节  |
| ----- | ------------------- | -------------- | --------------------- | --- |
| 简历解析  | 多格式简历统一转成结构化候选人数据   | PDF/DOCX/MD 简历 | 结构化候选人数据（对齐字段标准）      | §2  |
| 评分排序  | 候选人对照 JD 打分排序       | 结构化数据 + JD     | ranking JSON（评分 + 排序） | §3  |
| 画像生成  | 把评分结果渲染成可视化画像       | ranking JSON   | HTML 候选人画像            | §4  |
| 人才库检索 | 候选人向量化入库、按语义找相似的人   | 候选人数据          | 检索结果 + 维度级解释          | §5  |
| 面试纪要  | 面试录音转写，按发言人组织成结构化纪要 | 面试录音           | 结构化面试纪要               | §6  |




### 为什么是这个顺序：数据流定死的

- **主链（解析 → 评分 → 画像）首尾相接**：上一个能力的输出，正好是下一个能力的输入。解析出结构化数据，评分才逐字段打分；评分产出 ranking JSON（含 8 维分、综合分、排序），画像才把它渲染成可视化页面。
- **人才库检索是一条支路**：输入是简历解析产出的候选人数据，从"解析产出"这个点分叉出去，和评分排序**并列**，不接在画像后面（HTML 画像是给人看的，不可能反过来当向量检索输入）。
- **面试纪要是另一条支路**：输入是面试录音（音频），与主链的"简历"（文档）完全是两类数据，走的是另一条数据通路。



### 这条链最脆弱的地方：数据契约

能力之间一环扣一环，靠的是**数据契约**——上游输出的字段结构，必须正好是下游期望的输入结构。

> **典型例子**：评分产出的 ranking JSON 里每位候选人有一个 8 维评分对象，画像的雷达图正是读这 8 个维度画的。若某天评分把维度从 8 改成 6、又没同步画像，雷达图要么画错要么报错。**一处字段对不上，错误会沿着整条链一路传到底。**

这就是为什么 §2 不直接写代码，而是先定义 `candidate-profile-schema.md`（契约的成文形式）——**契约必须先定义、后开发**。

## §2 数据资产先行与"真实复杂度"原则

开发一个能解析简历的 Agent，第一件事不是写代码，是先确认手里有没有像样的简历。本集建立在一份提前构造好的数据资产之上：


| 资产        | 内容                                  | 数量   | 用途            |
| --------- | ----------------------------------- | ---- | ------------- |
| 简历样本库     | 技术/产品/运营/职能 4 类岗位，每类 7 份            | 28 份 | 解析、评分的真实测试输入  |
| JD 库      | 4 种公司风格（大厂/创业/央国企/外企），每种 3 份        | 12 份 | 简历对照 JD 做匹配评分 |
| 候选人画像字段标准 | `candidate-profile-schema.md`，6 组字段 | 1 份  | 解析、画像共用的字段规范  |




### 为什么必须是"真实复杂度"

如果图省事造一批"姓名/学历/技能"排得整整齐齐的简历，"简历解析"就退化成"读字典"，技术含量归零，也测不出真问题。真实 HR 面对的简历：

- **格式杂**——PDF、Word、纯文本混投（本集：7 份 PDF、7 份 DOCX、14 份 MD，模拟多渠道投递）。
- **表述乱**——同样"负责订单系统"，十个人十种写法。
- **有不规则性**——跳槽频繁、职业空窗期、跨行业转型，恰恰是评分要识别的信号。

> **反面样本设计**：每一类岗位里都藏了 1 份反面样本（如经历时间线对不上），意义是给评分环节一个真实检验——Agent 到底能不能自己把硬伤找出来。个人信息全部脱敏。



### 构造测试数据时验收过的两个坑

- **坑一 · 化名撞名**：早期 3 个候选人都叫"陈思远"，人才库检索"找像陈思远的人"时指代直接失效。**教训：测试数据里有标识作用的字段（尤其姓名）必须唯一。**
- **坑二 · 反面样本被元信息剧透**：早期法务简历开头写"注：疑似伪造院校"，等于把答案写在题面上。**教训：缺陷要藏进正文，绝不能在标题、注释这类元信息里剧透。**

## §3 核心方法论：给 Agent 加一个能力的工业四步

这是本集最核心的方法论，讲一次、后面五个能力全部复用。

### 为什么不直接写脚本：裸脚本 vs Skill


| 维度              | 裸脚本                                | Skill（工业级）                   |
| --------------- | ---------------------------------- | ---------------------------- |
| Agent 怎么知道有这个能力 | 不知道——靠人在消息里硬写 `exec python xxx.py` | 启动时预加载能力的名称与描述，Agent 自己判断何时用 |
| 何时用、怎么用         | 人来决定，每次都要交代                        | 文档里写清楚，Agent 自己读             |
| 依赖、工具需求         | 隐式，跑挂了才知道缺什么                       | 显式声明，缺失能优雅降级                 |
| 可复用、可分享         | 拷脚本、改路径，容易改漏                       | 标准目录，可装可测，可上 Skill 市场        |
| 可测试             | 没有约定                               | 有"验证加载 + 端到端测"的固定流程          |


核心区别在第一行：**裸脚本的能力 Agent 自己是不知道的**。除非有人明确告诉它"去跑这个脚本"，否则它根本不会想到用。

### Skill 是什么

Skill 是 OpenClaw 里一项能力的标准封装——本质是一个目录，核心是一份 `SKILL.md`。它靠两个机制把"一段功能代码"升级成"一个 Agent 能自己发现、自己判断何时调用的能力包"：

1. **自描述**：`SKILL.md` 写明自己叫什么、做什么、什么时候该用。OpenClaw 启动时把每个 Skill 的名称和描述预加载进 Agent 上下文。
2. **渐进式披露（progressive disclosure）**：`SKILL.md` 正文只当"目录"（简短）；详细文档拆进 `references/`，可执行脚本放进 `scripts/`。Agent 按需加载——既知道有这个能力，又不浪费上下文窗口。

> 一句话：**Skill 化 = 给每个反复使用的功能套一层"自描述 + 渐进式披露"的标准外壳**，让 Agent 能发现它、知道何时调它，而不是靠人硬编排。



### 工业四步流程（缺一不可）

1. **建 Skill**：写 `SKILL.md`，按渐进式披露把脚本放进 `scripts/`、详细文档放进 `references/`。产出"能力本身"。
2. **改核心 md 文档**：三份 persona 文档各管一段——
  - `TOOLS.md`："你手上有什么、怎么用"——加这个 Skill 的用途、调用要点。
  - `AGENTS.md`："你做什么、怎么做"——加它的调用时机、嵌进工作流的哪一步。
  - `SOUL.md`："你是谁"——人格与硬边界，若能力涉及价值观或边界补一条。
3. **改配置（如需）**：检查工具权限组、Skill 启用表（allowlist）。**即使确认"无需改动"也不能省，必须主动确认。**
4. **调用测试**：先 `skills list` 验证已加载，再用 `agent` 命令发真实任务做端到端测试——看 Skill 有没有被 Agent 自己选中、脚本有没有真跑、产出对不对。



### SKILL.md 怎么写：两个必需字段

- `name`：唯一标识，小写字母 + 数字 + 连字符。**命名用动名词形式**——`parsing-resumes`、`scoring-candidates`，不是 `resume-parser` 这种名词。
- `description`：单行、第三人称、**写给 AI 看**，说清"做什么 + 什么时候用"。这是 Agent 从几十个 Skill 里选中它的唯一依据，写得含糊 Agent 就选不准。
- 可选：`metadata.openclaw.requires.bins`——声明依赖哪些命令行二进制（如 `node`），缺失时优雅降级。

> **正文原则**：控制在 500 行以内，只写 Agent 不知道的东西；字段级细则一句话引到 `references/`，**引用只能一层深**（正文直接链到 reference，不要 reference 再套 reference）。



### 一条铁律与一个活反例

**铁律**：`SKILL.md` 必须在 Skill 目录的第一层，且带合法 YAML frontmatter（至少有 `name`）。OpenClaw 扫描规则是找 `skills/<skill-name>/SKILL.md`，第一层找不到合法 SKILL.md，整个 Skill 就不被加载。

**活反例 ·** `office-to-md-v2`：它装进了 recruitment 的 workspace，文件确实在，但 `skills list` 里根本没有它。排查发现——它第一层的 `SKILL.md` 没有 frontmatter（是给人读的说明文档），真正带合法 frontmatter 的那份嵌在 `office-to-md/` 子目录里。**扫描器在第一层找不到合法 SKILL.md，整个 Skill 被跳过——文件在，但能力等于不存在。**

### 哪些能力用现成 Skill、哪些自己写

判断标准很清楚：**"换个行业也一样要做"的通用问题优先找现成的；"只有招聘场景才这么做"的业务逻辑才自己写。**


| 能力                | 现成还是自建    | 原因                                   |
| ----------------- | --------- | ------------------------------------ |
| 简历解析（格式转换）        | 用现成 Skill | 通用文档格式转换，生态里有成熟方案                    |
| 简历解析（结构化抽取、真实性核对） | 自建        | 要对齐字段标准、逐字回溯，是业务逻辑                   |
| 评分排序              | 自建        | 8 维评分、合规过滤是招聘业务的具体逻辑(需要找HR进行落实总结出来的) |
| 画像生成              | 自建        | 七区块画像是为 HR 决策定制的                     |
| 人才库检索             | 自建为主      | 向量构造、维度级解释是业务定制逻辑                    |
| 面试纪要              | 现成 + 自建   | 转写用现成，结构化纪要的组织逻辑自建                   |


> **Skill 保存位置决定可见范围**：`<workspace>/skills/` 是单个 Agent 专属，`~/.openclaw/skills/` 是所有 Agent 共享。本课所有招聘 Skill 都装在 `workspace-recruitment/skills/`——**能力按业务边界隔离，是多 Agent 系统的基本纪律**（绩效子 Agent 不需要解析简历，简历解析就不该出现在它的 workspace 里）。

## §4 简历解析与真实性纪律（解析 + 核对）

简历解析的核心不是"把文件转成文字"，而是把文字变成**对齐 schema 的结构化候选人数据**——后续评分、画像、检索全依赖它。§2 要建两个业务 Skill：`parsing-resumes`（结构化抽取）和 `auditing-extraction`（字段真实性核对）。

### 为什么"指令约束"不够，还要"事后核对"

抽取指令里写"绝对不要编造"是必要的，但不够。**LLM 抽取结构化数据时有一种内在倾向——补全**：原文某字段缺失或模糊时，它倾向"填一个看起来合理的值"，而不是老实留空。一句"不要编造"能压低这种倾向，但压不到零。

> **指令是事前约束，核对是事后验证，两者缺一不可。** 招聘是对真实性零容忍的场景——一个被编造出来的"5 年经验"，可能让一个根本不够格的候选人进入面试。



### 两个 Skill 的分工：形状对 vs 内容真


|       | `validate_profile.js`（parsing-resumes 内置） | `auditing-extraction`（独立 Skill） |
| ----- | ----------------------------------------- | ------------------------------- |
| 管什么   | schema / 合规结构校验                           | 抽取值逐字段回溯简历原文                    |
| 怎么判   | 字段组齐不齐、红线字段在不在、派生字段自洽                     | 硬提取字段逐字符比对原文出处；软推断字段确认已标注       |
| 抓得出的错 | 缺字段、混进 age、job_count 对不上段数                | 抽取值与原文对不上、软推断字段漏标注              |
| 产出    | 通过 / 不通过                                  | 逐字段核对表 + 可追溯率                   |


> 一句话：`validate_profile.js` 保证产出"**形状对**"，`auditing-extraction` 保证产出"**内容真**"。形状对不代表内容真——一个字段组齐全的 JSON 里，照样可能藏着编造的薪资。



### 一个必须区分的核心概念：提取 vs 推断

结构化产出里的字段，本质上分两类：

- **硬提取字段**——值在原文里有明确对应（姓名、薪资、学校、起止时间）。核对标准是**逐字符匹配**，差一个字都算错。
- **软推断字段**——原文没直接写，Agent 根据上下文合理推导（如从公司名推行业 `industry`）。这类可以产出，但核对标准不同——只能判断"推断合不合理"，没法逐字符比对。

区分这两类的原因是**合规分量不同**：硬提取字段是"简历事实"可直接用于评分；软推断字段是"AI 的判断"——用它时必须知道它是推断。工程化做法是**在 schema 里把推断字段显式标注**（`industry` 必须带 `industry_inferred: true`）。

> **法律分量**：个保法第 24 条要求自动化决策可解释、候选人有权要求说明——"每个字段都能追溯到原文出处"，正是"可解释"在数据层面的落地。



### 可迁移性

"抽样 + 字段级逐字回溯原文 + 区分提取与推断"这套核对方法不只适用于简历——任何"用 LLM 从非结构化文本里抽取结构化数据"的场景（合同抽关键条款、病历抽诊断信息、财报抽财务指标）都适用。

## §5 评分 Pipeline 三层架构（合规 / 评分 / 回核）

评分看起来是 5 能力里最简单的，却是整个招聘子 Agent 里**最不能拍脑袋**的一块。它要同时解决三件互相缠在一起的事：

- **合规**——评分不能用年龄、性别、籍贯等受法律保护的特征。难点不在"知道不能用"，在"怎么向监管和候选人证明确实没用"。
- **准确**——从哪几个维度评、各维度怎么加权、怎么把"对口但不出色"和"出色但不对口"的人区分开。一个综合总分远远不够。
- **可追溯**——每一句评分理由、每一个数字都要能反查回简历原文。



### 三层架构：顺序固定，缺一层不能上线


| Pipeline 层  | 对应 Skill                     | 这一层做什么                   |
| ----------- | ---------------------------- | ------------------------ |
| 第一层 · 合规过滤  | `filtering-sensitive-fields` | 评分前**物理删除**敏感字段          |
| 第二层 · 8 维评分 | `scoring-candidates`         | 8 维度打分 + 综合分 + 硬伤识别      |
| 第三层 · 数字回核  | `auditing-numbers`           | 抽取评分文字数字、反查原简历、判定虚构、精确修正 |


三层职责互相独立、边界清晰，正好对应三个自建 Skill——**一层一个**。为什么不塞进一个 Skill？因为那等于把三件边界清晰的事重新搅成一个黑盒；一层一个更符合渐进式披露，也让每一层可独立审计。

### 为什么三层不能合并、顺序不能换

- **合规过滤必须在评分之前**：评分模型一旦在 prompt 里看到年龄和性别，合规边界就已破了。要保证它没用敏感特征，唯一办法是让它**从一开始就看不到**。
- **数字回核必须在评分之后**：它要回核的对象正是评分层产出的自由文本（亮点、顾虑、评分理由）。
- **三层各自独立才能各自审计**：剥了哪些字段、给了几分、改了哪个数字——三件事分在三层各留独立日志，出问题能精确定位。合并成一个函数就说不清是哪一环错了；招聘是要向监管解释的场景，"说不清"等于不合规。



### 第一层 · 合规过滤：设计灵魂

**核心原则一句话：不是求大模型别用敏感特征，是让它根本看不到。**

一句"请不要根据年龄、性别评分"无法被证明——你没法证明它在打分时没受影响（哪怕"潜意识"地）。业界有血的代价：iTutorGroup 直接用年龄筛选被 EEOC 起诉、36.5 万美元和解；亚马逊招聘 AI 从"women's"字样、女子学院间接学到性别歧视，整个项目下线。

正确做法是维护一份敏感字段黑名单，在数据进评分前**物理删除**。两个关键工程点：

- **拷贝一份再删**：脚本 `structuredClone` 出副本，删的是"评分输入"副本，**原始画像保留敏感字段**供 HR 做性别比例统计、年龄分布——这是"**画像要完整、评分要干净**"的分层设计。
- **递归扫所有层级 + 词干双保险**：黑名单（`FORBIDDEN_KEYS`）逐字列出，词干（`FORBIDDEN_STEMS`）做自检兜底。基线漏掉的 `education.school_tier` 藏在子层——只扫顶层会漏。
- **自检要写成"硬失败"**：用 `process.exit(1)` 而非可被优化掉的 `assert`（Python `-O` 会移除 assert，合规闸门会静默消失）。**一道会被优化抹掉的检查，等于把合规证据也抹掉。**

> **两道防线**：字段级物理删除是主；评分 prompt 里仍保留"禁止使用年龄、性别……"声明作兜底（万一敏感信息藏在 `self_evaluation` 自由文本里，字段级黑名单清不掉）。



### 第二层 · 8 维评分：为什么是 8 个维度

一个综合总分丢掉了 HR 最需要的信息——分是怎么来的。两位都拿 60 分：一位方向对口各维度中规中矩，一位某维度突出但方向不对——处置完全不同。8 维度让 ranking 可解释。

8 个维度来自 `candidate-profile-schema.md` §8：专业技能、经验匹配、逻辑能力、学习力、沟通能力、协作能力、抗压能力、价值观（各 1-5 分）。

> **关键澄清：综合分不是 8 维加权。** 综合匹配分的真实含义是评分模型对"候选人 × 岗位"整体匹配度的判断，综合了两部分：8 维能力表现 + 岗位 fit 因素（薪资期望、期望城市、经验年限错配）。这解释了张磊——8 维能力强，综合分却只有 65，落差来自岗位 fit（期望薪资 60K-75K 超预算、13 年经验 overqualified）。

`concerns` **vs** `hard_issues` **的严格边界**：`hard_issues` 只装三类——工作经历时间矛盾、学历存疑、简历自相矛盾。薪资过高、期望城市不符属于岗位匹配度问题，归 `concerns`。两者后果不同，硬伤会触发"复核简历真实性"这种更重的处置建议。

**只评分不淘汰**：建议动作只输出"建议进入面试候选名单""建议人工复核"，绝不输出"通过""淘汰"。这是个保法第 24 条 + Workday 判例的硬性要求。

### 第三层 · 数字回核：从"58 万笔/秒"事故说起

**事故现场**：张磊简历里唯一峰值数字是"12.8 万 TPS"，但某次评分产出的 `highlights` 写成了"58 万笔/秒"——差 4.5 倍。追因：这个"58 万笔/秒"真实存在于**后端 JD 的岗位职责**里，大模型生成自由文本时把 JD 的数字张冠李戴安到了候选人头上。这叫**上下文串台（上下文污染）**：两份相关文档同时在上下文里，大模型复述其中一份时会把另一份的细节混进来。

回核层工作分三步，性质各不同：

1. **抽取（extract）· 确定性**：正则扫评分文字里所有"数字 + 单位"（TPS/QPS/万/亿/%/年/人/倍/ms）。**必须确定性——LLM 临场抽只抽出 11 个，正则扫出 26 个，漏的里可能正藏着串台。**
2. **比对（verify）· 确定性**：归一化（去空白）后子串匹配。三态：命中 / 查不到 / 数字对上但单位存疑。
3. **判定（adjudicate）· 非确定性**：简历里对不上的数字交大模型判是否真虚构（排除约数、职级代号、JD 要求、合理换算）。

> **核心设计骨架：确定性的步骤交脚本，判断的步骤交大模型。** 抽取/比对是机械的用正则，"算不算虚构"需要语义理解才交大模型。

**三条铁规则**：

- **基准只能是候选人原简历，绝不能用 JD**——JD 恰恰是串台的来源，把 JD 当基准等于让串台的源头给串台背书。工程落地：脚本 CLI 签名**只留两个数据参数（评分结果 + 简历），不留 JD 参数位**——从机制上让它无法被违反，比在 prompt 里写十遍"不要用 JD"都强。
- **非确定性步骤失败要显式报错**：判定步多次重试仍失败就退出码 1，绝不把"判定没拿到"静默当"无虚构"放行。"没核成"和"核过了没问题"是两种状态，混了比不核更危险。
- **必须每次评分都跑**：大模型串台是非确定性的（演示那次串台 2 处，批量重评 0 处）——你没法预测下次会不会串。靠回核层兜底才能保证交到 HR 手里的每个数字都是真的。

> **业界对位**：这个思路业界叫 grounding verification（接地核验），学术上有 CoVe（Chain-of-Verification）框架。迁移到自己场景只需换原始数据源（财报原文、会议转写、产品规格表）。**任何引用原始数据的大模型产出都可能串台，加一道以原始数据为基准的数字回核应是常态，不是可选项。**



#### 白话解读（便于理解）

上面是完整的技术叙述，下面用更直白的语言把同一层再讲一遍。

**这一层在防什么？**

第二层（8 维评分）会产出带数字的自由文本——亮点、顾虑、评分理由里常有「12.8 万 TPS」「58 万笔/秒」「5 年经验」等。大模型同时读了**简历**和 **JD**，写评语时可能把 JD 里的数字当成候选人的，这叫**上下文串台**。张磊的例子：简历写的是 12.8 万 TPS，AI 亮点却写 58 万笔/秒——58 万来自 JD 岗位要求，不是张磊简历里的，差 4.5 倍。HR 若据此决策就错了。

第三层只做一件事：**把评分文字里的每个数字，逐条核对「简历里有没有」。**

**三步怎么走？（用张磊的例子）**

假设 AI 写了：「候选人曾负责 58 万笔/秒的系统优化……」


| 步骤     | 做什么                 | 谁来做       | 为什么                                               |
| ------ | ------------------- | --------- | ------------------------------------------------- |
| 1 · 抽取 | 从评分文字里找出所有「数字 + 单位」 | 脚本（正则）    | 机械活，要稳定、不漏。LLM 临场抽只找到 11 个，正则扫出 26 个——漏掉的里可能正藏着串台 |
| 2 · 比对 | 每个数字去**简历原文**里找     | 脚本（字符串匹配） | 在简历里能找到 → 通过；找不到 → 可疑；数字对但单位怪 → 存疑                |
| 3 · 判定 | 对「找不到」的数字，判断是否真编造   | 大模型       | 有些不是编造：约数（「5 年左右」）、职级代号、合理换算。需要语义理解               |


**设计原则**：能算准的交给脚本，需要「懂意思」的才交给大模型。

对「58 万笔/秒」：比对会在简历里找不到 → 进入判定 → 判为串台/虚构 → 报告或修正。

**三条铁规则，各一句话**

1. **只拿简历当标准，不用 JD**——JD 正是串台来源。工程上：回核脚本只收「评分结果 + 简历」两个参数，接口里不留 JD 位置，从机制上杜绝误用。
2. **核失败了要报错，不能静默放行**——「没核成」和「核过了没问题」是两回事。判定失败却当「无问题」放行，比不核更危险。
3. **每次评分都要跑**——串台是随机的，同一份简历这次串 2 处、重跑可能 0 处。无法预测，只能每次都兜底。

**和前后两层的关系**

```
简历 + JD
    ↓
[第一层] 删掉敏感字段（年龄、性别等）→ 评分模型看不到
    ↓
[第二层] AI 打分 + 写亮点/顾虑（可能串台）
    ↓
[第三层] 把第二层文字里的数字，逐条对简历  ← 本节
```

第三层**必须在第二层之后**，因为核的是第二层产出的文字。

> **一句话总结**：AI 写评语时会把 JD 的数字误写成候选人的；第三层用脚本把数字全捞出来、跟简历对一遍，对不上的再让 AI 判断是否真编造——且永远只信简历，不信 JD。

## §6 HTML 画像的可视化设计哲学

评分产出是结构化 JSON，但 **HR 看不懂 JSON，也不会去看**。画像把 JSON 变成一张图文并茂的 HTML 页面。七区块：基本信息卡、综合评级横幅、8 维能力雷达图、与 JD 匹配度对比、工作经历时间线、技能词云、亮点/顾虑/硬伤三栏。

> **每个区块对应一个 HR 决策**——不是凑数：信息卡回答"这是谁、要多少钱"、评级横幅回答"该不该面"、雷达图回答"能力结构对不对口"、时间线回答"职业路径稳不稳"。**画像本身不产生任何新数据，它是评分结果的可视化。**



### 三个关键设计决策

**决策一 · 能力用 8 维雷达图，不用一个总分。** 一个总分把能力结构全压平了。雷达图看轮廓就有整体印象：全面型还是偏科型。两点要讲准——所有画像用**同一套固定维度轴序**（轮廓才能横向比）；雷达图给整体轮廓、旁边的维度分条给精确数值，**两者互补**。

**决策二 · 工作经历用竖向时间线，不用履历表。** 履历表看不出"职业路径的形状"。时间线一眼看出稳步上升、频繁跳槽、有无空窗期——这正是初筛要判断的职业稳定性。

**决策三 · 技能用词云，不用熟练度条形图——被真实数据逼出来的。** 第一版设计的是按"精通/熟练/了解"着色的技能条形图，但跑出来张磊 33 项技能全是浅色——因为 ranking JSON 里技能字段是纯技能名，没有熟练度标注，脚本只能"猜"，而猜就是编造。处理办法不是去别处拼凑数据，而是**改图表形式去适配真实数据**：改成词云，字号只编码"技能在简历里被列出的先后顺序"——这个信号真实存在、不需要脚本猜。

> **决策三背后的原则（与全集真实性纪律一脉相承）**：做可视化，**图表形式必须迁就真实数据的粒度，不能为了"图好看"去编造数据里没有的维度**。可视化越精美，越不能让它成为编造数据的入口。



### 画像特有的第三道合规闸

敏感字段在招聘数据流里有**三层处置**：数据资产照常记录 → 评分前物理剥离 → **画像绝不渲染**。

画像比评分更下游——它是给用人方直接看的展示页。一旦信息卡渲染出"性别 男""年龄 38"，看画像的人会不自觉当成筛选依据，构成就业歧视风险。这一环的合规风险和评分环节不同（评分怕影响打分，画像怕被当筛选依据），所以画像校验器必须有一道前两个 Skill 都没有的检查——扫产出 HTML 有没有渲染合规红线字段。

> **原则**：**合规边界要随"数据流到了哪个环节"重新评估。** 数据资产里允许记录的字段，到展示性产出未必能渲染——每个环节的合规闸要单独设。



### 工程取舍

- 图表用 matplotlib 渲染成图片、base64 内嵌进 HTML——画像是**单文件自包含**，不联网、不依赖外部资源也能打开（代价：约 150-200KB）。备选：matplotlib 输出 SVG 内联，无损放大、打印不糊。
- **诚实标出已知简化**：技能词云只反映"列出顺序"，不反映熟练度——因为数据源就没有。**画像能呈现的，永远不会超过它拿到的数据。**

## §7 人才库语义检索的选型与可解释设计

"再找几个像张磊的"——这是 HR 用关键词搜索几乎做不到的事。关键词搜索的本质是"找字面一样的"，看不懂"Java 后端"和"大数据开发"在语义上是近亲。语义检索先把每份简历压缩成向量，判断两个人像不像看向量在数学空间里离得近不近——**哪怕一个词都不重合**。

这个能力由三部分组成，封装成一条流水线的三个 Skill：

- `ingesting-talent-pool`——入库能力，把候选人简历向量化建库。
- `searching-talent-pool`——检索能力，按语义相似度捞 Top N。
- `explaining-similarity`——解释能力，把检索结果翻译成"为什么像"。



### 选型：从"零假设"开始，三个现成方案都不直接用

**实操铁律：资料里给的方案名不能照抄，必须自己 search 实测。** 实测三个候选：

- `fastio` Skill——两层坑：真实 slug 是 `fast-io`（名字坑）；就算找到，它是给 Agent 团队做文件工作区管理的，**没有 embedding、没有相似度检索**（工具误用）。**教训：不光方案的名字要实测，方案"适不适用"也要实测。**
- `@openclaw/memory-lancedb`——官方插件，真能做向量检索。
- 内置 `memory-core`——SQLite + sqlite-vec + FTS5，支持向量 + 关键词混合检索。

**最终选择：三个现成方案都不直接采用，核心逻辑自己手写**（把简历向量化存成本地 JSON `talent-pool.json`，检索时读进内存逐一算相似度）。三个理由：

1. **数据粒度匹配**：现成方案把"一条记忆当一个整体文本块存"，检索只能给整体分数，没法拆到维度。手写能控制"简历的哪些字段、按什么方式拼成向量化文本"——这是"维度级解释"能成立的前提。
2. **embedding 国内适配**：memory-lancedb 默认走 OpenAI/本地 Ollama，国内受限；手写能精确指定通义 text-embedding-v3（走 DashScope）。
3. **可解释 vs 能跑**（最关键）：现成插件解决"能跑"，手写解决"可解释"。HR 拿到"像张磊的 Top 5"一定追问"凭什么说像"——不透明的现成记忆块答不出来。

> **同一个逻辑**：凡是涉及"必须对业务方解释清楚"的环节，现成方案负责打底，关键逻辑自己写。（与 §3 评分、§5 检索一脉相承。）



### 4 维度向量设计：让"为什么像"答得出来

**每个候选人入库时不存 1 个向量，存 5 个**——1 个整体向量 + 4 个维度向量（教育、经历、技能、行业）。

如果只存 1 个整体向量，检索结果只能给 HR 一个黑盒分数"0.67"——是教育像还是经历像？HR 一无所知。存 5 个后，检索能用整体向量算"综合像不像"，同时用 4 个维度向量分别算"哪个维度像"，结果变成"这个人主要是经历和技能像张磊，教育差一些"。

> **一句话记住本质**：**整体向量回答"像不像"，维度向量回答"哪儿像"。** 整体向量是单独 embed 一段完整摘要文本得到，不是 4 个维度向量求平均（求平均会丢掉字段之间的关联）。



### 检索与解释的真实性纪律：算分与说人话分离

- **检索**：相似度排名必须是**真实余弦算出来的，不能让大模型凭印象排**（这是 §3 评分"数字串台"坑的翻版——大模型一碰数字就可能出错，排错了 HR 会照着联系候选人）。
- **解释**：解释这一步必然要用大模型，但**必须把大模型挡在"算数字"之外**。分数由检索 Skill 用余弦算死、原样传入，大模型只组织语言。

> **架构级做法**：防"数字串台"不靠 prompt 多叮嘱几句"别改数字"，而靠脚本把"确定性的算分"和"非确定性的说人话"在架构上**彻底切开**——大模型在解释这一步根本拿不到"重新算分"的权限。**算分是裁判的事，解释是解说员的事——裁判和解说员不能是同一个人。**

**关键词 vs 向量 vs 混合**：结论不是"向量全面取代关键词"。生产环境推荐混合策略——向量做粗排（语义找相似），关键词做精筛（学历、年限、城市等硬条件）。"再来一个像张磊的"靠向量，"这批人里只要 985 硕士"靠关键词。

#### 白话解读（便于理解）

上面是完整的技术叙述，下面用更直白的语言把同一节再讲一遍。

**这一节在解决什么问题？**

HR 说「再找几个像张磊的」——关键词搜索做不到：搜「Java 后端」找不到写「大数据开发」的人，但 HR 知道这两个人经历很像。**语义检索**换了一种思路：把每份简历变成一串数字（向量），意思相近的简历数字也相近；问「谁像张磊？」就是算张磊的向量和库里每个人的向量有多近——**哪怕一个词都不重合**，只要意思像也能找出来。

**三个 Skill：一条流水线**


| Skill                   | 干什么              | 类比        |
| ----------------------- | ---------------- | --------- |
| `ingesting-talent-pool` | 入库：把简历变成向量，存进人才库 | 把书编目放进图书馆 |
| `searching-talent-pool` | 检索：按相似度捞出 Top N  | 按主题找相似的书  |
| `explaining-similarity` | 解释：告诉 HR「为什么像」   | 管理员说明推荐理由 |


顺序固定：**先入库 → 再检索 → 再解释**。

**为什么三个现成方案都没直接用？**

文档测了三个，结论是：**能跑 ≠ 能满足 HR 业务**。


| 方案                         | 问题                                       |
| -------------------------- | ---------------------------------------- |
| `fastio`（实际叫 `fast-io`）    | 名字容易搞错；本质是文件管理，**没有 embedding/检索**       |
| `@openclaw/memory-lancedb` | 真能做向量检索，但国内 embedding 走 OpenAI/Ollama，受限 |
| 内置 `memory-core`           | 也能跑，但把简历当成「一整块记忆」存                       |


**最终选择：核心逻辑自己写**（向量存本地 `talent-pool.json`，检索时算相似度）。三个理由，按重要性：

1. **可解释（最关键）**——现成方案只能给 HR 一个分数「0.67 像张磊」，**凭什么像？教育像还是经历像？** 答不出来。HR 一定会追问。
2. **数据粒度**——手写能控制简历哪些字段、怎么拼成向量化文本。这是后面「分维度解释」的前提。
3. **国内可用**——手写可以指定通义 text-embedding-v3（DashScope），不依赖 OpenAI。

> 和 §5 数字回核同一逻辑：**业务方要解释清楚的地方，关键逻辑自己写；现成方案最多打底。**

**5 个向量：「像不像」和「哪儿像」**

如果只存 1 个整体向量，检索结果只能是「李四，相似度 0.67」——HR 问「哪里像？」答不了，是黑盒。

所以每人存 **5 个向量**：

```
张磊入库时：
├── 1 个整体向量  → 回答「综合像不像」
└── 4 个维度向量  → 回答「哪儿像」
    ├── 教育
    ├── 经历
    ├── 技能
    └── 行业
```

检索结果可以变成：「王五综合像张磊（0.72），主要是**经历和技能**像，**教育**差一些。」

**注意**：整体向量是单独 embed 一段完整摘要得到的，**不是**把 4 个维度向量求平均——求平均会丢掉字段之间的关联（比如「某段经历 + 某技能」的组合含义）。

**算分 vs 说人话：必须分开**

这和 §5「数字回核」是同一类问题——**大模型一碰数字就容易出错**。


| 环节      | 谁做  | 做什么                      |
| ------- | --- | ------------------------ |
| 检索（算分）  | 脚本  | 用余弦相似度算出真实分数、排出 Top N    |
| 解释（说人话） | 大模型 | 把脚本算好的分数**原样传入**，只负责组织语言 |


不能让大模型凭印象排相似度——排错了 HR 会照着去联系候选人。

> **算分是裁判的事，解释是解说员的事——裁判和解说员不能是同一个人。** 大模型在解释这一步拿不到重新算分的权限，只能在脚本给的数字基础上写说明。

**关键词 vs 向量：不是二选一**


| 场景                    | 用什么        |
| --------------------- | ---------- |
| 「再来几个像张磊的」            | 向量（语义相似）   |
| 「这批人里只要 985 硕士、5 年以上」 | 关键词（硬条件过滤） |


生产环境推荐**混合**：向量粗排找语义相似的人，关键词精筛学历、年限、城市等硬性条件。

**和 §5 的关系**

```
§5 评分 Pipeline          §7 人才库检索
─────────────────        ─────────────────
合规过滤                  入库（向量化）
    ↓                         ↓
8 维评分                  语义检索（脚本算分）
    ↓                         ↓
数字回核                  解释相似度（大模型说人话）
（脚本核对数字）           （大模型不能改分数）
```

共同纪律：**确定性的事交给脚本，需要语义理解的事才交给大模型；且两者在架构上切开，不能混。**

> **一句话总结**：HR 要「找像张磊的人」并知道「凭什么像」——关键词做不到语义匹配，现成插件给不了维度级解释，所以手写向量库；每人存 5 个向量分别回答「像不像」和「哪儿像」；分数由脚本算死，大模型只负责把数字翻译成 HR 能懂的话。

## §8 面试纪要的选型取舍与真实性纪律

面试纪要是第五个能力，输入不是文字而是**一段音频**。它把面试录音自动变成一份按发言人组织、带 AI 评分建议的结构化纪要，由三段串成：ASR 转写 + 说话人分离 → LLM 结构化纪要 + 数字回核。

### 为什么不直接用飞书妙记

飞书妙记这类工具确实好用，但本课要的是能**嵌进招聘子 Agent** 的纪要能力，有三点是现成工具给不了的：① 它是黑盒——纪要怎么生成不可控，没法接进自己的招聘链路；② 录音和转写都要上云——候选人的面试隐私数据出了本地；③ 它不做数字回核——候选人口述的 TPS、降幅不会反查简历。本课这套是**自己的、可嵌入、本地闭环、带数字回核**的纪要能力。

### 选型：零假设、实测为准——两处"标准答案"国内不可用


| 选型点        | 方案                                 | 国内可用 | 认证                                       | 取舍                                          |
| --------- | ---------------------------------- | ---- | ---------------------------------------- | ------------------------------------------- |
| TTS       | 云端 provider（openai 等 14 个）             | 超时   | 需云端 Key                                  | 不选                                          |
| TTS       | tts-local-cli + macOS say          | 无    | 无                                        | 选用——本地命令、零外网                                 |
| ASR (单)    | OpenClaw 内置 11 个 provider             | 超时   | 需云端 Key                                  | 不选                                          |
| ASR (单)    | faster-whisper（本地）                   | 无    | 无                                        | 降级——TTS 双音色勉强能跑，真实面试分段与说话人都分得不够好              |
| 说话人分离      | WhisperX / pyannote-audio（业界标准）        | 受阻   | 需 HuggingFace token + 接受协议                 | 不选——认证墙                                     |
| 说话人分离      | 基频阈值分离                               | 无    | 无                                        | 演示专用——TTS 双峰勉强可分，真实面试多人/口音相近时直接失效                 |
| **ASR + 说话人分离** | **FunASR (Paraformer-zh) + CAM++（CAM++=ModelScope/speech_campplus_sv_zh-cn_16k-common）** | **无** | **无（开源 MIT、ModelScope 国内直下载，连 HuggingFace token 都不用）** | **选用**——一次推理同时输出字幕 + 说话人标签，免认证、CPU RTF 0.131 (7.6× 实时), GPU RTF 0.031 (32.6× 实时), 显存 1.70 GB |


**说话人分离 / ASR 一体化的诚实工程取舍**：pyannote 有一道认证墙（需 HuggingFace token + 接受协议 + 国内下载受阻），这正是"遇到说话人分离绕路就放弃"的常见卡点。第一版用**基频（F0）阈值分离**硬扛过去——靠 TTS 双音色"双峰可分"（女面试官 220-246Hz vs 男候选人 110-122Hz 降基频）。能跑通演示，但只对两人音高差异明显、轮次均衡的合成录音有效，真实面试多人 / 口音相近时直接失效。

第二版改用 **FunASR (Paraformer-zh) + CAM++**：ModelScope 上的开源 MIT 模型，**没有 HuggingFace 那道认证墙**，国内直下载、零 token；CAM++（`speech_campplus_sv_zh-cn_16k-common`，28 MB）用 speaker embedding + 凝聚聚类，**自动判断"几个人、谁是谁"**，不再是固定二分；并且 ASR + 说话人分离**两步合成一步**，一次推理同输出字幕与说话人标签。详细实测见 §8.1。

> **术语要说准 · 基频聚类**：本课"基频聚类"如果还在用（演示 / TTS 录音专用），要清楚它是**最简实现**——固定用中位数做阈值二分，不是真正会自动寻找两簇边界的聚类算法。"26 段分成 13/13"是**中位数二分的数学必然，不是"分对了"的证据**。
>
> **术语要说准 · FunASR + CAM++**：`speech_campplus_sv_zh-cn_16k-common` 不是固定二分的算法。说话人 embedding（192 维）算出来后，用凝聚聚类按余弦相似度自动决定"几个人、谁是谁"，多人场景也不需要改任何参数；模型 28 MB、单次推理 < 100 ms。

### §8.1 FunASR + CAM++ 实测验证（playground/1.step_6_arc）

FunASR 一体化方案已在 `hr_claw_hub/playground/2.step_B_recruitment/playground/1.step_6_arc/` 端到端跑通——同一条 wav (`transcripts/interview-zhanglei-tech2.wav`, 282.84 s, 16 kHz 单声道) 重跑三遍，结果稳定可重现。

| 段数                          | 105                                  | 105                                    |

| RTF                          | 0.131                                | **0.0307**                             |

#### §8.1.2 自动化与可复现

- 设备自动检测：`scripts/transcribe_funasr.py --device auto` 默认走 `torch.cuda.is_available()`，有 NVIDIA 卡用 `cuda:0`，否则 `cpu`；不强制改代码。

### 纪要的真实性纪律

`gen-minutes.py` 做三件事：① 确定性地按说话人重组转写稿；② 调 DeepSeek V4 生成结构化 JSON；③ 数字回核。

**prompt 的关键设计**——数字回核那条写"**你不要判断真假，只负责提取**"：这是从 §3.5 评分事故学到的纪律——LLM 复述原始数据会串台，所以不让 LLM 自己判断复述的数字对不对。LLM 负责"看见数字"，代码负责"核对数字"（把口述数字对照原简历，是子集则可追溯、否则标"需人工核实"）。

> **两个边界**：① 本集录音是 TTS 构造的（真实面试涉及隐私），生产环境直接换真实录音、后面链路一行不改；② 纪要里的"评分建议"是建议不是决定，末尾带合规声明。
>
> **ASR 误识可容忍**：small 模型会把"张磊"听成"张蕾"、"80 万行"听成"80 万型"——下游 LLM 整理纪要时会从上下文把大部分错字纠回来。



#### 白话解读（便于理解）

上面是完整的技术叙述，下面用更直白的语言把同一节再讲一遍。

**这一节在解决什么问题？**

前四个能力处理的是**文字**（简历、JD）。面试纪要是第五个能力，输入是**一段音频**——面试录音。目标：自动变成一份结构化纪要——谁说了什么、关键数字是什么、AI 评分建议是什么。

整条链路分两段：

```
面试录音（音频）
    ↓
[第一段] ASR 转写 + 说话人分离  →  带标注的逐字稿（面试官/候选人各说了什么）
    ↓
[第二段] LLM 结构化纪要 + 数字回核  →  结构化 JSON 纪要
```

**为什么不直接用飞书妙记？**

飞书妙记好用，但本课要的是**能嵌进招聘子 Agent** 的能力，现成工具有三处给不了：


| 问题   | 飞书妙记                    | 本课方案             |
| ---- | ----------------------- | ---------------- |
| 可控性  | 黑盒，纪要怎么生成不可控，接不进自己的招聘链路 | 自己的脚本，每一步可审计     |
| 隐私   | 录音和转写都要上云               | 本地闭环，数据不出机器      |
| 数字可信 | 不做数字回核，口述的 TPS、降幅不会反查简历 | 带数字回核（和 §5 同一纪律） |


**选型：三个环节各选什么？**

本课用 TTS **造**模拟录音做演示（真实面试涉及隐私），所以选型表里有 TTS 一行。生产环境换成真实录音，后面链路一行不改。


| 环节         | 不选什么                       | 为什么                                | 选什么                                                       |
| ---------- | -------------------------- | ---------------------------------- | -------------------------------------------------------- |
| TTS（造录音）   | 云端 14 个 provider           | 国内超时、需 Key                         | `tts-local-cli` + macOS say，本地零外网                          |
| ASR + 说话人分离 | WhisperX / pyannote（业界标准） | HuggingFace token + 协议 + 国内下载受阻     | **不选**                                                     |
| ASR + 说话人分离 | faster-whisper + 基频阈值分离   | TTS 双音色下勉强能用，真实面试多人/口音相近时直接失效     | **降级演示专用**                                                 |
| ASR + 说话人分离 | (无)                       | (无)                                | **FunASR (Paraformer-zh) + CAM++**——一次推理同时出字幕 + `speaker_A/B` 标签，免认证，CPU 7.6× 实时, GPU 32.6× 实时 |


**ASR + 说话人分离：第二版为什么换 FunASR**

第一版用**基频阈值分离**硬扛过去，但只对两人音高差异明显、轮次均衡的合成录音有效。真实面试多人 / 口音相近的场景直接失效。

第二版用 **FunASR + CAM++**，关键差别：
- **绕过认证墙**：FunASR 是 ModelScope 上的 MIT 开源模型，国内直下载，**连 HuggingFace token 都不用**。
- **一步到位**：CAM++ 用说话人 embedding（192 维）+ 凝聚聚类，**自动判断"几个人、谁是谁"**——多人场景也不用预设。
- **中文专属**：Paraformer-zh + CAM++ 都针对中文优化，比 whisper 派生的英文侧模型在中文场景稳定得多。
- **可量化**：同一条 wav 跑过三遍 (v1/v2/v3)，105 段数、文本逐字、说话人分配全部 100% 一致；GPU 比 CPU 快 4.27×，显存仅 1.70 GB。

数据见 §8.1 + `1.step_6_arc/reports/cpu-vs-gpu.md`。

`gen-minutes.py` **做三件事**


| 步骤        | 谁做      | 做什么                         |
| --------- | ------- | --------------------------- |
| 1 · 重组转写稿 | 脚本（确定性） | 按说话人标签把 ASR 片段拼成「面试官/候选人」对话 |
| 2 · 结构化纪要 | 大模型     | 把对话整理成结构化 JSON（亮点、顾虑、评分建议等） |
| 3 · 数字回核  | 脚本（确定性） | 把纪要里的数字对照原简历核对              |


**真实性纪律：和 §5 同一套路**

§5 评分事故教训：**大模型复述数字会串台**。纪要里同样不能让 LLM 自己判断数字真假。


| 角色  | 负责什么                                            |
| --- | ----------------------------------------------- |
| 大模型 | **看见数字**——从转写稿里提取口述的数字（prompt 写「你不要判断真假，只负责提取」） |
| 脚本  | **核对数字**——对照原简历，能对上 → 可追溯；对不上 → 标「需人工核实」        |


> **LLM 负责「看见」，代码负责「核对」**——和 §5 数字回核「脚本算分、大模型说人话」是同一架构纪律。

**两个边界 + ASR 容错**

1. **演示 vs 生产**：本集录音是 TTS 构造的；生产环境换真实录音，后面链路不改。
2. **评分建议 ≠ 决定**：纪要里的 AI 评分建议是建议不是录用决定，末尾带合规声明。
3. **ASR 误识可容忍**：small 模型会把「张磊」听成「张蕾」、「80 万行」听成「80 万型」——下游 LLM 整理纪要时会从上下文纠回大部分错字，不必在 ASR 层追求 100% 准确。

**和 §5、§7 的关系**

```
§5 评分文字里的数字  →  脚本核对 vs 简历
§7 检索相似度分数    →  脚本算分，大模型只解释
§8 纪要口述的数字    →  大模型提取，脚本核对 vs 简历
```

共同纪律：**数字相关的「算/核」交给脚本，大模型只做它擅长的事（理解、组织语言、提取），且在架构上切开权限。**

> **一句话总结**：面试纪要 = 本地 ASR 转写（FunASR + CAM++ 一次推理同时出字幕 + 说话人标签）+ LLM 结构化 + 数字回核；不直接用飞书妙记是因为要可控、本地、可核对；选型上 pyannote 因 HuggingFace 认证墙改走 FunASR（ModelScope + MIT），基频阈值分离仅作 TTS 演示降级；数字真假仍靠脚本核对简历，不让大模型自己判。

## §9 端到端串联：把五能力变成一个数字员工

前面五个能力是一个一个开发、一个一个验收的。端到端把它们放进一个真实工作日跑一遍——对应 HR 的周一三件事：批量筛简历 + 候选人画像（§2/§3/§4）、找"像张磊的"人（§5）、整理面试纪要（§6）。

把五能力串成端到端业务链路，**关键不是把脚本堆在一起跑，而是能力之间的数据契约要稳**——解析的输出正好是评分的输入，评分的输出正好是画像的输入。一处契约对不上，整条链路就断。

### 提炼成可复用方法：四件事

1. **数据流契约**：能力之间靠稳定的数据格式衔接（解析→结构化字段、评分→ranking JSON、画像消费 ranking JSON）。契约稳，能力才能接力。
2. **能力接力**：每个能力只做自己那一段，不越界（解析不评分、评分不画像、检索不算分只解释）。职责清晰，单点能力才能独立开发、独立验收，最后才串得起来。
3. **数字可追溯**：链路里每一处 LLM 引用原始数据的地方，都挂一道数字回核。
4. **合规边界落实**：评分给建议不做淘汰、检索给排名不做录用、纪要给评分建议不做定级——AI 的边界落到每个能力的产出物里。

> **这四条不只属于招聘子 Agent。** 换一个业务做数字员工（AI 客服、AI 财务助理），把单点能力开发清楚、用稳定契约串起来、在引用数据处挂回核、把合规边界落到产出物——方法一字不改。**这是本集真正要交付的东西：不是"招聘子 Agent 能筛简历"，而是一套把若干能力串成一个可上线数字员工的工程方法。**



### 诚实的局限

- **这一天没做完的事**：面试调度（接飞书日历）、候选人 7×24 答疑（接飞书机器人）——它们的核心价值依赖真实外部入口，留到 Lesson 3 接入飞书后再做。**不假装做了没做的事，这本身也是工业级该有的态度。**

## §10 合规红线的工业级落实总览



### 一条底层原则

**AI 只评分排序，最终淘汰由人工。** 这有明确法律依据：个保法第 24 条（自动化决策对个人有重大影响时，个人有权要求说明、有权拒绝仅由算法做出的决定）、GDPR 第 22 条、EU AI Act（招聘 AI 列为高风险、强制人工监督）。血的判例：Workday Mobley 集体诉讼——约 11 亿份申请被招聘软件拒绝，核心争议是"AI 自动拒绝、无人工复核"。

### 为什么"知道要 HiTL"还不够

很多教程讲到"要 Human-in-the-Loop"就停了——但"要 HiTL"是一句态度，不是落实。**落实意味着这条红线要拆成具体工程措施，每个措施落在代码或产出物的某个看得见的位置。** 本集拆成 5 处：


| #   | 落实措施             | 落在哪里                               | 防住什么                         |
| --- | ---------------- | ---------------------------------- | ---------------------------- |
| 1   | 合规过滤层（§3.3）      | 送 LLM 评分前剥掉年龄/性别/婚育/户籍/民族/健康/院校层次等 | 用受保护特征评分；亚马逊、iTutorGroup 同类坑 |
| 2   | 评分只给建议（§3.4）     | 建议动作字段只输出"建议进入面试/人工复核"，不输出"通过/淘汰"  | AI 替人做录用/淘汰的最终决定             |
| 3   | 反面样本标硬伤不淘汰（§3.4） | 识别经历时间矛盾标"硬伤"提示人工核实，不自动判负          | AI 凭一处疑点直接淘汰候选人              |
| 4   | 画像定位为辅助材料（§4.2）  | 七区块画像是辅助决策的可视化，是"建议而非决断"           | 把 AI 画像当成淘汰判决书               |
| 5   | 数字回核（§3.5）       | LLM 产出里每个数字反查原始数据，串台即报告            | 决策依据不可追溯、HR 拿错数字做判断          |


**串起来看**：合规过滤层保证 AI 不看不该看的特征；评分建议 + 硬伤不淘汰保证 AI 不做不该做的决定；画像辅助定位保证 AI 的产出不被当判决；数字回核保证每个数字可追溯。**不看、不做、不被误用、可追溯**——这就是"AI 只评分排序、最终淘汰由人工"在代码层面的全部含义。

### 诚实的局限：合规边界会变

本集 5 处落实基于 2026 年法律环境（个保法第 24 条、算法推荐管理规定、个人信息保护合规审计管理办法；EU AI Act 分阶段生效；纽约市 Local Law 144 强制年度偏见审计）。**本集教的不是"一次写好永远合规"的代码，而是一种把合规红线工程化落实的方法**——法律变了，敏感字段清单、审计要求都可能要调，但"把红线拆成可落地的工程措施、每个措施落在看得见的位置"这个方法不变。

> **做 HR AI，合规不是写完代码再补的附录，是从第一行评分逻辑就要在场的约束。**

## 附录 A：贯穿全集的 8 条工程纪律

这些纪律在多个能力里反复出现，是本集最该带走的通用方法：

1. **契约先定义、后开发**——schema 定下来，五个能力才有共同的"接口规范"可对齐。
2. **确定性规则写进 SKILL.md 正文、并交给脚本强制把关**——正文是 Agent 一定会读的，reference 按需加载可能不读；脚本是"裁判"，比"提示 Agent 照做"可靠得多。
3. **脚本先单独跑、再接 Agent**——隔离变量，后面出问题能锁定在 Agent 一侧还是脚本一侧。
4. **建完 Skill 立即** `skills info` **验证被识别**——`office-to-md-v2` 就栽在"装了但没被加载"。
5. **验证 Agent 真做事**：显式声明前置状态（"文件不存在、不要假设") + 要求贴回可核验产物（脚本输出）——Agent 会幻觉"已做过"而偷懒。
6. **相似 Skill 并存时，**`description` **要写清区别 / 在流水线的位置**——Agent 靠 description 选 Skill，含糊就会混用；流水线型还要写"我是第几环、上下游是谁"。
7. **铁规则靠机制钉死，不靠 prompt 叮嘱**——合规靠物理删除、基准靠脚本签名不留参数位，比在 prompt 写十遍都强。
8. **persona 文档不是无限容器**——`AGENTS.md` 有 12000 字符注入上限（超出静默截断），能力加多了要给默认样板做减法；核验超限以 OpenClaw 运行时 truncating 日志为准，不看本地 `len()`。



#### 白话解读（便于理解）

上面是 8 条工程纪律的浓缩版，下面逐条用大白话讲清楚「什么意思、为什么、怎么做」。

**1 · 契约先定义、后开发**

五个能力像流水线接力：解析 → 评分 → 画像 → 检索 → 纪要。上游输出必须是下游期望的输入格式，否则链路断。

- **做法**：先定 `candidate-profile-schema.md` 这类 schema，再写各 Skill。
- **类比**：盖楼先画图纸，再砌砖——没有统一接口规范，五个能力各说各话。

**2 · 确定性规则写进 SKILL.md 正文，并交给脚本强制把关**

Agent 读文档有「渐进式披露」：`SKILL.md` 正文一定会读，`references/` 按需加载可能不读。

- **铁规则放正文**：Agent 必须遵守的，写在正文里。
- **铁规则交脚本**：能算准、能判定的，写进脚本强制执行——脚本是「裁判」，比 prompt 里写「请照做」可靠得多。
- **例子**：合规过滤不靠 prompt 说「别用年龄评分」，而是脚本物理删除敏感字段。

**3 · 脚本先单独跑，再接 Agent**

开发一个新能力时，先命令行跑通脚本，再让 Agent 调它。

- **为什么**：出问题能快速定位——是脚本 bug，还是 Agent 没选对 Skill、没传对参数。
- **类比**：先单独测试每个零件，再组装整机。

**4 · 建完 Skill 立即** `skills info` **验证被识别**

文件放进 `skills/` 目录 ≠ Agent 能用到。OpenClaw 扫描规则很严：第一层必须有带合法 frontmatter 的 `SKILL.md`。

- **活反例**：`office-to-md-v2` 文件在，但 `skills list` 里没有——第一层 SKILL.md 缺 frontmatter，整个 Skill 被跳过。
- **做法**：建完立刻跑 `skills info <name>`，确认已被加载。

**5 · 验证 Agent 真做事**

Agent 可能「幻觉」——说已经跑过了，其实没跑。

- **做法**：测试时显式声明前置状态（「文件不存在，不要假设」）+ 要求贴回可核验产物（脚本 stdout、输出文件路径）。
- **目的**：逼 Agent 拿出证据，不能空口说「已完成」。

**6 · 相似 Skill 并存时，**`description` **要写清区别**

Agent 靠 `description` 选 Skill。多个 Skill 功能相近时，description 含糊就会混用。

- **流水线型 Skill 还要写位置**：「我是第几环、上游是谁、下游是谁」。
- **例子**：评分 Pipeline 三层各一个 Skill——合规过滤、8 维评分、数字回核，`description` 必须写清各自管哪一段。

**7 · 铁规则靠机制钉死，不靠 prompt 叮嘱**

在 prompt 里写十遍「不要用 JD 当基准」，不如从机制上让它做不到。


| 规则       | 机制做法                            | 不靠 prompt 的原因          |
| -------- | ------------------------------- | ---------------------- |
| 评分不用敏感字段 | 脚本物理删除，模型根本看不到                  | 说了也可能「潜意识」违反           |
| 数字回核只用简历 | CLI 只收两个参数，不留 JD 参数位            | 给了 JD 参数就可能误用          |
| 合规自检不能消失 | 用 `process.exit(1)` 而非 `assert` | Python `-O` 会移除 assert |


> **能写进代码/接口的，就不靠人记、不靠模型自觉。**

**8 · persona 文档不是无限容器**

`AGENTS.md`、`TOOLS.md`、`SOUL.md` 会注入 Agent 上下文，但有上限——`AGENTS.md` 约 12000 字符，超出**静默截断**（不报错，后面的内容直接丢）。

- **能力加多了要做减法**：新 Skill 写进 TOOLS/AGENTS 时，检查是否超限；必要时精简默认样板。
- **怎么查超限**：看 OpenClaw 运行时的 truncating 日志，**不要**只看本地 `len()`——注入时的截断规则和本地字符数可能不一致。

**8 条串起来看**

```
定契约 → 规则写正文+脚本 → 脚本先单测 → Skill 验证加载
    → Agent 测试要证据 → description 写清 → 铁规则靠机制 → persona 控篇幅
```

这 8 条不只属于招聘子 Agent——换任何「多个能力串成数字员工」的场景，方法一样适用。

> **一句话总结**：先定数据契约；铁规则写正文、交脚本、靠机制；开发时脚本单测、Skill 验证加载、Agent 测试要证据；相似 Skill 写清区别；persona 文档有上限要控篇幅——这是把「能跑的 Demo」做成「能上线的工业级 Agent」的通用纪律。
