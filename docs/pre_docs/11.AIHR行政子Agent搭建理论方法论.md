## §0 一句话主旨：把答疑与月报交给不知疲倦的小慧

行政子 Agent「小慧」要接走 HR 两件每天/每月都躲不掉的信息处理活：

- **员工答疑**：小李晚上、周末、出差路上想起一个政策问题（年假会不会清零、高铁票怎么报、试用期给不给公积金），答案都白纸黑字写在政策文件里，但小李不知道在哪份、第几条；HR 一天要接几十条这样的消息，回复总慢半拍。
- **月度报表**：招聘漏斗、岗位进度、入职留存、培训、人力成本、离职，六个口径的数据散在不同表里，要一个个拉出来、算指标、画成图、写解读，拼成一份发给管理层的报告。不难，但耗时间，每个月从头再做一遍。

这两件活分别对应两种范式——**RAG 问答**（信息已在库里，要精准检索和回答）和**数据→报告**（信息是结构化数据，要定时、计算和呈现）。它们不像签合同、定薪资那样有明确决策动作，是大量的、重复的、"知道怎么做但就是耗时间"的体力活——占用时间多，又恰恰是 AI 最擅长的。

> **一条从头绷到尾的线**：HR 答疑不能滑成 AI 给法律意见，月报里的数字不能是 AI 顺手编出来的。合规嵌在每个范式里：答疑场景讲"复杂问题硬性转人工"（§4），月报场景讲"每个数字都要能追回源头"（§5）。

## §1 RAG 问答范式：HR Helpdesk 是什么、边界在哪

### HR Helpdesk 是什么

**HR Helpdesk（HR 服务台）**是给员工的 7×24 小时政策答疑服务台——员工提一个政策问题，行政子 Agent 先在公司政策知识库里检索出相关政策原文，再基于检索到的原文回答，并在结尾标明依据哪份政策；遇到法律、个人数据、争议这类问题，不自己答，明确转人工。它对应 RAG 问答范式——**用户问、知识库检索、引用原文回答、复杂问题升级**。RAG 是 Retrieval-Augmented Generation（检索增强生成）的缩写：先检索、再生成。

**为什么交给 AI**（不是因为它"听起来先进"，而是它在 HR 日常里是稳定、持续、消耗注意力的负担）：

1. **HR 是朝九晚六的人，员工的疑问不是**——员工非工作时间想起问题，没 HR 在线，积压到第二天要办的事也跟着拖。
2. **高频问题被反复手动回**——"年假能不能跨年""试用期有没有社保"一天被问十几遍，HR 每次重新组织同样的答复，纯体力消耗、没有判断含量。
3. **答一个问题，HR 自己也得先翻文档**——十几份政策文件，没人记得住每一条数字，差一天就是事故。

> 行业调研佐证：《HR Help Desk Statistics 2026》显示 67% 员工反映难以及时获得 HR 对政策问题的回复；《HR Perception Report》显示 85% 员工对主动走向 HR 寻求帮助有顾虑（保密性存疑、怕被针对、怕显得"基础的事都不懂"）。一个 7×24、不评判、随问随答的 Helpdesk 恰好把这两道门槛一起拆掉。

### 答疑流程：检索、判断该不该答、引用原文

HR Helpdesk 的核心是一个判断：员工问的是"政策怎么规定"的问题，还是"我的个案/我的数据/我的法律处境"的问题。前者答，后者升级。流程围绕这条线展开：

1. 员工提问，进入行政子 Agent。
2. **检索政策知识库**：子 Agent 先对 **IMA 上已入库的政策**做检索（现行：跑 Skill 脚本 `search_ima_policies.cjs`，经 OpenAPI 拉取原文并匹配片段）——不是凭印象答，是先把依据找出来。
3. **判断该不该自己答**：如果问题落入法律纠纷、个人数据、个案争议这几类，不自己下结论，给出政策背景后明确转人工（这就是 HiTL，Human-in-the-Loop，完整清单见 §4）。
4. **基于原文回答并引用出处**：常规政策问题，用员工能听懂的话转述检索到的原文，关键数字一字不改，结尾标注"政策依据：《X 政策》"。

> 第 3 步那个分叉不是事后补的安全网，而是流程里和"回答"平级的一条主路径。相对"直接问大模型"的价值在于：答出来的是这家公司的政策，而且每条答复都能回溯到"依据哪份文件"。直接问大模型会用训练数据里的通用知识答——很可能是别家公司的政策，对本公司就是错的，而且无从追溯。RAG 这一步检索，就是强制把答复挂靠到公司政策原文上。

### 一条贯穿全程的红线：检索得到 ≠ 该回答

HR Helpdesk 和普通客服机器人的差别不在"答得快"，在于它知不知道自己的边界。**本节最该记住的一句话：检索得到相关政策，不等于这个问题就该由 AI 回答。**

设想员工发来"我这个月到手工资比上个月少了 800 块，是不是算错了？"——一个只会检索 + 回答的 Helpdesk 会在政策库检索"工资""扣款""个税"全都检索得到，于是顺着政策"帮你分析一下可能的原因"甚至直接给判断。问题在于，"你这 800 块具体是什么原因"需要查这名员工的**个人薪资明细**，而子 Agent 没有、也不该有这个数据访问权限。它检索得到的是通用政策，它编出来的"原因"是猜的——猜出来的答复就是误导。

法律纠纷类更严重：员工问"公司这样辞退我合不合法"，AI 一旦给出"合法/不合法"的结论，就是在充当法律顾问——越过了 AI 在 HR 场景的法律边界。**涉及个人薪资数据、个案争议、合同解除合法性、工伤认定这类问题，正确的做法不是"答得更小心一点"，而是不答，明确转人工。**

## §2 RAG 方案选型：为什么改用腾讯 IMA 知识库

那 14 份政策文件用什么东西装起来才能让行政子 Agent 检索得到？这一节不讲向量公式细节，只回答三件事：**现行选型是什么、怎么组织、为什么不继续用 Builtin Memory / 自建向量库**。

### 摸底结论（现行）：政策库落在腾讯 IMA，Skill 用 OpenAPI 检索原文

现行 HR Helpdesk **以腾讯 IMA 知识库为唯一答疑检索源**（示例库名 `hr_er_kg`），不再用 OpenClaw `memory_search` / Builtin Memory 回答政策问题。工作方式拆成四点：

- **存储与入库（运维一次性）**：在 IMA 创建知识库，把 00–13 政策 markdown/txt **上传进 IMA**；凭证写在 profile 的 `env.sh`（`IMA_OPENAPI_CLIENTID` / `IMA_OPENAPI_APIKEY`，推荐固定 `IMA_HR_KNOWLEDGE_BASE_ID`），**不要写进 Skill 正文或公开仓库**。
- **检索（答疑每次）**：er-admin 经 Skill 用 `exec` 跑 `scripts/search_ima_policies.cjs`。脚本按官方 ima-skills 路径调用 Wiki OpenAPI：`get_knowledge_list` 列出库内文档 → `get_media_info` 拉取原文（`url_info.url` + headers；笔记类型再走 `get_doc_content`）→ **在本地对正文任意片段做全文匹配**，返回带 `title` / `highlight` 的命中供 Agent 引用。
- **本地 `memory/hr-policies/`**：仅作**备份 / 对照 / 课程交付源**，**答疑运行时不读本地索引**，也不再依赖 `memory index`。
- **和 IMA 网页端的差别（易混）**：IMA **客户端/网页问答**走产品内 RAG（可含语义能力）；OpenAPI **没有对外提供词向量检索接口**。Skill 侧用「拉全文 + 本地全文匹配」补齐「任意片段命中」，而不是指望 `search_knowledge` 的标题向召回。

对落地来说一句话：**政策上传到 IMA → 配好 OpenAPI 凭证与知识库 ID → 答疑 Skill 只负责「先跑检索脚本、再按原文答、红线升级」。**

> **为什么从小库全文扫得起**：现行演示库约十几篇 markdown，全库拉取 + 本地缓存（默认约 24h）可接受。文档规模显著变大时，应改为「先窄候选再全文」或自建向量层——那是规模化下一步，不是当前 OpenAPI 已提供的能力。

### 入库结构：IMA 主库 + 本地备份隔离

| 位置 | 角色 |
|---|---|
| **IMA 知识库**（如 `hr_er_kg`） | 答疑**主库**：Agent 只从此检索 |
| `workspace-er-admin/memory/hr-policies/` | **备份/对照**：方便 diff、课程交付、离线核对数字；不参与答疑检索 |
| Agent 运行记忆（`memory/` 其它文件） | Agent 自写笔记，与政策主库分离 |

> **要说明白**：切换到 IMA 之后，「政策源」与「Agent 运行记忆」在系统边界上真正分开了——政策在 IMA，运行记忆仍可在 OpenClaw workspace。更新公司政策 = 更新 IMA 文档（并视需要同步本地备份），Skill 规程本身通常不用改。

### 方案对照：为什么选 IMA，Builtin Memory 放哪

| 方案 | 是什么 | 本场景怎么看 |
|---|---|---|
| **腾讯 IMA 知识库 + OpenAPI（现行选用）** | 云端知识库托管；Skill 脚本拉原文并全文匹配片段 | 政策可在 IMA 侧独立维护/共享；与 OpenClaw 运行记忆解耦；符合「检索接地 + 可引用出处」 |
| Builtin Memory（课程早期 / 备选） | 自带 `memory-core`，`memory index` + `memory_search`，SQLite 混合检索 | 零额外部署、适合纯本地实验；但政策与运行记忆同索引、且本课已切换 IMA，答疑路径**禁止**再改回 `memory_search` 硬答 |
| Memory Wiki | 随包插件，wiki 编译 | 更重，14 份规整政策用不上 |
| 单独部署 LanceDB / Pinecone | 第三方向量库 | OpenAPI 无现成向量检索时，自建向量是规模化选项，不是当前必选项 |
| 不用 RAG，直接问大模型 | 跳过检索 | 不可控、不可追溯——HR 答疑不合格 |

> **选型判断**：要的是「本公司政策原文可追溯」，不是「再部署一套向量库」。IMA 负责托管与 OpenAPI 读原文；Skill 负责规程与 HiTL。Builtin Memory 仍是 OpenClaw 体系内合法备选，但**与现行 IMA 答疑路径二选一，不要两套同时当权威源**。

## §3 两类 Skill 形态：指令型 vs 脚本型

行政子 Agent 的两个能力正好是两类 Skill 形态的对照样本，这是本集在 L2-1 之外要新讲的东西。

L2-1 封装的几个 Skill（`parsing-resumes`、`scoring-candidates`）都有一个共同点：核心是 `scripts/` 下一段可执行脚本。这是**脚本型 Skill**。HR Helpdesk 答疑则不同——**主体仍是行为规程**（先检索 → 引用原文 → 必要时升级），但现行落地给规程配了一个**薄检索脚本** `scripts/search_ima_policies.cjs`：负责调 IMA OpenAPI、拉原文、吐出可引用片段。政策**入库**仍是运维一次性操作（上传到 IMA），不属于答疑步骤本身。

因此答疑 Skill 是 **指令型为主、检索脚本为辅**：`SKILL.md` 写死三步协议与 5 类升级红线；`scripts/` 只做检索封装，**不**承担「该不该答」的判断——那仍靠正文指示强度。

| 对照维度 | 答疑 Skill（指令型为主 + 检索脚本） | 脚本型 Skill（月报） |
|---|---|---|
| 目录布局 | `SKILL.md` + `references/` + `evals/` + **薄** `scripts/search_ima_policies.cjs` | 有 `scripts/`，且它是核心业务 |
| frontmatter 依赖声明 | `requires.bins: ["node"]` + `env: IMA_OPENAPI_*`（经 `exec` 跑检索脚本） | `requires.bins: ["python3"]` |
| 确定性来源 | HiTL / 数字纪律靠 `SKILL.md` 指示强度；检索结果形态靠脚本 | 靠脚本兜底算数与出图 |
| 验证方式 | 脚本可单独冒烟（`--list-kb` / 问一句看 `hits`）；规程仍须 Agent 端到端测 | 能"不经 Agent 单独跑脚本"隔离验证 |

> **两类 Skill 的判据仍是一句话**：能力重心是"Agent 该怎么做"还是"该跑什么业务代码"。答疑重心仍是规程（HiTL、引用出处），脚本只是检索引擎适配层；月报重心是 pandas 流水线。不要因为答疑多了一个 `scripts/` 就把它当成月报同类的脚本型 Skill。

**指令型（规程）写法要点**：HiTL 与数字纪律没有「裁判脚本」——那几条硬规则（政策数字一字不改、检索得到 ≠ 该回答、红线升级、升级要拆成「政策能答的 + 必须升级的」）**必须写进 `SKILL.md` 正文「关键规则」、措辞要硬**。检索脚本只保证「有命中片段可引用」，不保证「该不该答」。

> **值得记住**：Skill 的本质仍是「自描述的能力包」。IMA 切换后，答疑包里多了一层 OpenAPI 适配脚本，但**权威规程仍是 `SKILL.md`**，不是脚本替 Agent 做合规判断。

## §4 HiTL 升级红线：Agent 知道自己不该答什么

一个只会答的答疑 Agent 是不能放进生产的。它的另一半——遇到自己不该答的问题，主动停下来、转人工——就是 **HiTL（Human-in-the-Loop，人工介入）**，对应答疑三步协议的第 3 步。

### 升级红线为什么是答疑 Agent 能否进生产的分水岭

HR 答疑 Agent 和普通客服机器人最大的区别不在答题能力，在答不出（或不该答）时的行为。普通客服机器人答不出会顺着话头瞎编；HR 答疑 Agent 答不出、或不该答，必须明确转人工——因为 HR 答疑里有几类问题，AI 硬答就是合规事故。

**最容易踩的误区**（也是 `SKILL.md` 正文把它列为头条"关键规则"的原因）：**"政策库里检索得到相关内容"不等于"这个问题该由 AI 答"。** 员工问"工资少了 800 块"，政策库里有《薪酬与社保公积金》，工资构成、扣款规则全检索得到——但"你这 800 块具体什么原因"需要的是个人数据，不是政策。**判断"该不该答"，必须先于"能不能检索到"。**

> 这也是这套 Agent 和"用低代码平台快速拼一个问答机器人"的分界。用 FastGPT 这类平台半天就能搭出一个 HR 政策问答机器人、答案又快又准——但它优化的是"把答案做准"，没有"这个问题该不该由我来答"这一层判断。**能答得准是基线，知道哪些不该答，才是答疑 Agent 能进生产的那道门槛。**

### 5 类升级红线

Skill 化后，5 类升级红线的权威副本从 `SOUL.md` 迁进了 `answering-hr-policy-questions` Skill——`SKILL.md` 正文三步协议第 3 步列出 5 类概述和判断原则，每类的判断边界、典型问法、处理示范引到 `references/escalation-redlines.md`，`SOUL.md` 只留一句核心判断"检索得到 ≠ 该回答"。

| # | 升级情形 | 为什么必须升级 |
|---|---|---|
| 1 | 涉及个人具体金额 / 数据 | 回答需查个人考勤、薪资、社保、个税、年假余额记录，Agent 无数据访问权限，硬答只能靠猜 |
| 2 | 个案争议 | 员工对绩效结果不服、对扣款有异议、认为公司做法不合理——需人工判断个案具体情况 |
| 3 | 法律纠纷 / 劳动仲裁 | 涉及对个案的法律定性（合同解除是否合法、经济补偿争议、工伤认定），AI 给法律意见是越界 |
| 4 | 知识库无依据 | IMA 检索脚本 `search_ima_policies` 无命中（`hit_count=0` / 退出码非 0），或明显超出政策库覆盖范围，不许用通用知识硬答 |
| 5 | 需要决策审批 | 员工申请特殊安排、破例处理，需人工 HR 做"批不批"的决策 |

> 从员工视角最典型的是前 3 类（法律、个人数据、个案争议）；第 4、5 类是再加的两条 Agent 自身能力边界护栏。

### 一个关键设计判断：情形描述 vs 触发词列表

升级红线该用"情形描述"还是"触发词列表"？一种朴素做法是列一串敏感词（"仲裁""工伤""解除"）命中就升级。它的问题是**覆盖不全**：实测里那个问题"我这个月工资比上个月少了 800 块"整句话一个敏感词都没有，纯关键词匹配会直接放过它；而"涉及个人具体金额 / 数据"这个**情形描述靠语义理解**，能把它准确归类。所以本课 `SKILL.md` 用的是情形描述。

**但这不是二选一。** 生产环境最稳的做法是两层叠加（防御纵深）：

- 一层确定性的**关键词硬过滤**，命中"劳动仲裁""工伤认定""违法解除"这类明确高危词就无条件升级、绝不漏；
- 再叠一层 `SKILL.md` 的**语义情形判断**，兜住那些口语化、没有敏感词的案例。

关键词层负责"绝不能漏的硬命中"，情形描述层负责"语义召回"。本课 Skill 实现的是情形描述这一层，生产部署时把关键词硬过滤另行叠加上去才是更完整的形态。

> 这正是答疑「规程侧」没有合规裁判脚本的体现：检索脚本只负责命中片段，升级判断靠 `SKILL.md` 语义指示——覆盖面广但非 100% 确定，"再叠一层关键词硬过滤"补的就是这个确定性缺口。

### 升级判断做法对比

| 做法 | 评价 |
|---|---|
| 纯触发词列表（关键词命中即升级） | 漏召口语化案例——"工资少了 800 块"整句无敏感词，会被放过 |
| 让 AI 运行时自己判断"要不要升级" | 不可控。标准全靠模型临场发挥，同样的问题这次升级、下次可能硬答，还容易被追问带着突破边界 |
| 干脆不设升级路径 | 违法。遇到法律、个人数据问题只能硬答，硬答就是合规事故 |
| Skill 正文 5 类情形描述（本课实测） | 语义判断，覆盖口语化案例；红线作为 Skill 的一部分可单独维护、有评测闭环；但靠 LLM 语义理解、非 100% 确定 |
| **情形描述 + 关键词硬过滤兜底（推荐生产形态）** | 防御纵深：关键词保证高危词绝不漏，情形描述兜住口语化案例 |

### 三条要诚实讲清的边界

1. 5 类升级情形要**随业务和法规演变**更新——封成 Skill 后这个更新只动 Skill 文件、不动 Agent 人格文件，风险面更小。
2. 情形归类靠 LLM 语义理解、**不是 100% 确定性判断**；`SKILL.md` 硬约束把"必须升级"从"模型自由发挥"变成"明文守则约束下的判断"，但具体某个问题落不落入某类情形仍经过模型语义判断——这正是推荐"再叠关键词硬过滤"的原因。
3. 本课实现的"升级"**止于对话层**：Agent 在回复里说明边界、把人工渠道告诉员工，但没有自动创建工单、没有通知到某个具体 HR、也没有把会话路由给人工坐席。一个真正闭环的升级要把这个动作接到工单或通知系统上，不在本集范围。

> **升级不是甩一句"请联系人工"**：真正的 HiTL 是把问题拆成"政策能答的 + 必须升级的"两部分——政策性通用知识（个税累计预扣会导致后几个月波动）照常讲，需要查个人数据的判断留给人工。一刀切"凡涉及工资就转人工"会让 Agent 变得没用，一律硬答又会出合规事故——真正的 HiTL 是在这两者之间精确划界。

## §5 数据→报告范式：HR 月报为什么这么设计

### HR 月报是什么范式

**HR 月报**是每个月底都要交的一份固定作业：把当月的招聘、入职、培训、离职、成本数据拉出来，算成指标，配上图表和文字解读，汇成一份报告交到管理层手里。它属于**数据→报告**范式——定时从数据源拉数据、按固定规则算指标、输出成图文报告。

人工做月报耗的是一个 HR 的半天到一天：从各系统导出七八个 Excel、在 Excel 里手动算转化率/到位率/人均成本（公式拉错一格数字就跟着错）、把图表截图调色插进 PPT、写几段解读。痛点不在"难"，在"耗"，而且**每个月都要重来一遍——数据换了，但口径、图表、报告结构基本不变**。这正是数据→报告范式的典型特征：固定的流程适合写成脚本一次，变化的数据由脚本每月重新读一遍。

本集月报数据源是 **6 个 CSV**：`recruitment-funnel`（招聘漏斗）、`positions-progress`（岗位进度）、`onboarding-retention`（入职留存）、`training-completion`（培训完成）、`hiring-cost`（招聘成本）、`attrition`（离职）。6 个 CSV 经 pandas 读取、算指标、对标业界基准，再由 matplotlib 画图，最后拼成一个单文件 HTML 月报，由 OpenClaw Cron 在月末定时唤醒 er-admin 执行——从数据进到报告出全程是一套确定性脚本。

### 月报不是"报数"，是"报数加给参照系"

一份只罗列数字的月报价值有限。"本月入职 8 人""人均招聘成本 8250 元"这些数字单独看，HR 说不出是好是坏。**月报真正的价值在于给每个数字配一个参照系。** 本集用两种：

- **业界基准**：月报对标 5 项业界指标（来源见各条括号）。两种呈现：转化率和 Time to Hire 画进 6 个月趋势线、旁边叠一条橙色基准虚线；5 项完整对标汇在一张表里逐项标"达标 / 需关注"。**把基准写成脚本里的常量，好处是它确定、不靠 HR 临场去记。** 五项含义与好向：
  - **面试→Offer 转化率 27%**（Jobvite 2024）：进了面试的人里最终拿到 Offer 的比例。越高通常越好（筛选与人岗匹配更有效）；公司值明显低于 27% 标"需关注"。
  - **Offer 接受率约 50%**（CareerPlug 2024）：发出 Offer 后候选人实际接受的比例。反映薪酬竞争力、雇主品牌与竞品抢人；过低常见于薪资或流程拖沓。
  - **Time to Hire 43 天**（CareerPlug 2024）：从启动招聘到入职（或接受 Offer，视口径）的平均天数。**越短越好**；长于 43 天往往意味着环节堵、空窗成本高——趋势图橙色虚线即此线。
  - **入职 45 天内离职率 20%**（SHRM）：新人入职后约一个半月内离职的比例。**越低越好**；偏高要查 onboarding、预期管理与试用期体验（若尚在观察期则如实标"统计中"，勿硬凑）。
  - **培训满意度 4.0**（Kirkpatrick L1）：柯氏四级的 **L1 反应层**——学员对培训的主观满意度（常见 5 分制）。≥4.0 视为体验尚可；它不等于"学会了没有"（那是 L2）。
- **历史趋势**：同一指标连续 6 个月的走势画成趋势线，当月的成本柱在柱状图里高亮成另一种颜色。单看一个月不知深浅，6 个月并排一眼可见当月处在什么水平。

### 特有风险：月报数字最怕 LLM 编造

数据→报告范式有一个特有风险，必须在动手前就讲清楚：**月报的数字一旦交给 LLM 去复述或生成，就可能被改、被编、被串台。** 月报是给管理层做判断用的——看到"面试转化率低于业界"管理层会复盘招聘渠道，数字错一个下游判断就跟着错。

本集的对策，是把**数值计算彻底交给确定性的 pandas 脚本，让 LLM 完全不碰数字**，再用一张"数字回核表"把每个数字指回它的 CSV 来源。

**18 项数字回核表**：脚本跑完自动打印一张表，把 18 个进入 HTML 的数字逐条列出来源（如"漏斗-投递数 = 530，出自 `recruitment-funnel.csv` 2026-05 行 投递数列"）。它不是魔法，就是脚本里一个 `audit` 列表的累加——每算出一个要进 HTML 的数字，就同步往 `audit` 追加一条"(指标名, 值, 来源)"，脚本末尾把整张表打印出来。价值不在代码量，在那条纪律：**凡是进 HTML 的数字，必须在 `audit` 里有一条对应记录。**

> **和 L2-1 数字回核的对照**：这套机制和 Lesson 2-1 评分环节的数字回核是同一套工程思路——不同的是，L2-1 评分是"LLM 先产出自由文本、回核层在产出之后抽取-比对"，月报这里是"从架构上让 LLM 根本不碰数字、pandas 确定性算出、回核表是这个设计的证据"。月报场景比评分更彻底：评分的自由文本绕不开 LLM 只能事后回核，月报的数字本来就是确定性计算，于是干脆从设计上把 LLM 隔离在数值之外。

> **"统计中"也是一种要被回核的状态**：月报里 45 天内离职率写"统计中"——不是脚本算错，是 5 月入职员工还在 45 天观察期、结果尚未产生。脚本对这种"还没有答案"的指标如实标注。回核表把它一并列出——"暂时没有答案"也是一种需要被回核的状态，标"统计中"比硬凑一个数字诚实。`SKILL.md` 把这写成硬规则"『统计中』不是错误，不要去补"。

## §6 无人值守：Cron 触发、月末守卫与时区

"能跑"不等于"能上线"。一套能交付的月报自动化还要做到真正无人值守——到点自己跑，不靠 HR 记得每月月底去点一下。月报最终投产形态是 **OpenClaw Cron 在月末定时唤醒 er-admin、由它经 `generating-monthly-report` Skill 执行月报脚本**。

### Cron 三种 schedule 与"到点唤醒一个 Agent"

OpenClaw Cron 提供三种 schedule：`at`（指定时刻触发一次）、`every`（固定间隔周期触发）、`cron`（标准 5 字段 crontab 表达式）。每个任务还能绑定会话类型（`main` / `isolated` / `current` / `session:<id>`）。

**核心认知**：Cron 不是简单地"到点跑个脚本"，而是**到点唤醒一个子 Agent，让这个 Agent 经它的 Skill 去干活**。任务和执行者是分开配置的（`--agent er-admin` 是关键字段）。月报任务用 `--session isolated`（独立会话，不污染主对话）、`delivery: not requested`（只生成到目录、不自动发给任何人）。

### Cron 触发成功 ≠ 子 Agent 能干活

一个真实的 error/ok 对照（月报 Cron 实验）说明了一件事：**无人值守链路有两个独立的环节——"定时触发"和"被唤醒的 Agent 有权限干活"，两个都对链路才通。**

- 第 1 次到点真·自动触发（没有人敲命令），却 `status = error`，报 `No callable tools remain after resolving explicit tool allowlist`——工具权限解析完后没有任何可调用的工具剩下。根因在 `deny` 名单拦掉了 `group:runtime`（这一组包含月报脚本要用的 `exec`）。`exec` 被拦掉，子 Agent 就算被叫醒也"手被绑住"，在工具权限解析这一步秒退。
- 第 2 次（修复权限后）`status = ok`，链路完整跑通。

> 这正是脚本型 Skill 第三步"改配置"要确认 `group:runtime` 到位的原因——脚本型 Skill 装进 workspace 只是第一步，Agent 还必须有跑脚本的工具权限。**调试自动化故障时，先看 `cron runs` 里是 error 还是根本没有触发记录：没记录是调度问题，有记录却 error 多半是被唤醒方的权限或环境问题。**

> **生产应遵循最小授权**：实验里直接把 deny 里拦 `group:runtime` 的那条移除了；生产环境应只为 `exec` 单独放行，或注册 Cron 任务时用 `--tools exec` 限定。

### 月末守卫与时区

生产表达式 `59 23 28-31 * *`（每月 28-31 日的 23:59 各触发一次）有两个细节，封在 `run_monthly_report.sh` 脚本里、随 Skill 一起交付：

- **只在月末跑一次**：`59 23 28-31 * *` 会在 28/29/30/31 日各触发一次，但月报只该在真正的月末当天生成。办法是加一道"月末守卫"：脚本判断"明天是不是 1 号"，只有明天是 1 号（即今天是本月最后一天）才往下生成，其余几天空跑退出。这是标准 cron 实现"仅月末触发一次"的通用做法——因为 cron 的 `L`（last day）修饰符并非所有调度器都支持。
- **时区**：`cron show` 的 schedule 末尾那个 `Z` 表示 OpenClaw Cron 默认按 **UTC** 理解时间。`59 23 28-31 * *` 不指定时区，`23:59` 会被当成 UTC，换算成北京时间是次日 07:59。推荐注册时带 `--tz "Asia/Shanghai"`。**更要紧的是：cron 表达式的求值时区，和月末守卫脚本里 `date` 命令读的系统时区，必须一致**——两者错位，"28-31 日触发"和"判断明天是否 1 号"就会对不上。

## §7 业界对位：基线 / 差异化 / 要警惕的坑

把绩效 360、HR Helpdesk、HR 月报三种范式放进业界坐标系，小慧的绩效子 Agent 和行政子 Agent 是什么水平？分三层看。

### 第一层：基线——绝大多数 HCM 产品都有

| 基线能力 | 业界主流产品 | 小慧绩效 + 行政子 Agent |
|---|---|---|
| HR 政策答疑（对话式） | 北森 / Moka / 钉钉智能人事 / 飞书 People 都有 | 14 份政策入 IMA + OpenAPI 检索原文后答复 |
| 360 反馈聚合 | 北森 / 用友 等 HCM 平台的绩效模块标配 | 多源聚合 + 四视角雷达看板 |
| HR 数据报表 | 几乎所有 HCM 平台都有报表 / 看板模块 | 月报 Pipeline + HTML 图文月报 |

政策答疑、绩效聚合、数据报表这三类能力是绝大多数一体化 HCM（Human Capital Management）平台都具备的——它们不是亮点，是入场券。这一层要诚实：没有一项是小慧的独创，小慧在基线上做到的是"也有，且工业级"。基线必须扎实，否则后面谈差异化没有意义。

### 第二层：差异化——少数产品才做到工业级的地方

真正拉开差距的不是"有没有这个功能"，是"这个功能做没做到工业级"。

| 差异化点 | 多数商业 SaaS 的做法 | 小慧的做法 |
|---|---|---|
| 合规边界落实 | 内置合规模块，但"怎么落实"通常是黑盒；不少 SaaS 把合规控制权交给用户自己把握 | 五处工程化落实——首尾声明、橙色 banner、评级核查、产出定位、分歧表述，每处落在代码或产出物看得见的位置 |
| 月报数字可追溯 | 报表数字由系统或 LLM 直接生成，少有逐个数字回溯到源单元格 | 18 项数字回核——每个进 HTML 的数字指回某个 CSV 单元格或一条可验算公式 |
| 答疑的边界与精度 | RAG 答疑虽常带引用出处，但很少做"该不该答"的判断、也很少逐字核查关键数字 | HiTL 的 5 类升级红线写进硬约束（敏感问题不硬答），每条答复关键数字与政策原文逐字核对 |

对位要分清两类参照系。一类是一体化 HCM 平台（北森、Moka、用友），能力厚度、客户规模和小慧不在一个量级——拿单个子 Agent 比整条产线本就不对等。另一类才是和"小慧子 Agent"形态最接近的参照：AI-native 的 HR 智能体（IBM watsonx Orchestrate 的 HR agent、Microsoft Copilot for HR），它们同样把招聘、绩效、答疑拆成各自的 agent。对位这一类，**小慧的差异化是定位上的：它是一个工程师完全可控的开源方案，合规边界的每一处落实、月报每个数字的来源、答疑的每一条出处，都看得见、改得动。** 商业 SaaS 的合规模块对买家而言透明度参差——你知道它"有合规功能"，但不一定清楚它具体怎么落实、能不能按自己公司的制度调整。

### 第三层：要警惕的坑——业界血的教训

| 真实案例 | 踩了什么坑 | 对位本集哪个设计 |
|---|---|---|
| 麦当劳 McHire 凭据漏洞（2025） | 招聘 AI 平台测试管理员账号用户名密码都是 "123456"、无多因素认证，加一个 IDOR 漏洞（改申请人 ID 就能翻看别人聊天记录），约 6400 万份求职申请暴露 | Helpdesk 的 HiTL 设计——Agent 没有、也不该有个人薪资/考勤数据的访问权限。Agent 能碰的数据越少，泄露面越小 |
| Eightfold AI 集体诉讼（2026-01 加州立案） | 被诉在候选人不知情、未同意下从社交媒体、定位、设备活动等未核实来源收集信息建档、按 0-5 分打分，低分者人工查看前就被淘汰，按 FCRA 立案 | 360 反馈全程用模拟数据、产出不打评级、附合规声明，规避"未授权数据 + 不透明评分" |
| "AI 自动绩效评级"营销话术 | 宣称 AI 能一键读完反馈直接产出 S/A/B/C/D 综合评级。绩效评级属"对个人权益有重大影响的决定"，由 AI 单独作出触个保法第 24 条 | 绩效五处落实就是这个营销陷阱的工程化答案：AI 聚合好、分析清楚，"定级"留给人工三级流程 |

> 这三个坑的共同点：**看起来"更智能"的设计，往往是法律风险最大的设计。** McHire 图省事用弱口令、Eightfold 图数据多去抓取、"自动评级"图一步到位——省的每一步，后面都要还。

## §8 合规红线工业级落实总览（5 个落实点）

从三种范式一路讲下来，合规一直在出现——绩效 360 不给评级、Helpdesk 敏感问题转人工、月报每个数字回核。这一节把它们收到一起做总览。

### 一条底层原则

本集三种范式技术上完全不同，但合规设计指向同一句话：**AI 负责把信息处理好，不替人做对个人权益有重大影响的决定。** 它有明确法律依据：

- **《个人信息保护法》第 24 条**——自动化决策作出对个人权益有重大影响的决定，个人有权要求说明、有权拒绝仅由算法作出的决定。
- **《互联网信息服务算法推荐管理规定》（2022-03）**——算法决策要透明、用户有拒绝权。（主要规制面向公众的算法推荐，企业内部 HR 系统是否落入视具体形态而定；但"算法透明、可拒绝"已被个保法第 24 条吸收，作为设计准则同样成立。）
- **就业促进法**——禁止基于民族、种族、性别、宗教信仰的就业歧视；绩效、用工判断不得把这些特征当依据。
- **《个人信息保护合规审计管理办法》（2025-05）**——处理超过 1000 万人个人信息的处理者每两年至少开展一次合规审计，大型企业普遍会触发，其 HR 系统会被纳入审计范围。

### 5 个落实点

| # | 落实点 | 范式 / 章节 | 防住什么 |
|---|---|---|---|
| 1 | 绩效 360 五处落实 | 多源聚合（见 `9.` §6） | AI 替人给员工定绩效等级 |
| 2 | Helpdesk 升级红线 | RAG 问答（§4） | AI 对法律 / 薪资敏感问题硬答、越界给法律意见 |
| 3 | 月报 18 项数字回核 | 数据→报告（§5） | LLM 编造或串台数字 |
| 4 | 所有产出可追溯到源数据 | 贯穿三种范式 | 决策依据查不到、出错无法定位 |
| 5 | 受限场景诚实标注 | 贯穿三种范式 | 把"没有答案"包装成"有答案" |

- **落实点 4 · 可追溯**：绩效 360 看板数字全部读自 `aggregated-data.json` 这一份数据基准、绝不重算；Helpdesk 每条答复引用政策原文出处；月报每个数字进回核表。三种范式的产出都能回答"这个数字/这句话从哪来"。可追溯不是附加功能，是出错时能定位、被质询时能说明的前提。
- **落实点 5 · 诚实标注**：绩效 360 用模拟数据、明确标注"真实生产需企业历史数据"；月报里试用期通过率、45 天离职率因员工还在观察期如实写"统计中"而不硬凑；Helpdesk 检索不到政策就转人工、不用通用知识填空。**"不知道就说不知道"，比硬给一个答案更专业，也更安全。**

### 为什么"知道要合规"还不够

很多教程讲到合规就停在一句态度——"所以我们要守住边界""所以要 HiTL"。但"要合规"是一句态度，不是落实。**落实意味着：这条红线要拆成具体的工程措施，每个措施落在代码或产出物的某个看得见的位置，能被逐项核查。**

需要说清楚：AI 工程界这两年并不是没有合规工程化——OpenAI Agents SDK 提供 guardrails（输入/输出校验）和人工审批机制，2026 年"Harness Engineering"（Human Steer, Agent Execute）也成了热门范式。但那一层是**框架级的通用校验**（检测到敏感输入输出就拦、高风险动作暂停等人工确认）。本集要做的是更下沉一层、也更难的事：**把红线落进 HR 产出物本身**——报告的文案、看板的 banner、答疑的 prompt、章节的标题、分歧的措辞。框架级的 guardrail 拦不住"360 报告某一章标题写成'绩效结论'导致定位漂移"这种领域问题，只有领域级的工程落实能拦。

## 附录 A：贯穿行政子 Agent 的工程纪律

| # | 纪律 | 一句话 |
|---|---|---|
| 1 | 检索得到 ≠ 该回答 | 判断"该不该答"必须先于"能不能检索到" |
| 2 | 政策主库单一权威源 | 答疑只认 IMA；本地 `hr-policies/` 仅备份；禁止再改用 `memory_search` 硬答政策 |
| 3 | 两类 Skill 按判据分 | 答疑=规程为主（可附薄检索脚本），月报=业务脚本为核心 |
| 4 | 答疑规程靠正文指示强度 | HiTL/数字纪律写进 `SKILL.md`；检索脚本不代替合规判断 |
| 5 | 升级 = 情形描述 + 关键词硬过滤 | 语义召回口语化案例 + 确定性硬命中高危词，防御纵深 |
| 6 | 月报数字全 pandas 算、LLM 不碰 | 从架构上把 LLM 隔离在数值之外，回核表是证据 |
| 7 | "统计中"是要被回核的状态 | 没答案就诚实标注，不硬凑数字 |
| 8 | 无人值守两个环节都要对 | 定时触发 + 被唤醒方有权限，缺一链路不通 |
| 9 | 合规是领域级工程落实 | 拆成可逐条核查的措施，落进产出物本身 |
