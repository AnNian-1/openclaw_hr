# 任务：对照现行内容更新本 Agent 的 INTRO

你是 HR 数字员工「小慧」里的一员。这次**不是从零写介绍**，而是对照你们已经维护完的现行工作区，**改自己那份已有 INTRO**，让组员能拿去对导师讲：业务逻辑、亮点、经得住深挖。

---

## 硬规则

1. **先读再改**：必须先读本工作区已有 `*INTRO.md`（或 `INTRO.md`）、`SOUL.md`、`AGENTS.md`、`TOOLS.md`、真实存在的 `skills/*/SKILL.md`。没读到的不要补、不要猜。
2. **工作区隔离**：不要读、不要猜其它 `workspace-*` 的内部脚本。跨域只写「由总控路由」或「不是我的职责」。
3. **现行优先于课程**：`course-ref/` 里是课上手册，可能过时。和 SOUL / SKILL / 现有 INTRO 打架时，**以现行为准**，并在「课上这么设计，现在改成了」里写明差异。不要把课程旧口径写回正文当现状。
4. **安全**：不要粘贴 API Key、token、`env.sh`、会话敏感信息。外部依赖只写服务名。
5. **真实性**：声称能跑通的步骤必须能指出脚本或落盘路径；做不到就写失败条件。
6. **只改 INTRO**：不要改 `SOUL.md`、`AGENTS.md`、Skill 脚本或配置。
7. **Skill 列表**必须和本工作区 `skills/` 目录一致，禁止写目录里没有的能力。
8. ASCII 图只用 `+ - | / \` 和英数字，不要用 emoji 当框线。

## 你要补进 INTRO 的答辩结构（可与原章节合并，但这些句子必须能单独抽出来讲）

### A. 五句业务逻辑（放在靠前、独立成节）

用短句，不要空话：

- **负责什么**
- **拒绝什么**
- **人守哪扇门**（哪些决定必须人做，你只给材料/建议/催办）
- **从哪进来**（飞书直达 / 总控 `sessions_spawn` / 用户直连 / Cron 或宿主机脚本）
- **失败长什么样**（明确失败 vs 假成功；缺凭证、无命中、校验退出码 1 时你怎么说）

### B. 每个真实 Skill 四问（用表格，一行一个 Skill）

| Skill | 接什么 | 产出什么 | 缺了会怎样 | 不让大模型做的那一步 |
|------|--------|----------|------------|----------------------|

「不让大模型做的那一步」必须具体，例如：脱敏是物理删字段、月报数字由 pandas 算、人才库名次只来自向量余弦、审批门不代批、政策无命中不硬答。没有这种一步的 Skill，写「无（指令型编排）」或「无（纯校验脚本）」，不要编。

### C. 课上这么设计，现在改成了

先读 `course-ref/` 里属于你的手册（先看目录，再只读与现行 Skill 同名或同主题的节，**禁止通读全文**）。写 **3～8 条**，每条一行：

`课上：…… → 现在：……（依据：SOUL/SKILL/INTRO 哪一句）`

只写你能在现行文件里证实的差异。对不上就写「课程未覆盖 / 现行未改」，不要发明。

### D. 设计亮点（为什么这样设计）

写 **3～6 条**。每条必须是「做法 + 为了防什么」。不要写「智能化、高效、赋能」这类空词。优先从闸门、人在回路、明确失败、权限分人、脚本算数里挑。
