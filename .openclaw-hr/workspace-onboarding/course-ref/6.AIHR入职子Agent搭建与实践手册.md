## §0 入职子 Agent 全景与交付目录

入职子 Agent 有三块能力，各封成一个 Skill，通过 workspace 根的状态目录形成一条数据链：

```
running-onboarding-workflow    ──写──▶  stub-state/<pinyin>/   （5 准备节点 + workflow.json）
running-onboarding-review      ──写──▶  review-state/          （4 个 review 节点状态）
generating-onboarding-dashboard ──读──▶  stub-state*/ + workflow.json + review-state/
```

完整 workspace 目录：

```
workspace-onboarding/
├── SOUL.md / AGENTS.md / TOOLS.md          persona 文档（已写入三个 Skill 的用法与调用时机）
├── skills/
│   ├── running-onboarding-workflow/         入职 Lobster 工作流封 Skill（工作流型）
│   │   ├── SKILL.md
│   │   ├── scripts/
│   │   │   ├── run-onboarding.sh            启动包装脚本（封装 lobster 调用 + 路径推导）
│   │   │   ├── hr-onboarding.lobster        入职审批工作流文件（流程定义本体）
│   │   │   ├── contract.sh / it-account.sh / device.sh / buddy.sh / training.sh
│   │   │   ├── update-workflow.py / refresh-gate-stubs.py / build-approval-prompt.py …
│   │   ├── references/workflow-design.md
│   │   └── evals/eval-cases.md              4 个评测场景
│   ├── running-onboarding-review/           定时 review 封 Skill（脚本型）
│   │   ├── SKILL.md
│   │   ├── scripts/onboarding-review.sh / schedule-onboarding-reviews.sh
│   │   ├── references/review-milestones.md
│   │   └── evals/eval-cases.md
│   └── generating-onboarding-dashboard/     HTML 进度看板封 Skill（脚本型）
│       ├── SKILL.md
│       ├── scripts/build-dashboard.sh / build-dashboard.py
│       ├── references/dashboard-spec.md
│       └── evals/eval-cases.md
├── stub-state/<pinyin>/                    候选人隔离：5 准备节点 + workflow.json
├── stub-state-*/                           （可选）旧结构兼容
├── pending-approvals/                      halt 时审批快照
```

> **数据资产归属铁律**：工作流文件、stub / 辅助脚本是 Skill 私有资产，放进 `scripts/`；`stub-state/<pinyin>/*.json`（含 `workflow.json`）、`review-state/*.json`、`pending-approvals/` 是跨 Skill 共享数据，放进 workspace 根。（详见理论篇 §8）

## §2 入职审批工作流：running-onboarding-workflow

**工作流型 Skill**——封装的对象不是一段一次跑完的代码，是一条多步、有状态、带暂停点的流程。

### 2.1 业务 5 节点与 .lobster 文件结构

入职 5 个工作流节点（对照拓扑）：

```
prep（4 路并行准备）→ contract_gate（合同审批门）→ account_gate（账号权限审批门）→ buddy（带 when 条件）→ complete（带 when 条件）
```

`hr-onboarding.lobster` 骨架（不到 90 行）：

```yaml
name: hr-onboarding
args:                                    # 输入参数，带默认值
  name:    { default: 新员工 }
  pinyin:  { default: employee }
  role:    { default: 工程师 }
  salary:  { default: 面议 }
steps:                                   # 五个节点
  - id: prep                             # 节点 1 · 4 路并行准备
    run: |
      echo "=== 入职准备启动：${name}（${role}）==="
      ( bash "$STUB/contract.sh"   "${name}" "${role}" "${salary}" ) &
      ( bash "$STUB/it-account.sh" "${name}" "${pinyin}" ) &
      ( bash "$STUB/device.sh"     "${name}" ) &
      ( bash "$STUB/training.sh"   "${name}" ) &
      wait
      echo "=== 4 路并行准备全部完成 ==="
  - id: contract_gate                    # 节点 2 · HiTL 审批门 1：合同审批
    run: |
      # 读 contract.json，用 python 拼出一段带 prompt 字段的 JSON
      cat "$STATE/contract.json" | python3 -c 'import json,sys; c=json.load(sys.stdin);
        print(json.dumps({"prompt":"HR 主管，请审批 "+c["candidate"]+" 的劳动合同：岗位 "+c["role"]+" / 薪资 "+c["salary"]+" / 试用期 "+c["probation"]+"。是否批准进入签约？","items":[c]},ensure_ascii=False))'
    approval: true
  - id: account_gate                     # 节点 3 · HiTL 审批门 2：账号权限审批
    run: |
      # 读 account.json，用 python 拼出一段带 prompt 字段的 JSON
    approval: true
  - id: buddy                            # 节点 4 · Buddy 匹配
    run: bash "$STUB/buddy.sh" "${name}" "${role}"
    when: $contract_gate.approved && $account_gate.approved
  - id: complete                         # 节点 5 · 入职归档
    run: |
      echo "=== ${name} 入职审批工作流完成 ==="
    when: $contract_gate.approved && $account_gate.approved
```

> **三个前置发现（写之前不知道一定踩坑，详见理论篇 §3）**：
> 1. `steps` 严格串行，并行靠单个步骤内 shell `( ) &` + `wait`（没有 `parallel`/`needs` key，dry-run 看不出串并行）。
> 2. `approval` 字段不做 `${...}` 模板替换（不报错的坑）——审批信息走 `run` 产出 JSON 的 `prompt` 字段。
> 3. `args` + `${...}` 模板让一个文件服务所有新员工——只改 `--args-json`。
>
> 工作流文件本身**不写 `env` 块**（`$STUB`/`$STATE` 由启动脚本注入，原因见理论篇 §5 封装踩坑）。

### 2.2 裸命令跑通（先看清要封装什么）

先用最朴素的裸命令把功能跑一遍。先把工作流文件 + 5 个 stub 部署到位：

```bash
# 把 lobster 二进制和工作流文件路径存成变量
LOBSTER=~/.openclaw-hr/npm/node_modules/@clawdbot/lobster/bin/lobster.js
WF=~/.openclaw-hr/workspace-onboarding/workflows/hr-onboarding.lobster
STUB=~/.openclaw-hr/workspace-onboarding/stub-system
STATE=~/.openclaw-hr/workspace-onboarding/stub-state
```

完整部署结构（**这一步不能省**，dry-run 不真跑脚本、缺 stub 也过，但真跑时 `prep` 找不到 stub 直接报错）：

```
workspace-onboarding/
├── workflows/hr-onboarding.lobster      # 工作流文件
├── stub-system/                         # 5 个 stub 脚本（chmod +x stub-system/*.sh）
│   ├── contract.sh / it-account.sh / device.sh / training.sh / buddy.sh
└── stub-state/                          # stub 写状态文件的目录（建一个空目录即可）
```

**① dry-run 验证执行计划**（只解析文件、打印计划，零副作用）：

```bash
node "$LOBSTER" run --dry-run --mode tool --file "$WF" \
  --args-json '{"name":"张磊","pinyin":"zhanglei","role":"后端工程师","salary":"32K"}'
```

核对要点：首行 `[DRY RUN] Would execute 5 steps`；`prep` 里 `${name}` `${role}` 已替换成"张磊""后端工程师"（发现 3 生效）；`contract_gate` / `account_gate` 各标一行 `[approval required]`；末尾 `status: ok`。

> dry-run 只验证**静态**的东西（语法、步骤数序、审批门识别、参数替换）；4 路并行真不真、stub 能不能产 JSON、审批门 halt 返回什么，都要真跑才知道。

**② 真跑，停在第一个审批门**：

```bash
rm -f $STATE/*.json      # 清掉旧状态文件，确保这次审批看到本次跑出来的数据
node "$LOBSTER" run --mode tool --file "$WF" \
  --args-json '{"name":"张磊","pinyin":"zhanglei","role":"后端工程师","salary":"32K"}' \
  | tee /tmp/d1-run1.json
```

输出核心：`status` = `needs_approval`（不是 `ok`），流程停在 `contract_gate`。`requiresApproval` 里带四样东西：`prompt`（候选人专属信息已拼进去）、`items`（待审数据）、`resumeToken`（恢复凭证，base64）、`approvalId`（短标识）。

> `resumeToken` 和 `approvalId` 每次跑值都不同（每次 halt 生成新的流程状态和凭证）。

**③ 4 路并行加速实测**（stub 是毫秒级，加 0.5 秒延迟做受控对比）：

```bash
# 串行：四个 stub 依次执行，每个跑完补 0.5 秒
time ( bash "$STUB/contract.sh" "张磊" "后端工程师" "32K"; sleep 0.5
       bash "$STUB/it-account.sh" "张磊" "zhanglei";       sleep 0.5
       bash "$STUB/device.sh" "张磊";                      sleep 0.5
       bash "$STUB/training.sh" "张磊";                    sleep 0.5 )
# 并行：四个 stub 同时执行——这就是 prep 节点的写法
time ( ( bash "$STUB/contract.sh" "张磊" "后端工程师" "32K"; sleep 0.5 ) &
       ( bash "$STUB/it-account.sh" "张磊" "zhanglei";       sleep 0.5 ) &
       ( bash "$STUB/device.sh" "张磊";                      sleep 0.5 ) &
       ( bash "$STUB/training.sh" "张磊";                    sleep 0.5 ) &
       wait )
```

| 跑法 | 实测耗时 | 解释 |
|---|---|---|
| 串行 | 2.137 秒 | 四件事依次做，耗时是四个之和 |
| 并行 | 0.542 秒 | 四件事同时做，耗时取决于最慢的那一个 |

> 接近 4 倍加速，证明 `( ) &` + `wait` 是真并发。耗时受机器影响会有出入，但"并行约等于串行四分之一"这个比例稳定。

**④ 双门 resume**：

```bash
# 从上一步输出取 resumeToken，批准第一个门
TOKEN1=$(python3 -c "import json; print(json.load(open('/tmp/d1-run1.json'))['requiresApproval']['resumeToken'])")
node "$LOBSTER" resume --mode tool --token "$TOKEN1" --approve yes | tee /tmp/d1-run2.json
# 此时 status 仍 needs_approval，但停在第二个门 account_gate，返回新 token
TOKEN2=$(python3 -c "import json; print(json.load(open('/tmp/d1-run2.json'))['requiresApproval']['resumeToken'])")
node "$LOBSTER" resume --mode tool --token "$TOKEN2" --approve yes    # 批准第二门
# 此时 status 回到 ok，requiresApproval = null，buddy 和 complete 执行
```

**⑤ reject 反面验证**（换李娜，第一个门拒绝）：

```bash
rm -f $STATE/*.json
node "$LOBSTER" run --mode tool --file "$WF" \
  --args-json '{"name":"李娜","pinyin":"lina","role":"产品经理","salary":"28K"}' > /tmp/d1-reject.json
TOKEN_R=$(python3 -c "import json; print(json.load(open('/tmp/d1-reject.json'))['requiresApproval']['resumeToken'])")
node "$LOBSTER" resume --mode tool --token "$TOKEN_R" --approve no    # --approve no 拒绝
ls $STATE/buddy.json     # 关键验证：检查 buddy 节点有没有产出文件
```

两处交叉验证："它说它停了"——resume 结果 `status` 是 `cancelled`；"它确实没做"——`ls $STATE/buddy.json` 返回 `No such file or directory`，`buddy` 节点根本没跑。（详见理论篇 §4）

**基线暴露的三个痛点** → 就是下一步封 Skill 要装进去的：① 发起方式不稳定；② `resumeToken` 易丢（别记成 `approvalId`）；③ 文件散落靠人记路径。

### 2.3 封装成 Skill（工业四步）

**第一步 · 建 Skill**，标准布局在 `workspace-onboarding/skills/running-onboarding-workflow/`（结构见 §0）。frontmatter：

```yaml
---
name: running-onboarding-workflow
description: Run the new-hire onboarding approval workflow for a single
  employee using the Lobster workflow engine. Use this skill whenever a new
  hire needs to go through onboarding — it drives 4 parallel preparation
  tracks and 2 human-in-the-loop approval gates. Handles the full lifecycle:
  start the workflow, hand back the resumeToken when it halts at an approval
  gate, and resume with approve or reject. The agent never approves on a
  human's behalf.
metadata:
  openclaw:
    requires:
      bins: ["node", "bash", "python3"]
---
```

> 要点：`name` 用动名词；`description` 第三人称含 what（用 Lobster 引擎跑入职审批）+ when（一名新员工要走入职流程），并点明 **"the agent never approves on a human's behalf"**（把 HiTL 边界写进 Agent 选 Skill 的第一眼依据）；`requires.bins` 显式声明 `node`/`bash`/`python3`。

正文写死三条硬规则（各对应 §2.2 一个痛点）：审批门是给人的（绝不替人批）、`resumeToken` 必须原样留存（不能用 `approvalId` 顶替）、启动前不要手动跑 stub。

**启动包装脚本 `run-onboarding.sh`**，对外只暴露三个动作：

```bash
run-onboarding.sh start  <姓名> <拼音> <岗位> <薪资>   # 启动工作流（到第一个审批门 halt）
run-onboarding.sh resume <resumeToken> yes|no           # 批准/拒绝一个审批门
run-onboarding.sh dry    <姓名> <拼音> <岗位> <薪资>   # dry-run，只打印执行计划
```

脚本内部做三件对应痛点的事：固定 lobster CLI 入口、由脚本自身位置（`BASH_SOURCE`）反推路径（不依赖调用方目录）、在调 lobster 前 export `$STUB`（指向 Skill 自己的 `scripts/`）和 `$STATE`（指向 workspace 根的 `stub-state/`）。**启动脚本还做前置检查**：工作流文件、lobster CLI、5 个 stub 齐不齐——任一缺失立即明确报错、退出码 3。

> **封装期两个路径坑（必解，详见理论篇 §5）**：① 脚本 / 工作流文件假设自己在 workspace 直属子目录（`../` 推错）→ stub 改读 `$STUB_STATE_DIR` 兜底、工作流删 `env` 块；② lobster 的 `env` 块优先级高于外部 export → 工作流文件里不能保留写死路径的 `env` 块。

**单独验证脚本 + 验证加载**（先隔离变量，不经 Agent）：

```bash
bash skills/running-onboarding-workflow/scripts/run-onboarding.sh start 周涛 zhoutao 后端工程师 30K
$OPENCLAW_HR_BIN skills info running-onboarding-workflow --agent onboarding
```

| 场景 | 命令 | 结果 |
|---|---|---|
| 1 启动 | `run-onboarding.sh start 周涛 zhoutao 后端工程师 30K` | `status: needs_approval`，停在 `contract_gate`，返回 `resumeToken` |
| 2 推进 | `resume <token1> yes` → `resume <token2> yes` | 第一次停到 `account_gate`（新 token），第二次 `status: ok`，`buddy.json` 生成 |
| 3 拒绝 | `resume <tokenR> no` | `status: cancelled`，`buddy.json` 未生成 |
| 4 边界 | 把脚本拷到 `/tmp` 当孤立脚本跑 | 检测到工作流文件缺失，明确报错，退出码 3 |

关键验证点：stub 状态文件正确落到 workspace 根的 `stub-state/`（不是 Skill 目录里）、`contract.json` 的候选人是"周涛"。加载输出 `✓ Ready`、`Source: openclaw-workspace`、`Visible to model: yes`——skill 总数从 52 变 53，无需重启 gateway。

**第二步 · 改核心 md 文档**：

### §2.5 halt 之后的三个兜底（实操层）

§2 把「start / 4 路并行 / halt / resume / reject」的端到端跑通了——但**流程停住之后**还有三件事 §2 没讲到，文档要补、Skill 要落实，否则 HR 真到生产环境会卡住。

#### 兜底 1 · 审批人看到的 prompt 必须是当下 stub 状态的投影

**问题**：当前 `hr-onboarding.lobster` 两个 `approval: true` 步骤的 `run` 是行内 Python，**只在 run 现场重读** `$STATE/*.json`。合同门在 start 那一刻 run 完就 halt 等待，halt 期间如果有人外部改了 `contract.json`（IT 系统追加字段、HR 修订试用期），HR 看到的 prompt 还是 start 那一刻的快照。

**当前实操行为**：账号门在 start 时 run 完一次出 prompt、HR 看到的是当时的 stub 状态；下次 resume 推进到 buddy 时不再跑账号门 run。Lobster 不感知 stub 被改。

**显式化做法**（可独立落、不动 Lobster 引擎）：

1. 把行内 Python 抽到 `scripts/build-approval-prompt.py <contract|account>`，工作流文件两处 `run` 各改成 `python3 "$STUB/build-approval-prompt.py" contract|account`。
2. 缺状态文件 → 脚本明确报错（行内 Python 失败是 traceback，更难读）。
3. `run-onboarding.sh resume` 分支里、调 lobster 之前**先调** `build-approval-prompt.py` 把两门当下 prompt 渲染出来打给 HR 看（标题行写「非陈旧快照」）。

**验证**（用真实 stub-state 跑）：

```bash
# stub 改前
STATE=.../stub-state python3 build-approval-prompt.py contract
# → HR 主管，请审批 陈思远 的劳动合同：岗位 后端开发 / 薪资 30K / 试用期 6个月...

# stub 改后（HR 修订 salary）
sed -i 's/30K/50K (终面特殊)/' .../stub-state/contract.json

STATE=.../stub-state python3 build-approval-prompt.py contract
# → HR 主管，请审批 陈思远 的劳动合同：岗位 后端开发 / 薪资 50K (终面特殊) / 试用期 6个月...
```

—prompt 立刻反映新值，证明"当下 stub 状态投影"成立。

#### 兜底 2 · halt 时把 token 落盘（pending-approvals/）

**问题**：当前 `resumeToken` 只活在对话上下文里——halt 返回的 JSON 含 `requiresApproval.resumeToken` 字段，HR 必须记下、两天后凭它去 resume。文档 §5 痛点 #2 已点出这是常见踩坑。

**事实澄清**：**流程状态本身没有丢**——Lobster 把它落盘在 `~/.lobster/state/`，按 `stateKey` 索引。丢的是 token 这个**指针字符串**（base64 编码 `{kind, stateKey}`）。

#### 三个兜底的因果链

| 兜底 | 解决的真问题 | 关键约束 |
|---|---|---|

#### 2. 5 个 stub 加时间字段

- **`items` 整段透传**——`items[0].prepared_at` / `items[0].updated_at` 也在结构化数据里能看到，prompt 是文本化表述、items 是结构化数据，两条路都给 HR。

#### §2.7 中档 + 重档落地：halt 时落盘 + 查询 Skill 输出 stub_changed_after_halt

§2.6 轻档解决了"内容 + 时间双维度当下"。但 HR 真正在生产环境还会遇到更深的问题：
- **stop 之后外部系统改了 stub**——IT 系统调整了试用期、HR 调了薪资、权限范围扩充。

理论篇 §13 的中档 + 重档给出了工程化路径：本节把这两档都落地。

#### 1. 中档：halt 时落盘 stub 快照

新增 `scripts/record-pending-approval.py`：

```bash
usage: record-pending-approval.py <gate> <pinyin>

```


```yaml
- id: account_gate
  run: |
```

- record 记的是 halt 前快照；build 产出含 `prompt` 的 JSON 供 Lobster 当审批问题。
- 真实 lobster 在 `approval: true` 节点的 run 全部跑完后才 halt。

#### 4. query-onboarding-status.py 关键片段

```python
def _shallow_diff(pre, cur):
    """浅层字段 diff：只比第一层。返回 [(field, pre_val, cur_val), ...]"""
    diffs = []
    keys = sorted(set(pre.keys()) | set(cur.keys()))
    for k in keys:
        p = pre.get(k)
        c = cur.get(k)
        if p != c:
            diffs.append({"field": k, "pre_halt": p, "current": c})
    return diffs


def _render_current_prompt(stub_scripts_dir, gate, state_dir):
    """调 build-approval-prompt.py 重渲染 prompt，保证 HR 看到的与 lobster run 一致"""
    proc = subprocess.run(
        ["python3", os.path.join(stub_scripts_dir, "build-approval-prompt.py"), gate],
        env={**os.environ, "STATE": state_dir},
        capture_output=True, text=True, timeout=10,
    )
    if proc.returncode == 0 and proc.stdout.strip():
        return json.loads(proc.stdout.strip()).get("prompt", "")
    return None


def _query_gate(workspace, stub_scripts_dir, gate, pinyin):
    pending_path = os.path.join(workspace, "pending-approvals", f"{pinyin}-{gate}.json")
    state_path = os.path.join(workspace, "stub-state", f"{gate}.json")
    if not os.path.exists(pending_path):
        return None
    with open(pending_path, encoding="utf-8") as f:
        rec = json.load(f)
    pre = rec.get("pre_halt_snapshot", {})
    cur = {}
    if os.path.exists(state_path):
        with open(state_path, encoding="utf-8") as f:
            cur = json.load(f)
    diffs = _shallow_diff(pre, cur)
    prompt_now = _render_current_prompt(stub_scripts_dir, gate,
                                         os.path.join(workspace, "stub-state"))
    return {
        "halted_at": rec.get("halted_at"),
        "stub_pre_halt": pre,
        "stub_current": cur,
        "stub_changed_after_halt": len(diffs) > 0,
        "diff_fields": diffs,
        "current_prompt": prompt_now,
    }
```

**关键设计**：

- **不递归嵌套结构**——stub 是平铺 JSON 字段；递归到嵌套字段反而引入歧义（如 `files: "岗位说明书/保密协议/员工手册确认书 已备齐"` 这种中文自然语句不该被 diff）。
- **`build-approval-prompt.py` 是 prompt 的唯一真源**——重档不能自己拼 prompt，那会导致"HR 用 query 看到的 prompt 和 lobster run 出来的 prompt 不一致"的实际不一致。
- **`stub_changed_after_halt` 包括 `updated_at`**——有可能是其他字段值完全相同但 updated_at 时间戳变了（外部系统触发了 stub 重写）。这也视为"被改"。

```bash
$HR cron add --name "onboard-review-livetest" \
  --agent onboarding --at "$ATTIME" \

  --timeout-seconds 120 --tools exec \
```

每个参数都有理由：`--at` 一次性；`--session isolated` 每次触发在全新隔离会话跑；`--no-deliver` 关掉结果投递（**最关键**，不加会因投递失败被整体判为出错）；`--keep-after-run` 跑完保留、便于查执行历史；`--tools exec` 最小权限。

到点后查执行历史：

```bash

```

**任务真的执行了的硬证据**：`status: ok` + `durationMs`（17 秒的真实耗时——空跑不可能耗 17 秒）+ 落盘文件 `review-state/review-张磊-day7.json` 的修改时间。三者一起。（`runAtMs` 等于 `--at` 设定值是必然的，不能单独用来证明执行发生了。）

```bash
  --agent onboarding --at "2026-05-23T10:00:00+08:00" \
  --session isolated --no-deliver --keep-after-run \
  --timeout-seconds 120 --tools exec \
  --message "请执行命令并把完整输出返回：bash ~/.openclaw-hr/workspace-onboarding/review-system/onboarding-review.sh 张磊 7"
```

4 个生产 review 任务都加 `--keep-after-run`（入职 review 是合规敏感流程，"第 30 天 review 到底跑没跑"HR 事后最该能回溯）。确认：


## §4 HTML 进度看板：generating-onboarding-dashboard

**脚本型 Skill**——把 HTML 看板生成脚本封成 Skill，解决"进度不可见"。

### 4.1 裸脚本跑通

看板读三类真实落盘数据：

- 5 个准备节点 ← `stub-state/<pinyin>/{contract,account,device,buddy,training}.json`（§2；兼容旧 `stub-state-<姓名>/`）
- 流程角标 ← 同目录 `workflow.json` 的 `status` / `current_step`
- 4 个 review 节点 ← `review-state/*.json`（§3）

生成脚本 `build-dashboard.py` 干 5 件事：

1. 扫描 `stub-state*`（新结构子目录 / 旧结构平铺）；跳过空壳；同名优先 `stub-state/<pinyin>/`。
2. 读 5 个准备节点 JSON 的 `status`。
3. 归类成 3 标准态：done 含「已审批 / **已通过** / 已开通 / … / 已排期」；pending 含「待审批 / … / 未就绪」。
4. 读 `workflow.json` 拼卡片角标；扫 `review-state/` 判 review 是否已触发。
5. 算整体进度 = 9 节点完成占比，套 HTML 模板输出（角标不计入百分比）。

```bash
# 推荐：走 Skill 脚本（路径已自推导）
bash skills/generating-onboarding-dashboard/scripts/build-dashboard.sh
# 或：ONBOARDING_WORKSPACE=<workspace根> python3 .../build-dashboard.py
# 终端打印「[角标] 准备 X/5 · review Y/4 · 整体 Z%」，产出 onboarding-dashboard.html
```

看板验证要素：卡片角标（如「等待审批 · 合同审批门」/「已完成」）、5 准备节点色块（绿=已完成 / 橙=进行中 / 灰=待办·待审批）、4 review 节点、整体进度条、页脚数据来源。

> **进度数字两个边界**：① 整体进度仍分不清"还没到时间"和"卡住了"（review 要到日子才变绿）——看角标是否 `halted` 才能回答"谁卡在审批门"；准备节点全绿但角标仍「等待审批」是正常现象。② 是经办 HR 的"个案视图"，不做按部门 / 月份的聚合大盘。

#### 审批门 status 约定（与 lobster / refresh 一致）

| 时机 | stub `status` | 看板 |
|---|---|---|
| 进入审批门（halt 前） | **待审批** | pending（灰） |
| 审批通过后 | **已通过**（兼容「已审批」） | done（绿） |
| `refresh-gate-stubs` 保鲜 | 保持 **待审批** | 不假装已批 |

`hr-onboarding.lobster` 进门写「待审批」，过门写「已通过」；`refresh-gate-stubs.py` 刷新时也写「待审批」。细则见 Skill 内 `references/dashboard-spec.md` 与理论篇 §7。

## §5 三 Skill 端到端串联

至此入职子 Agent 三块能力全部封装成工业级 Skill。它们通过 workspace 根的状态目录形成一条完整数据链：

```
running-onboarding-workflow    ──写──▶  stub-state/<pinyin>/   （5 准备节点 + workflow.json）
running-onboarding-review      ──写──▶  review-state/          （4 个 review 节点）
generating-onboarding-dashboard ──读──▶  stub-state*/ + workflow.json + review-state/
```

一条典型的端到端剧本：

1. **启动入职审批**：Agent 触发 `running-onboarding-workflow`，4 路并行准备 → 进 `contract_gate` 时合同 stub 写「待审批」→ halt，交回 `resumeToken`；看板角标为「等待审批 · 合同审批门」。
2. **双门审批**：HR 主管批合同（resume yes）→ 合同改「已通过」、账号门写「待审批」→ 停在 `account_gate`（新 token）→ IT 安全批账号 → 账号改「已通过」→ `buddy` / `complete`，`workflow.json` 记 `completed`；complete 钩子注册 7/30/60/90 天 Cron。
3. **定时跟进**：4 个 `--at` Cron 到点触发 `running-onboarding-review`，各产出 `review-state/review-<姓名>-day<N>.json`。
4. **进度总览**：任何时候 Agent 触发 `generating-onboarding-dashboard`，扫候选人目录 + `workflow.json` + review-state，出带角标的 HTML 看板。

> 看板能跑通的前提，是上游 Skill 把数据真落到 workspace 根的 `stub-state/<pinyin>/`，不是各自 Skill 目录（详见理论篇 §8）。

### 二、Cron review 任务

> Cron review 任务不是一个配置文件，而是 4 条 `openclaw cron add` 注册命令（7/30/60/90 天），注册后存储在 `~/.openclaw-hr/cron/jobs.json`。改触发时间改 `cron add` 的 `--at` 参数。**所有任务务必带 `--no-deliver`**。

### 三、常见改造场景

| 改造场景 | 怎么改 |
|---|---|
| 接真实 IT / 设备系统 | 改 `running-onboarding-workflow/scripts/` 下对应 stub 脚本，工作流文件、其余 Skill 都不动 |
| 加 / 改一个审批门 | 改 `hr-onboarding.lobster` 的 `steps`：新步骤带 `run` 产出含 `prompt` 的 JSON + `approval: true` |
| 换 review 时点 | 改 `onboarding-review.sh` 的 `case "$DAY"` 分支，再配对应 `--at` Cron 任务 |
| 换公司 / 换看板样式 | 改 `build-dashboard.py` 内嵌的 HTML 模板与 CSS |
| 让看板自动刷新 | 把 `build-dashboard.sh` 配成一个 `--cron` 周期 Cron 任务（如每天 8:00 重生成），看板从"手动快照"变"准实时" |
| 加"逾期"状态 | 给每个节点定 deadline，`build-dashboard.py` 算状态时把超 deadline 仍未完成的节点标红 |
| 加聚合视图 | 在看板里增加按部门 / 入职月份聚合的统计，从"经办个案视图"补上"管理层大盘" |

> **改造底线（合规红线，不是可选项）**：关键决策节点（涉及法律责任、资金、权限的）必须保留 `approval: true` 审批门。把审批门去掉换成全自动，流程跑得更快，但 HiTL 这道工业级安全保障也就没了。（详见理论篇 §10）

### 四、拿到附件包后的推荐路径

1. **先看实验记录**——理解"为什么这样设计"，尤其是三个前置发现（`steps` 严格串行 / `approval` 不做模板替换 / `args` 模板可用），每条都省一次踩坑。
2. **跑通一条范式**——把 `--args-json` 换成自己业务的新员工，跑一遍 `hr-onboarding.lobster`，体验 halt → resume → reject 全流程。
3. **改造**——上表"使用 / 改造路径"写明了想改什么改哪里。换业务场景时，先用 §9（理论篇）的 4 维度判断准则确认走 Lobster 还是 Pipeline，再选对应骨架改造。

## 附录 A：Lobster DSL 速查表

| 键 / 写法 | 作用 | 备注 |
|---|---|---|
| `name:` | 工作流名 | — |
| `args:` | 输入参数块，每个参数带 `{ default: ... }` | 用 `--args-json '{...}'` 覆盖 |
| `env:` | 环境变量块 | **优先级高于外部 export**；封 Skill 时不写死路径的 `env` 块（非文档行为） |
| `steps:` | 有序节点列表 | **严格串行**，没有 `parallel`/`needs`/`depends` |
| `id:` | 步骤名 | resume 条件里用 `$<id>.approved` 引用 |
| `run:` | 步骤执行的 shell（做 `${...}` 模板替换） | `run step` 是 shell，继承外部环境变量 |
| `approval: true` | 标记审批门（**不做**模板替换） | 审批信息走 `run` 产出 JSON 的 `prompt` / `items` 字段 |
| `when:` | 执行条件，为假则跳过 | 声明式依赖，不是阻断机制本身 |
| `${name}` | 引用 `args` 参数 | 只在做模板替换的字段里生效 |
| **并行写法** | 单个 `run` step 内 `( cmd ) &` ×N + `wait` | OS 级真并发，与引擎无关 |

命令：
- `node "$LOBSTER" run --dry-run --mode tool --file "$WF" --args-json '{...}'`——dry-run 看计划
- `node "$LOBSTER" run --mode tool --file "$WF" --args-json '{...}'`——真跑（halt 返回 `resumeToken`）
- `node "$LOBSTER" resume --mode tool --token "$TOKEN" --approve yes|no`——批准/拒绝
- 流程状态默认落 `~/.lobster/state/`，扛得住进程退出、机器重启

## 附录 B：Cron schedule 速查表

| 参数 | 作用 |
|---|---|
| `--at "<ISO时刻>"` | 一次性任务，到某时刻跑一次（入职 review 用这个）；触发后自动变 `disabled` |
| `--cron "<cron表达式>"` | 周期任务，按 cron 表达式重复（周报/月报用） |
| `--every "<时长>"` | 周期任务，每隔固定时长跑一次 |
| `--agent onboarding` | 绑定到哪个子 Agent |
| `--session isolated` | 每次触发在全新隔离会话跑，不带历史上下文 |
| `--no-deliver` | **必带**——关掉结果投递（HR 隔离 profile 没配 channel，不加会因投递失败被判出错） |
| `--keep-after-run` | 跑完保留任务定义和执行历史，便于审计回溯 |
| `--timeout-seconds N` | 超时时间 |
| `--tools exec` | 最小权限只给 exec |
| `--message "..."` | 触发时发给子 Agent 的任务 |

命令：
- `cron add ...`——注册任务
- `cron list --agent onboarding`——列任务
- `cron runs --id <jobId>`——查执行历史（`--id` 是**选项**）
- `cron get <id>` / `cron show <id>`——查任务详情（**位置参数**，与 `cron runs` 风格不统一，易踩）

## 附录 C：踩坑速查表

| # | 症状 | 原因 | 对策 |
|---|---|---|---|
| 1 | 写四个并列 step 想并行，实际是串行 | `steps` 严格串行，没有 `parallel` key | 并行写在单个 `run` step 内：`( ) &` ×N + `wait` |
| 2 | dry-run 看不出串/并行、看不出 stub 缺失 | dry-run 只解析不真跑 | 4 路并行、stub 产出、halt 返回值都要真跑验证；部署时把 5 个 stub 一次放全 |
| 3 | 审批问题里 `${name}` 原样显示没被替换 | `approval` 字段不做模板替换（不报错的坑） | 审批步骤同时带 `run`（产出含 `prompt` 的 JSON）+ `approval: true` |
| 4 | HR 批准后流程接不回去 | 记成了 `approvalId`，丢了 `resumeToken` | `resumeToken` 才是唯一钥匙，原样留存；每次 halt 换新 token，用最新的 |
| 5 | 封 Skill 后 stub 状态落错目录 / 找不到 | 脚本用 `../` 推 workspace，搬目录后深度变了 | 由脚本自身位置反推稳定锚点 + 环境变量兜底（连踩三次的坑） |
| 6 | 启动脚本 export 的路径被覆盖 | `.lobster` 的 `env` 块优先级高于外部 export | 工作流文件里不保留写死路径的 `env` 块 |
| 7 | 把脚本拷到别处当孤立脚本跑，报看不懂的错 | 缺工作流文件 / stub | 启动脚本做前置检查，缺文件立即报错、退出码 3 |
| 8 | Cron 任务跑成功却被判为出错（Channel is required） | HR 隔离 profile 没配 channel，投递失败 | 所有 Cron 任务带 `--no-deliver` |
| 9 | `--at` 任务跑完变 `disabled` | `--at` 一次性任务的正常行为 | 不是故障；要周期用 `--cron`/`--every` |
| 10 | `cron runs <id>` 报错 | `cron runs` 的 `--id` 是选项不是位置参数 | 用 `cron runs --id <jobId>`；`cron get`/`show` 才是位置参数 |
| 11 | 看板把缺失节点填成"已完成" | 没把"不编造"写成硬规则 | SKILL.md + `description` 写死"never invents any status"，缺失显示「未就绪」 |
| 12 | Agent 幻觉"看板已存在"偷懒不生成 | LLM 常见幻觉 | 发任务前 `rm` 旧文件、prompt 里显式声明"文件不存在，不要假设已存在" |
| 13 | 看板漏算某档进度 | 状态归类表没穷举真实数据里所有 status 文案 | 归类表要穷举（含「已通过」「待审批」），漏一个就少算一档 |
| 14 | 准备节点全绿却仍在等审批 | 进门误写「已审批」、或看板不读 `workflow.json` | 进门写「待审批」、过门写「已通过」；卡片角标读 workflow 才是「卡在哪扇门」 |
| 15 | refresh / query 后看板把待批节点刷成绿 | `refresh-gate-stubs` 用了「已审批」 | 保鲜刷新保持「待审批」，不假装已批 |
| 16 | Agent 替人批准/拒绝了审批门 | 没把 HiTL 边界写进 description + 硬规则 | `description` 写 "the agent never approves on a human's behalf"，正文写死"审批门是给人的" |
