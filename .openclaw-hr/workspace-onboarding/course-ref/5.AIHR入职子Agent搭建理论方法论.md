## §0 一句话主旨：从"靠人盯流程"到"引擎级 HiTL 工作流"

星桥科技的 HR 收到邮件——招聘子 Agent 评出的优秀候选人张磊接受 Offer，下周一报到。报到前 HR 要把入职准备铺开：劳动合同要 HR 主管审、IT 账号要 IT 安全过目、办公设备要配、带教 Buddy 要找、入职第一课要排期。**五件事分属三四个部门，大多互不相干，但 HR 习惯一项一项推、靠脑子记哪件做完了——漏一个，就是张磊报到当天没有电脑。** 报到之后还有第 7 / 30 / 60 / 90 天四次回访，散落在整整一个季度里，靠翻日历想起来，想不起来就错过。

这就是入职的工作模式：**一件事被拆成多个步骤，步骤之间有先后、有审批、有时间触发，靠人盯着把它们串起来。** 入职子 Agent 要做的，就是把这套"靠人盯"换成"引擎盯"。

> **交付定位**：入职子 Agent 不是 demo 级玩具，而是——① 能停在审批点等真人批（HiTL 真 halt）、② 能 4 路并行加速准备工作、③ 能在被拒时真阻断后续动作、④ 到点自动跑 7/30/60/90 天 review、⑤ 用 HTML 看板让进度可见的**工业级工作流子 Agent**。它不锁定星桥科技——换成自己业务的新员工和审批节点，一样能跑。

本集比"一个入职子 Agent"更值钱的，是夹在入职与培训两个子 Agent 中间的一个**判断力**：拿到一个新需求，怎么知道该用流程编排（Lobster），还是该用生成 Pipeline（ADDIE）？这两种范式表面很像，选错工程量成倍上涨。§1、§9 把这套判断讲透。

## §1 两种编排范式全景：流程编排 vs 生成 Pipeline

**编排范式**，指"把一个复杂任务拆成多个步骤、再把这些步骤组织起来跑"的方式。Agent 系统里几乎所有稍复杂的任务都要编排，但编排不止一种。Lesson 2-2 用到两种：


| 维度          | 流程编排型                     | 生成 Pipeline 型            |
| ----------- | ------------------------- | ------------------------ |
| 本集代表        | **入职子 Agent、Lobster 工作流** | 培训子 Agent、ADDIE Pipeline |
| 步骤的性质       | 混合——shell 命令、脚本调用、真人审批    | 同质——每一步都是 LLM 生成任务       |
| 步骤间的关系      | 有强先后依赖，有的步骤还要等审批          | 有上下游，前一步产出喂给后一步          |
| 要不要等人       | **要**——关键节点必须停下等真人点头      | 不要——从头到尾一次跑完             |
| 要不要按时间触发    | **要**——有的步骤要到某个时点才跑       | 不要——一次性生成                |
| 工程上要解决的核心问题 | 流程能**停得住、接得回、拒得掉**        | 阶段间的**数据契约**严丝合缝           |




### 生成 Pipeline 型：一句话区分

- **流程编排型**：混合 shell、脚本、真人审批——靠**引擎级**的 `approval` / `when` / `resumeToken` 锁住「停得住、接得回、拒得掉」。
- **生成 Pipeline 型**：每一步都是同质的 LLM 生成任务，前一步产出落盘成文件、后一步显式 `cat` 进来——靠 **prompt 设计**锁住「阶段间数据契约严丝合缝」。典型如培训子 Agent 的 ADDIE Pipeline（详见 `7.AIHR培训子Agent搭建理论方法论.md` §5）。

> 短记：**纯 LLM 生成 → Pipeline；混合命令、脚本、审批 → Lobster**（详见 §9 4 维度判断表）。

### 为什么要先分清这两种范式：两个反例

这两种范式表面上很像——都是"多步任务串起来跑"。正因为像才容易混用，而混用的代价是工程量成倍上涨。

- **反例一：把入职审批写成一条 prompt 链。** 入职审批的关键，是合同条款、账号权限这种节点必须停下来等真人批。用一条 prompt 链做——让大模型"先准备合同，再问 HR 批不批，批了就继续"——表面能跑，但那句"问 HR 批不批"只是 prompt 里的一句话。**prompt 链没有引擎级的暂停机制**：它不会真的把流程停下、把当前状态落盘、把控制权交还给人、等人回来再接着跑。实际发生的，要么是大模型自己假设一个答复继续往下，要么这一轮对话到此结束、下次从头说起。审批门成了摆设。HiTL 要真停，靠的不是 prompt 措辞，是引擎层面的 **halt 和 resume**。
- **反例二：把培训物料生成做成 Lobster 工作流。** 培训物料生成的若干步骤——分析需求、设计大纲、写讲师手册、出测试题——确实有上下游顺序，但它们之间没有"强依赖"那种硬约束：没有哪一步要停下等人审批，也没有哪一步要等到某个时点才能跑。硬套 Lobster 工作流，你要为它单独写工作流文件、配置每个步骤、处理审批字段——而这些机制一个都用不上。**工作流文件凭空多出一层复杂度，却没换来任何东西。**

> **结论**：选对范式，工程量是合理的；选错范式，要么是该停的停不住（反例一），要么是不该有的复杂度凭空冒出来（反例二）。

**先有手感，再有准则**：本集不一上来给判断准则，而是先把入职（Lobster）和培训（ADDIE）两种范式都真跑一遍，最后 §9 才回头给出 4 维度判断表。这套判断力不锁定 HR——可推广到任何 Agent 系统设计。

## §2 入职业务结构：为什么必须用工作流编排

入职子 Agent 的第一个问题不是"怎么写代码"，是"入职这件事到底长什么样"。看清业务结构，才知道为什么必须用工作流编排。

### 入职要协调的五件准备工作

照星桥科技 HR 知识库《09-入职流程》的入职准备清单，要协调五件事：


| 准备工作       | 归口部门 | 关键性          |
| ---------- | ---- | ------------ |
| 劳动合同起草     | HR   | 高——条款定法律责任   |
| IT 账号申请    | IT   | 高——权限定系统访问范围 |
| 办公设备配置     | 行政   | 中——事务性工作     |
| 入职培训排期     | 培训   | 中——事务性工作     |
| Buddy 带教匹配 | 用人部门 | 中——要占用一位资深员工 |


**前四件——合同、账号、设备、培训——彼此不相干**：起草合同不需要等账号开通，排培训不需要等设备到位。没有依赖关系，就可以同时做。**第五件 Buddy 匹配不一样，它要等**：只有合同和账号都确认了、这个人真的会入职，才值得占用一位资深员工的带教精力。

于是入职的结构是：**四件准备工作并行推进 → 合同审批 → 账号权限审批 → Buddy 匹配 → 入职归档。** 这就是入职子 Agent 要编排的五个工作流节点。拓扑里有两类节点：带锁标记的"合同审批""账号权限审批"是**审批门**（流程跑到这里会停、把待审内容交给真人）；其余是普通执行节点。Buddy 匹配和归档带**执行条件**，只有两个审批门都通过才会跑。

### 三个特征决定入职必须用工作流编排

这三个特征，正好是 §1"流程编排型"范式的三个判据：

1. **步骤间有强先后依赖。** Buddy 匹配必须排在两个审批之后，归档必须排在所有步骤之后。这个顺序不是建议、是硬约束——审批还没过就匹配 Buddy，是白白占用一位资深员工的时间。流程编排范式天然能表达这种先后约束。
2. **关键节点必须有审批门。** 合同条款关乎法律责任、账号权限关乎系统安全——这两个节点不能让 AI 自己拍板。流程必须能停在这里、把待审内容交给真人、等批准了再继续。这是 HiTL 的硬要求，靠 prompt 措辞实现不了，要靠引擎级的 halt 和 resume。
3. **多部门协调，漏一个就出事。** 五件准备工作分属四个部门，靠人脑记容易漏，漏一个就是新员工报到当天没电脑。把整个流程写成一个工作流文件，五个节点白纸黑字列在文件里，引擎照着跑，漏不了；文件还能版本管理、能审计——谁批的、什么时候批的，都有迹可查。

> **业务背景**：据 SHRM（美国人力资源管理协会）数据，约 **20% 的员工流失发生在入职后的前 45 天**。入职体验差、流程出纰漏是新人早期离职的重要原因之一。这意味着入职流程的"不出错"本身就有留人价值——它不只是行政事务，是留住人的第一道关。这一点在 §6 的 7/30/60/90 天 review 里再展开（第 7、30 天两个 review 节点正好落在这 45 天窗口里）。



### 账号和设备申请用 stub：工业级解耦

入职流程里的 IT 账号开通、设备配置，真实环境要调用企业的 IT 工单系统、AD 域控、行政设备系统——对接这些是企业自己的开发工作，不是本集重点。本集用 **stub（桩——一段模拟真实系统行为的占位脚本）** 代替：每个 stub 脚本模拟一个企业系统，被调用时把"已申请 / 已开通"的结构化状态写成一个 JSON 文件、再打印一行进度。

> **用 stub 不是偷工减料，是工业级解耦设计。** 工作流文件只负责"编排"——什么时候调账号系统、调完卡哪个审批门——它不关心账号系统内部怎么实现。真实上线时，把 stub 脚本的内容换成调用企业真实接口的代码，**工作流文件一个字都不用动**。编排逻辑和系统对接彻底分开，这正是工作流文件作为"流程骨架"的价值。

## §3 Lobster 工作流文件三大块与三个前置发现

把入职拆成五个节点后，要落成一个真实的工作流文件。Lobster 工作流文件是一个后缀 `.lobster` 的文本文件，结构分三大块：


| 块       | 作用                            |
| ------- | ----------------------------- |
| `args`  | 声明工作流的输入参数，每个参数可带默认值          |
| `env`   | 声明环境变量，供步骤里引用（比如 stub 脚本所在目录） |
| `steps` | 工作流的核心——一个有序节点列表，每个节点是一个步骤    |


`steps` 是重点。每个步骤至少有一个 `id`（步骤名），通常带这几个字段之一或几个：

- `run`：这个步骤要执行的 shell 脚本。
- `approval: true`：把这个步骤标记成审批门，流程跑到这里会暂停。
- `when`：执行条件，条件为假这个步骤就跳过。

入职工作流 `hr-onboarding.lobster` 就是用这三大块写成的，不到 90 行、五个节点：`prep`（4 路并行准备）、`contract_gate`（合同审批门）、`account_gate`（账号权限审批门）、`buddy`（带 `when` 条件）、`complete`（带 `when` 条件）。

这个文件结构看起来直白，但里面有三处，是写之前不知道就一定会踩的坑。这三处也正是把 Lobster 用对的关键。

### 前置发现 1：steps 严格串行，并行要写在单个步骤内部

**最自然的直觉是错的**——以为写四个并列的 step、让 Lobster 自己并行调度，或去找一个 `parallel:` / `needs:` 并行声明 key。

**Lobster 的 steps 是严格串行的。** 翻 Lobster 的编译产物，工作流的执行核心是一个朴素循环 `for (idx = 0; idx < steps.length; idx++)`，按数组顺序一个接一个跑。它**没有** `needs` / `depends` / `parallel` 这类声明式并行 key。你写四个并列的 step，得到的是串行。

> **更危险的是：这个错误 dry-run 阶段看不出来。** dry-run 只打印执行计划、不真正跑，四个 step 的计划照样列得整整齐齐。要等到真跑、计时，才会发现四件事是依次做完的——错误被推迟到了最危险的环节。

**正确做法：把并行写在单个步骤内部，用 shell 的后台任务实现。** `prep` 节点的 `run` 里用 `( ... ) &` 把命令放进后台子 shell，四行 `&` 就是四个后台子进程同时跑，最后一行 `wait` 等它们全部结束。这是**操作系统级的真并发**——和 Lobster 引擎无关，是 shell 本来就有的能力。`prep` 在 Lobster 眼里仍是一个普通串行步骤，并行发生在它的 `run` 脚本内部。

> **一句话记住**：Lobster 负责"步骤之间的串行编排"，并行要靠步骤内部的 shell 自己实现。实测这个 `( ) &` 写法带来接近 4 倍加速（§实践手册 2.4）。



### 前置发现 2：approval 字段不做模板替换（不报错的坑）

审批门要给真人看一句话——"HR 主管，请审批张磊的劳动合同……"。这句里的"张磊"应从工作流参数 `${name}` 来。**最自然的写法是直接写进** `approval` **字段**：

```
approval: "HR 主管，请审批 ${name} 的劳动合同，岗位 ${role}。是否批准？"
```

**这样写，真跑出来的审批问题里** `${name}` ****`${role}` **会原样显示，不会被替换成"张磊""后端工程师"。** 这是一个**不报错的坑**——工作流照样跑、审批门照样停，只是交给真人看的那句话里带着没被替换的 `${name}` 字样，像一句没写完的话。

翻 Lobster 源码能看到原因：工作流引擎对 `run` / `command` / `pipeline` / `stdin` 这几个字段都做 `${...}` 模板替换，**唯独** `approval` **字段不做**——它被直接交给审批请求的提取逻辑，全程不经过模板替换。这种细节文档不会写，是读编译产物才能确认的**非文档行为**。

**绕过它的办法**藏在审批请求的提取逻辑里：提取逻辑会先看这个步骤 `run` 产出的 JSON——**如果 JSON 里有一个** `prompt` **字段，就用** `prompt` **的值作为审批问题**。而 `run` 是做模板替换的。所以正确写法是：**审批步骤同时带** `run` **和** `approval: true`。`run` 负责产出一段 JSON，JSON 里的 `prompt` 字段已经把候选人专属信息拼好（用一行 Python 读 stub 产出的 `contract.json` 拼出来）；`approval: true` 只负责把这个步骤标记成审批门。审批信息就这样绕过了 `approval` 字段的限制。

### 前置发现 3：args 配合模板，一个文件服务所有新员工（好消息）

文件顶部的 `args` 块声明了 `name` / `pinyin` / `role` / `salary` 四个参数，各带默认值。步骤里用 `${name}` 引用它们。调用工作流时用 `--args-json` 传一个 JSON 就能覆盖默认值：

```
--args-json '{"name":"张磊","pinyin":"zhanglei","role":"后端工程师","salary":"32K"}'
```

> **这次跑张磊就传张磊，下次跑李娜就传李娜——工作流文件本身一个字都不用改。** `args` + `${...}` 模板，让一个工作流文件能服务任意一名新员工。这正是入职流程"写成文件、反复复用"价值的落点：流程是固定的，新员工是变量，变量从参数进。

## §4 为什么是 Lobster：三种方案的取舍

把入职流程编排成 Lobster 工作流文件，相对另外三种做法各有取舍：


| 对比方案                              | 为什么不选                                                                                                                                                                                           |
| --------------------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| **prompt 链**                      | 没有引擎级暂停机制，"等 HR 审批"只是 prompt 里一句话，流程不会真停、状态不落盘、控制权不交还给人。Lobster 的审批门是引擎能力：跑到 `approval: true` 的步骤，引擎会把流程状态落盘、生成一个恢复凭证、把控制权真正交出去。                                                                |
| **自己手写状态机**                       | 你完全可以用 Python 自己写状态机实现 halt / resume——但要自己设计状态怎么落盘、用什么索引找回、怎么把待审内容结构化交出、恢复时怎么校验。这些是真实的工程量。Lobster 把它们做成引擎内置能力：审批门 halt 时直接返回一个 `resumeToken`，流程状态由引擎落盘、用一个 `stateKey` 索引。该自己造的轮子，Lobster 已经造好了。 |
| **成熟工作流引擎（LangGraph / Temporal）** | 它们也做 HiTL 审批、而且很成熟。这里用 Lobster 不是因为它更强，而是因为它是 **OpenClaw 的内置插件**：和这套子 Agent 生态、skill / tool 体系天然打通，不用额外引入一个框架、再处理它与 OpenClaw 的集成和部署。                                                            |


> **可推广的判断力**：你在这里学到的 halt / resume / reject，换到 LangGraph 就对应 `interrupt()` 和 `checkpoint`，是同一套 HiTL 思路。通用场景下 LangGraph、Temporal 是很好的选择；在 OpenClaw 体系内做 HR 子 Agent，Lobster 是接入成本最低、最顺手的那个。



### halt / resume 的机制本质：凭证 ≠ 状态

要把"恢复凭证"和"流程状态"分清——它们是两样东西。把 `resumeToken` 用 base64 解开，里面**没有流程状态，只有一个指针**，形如 `{"kind":"workflow-file","stateKey":"workflow_resume_<UUID>"}`。真正的流程状态由 Lobster 引擎持久化到磁盘（默认存在 `~/.lobster/state/`），`stateKey` 是找到它的钥匙。

> `~/.lobster/state/` 是主目录下的固定目录，所以一个 halt 住的流程**扛得住进程退出、机器重启**——resume 命令和真跑本来就是两个不同进程，能接上正是因为状态落在磁盘上。这是 prompt 链给不了的。



### 一条工作流可串多个审批门

入职现实里就是多人多节点审批：合同要 HR 主管批、账号权限要 IT 安全批。每个审批门**独立 halt、独立 resume，每次 halt 都生成新 token**——下一步 resume 必须用最新的那个 token。批准第一个门后流程会停到第二个门（`prompt` 换成账号权限审批、审批人从 HR 主管换成 IT 安全负责人），返回一个全新的 `resumeToken`。

### reject 路径：两个角度交叉验证"真阻断"

批准路径全通了，但 HiTL 的另一半同样重要：**审批被拒，流程要真的停下。** 换一个候选人（产品经理李娜）故意在第一个门拒绝（`--approve no`），验证要看两处输出：

- **第一处**：resume 的结果 `status` 是 `cancelled`——这是 Lobster 自己报告的，属于"它说它停了"。
- **第二处（最硬的证据）**：`ls $STATE/buddy.json` 返回 `No such file or directory`——`buddy.json` 不存在，说明 `buddy` 节点根本没跑。这是操作系统的客观事实，属于"它确实没做"。

> **为什么这一步特别重要**：判断"流程是否真的被拒绝阻断"，`status: cancelled` 是"它说它停了"，`buddy.json` 不存在是"它确实没做"。两个角度交叉验证，结论才硬。人类的"不批准"，真正阻断了后续动作——AI 不会在被拒之后还擅自往下推。

> **一个易混淆点**：`buddy` / `complete` 带的 `when: $contract_gate.approved && $account_gate.approved` 是**声明式的依赖声明，不是阻断机制本身**。真正让下游不执行的，是 reject 时 Lobster 引擎在被拒的门处**立即终止整条工作流**。

### §4.5 halt 之后的三个易被忽略工程问题

halt / resume 机制让流程「停得住、接得回、拒得掉」——但流程停住之后还有三件事文档没系统讲，工程上必须自己落实：审批人看到的 prompt 是不是当下的、HR 忘了 token 怎么找回、能不能让 Agent 主动报告「流程卡在哪」。

#### 1. 审批人看到的 prompt 是不是当下的 stub 状态？

**当前实现的事实**：`hr-onboarding.lobster` 两个 `approval: true` 步骤的 `run` 用行内 Python 拼 prompt：`cat "$STATE/<gate>.json" | python3 -c '...拼 prompt...'`。

**Lobster 的语义**：每次走到一个 `approval: true` 步骤——无论是 start 后第一次到、还是上一个门被批准后 resume 推进到——`run` 都会**现场执行**一次。所以账号门 halt 时跑一次行内 Python、HR 看到的是当下的 `$STATE/account.json` 内容；下一次 resume 推进到 buddy 时就不再跑账号门 run 了。

**潜在陈旧点**：合同门在 start 那一刻跑完一次 run 后就 halt 等待。如果在 halt 期间有人外部改了 `$STATE/contract.json`（真实环境接 AD / 企业微信时这是常态——IT 系统在背景追加工号、HR 修订试用期），HR 看到的 prompt 还是 start 那一刻的快照。**Lobster 不会感知 stub 被改**——它只在 run 现场重读，halt 之后不再读。

**显式化的做法（不破坏 Lobster 语义）**：把行内 Python 抽到一个独立脚本 `scripts/build-approval-prompt.py <contract|account>`，工作流文件两处 `run` 各改成一行 `python3 "$STUB/build-approval-prompt.py" contract|account`。这样：

- 每次走到审批门——脚本被现场调用、当下读 `$STATE/<gate>.json`、拼出当下 prompt。
- 代码集中在一处——合同门加字段、账号门加内网访问范围都改这一个脚本。
- 缺状态文件立刻 fail——脚本检查 `$STATE/<gate>.json` 是否存在，缺失给明确报错（行内 Python 失败会变成 traceback，更难读）。

**进一步**：在 `run-onboarding.sh resume <token> yes|no` 之前，**先调** `build-approval-prompt.py` 把两门当下 prompt 渲染出来打给 HR 看（标题行写「非陈旧快照」），HR 看完确认无误再 yes / no。这样 HR 看到的预览和 lobster 内部用的 prompt **来自同一份脚本**——不会出现两份 prompt 内容不一致。

#### 2. HR 隔两天忘了 `resumeToken` 怎么办？

**当前实现的事实**：

- 流程状态由 Lobster 引擎持久化到 `~/.lobster/state/`，按 `stateKey` 索引（§4 已述）。
- `resumeToken` 是 base64 编码的指针：`{"kind":"workflow-file","stateKey":"workflow_resume_<UUID>"}`——只包含指针，不含流程状态本身。
- 文档 §5 痛点表第 2 条原文：「`resumeToken` 这把钥匙容易丢 | 不知道区别的人很可能记下短小的 `approvalId`、丢掉长长的 `resumeToken`，HR 批准后流程接不回去」。

也就是说，**流程状态本身没有丢**——它一直躺在 `~/.lobster/state/`。丢的是 token 这个**指针字符串**。当前 Skill 实现里 token 只活在对话上下文里，**没有任何工程化兜底**。

**三种落地方案**（按推荐顺序）：

| 方案 | 做什么 | 改动量 | 兜底强度 |
|---|---|---|---|
| **A · halt 时落盘** | 每个 `approval: true` 步骤的 run 在拼完 prompt 后**同时**调 `record-pending-approval.py` 写 `pending-approvals/<pinyin>-<gate>.json`（含 token、候选人、prompt、等待时间） | 1 个新脚本 + lobster run 步骤小改 | 强：HR 忘 token 也能直接 `ls pending-approvals/` |
| **B · 让 lobster 自带查询** | 写一个 `list-pending-approvals.sh` 扫 `~/.lobster/state/`、列候选人 / 等待门 / 等待天数 | 中，依赖 lobster 状态文件结构 | 中：能找到 halt 流程，但 token 需现场 base64 重构 |
| **C · 文档写明找回路径** | SKILL.md 加一条「token 丢失 → `ls ~/.lobster/state/` 找 stateKey → base64 重构」 | 最小，0 行代码 | 弱：依赖人记得 lobster 内部细节 |

**A 是推荐方案**，理由：

- `pending-approvals/` 与 `stub-state/`、`review-state/` 同类——workspace 根的跨 Skill 数据资产，HR 丢失 token 时第一站就去那查。
- 不动 Lobster 引擎、不动 lobster 状态目录——将来 lobster 升级不会破。
- 一份 JSON 里同时存 token 和当下 prompt，HR 打开就知道「我在批 X 的合同 / 账号 / 等了几天 / 材料齐不齐」——回应「两天后打开就能看到当下状态」的需求。

#### 3. 能不能封装一个 Skill 查「X 的入职流程到哪了」？

**结论：能，且应当**。但**只读不写、绝不替人批**。

封装成查询 Skill `querying-onboarding-status` 是安全的，理由：

1. **只读**——读 `~/.lobster/state/`（lobster 自己落盘的事实数据）、读 `stub-state/*.json`、调 `build-approval-prompt.py` 渲染当下 prompt。**不**调 lobster resume、不写 approvalId、不修改任何状态文件。
2. **复用**——和 `generating-onboarding-dashboard` 一类：只读快照、永远不触发「AI 替人批」那条红线。
3. **不引入新审批路径**——查询 Skill 返回 `resumeToken` 字符串，HR 拿到后**仍须走** `run-onboarding.sh resume <token> yes|no` 的原始路径。审批决策权始终在人。
4. **合文档 §5 痛点 #2 的拍**——把「靠人记得 lobster 内部细节」换成「问 Skill」，正是 Skill 封装想解决的事。

**SKILL.md 硬规则必须写明**：

> **本 Skill 只负责查询，不负责批准 / 拒绝。** 拿到 token 之后，HR 仍须用 `running-onboarding-workflow/scripts/run-onboarding.sh resume <token> yes|no` 走人工确认路径。审批决策权始终在人，不在本 Skill。

**与方案 A 的关系**——两者**互补**，不是二选一：

- A 在 halt 端落盘 `pending-approvals/`（Skill 自己的数据资产）。
- 查询 Skill 在查询端**优先读** `pending-approvals/`、回退到扫 `~/.lobster/state/`。
- 这样查询 Skill **不依赖 lobster 内部目录结构**——将来 lobster 升级不会破。

**查询 Skill 的输出形态**：

```json
{
  "candidate": "张磊",
  "pinyin": "zhanglei",
  "halted_at_gate": "contract_gate",
  "gate_label": "合同审批（HR 主管）",
  "waiting_days": 2,
  "resume_token": "<base64 字符串，HR 拿这个去 resume>",
  "current_prompt": "HR 主管，请审批 张磊 的劳动合同：岗位 后端工程师 / 薪资 32K / 试用期 6个月。是否批准进入签约？",
  "stub_snapshot": { "candidate": "张磊", "role": "后端工程师", "salary": "32K", "probation": "6个月" }
}
```

**不**返回 `yes` / `no` 自动审批入口。HR 拿 token 走原路径。

#### 4. 三个问题的因果链

- **问题 1**（prompt 是否当下）—— 是**当下 vs 快照**的工程问题，靠「run 现场重读 + 脚本集中化 + resume 前预览」解决。
- **问题 2**（token 易丢）—— 是**人记不住的工程问题**，靠 halt 时落盘 `pending-approvals/` 解决。
- **问题 3**（查询 Skill）—— 是**找回路径的封装**，靠 Skill 把「扫 lobster state + 渲染 prompt」工程化。

三者构成完整的 halt 之后兜底：HR 当时就批（问题 1 保证当下）、HR 隔几天批（问题 2 保证 token 可找回）、HR 想主动查（问题 3 给出一句话入口）。

## §5 把工作流封成 Skill：工作流型 SKILL.md 的新形态

裸命令跑通入职工作流后，暴露三个真实痛点——它们正是 `running-onboarding-workflow` Skill 要解决的：


| #   | 痛点                         | 表现                                                                                                                                              |
| --- | -------------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------- |
| 1   | 工作流发起方式不稳定                 | CLI 入口定位、`.lobster` 文件路径、`--args-json` 参数怎么传、环境变量怎么注入，第一次全靠试                                                                                    |
| 2   | `resumeToken` 这把钥匙容易丢      | halt 返回的 JSON 里既有 `resumeToken` 又有 `approvalId`，**只有** `resumeToken` **能 resume**；不知道区别的人很可能记下短小的 `approvalId`、丢掉长长的 `resumeToken`，HR 批准后流程接不回去 |
| 3   | 工作流文件、stub 脚本散落在多个目录，靠人记路径 | 换个不知情的人接手就跑不起来                                                                                                                                  |


> **这也回答了"为什么 Lobster 工作流要封成 Skill"**：工作流文件本身只是"流程定义"，Skill 才是"怎么发起、怎么接管这条流程的操作手册"。



### 工作流型 Skill 与脚本型 Skill 的三个设计差异

Lesson 2-1 封装的 `parsing-resumes`、`auditing-extraction` 都是"把一个脚本封成 Skill"。`running-onboarding-workflow` 不一样——它封装的对象不是一段一次跑完的代码，是一条**多步、有状态、带暂停点的流程**。这个区别决定三个设计决策：

1. **Skill 的资产 = 工作流文件 + stub 脚本，都放进** `scripts/`**。** `hr-onboarding.lobster`（流程定义本体）和 5 个 stub 脚本（模拟企业系统的可执行资产）一起搬进 Skill 的 `scripts/`。它们是 Skill 的"被执行的资产"，不进 Agent 上下文。
2. **加一层启动包装脚本** `run-onboarding.sh`**，把 lobster 调用固化成 low-freedom 指令。** lobster 的发起（`run --file --args-json`）和接管（`resume --token --approve`）是脆弱、要一致的操作，按方法基线属于"low freedom，照命令跑别加参数"。所以不让 Agent 直接拼 lobster 命令，而是包一层 `run-onboarding.sh`，对外只暴露三个动作：`start` / `resume` / `dry`（分别对应真跑 / 批准拒绝 / dry-run）。
3. **SKILL.md 正文是"工作流操作手册"，讲清流程生命周期。** 这是工作流型 SKILL.md 和脚本型最不同的地方——脚本型讲"输入→输出"，工作流型必须讲"**流程的生命周期**"：启动后会停在哪、停下时返回什么、哪个字段是接管流程必须留存的钥匙、批准/拒绝分别会怎样、多个审批门怎么串。



### description 把 HiTL 边界写进 Agent 选 Skill 的第一眼依据

`running-onboarding-workflow` 的 `description` 特意点明 **"the agent never approves on a human's behalf"**——把 HiTL 边界写进了 Agent 选 Skill 的第一眼依据。正文里写死三条硬规则，每条对应一个痛点：

- **审批门是给人的，不是给你的。** 流程在 `contract_gate` / `account_gate` 暂停时，Agent 的职责是把 `prompt` + `items` + `resumeToken` 交回给人，**绝不替人批准或拒绝**。
- `resumeToken` **必须原样留存。** 每次 halt 返回的 token 是流程状态的唯一钥匙，不能用 `approvalId` 顶替（对应痛点 2）。
- **启动前不要手动跑 stub 脚本。** `start` 会自己清掉旧状态、跑 4 路并行准备，重复跑会污染状态文件。



### 封装期的两个路径坑

把工作流文件和 stub 脚本从 `workflows/` / `stub-system/` 搬进 Skill 的 `scripts/`，目录深度变了，实测撞上两个必须解决的问题：

1. **脚本和工作流文件都假设自己在 workspace 直属子目录下。** 原来 stub 脚本用 `$(dirname "$0")/../stub-state` 推状态目录、工作流文件 `env` 块写死了绝对路径——它们都假设"脚本在 workspace 的直属子目录里，向上一级就是 workspace 根"。搬进 `skills/running-onboarding-workflow/scripts/` 后目录变深，`../` 推出来的不再是 workspace 根。**修正**：stub 脚本改成优先读环境变量 `$STUB_STATE_DIR`、未设时回退原逻辑；工作流文件删掉 `env` 块，路径由启动脚本注入。
2. **lobster 的** `env` **块优先级高于外部环境变量。** 实测发现，`.lobster` 文件里若保留 `env: STUB: /某路径`，它会**盖掉**启动脚本 export 的同名变量。所以工作流文件里不能保留写死路径的 `env` 块，否则启动脚本注入的路径会被它覆盖。实测同时确认：lobster 的 `run step` 是 shell，会**继承**外部环境变量——`env` 块没定义的变量，外部 export 的能读到。

> 这两个坑合起来，得出启动脚本的路径方案：`run-onboarding.sh` 由 `BASH_SOURCE` 自身位置反推目录，在调 lobster 前 export 四个变量——`$STUB` 指向 Skill 自己的 `scripts/`（工作流文件和 stub 都在这），`$STATE` 指向 workspace 根的 `stub-state/`，`$STUB_STATE_DIR` 指向 `$STATE/<pinyin>/`（候选人隔离目录），`$WORKSPACE` 指向 workspace 根（`pending-approvals/` 落盘用）。
>
> **非文档行为提醒**：Lobster 的 `env` 块优先级、`run step` 继承外部环境变量——这些是文档不会写的行为，靠读编译产物 + 实测才知道。封装任何一个工作流文件前，都要先把"它的路径从哪来"实测清楚。**切勿**在 `.lobster` 里写 `env:` 块试图"显式注入"——`${STUB}` 不会被替换，会作为字面字符串覆盖外部真值。



### 数据资产归属：私有进 Skill，共享进 workspace 根


| 资产                               | 归属           | 放哪                   |
| -------------------------------- | ------------ | -------------------- |
| 工作流文件、stub / 辅助 Python 脚本       | Skill 私有资产   | Skill 的 `scripts/` 内 |
| stub 写出的状态文件 `stub-state/<pinyin>/*.json` | 跨 Skill 共享数据 | workspace 根          |
| 同目录 `workflow.json`             | 跨 Skill 共享数据 | workspace 根（流程扭转真相源） |


> **为什么状态文件要落在 workspace 根、不落在 Skill 目录里？** 因为 `stub-state/<pinyin>/` 是 §6 的 `running-onboarding-review`、§7 的 `generating-onboarding-dashboard` 两个下游 Skill 都要读的数据——它是三个 Skill 协作的"状态真相源"。私有资产进 Skill，共享数据进 workspace 根，这条边界 §6、§7 会一以贯之（详见 §8）。

## §6 定时 review：调度配置 vs 被触发要跑的事

入职流程不是新人报到当天就结束。试用期里还有几个固定跟进节点——第 7 天确认公司级 Onboarding 完成、第 30 天部门岗位培训跟进、第 60 天带教进展检查、第 90 天试用期中期反馈。这些节点靠 HR 用脑子记、在日历上手动标，带的新人一多就漏。

**入职跟进 review 是给入职子 Agent 配的定时能力**：到入职后第 7、30、60、90 天，调度器自动触发子 Agent 跑一次跟进 review，不需要 HR 记日期。OpenClaw 内置的定时调度子系统是 **Cron**（命令 `openclaw cron`），它把"到点该做什么"交给系统，而不是交给人的记忆。


| review 时点 | 跟进重点                         |
| --------- | ---------------------------- |
| 入职后第 7 天  | 完成公司级 Onboarding；导师启动带教；融入团队 |
| 入职后第 30 天 | 部门岗位培训；HR 第一次新人关怀沟通          |
| 入职后第 60 天 | 带教进展检查；岗位胜任度初评               |
| 入职后第 90 天 | 导师带教结束；6 个月试用期者中期反馈          |


> 第 7、30 天对应 HR 业界通行的入职跟进节点，正好落在 SHRM 数据里"20% 离职发生在前 45 天"的窗口里——**错过一次 review，就是错过一次把人留住的机会**。



### Cron 只负责"到点"，判断力在 review 脚本和子 Agent

要分清 review 脚本和 Cron 各自的职责：**Cron 只负责"到点"**——它是一个定时触发器，到了第 7 天就把子 Agent 叫起来。"跟进什么、怎么判断"是 review 脚本和子 Agent 的事：脚本读入职工作流落盘的 5 个准备节点真实状态，子 Agent 据此给出 review 结论。**Cron 触发的不是一个死脚本，是一个会判断的子 Agent。**

### 为什么用 `--at` 不用 `--cron`

OpenClaw Cron 提供三种 schedule 方式：`--at`（一次性任务，到某时刻跑一次）、`--cron`（周期任务，按 cron 表达式重复）、`--every`（周期任务，每隔固定时长跑一次）。给入职 review 配任务，正确的选择是 `--at`。

> **原因在这 4 个时点的本质**：张磊的"入职后第 30 天 review"，是从张磊自己的入职日往后算出来的一个确定的日历日期，跑完这一次就结束了——**它是一次性事件，不是循环**。`--cron` 和 `--every` 都是周期调度，给"每周一发周报""每月末出月报"这种永远重复的任务用。把"张磊的第 30 天 review"写成 `--cron`，是范式错配。一次性事件就该用一次性调度 `--at`。每来一个新员工，就给他配 4 个 `--at` 任务，触发时刻分别是入职日 +7 / +30 / +60 / +90 天。



### 封装的核心判断：可变的调度 vs 不变的执行

Cron 链条上有两层东西：**调度配置**（`cron add` 的一长串参数——`--at` 时刻、`--session isolated`、`--no-deliver`……，决定"什么时候触发、怎么触发"）和**被触发后要跑的事**（`onboarding-review.sh` 这个 review 脚本，决定"跑一次 review 到底做什么"）。

这两层该不该都封进 Skill？**不是。** 调度配置随每个新员工的入职日期变（张磊的第 30 天和李娜的第 30 天是不同的日历日期），它是用 `cron add` 命令做的、不该进 Skill；review 脚本对所有员工一致——"跑一次 review 做什么"是固定的，这才是该封成 Skill 的部分。

> **把可变的调度和不变的执行分开，是这一节封装的核心判断。** 这句话要写进 `running-onboarding-review` 的 SKILL.md 正文本身，Agent 才不会把 Cron 注册也当成 Skill 的一部分。



### 三条正文硬规则

- **天数节点固定。** review 的跟进重点对应固定的入职天数（7/30/60/90），传别的天数会落到"常规跟进"。
- **某节点显示「未就绪」时不要替它编状态。** review 读的 5 节点状态来自入职工作流的真实落盘文件，某节点文件不存在就如实报告「未就绪」。
- **落盘文件名格式不能改。** 结构化落盘的 `review-<姓名>-day<N>.json` 是 §7 入职看板的数据源，文件名格式一改，看板就读不到。



### 实操中的三个坑

- **所有 Cron 任务必须带** `--no-deliver`**。** HR 隔离 profile 没配聊天 channel，不加这个参数，Cron 任务跑完会因投递失败（"Channel is required"）而被整体判为出错——任务本身明明跑成功了。
- `--at` **一次性任务触发后会自动变成** `disabled`**。** 这是 `--at` 任务的正常行为（它本来就只该跑一次），不是故障。
- **参数风格不统一**：`cron runs` 必须带 `--id <jobId>`（是选项不是位置参数），而 `cron get <id>` / `cron show <id>` 用的是位置参数——同一个子系统里容易踩。

## §7 HTML 进度看板：不编造纪律与数据契约

Cron 解决了"到点自动跟进"，但还剩一个痛点没解决：**进度不可见**。一个新员工的入职流程横跨合同、IT、行政、导师、培训 5 个准备节点，外加 7/30/60/90 天 4 个跟进节点——HR 想知道"张磊现在卡在哪一步"，得挨个翻系统。员工一多，没人说得清整体情况。

### 看板读的是真实落盘文件，不是手填

看板不凭空生成，它读三类已经落盘的真实数据：

- **5 个入职准备节点的状态** ← §2 入职 Lobster 工作流落盘的 `stub-state/<pinyin>/{contract,account,device,buddy,training}.json`（兼容旧结构 `stub-state-<姓名>/`）。
- **流程角标（卡在哪扇门）** ← 同目录 `workflow.json` 的 `status` / `current_step`（由 `update-workflow.py` 随 lobster 各节点扭转落盘）。
- **4 个 review 节点的状态** ← §6 Cron 定时触发、`onboarding-review.sh` 落盘的 `review-state/*.json`。

> **为什么要单独读 `workflow.json`？** 准备节点进审批门时会写成「待审批」、批过后才写成「已通过」——但若只看准备节点，仍可能把「材料已备好、等真人批」误读成「准备阶段都办妥了」。卡片右上角角标（如「等待审批 · 合同审批门」）才是「流程卡在哪」的定性真相源。



### 数据和展示分离：为什么用生成脚本，不手写 HTML

看板不是手写 HTML，而是一个生成脚本 `build-dashboard.py`——它读状态文件、归类状态、算进度、套模板输出 HTML。这样做的原因是**数据和展示分离**：状态文件变了（合同审批通过、Cron 又触发了一次 review），重跑一次脚本看板就刷新，不用手改 HTML。脚本干 5 件事：

1. 扫描 `stub-state*`：新结构 `stub-state/<pinyin>/`、旧结构 `stub-state-<姓名>/`；跳过既无 `contract.json` 也无 `workflow.json` 的空壳；同名时优先保留新结构。
2. 按员工读 5 个准备节点 JSON 的 `status` 字段。
3. 把中文状态文案归类成 **3 个标准态**：已完成 / 进行中 / 待办。其中 **done** 含「已审批 / **已通过** / 已开通 / 已配齐 / 已匹配 / 已完成 / 已签署 / 已排期」；**pending** 含「待审批 / 待办 / … / 未就绪」。
4. 读同目录 `workflow.json` 拼卡片角标；扫 `review-state/`，按文件名 `review-{姓名}-day{N}.json` 判断哪些 review 已触发。
5. 算整体进度 = 9 个节点（5 准备 + 4 review）里完成的占比、等权重，套 HTML 模板输出（角标不计入百分比，只做定性提示）。

### 审批门 status 语义：待审批 ≠ 已通过

工作流与看板共用同一套 status 文案约定（由 `hr-onboarding.lobster` 进门 / 过门时写入 stub）：

| 时机 | stub `status` | 看板归类 | 含义 |
|---|---|---|---|
| 进入审批门（halt 前刷新） | **待审批** | pending（灰） | 材料已备，等真人批 |
| 审批通过后 | **已通过**（兼容旧文案「已审批」） | done（绿） | HiTL 门已批过 |
| 查询 / refresh 保鲜 | 保持 **待审批** | pending | 刷新落盘时间，不假装已批 |

`refresh-gate-stubs.py` 在 query / emit 前重跑对应 shell 时，也必须写「待审批」——否则看板会在 halt 期间把合同 / 账号节点误标成绿。



### 这个进度数字的两个边界

- **整体进度仍分不清"还没到时间"和"卡住了"。** 4 个 review 节点要等入职天数到了才会变绿，一个完全顺利的新人在第 90 天之前也到不了 100%。要精确回答"谁卡在审批门"，看卡片角标是否为「等待审批 · …」；准备节点全绿但角标仍 `halted` 是正常现象（材料齐了、人还没批）。
- **这是经办 HR 的"个案视图"，不是管理层大盘。** 几张卡片并排，解决的是"盯这几个新人各自卡在哪一步"。它不做按部门、按入职月份的聚合统计——那是另一个方向的看板（改造路径会提到）。



### 核心纪律：不编造，只镜像真实文件

裸脚本暴露两个痛点：① 看板最该守的"不编造"纪律，没有任何东西替它守住——换个人维护、或让 Agent 来调，很容易为了"看板好看"把缺失节点填成"已完成"；② 新员工名单怎么来、看板要不要缓存，没有说明。

把看板生成脚本封成 `generating-onboarding-dashboard`，就是要把这几条从散落的脚本逻辑沉淀成硬规则：

- **不编造（写进 SKILL.md 硬规则 + description）**：某节点 JSON 文件缺失时显示「未就绪」、绝不替它填「已完成」。`description` 里就点明 **"the dashboard never invents any status"**，让它成为 Agent 选 Skill 的第一眼依据。
- **名单靠扫描自动发现**：靠扫描 `stub-state*`（含 `stub-state/<pinyin>/`）自动发现新员工，不在脚本里写死名单；空壳目录不计入。
- **「待审批」≠「已通过」**：进门灰、过门绿；是否卡在门上以 `workflow.json` 角标为准，不要只看准备节点颜色。
- **不缓存**：状态变了重跑即刷新。

> **这条纪律真在起作用的证据**：端到端测里 Agent 主动报告"看板未包含张磊——他的入职工作流曾在共享 `stub-state/` 目录跑过，但随后被赵敏的工作流覆盖；目前没有 `stub-state-张磊` 独立目录，自动扫描未发现"。Agent 没有为了凑数把张磊编进看板，而是如实报告"扫描不到他的状态目录"——这是"名单靠扫描自动发现"与"绝不编造状态"两条规则的真实落地。现行结构下每位候选人落在 `stub-state/<pinyin>/`，并发入职不再互相覆盖。

## §8 三 Skill 协作：共享数据 vs 私有资产

入职子 Agent 的三个 Skill 通过 workspace 根的状态目录形成一条数据链：

```
running-onboarding-workflow    ──写──▶  stub-state/<pinyin>/   （5 准备节点 + workflow.json）
running-onboarding-review      ──写──▶  review-state/          （4 个 review 节点）
generating-onboarding-dashboard ──读──▶  stub-state*/ + workflow.json + review-state/
```

看板能跑通的前提，是上游两个 Skill 把数据真落到了 workspace 根、不是落进各自的 Skill 目录。**多 Skill 协作链上，共享数据放 workspace 根、私有资产放 Skill 内**——这条边界 §2、§6、§7 三个 Skill 一以贯之。

### 一个连续踩了三次的坑：脚本封进 Skill 后路径推导必查

`running-onboarding-workflow`（§5）、`running-onboarding-review`（§6）、`generating-onboarding-dashboard`（§7）三个 Skill 里，**同一个路径坑连续出现三次**：脚本原本假设自己在 workspace 直属子目录下，用 `../` 或 `os.path.dirname` 推 workspace 根。搬进 `skills/.../scripts/` 后目录深度变深，推导全错。

> **封装任何一个脚本，路径推导都是必查项**：改成由脚本自身位置反推稳定锚点（如"向上三级正是 workspace 根"）、再配一个环境变量兜底（如 `ONBOARDING_WORKSPACE`），不依赖调用方目录深度。



### 落盘文件名是跨 Skill 的数据契约

`running-onboarding-review` 产出的 `review-<姓名>-day<N>.json`，文件名格式被 §7 的看板 Skill 依赖——看板靠扫描这个文件名格式判断每个员工哪些 review 节点已触发。**文件名格式一改，看板就读不到。** SKILL.md 正文要把"文件名格式不能改"作为硬规则写死——这是多 Skill 协作链上典型的隐性契约，不写进规则，下一个改脚本的人很容易踩。

同理：候选人目录约定为 `stub-state/<pinyin>/`，看板 / 查询 / review 都按拼音子目录读；`workflow.json` 的 `status` / `current_step` 字段名是看板角标的契约，不要随意改名。

### 入职子 Agent 的完整交付结构

```
workspace-onboarding/
├── SOUL.md / AGENTS.md / TOOLS.md      入职子 Agent 的 persona 文档（已写入三个 Skill 的用法与调用时机）
├── skills/
│   ├── running-onboarding-workflow/    入职 Lobster 工作流封 Skill（工作流型）
│   ├── running-onboarding-review/      定时 review 封 Skill（脚本型）
│   └── generating-onboarding-dashboard/ HTML 进度看板封 Skill（脚本型）
├── stub-state/<pinyin>/                候选人隔离：5 准备节点 + workflow.json（workflow Skill 写）
├── stub-state-*/                       （可选）旧结构兼容目录
├── pending-approvals/                  halt 时审批快照（查询 Skill 用）
└── review-state/                       4 个 review 节点的状态文件（review Skill 写）
```

## §9 4 维度范式判断准则

入职（Lobster）和培训（ADDIE）两种范式都跑透之后，回头给出判断准则。一句话：**纯 LLM 生成 → Pipeline；混合命令、脚本、审批 → Lobster。**

把 4 个维度套到 4 类常见 HR Agent 需求上，判断结果一目了然。表的上半部分（②①④）决定走哪种范式，③ 单独列在最下面——它不参与范式判断，只回答"要不要再叠一层 Cron"：


| 判断维度                    | 新员工入职审批              | 培训物料生成       | 报销 / 调薪审批    | Offer 发放 |
| ----------------------- | -------------------- | ------------ | ------------ | -------- |
| ② **审批门**（硬指标）          | 有（合同 + 账号 2 门）       | 无            | 有（主管 / 财务审批） | 有（发放前审批） |
| ① **强先后依赖**（运行时条件控制）    | 有（reject 终止后续节点）     | 无（五阶段纯线性）    | 有（超额自动加签上级）  | 部分       |
| ④ **纯 LLM 任务**          | 否（脚本 + 审批 + 条件）      | 是（每步都是生成）    | 否（金额校验 + 打款） | 混合       |
| **→ 范式判断**              | **Lobster**          | **Pipeline** | **Lobster**  | **拆分**   |
| ③ 是否叠加 Cron（正交，不参与范式判断） | 是（7/30/60/90 review） | 否（单次跑）       | 否（提交即触发）     | 否        |


> **② 审批门是硬指标**：只要有"必须停下等真人批"的节点，就必须用 Lobster——因为 prompt 链停不住、接不回（§4）。这也是 §10 合规红线的工程基础。

## §10 合规红线：入职 HiTL 的工业级落实



### 红线：有法律或安全责任的决策，AI 不能单独拍板

入职流程里有两个节点带着责任：**合同条款定的是法律责任**（劳动合同法管着），**账号权限定的是系统访问的安全责任**。这两个节点的关键不是"AI 算得准不准"，是"出了事谁负责"——合同条款写错引发劳动纠纷、账号权限配错导致越权访问，这些后果要有人承担。**AI 不能承担法律责任，所以这类决策必须由真人拍板，并留下审批痕迹。**

**法律依据**：

- 中国《个人信息保护法》第 24 条：通过自动化决策方式做出对个人权益有重大影响的决定，个人有权要求说明、并有权拒绝仅由算法做出的决定。员工的账号权限范围、劳动合同的签订，对当事人就是"对个人权益有重大影响的决定"。
- 类似约束在欧盟 GDPR 第 22 条、EU AI Act（HR AI 被列为高风险、强制人工监督）里也都有。

> **血的判例**：在持续多年的 **Workday Mobley 就业歧视集体诉讼**中，2024 年 7 月美国加州北区法院认定"AI 服务提供商可作为雇主的代理人承担直接责任"这一主张可进入后续审理；2025 年 5 月该案进一步获批 ADEA 集体诉讼的有条件认证。核心争议始终是"AI 自动决策、没有人工复核"——这类设计今天已是明确的法律风险。



### 三处工程落实

"知道要 HiTL"是一句态度，不是落实。落实意味着把红线拆成具体的工程措施，每个措施落在流程里看得见的位置：


| #   | 落实措施             | 落在哪里                                                                                                                                   | 防住什么                                   |
| --- | ---------------- | -------------------------------------------------------------------------------------------------------------------------------------- | -------------------------------------- |
| 1   | **双审批门强制 halt**  | `hr-onboarding.lobster` 的 `contract_gate`（HR 主管批合同）和 `account_gate`（IT 安全负责人批账号权限）两节点，`approval: true` 标记——流程跑到这里真的暂停、交出 `resumeToken` | AI 替人做合同 / 账号这类有法律、安全责任的决定             |
| 2   | **reject 路径真阻断** | 审批门被拒，Lobster 立即终止整条工作流——`status` 变 `cancelled`、buddy / 归档节点根本执行不到（李娜案例：`buddy.json` 根本没生成）                                            | 拒绝之后流程照样往下跑——审批门变成"日志报个错但事情还在做"的摆设     |
| 3   | **审批门只设在该设的地方**  | 审批门卡在合同、账号权限两个高责任节点；设备申请、培训排期这类低风险事务性步骤不设门                                                                                             | 该卡的不卡（漏掉责任）/ 不该卡的乱卡（流程处处停、HiTL 变成形式主义） |


> 这三处合起来才是完整落实。措施 1 保证审批门停得住，措施 2 保证拒绝真阻断，措施 3 保证审批门设在对的位置。这正是 §9 说的"有审批门必须用 Lobster"那个硬指标背后的合规理由——纯 prompt 链停不住、接不回，落实不了这三处的任何一处。



### 诚实的局限：合规边界会变

合规边界不是固定的，它随法律演变（2025.05.01 施行的《个人信息保护合规审计管理办法》要求处理超 1000 万人个人信息的处理者每两年至少一次合规审计；EU AI Act 高风险义务的时间表也一直在调整）。

> **本集教的不是一套"一次写好永远合规"的代码，而是一种把合规红线工程化落实的方法**——把红线拆成可落地的工程措施、每个措施落在流程里看得见的位置（一个审批门、一行文件 header 标注）。法律变了措施要调；但"红线必须落到看得见的工程位置、不能停留在态度"这个方法不变。合规不是功能做完再补的附录，是从设计第一个工作流节点时就要在场的约束。

## §11 业界对位：基线 / 差异化 / 营销陷阱

把入职子 Agent 放回真实世界，和市面上的 HR 数字员工产品（北森、Moka、飞书 People、钉钉智能人事等）摆在一起比。

### 第一层：基线——90% 的产品都有，不做就被淘汰

据 HR 数字员工行业知识库，**入职通知与任务追踪是约九成 HR 数字员工产品都具备的能力**。它不是亮点，是入场券。小慧的入职子 Agent 在基线上做到的是"也有，且做扎实了"（§2-§4 的 5 节点流程串联 + HTML 进度看板）。基线必须扎实，否则后面谈差异化没有意义。

### 第二层：差异化——头部 10% 才做的事


| 差异化点      | 一体化 HR 平台的通行做法                               | 小慧的做法                                                                                           |
| --------- | -------------------------------------------- | ----------------------------------------------------------------------------------------------- |
| 入职审批      | checklist 勾选、状态流转——"审批"多是发条通知、人工在别处批，流程本身停不住 | Lobster HiTL 审批门——流程真 halt、交出 `resumeToken`、reject 真阻断后续节点                                      |
| 多步并行与流程控制 | 串行推进，或靠 HR 人工同时催几个部门；流程引擎是黑盒                 | 并行准备、审批门 halt、reject 阻断统一写进同一个 `.lobster` 文件——可读、可审计、可改（并行实测 2.137s→0.542s、接近 4 倍，是顺带结果、不是卖点本身） |
| 入职后跟进     | 日历提醒，到点 HR 自己去做                              | Cron 7/30/60/90 自动触发 review——到点子 Agent 自己醒来跑、状态落盘                                               |
| 可控性       | 商业 SaaS 的流程引擎是黑盒，审批逻辑、阶段串联改不动                | 工作流文件、Cron 调用全部看得见、改得动                                                                          |


> **"差异化"不是说小慧比北森强**。北森是完整的 HCM 平台、六大模块全覆盖，能力厚度不在一个量级。小慧的差异化是**定位上的**：它是一个工程师完全可控的开源方案，入职工作流的每个审批门设在哪里都看得见、改得动。商业 SaaS 的流程引擎对买家是黑盒——审批卡在哪一步、为什么这么卡，改不动。这恰恰是我们做自己业务入职 Agent 时最需要的。



### 第三层：营销陷阱——"全自动入职"话术

**"新员工入职全自动、AI 自动开通账号、自动配齐权限"**——这类宣传在 IT 账号自动化工具、RPA 入职机器人上尤其常见。听起来省事，但**账号权限自动开通是有代价的**：账号权限定义的是新员工能访问哪些系统、能动哪些数据，这是一个有安全责任的决策。让 AI 不经审批就开通，一旦权限配错（多给了、给错了人），没有审批留痕就追不到责任，权限边界等于失控。

> **工业级的做法恰恰相反**——账号权限这一步必须卡一个 HiTL 审批门，由 IT 安全负责人核准（这正是 §2 的 `account_gate` 做的事）。"全自动"省掉的那一步，正是不能省的那一步。省掉的环节往往正是工业级和 demo 级的分界线。



### 什么时候用商业 SaaS，什么时候自己做

- **要一套开箱即用、覆盖 HR 全流程、有 SLA 保障的系统** → 买商业 SaaS（北森、Moka、飞书 People）。
- **要一个完全可控、能按自己业务深度定制、审批逻辑透明、能嵌进自己工作流的入职 Agent** → 本课这套方案就是骨架。它的价值不在"功能比 SaaS 多"，在"每一处都是你自己的，看得见、改得动"。

> **诚实的局限**：入职子 Agent 不是商业 HR SaaS 的替代品。入职流程里账号、设备申请用的是本地 stub，没有接真实 IT 系统——真实对接企业微信 API、IT 工单系统、AD 域控需要企业自己开发（工作流文件不用动，只换 stub 实现）。它也没有一体化能力厚度、没有 SLA 承诺。它是教学示例与可改造骨架，生产上线前需按业务调整，并且**入职审批门必须保留**——这是合规红线，不是可选项。

### 2. 新增 `scripts/build-approval-prompt.py`

```python
#!/usr/bin/env python3
"""
build-approval-prompt.py —— 入职审批门 prompt 构建器

由 hr-onboarding.lobster 的两个 approval: true 步骤调用：
    run: python3 $STUB/build-approval-prompt.py contract
    run: python3 $STUB/build-approval-prompt.py account

负责两件事：
  1. 读 $STATE/<gate>.json —— 永远是当下磁盘上的最新值，不是 halt 时的快照。
     start→resume 之间外部系统改了 stub 文件（真实环境接 AD / 企业微信时是常态），
     审批人看到的 prompt 跟着 stub 走，不跟着 halt 时刻的快照走。
  2. 按门类型（contract / account）拼出中文 prompt + items，输出 Lobster 期望的 JSON。
"""
import json, os, sys


def _read_state(path):
    if not os.path.exists(path):
        sys.stderr.write(
            f"[build-approval-prompt] 缺少状态文件：{path}\n"
            "——通常因为 4 路并行准备没跑完、或被人手动删了。"
            "请重新执行 run-onboarding.sh start ... 让 prep 步骤重写 stub-state。\n"
        )
        sys.exit(2)
    with open(path, encoding="utf-8") as f:
        return json.load(f)


def build_contract_prompt(state_dir):
    c = _read_state(os.path.join(state_dir, "contract.json"))
    prompt = (
        f'HR 主管，请审批 {c["candidate"]} 的劳动合同：'
        f'岗位 {c["role"]} / 薪资 {c["salary"]} / 试用期 {c["probation"]}。'
        f'是否批准进入签约？'
    )
    return {"prompt": prompt, "items": [c]}


def build_account_prompt(state_dir):
    a = _read_state(os.path.join(state_dir, "account.json"))
    prompt = (
        f'IT 安全负责人，请审批 {a["candidate"]} 的账号权限范围（'
        f'工号 {a["workno"]} / 邮箱 {a["email"]} / 企业微信 + 内网访问）。'
        f'是否批准开通？'
    )
    return {"prompt": prompt, "items": [a]}


def main():
    if len(sys.argv) < 2:
        sys.stderr.write("usage: build-approval-prompt.py <contract|account>\n")
        sys.exit(1)
    gate = sys.argv[1]
    state_dir = os.environ.get("STATE")
    if not state_dir:
        sys.stderr.write("[build-approval-prompt] 缺少 $STATE 环境变量。\n")
        sys.exit(2)
    if gate == "contract":
        payload = build_contract_prompt(state_dir)
    elif gate == "account":
        payload = build_account_prompt(state_dir)
    else:
        sys.stderr.write(f"[build-approval-prompt] 未知 gate: {gate}\n")
        sys.exit(1)
    print(json.dumps(payload, ensure_ascii=False))


if __name__ == "__main__":
    main()
```

**关键设计点**：

- **`STATE` 走环境变量**——`run-onboarding.sh` 在调 lobster 前已 export，python 进程继承即可。
- **缺文件立刻 fail**——`exit 2` 给明确 stderr 提示（行内 Python 失败是 traceback，难读）。
- **`items` 整段透传**——lobster 渲染的 items 是审批人「看清自己在批什么」的依据，整段传过去，prompt 与 items 一致。

### 3. 修改 `hr-onboarding.lobster`（仅 2 处 run 步骤）

**改前**（原始行内 Python）：

```yaml
  # ── 节点 2 · HiTL 审批门 1：合同审批 ───────────────────
  - id: contract_gate
    run: |
      cat "$STATE/contract.json" | python3 -c 'import json,sys; c=json.load(sys.stdin); print(json.dumps({"prompt":"HR 主管，请审批 "+c["candidate"]+" 的劳动合同：岗位 "+c["role"]+" / 薪资 "+c["salary"]+" / 试用期 "+c["probation"]+"。是否批准进入签约？","items":[c]},ensure_ascii=False))'
    approval: true

  # ── 节点 3 · HiTL 审批门 2：账号权限审批 ────────────────
  - id: account_gate
    run: |
      cat "$STATE/account.json" | python3 -c 'import json,sys; a=json.load(sys.stdin); print(json.dumps({"prompt":"IT 安全负责人，请审批 "+a["candidate"]+" 的账号权限范围（工号 "+a["workno"]+" / 邮箱 "+a["email"]+" / 企业微信 + 内网访问）。是否批准开通？","items":[a]},ensure_ascii=False))'
    approval: true
```

**改后**（run 委托给 build-approval-prompt.py）：

```yaml
  # ── 节点 2 · HiTL 审批门 1：合同审批 ───────────────────
  # prompt 拼接由 scripts/build-approval-prompt.py 承担。
  # 每次走到这一门都重读 $STATE/contract.json，prompt 跟 stub 走、不跟 halt 时刻的快照走。
  - id: contract_gate
    run: python3 "$STUB/build-approval-prompt.py" contract
    approval: true

  # ── 节点 3 · HiTL 审批门 2：账号权限审批 ────────────────
  - id: account_gate
    run: python3 "$STUB/build-approval-prompt.py" account
    approval: true
```

**为什么能这么改而不破坏 Lobster 语义**：

- Lobster 的 `run` 步骤本来就是 shell + 子进程。`python3 "$STUB/..."` 是合法 shell 命令。
- `run` 步骤的 stdout 被 Lobster 解析为 JSON 提取 `json.prompt` 作为审批问题（详见 §3「约束 1 · approval 字段不做模板替换」）。python 脚本 `print(json.dumps(...))` 输出的就是 Lobster 期望的格式。
- `run` 步骤的 `${arg}` 模板替换由 Lobster 在调用 shell 前完成，python 脚本**不需要**接收命令行参数——它直接读 `$STATE/<gate>.json` 拼 prompt，**永远拿当下 stub 状态**。

**改前**（原始前置检查 + resume 分支）：


**改后**（新增 `print_gate_preview` + resume 前先调它）：

```bash
for s in contract.sh it-account.sh device.sh buddy.sh training.sh build-approval-prompt.py; do
  [ -f "$SCRIPT_DIR/$s" ] || fail "stub / prompt 脚本缺失：$SCRIPT_DIR/$s"
done
mkdir -p "$STATE"

# ── resume 前预览：把当下 stub 状态的 prompt 打给 HR 确认 ─────
# token base64 解开后只有 {kind, stateKey}，不包含「当前停在哪个审批门」字段。
# 所以两门都打，让 HR 自己确认要批的是哪道门的内容。
print_gate_preview() {
  echo "────────────────────────────────────────────────────"
  echo "审批门 prompt 预览（基于 \$STATE/ 当前内容，非陈旧快照）："
  echo
  for gate in contract account; do
    printf "[%s] " "$gate"
    if prompt_out=$(python3 "$SCRIPT_DIR/build-approval-prompt.py" "$gate" 2>/dev/null); then
      printf "%s\n" "$(printf '%s' "$prompt_out" | python3 -c 'import json,sys; print(json.loads(sys.stdin.read())["prompt"])')"
    else
      printf "（缺 \$STATE/${gate}.json，跳过预览）\n"
    fi
  done
  echo "────────────────────────────────────────────────────"
}

ACTION="${1:-}"
case "$ACTION" in
  …
  resume)
    TOKEN="${2:-}"; DECISION="${3:-}"
    [ -n "$TOKEN" ] || fail "resume 需要 resumeToken 作为第 2 个参数"

    print_gate_preview

    case "$DECISION" in
      yes|no) exec node "$LOBSTER" resume --mode tool --token "$TOKEN" --approve "$DECISION" ;;
      *) fail "resume 的决定必须是 yes 或 no，收到：'$DECISION'" ;;
    esac
    ;;
  …
```

**两处改动的设计要点**：

- **前置检查加 `build-approval-prompt.py`**——保持 `run-onboarding.sh` 一贯的「fail fast」风格（详见 SKILL.md 关键规则：缺文件立即明确报错、退出码 3）。
- **`print_gate_preview` 是函数不是内联块**——同一段逻辑可能在未来扩展时被复用（如 dry-run 模式、查询 Skill 都可能想 preview），抽成函数方便调用。
- **两门都打**——resumeToken base64 解开只有 `{kind, stateKey}` 不含 gate 名，**没法精确挑出一道门**。`run-onboarding.sh` 选择两门都渲染，让 HR 自己挑出「我要批的就是这一行」。
- **缺文件时只跳过、不断 resume**——`if prompt_out=... 2>/dev/null` 翻译 build-approval-prompt.py 的 exit 2 为友好提示，不阻塞 HR 推进流程。

```
   │   行为：现场读 stub-state/account.json → 拼 prompt → halt      │
   │   返回：{status:needs_approval, resumeToken（新）, ...}          │
   └─────────────────────────────┬───────────────────────────────┘
                                 ▼  HR 决定 yes
                                 ▼
   ┌─────────────────────────────────────────────────────────────┐
   │ Phase 2a · 启动器（run-onboarding.sh resume $TOKEN2 yes）      │
   │   内部：                                                       │
   │     1) print_gate_preview    ← 调 build-approval-prompt.py  │
   │                                把两门当下 prompt 打给 HR 看      │
   │     2) node lobster resume --token $TOKEN2 --approve yes      │
   └─────────────────────────────┬───────────────────────────────┘
                                 ▼
   ┌─────────────────────────────────────────────────────────────┐
   │ Node 4 · buddy（条件执行）                                       │
   │   when: $contract_gate.approved && $account_gate.approved     │
   │   run 步骤（lobster run 步骤内联）：                              │
   │     bash $STUB/buddy.sh "${name}" "${role}"                   │
   │   调用的脚本：scripts/buddy.sh                                  │
   │   落盘：stub-state/buddy.json                                   │
   └─────────────────────────────┬───────────────────────────────┘
                                 ▼
   ┌─────────────────────────────────────────────────────────────┐
   │ Node 5 · complete（条件执行）                                    │
   │   when: $contract_gate.approved && $account_gate.approved     │
   │   run 步骤（lobster run 步骤内联）：3 行 echo                    │
   │   调用的脚本：(lobster run 步骤内联)                             │
   │   status=ok，工作流结束                                          │
   └─────────────────────────────────────────────────────────────┘
```

### 6. 关键差异（改前 vs 改后）

| 节点 | 改前 | 改后 |
|---|---|---|
| Node 2 run | 行内 Python `cat \| python3 -c '...拼 prompt...'` | `python3 $STUB/build-approval-prompt.py contract` |
| Node 3 run | 行内 Python | `python3 $STUB/build-approval-prompt.py account` |
| Resume 前 | 无预览 | `print_gate_preview` 把两门当下 prompt 打给 HR 看，标注「非陈旧快照」 |
| 启动器前置检查 | 5 个 stub | 5 个 stub + 1 个 `build-approval-prompt.py` |
| prompt 与 stub 的关系 | 改时拼（run 现场重读） | 改时拼（**显式抽出来**，未来扩展更清晰） |
| HR 看到的 vs lobster 内部的 prompt | 都是行内 Python，**等价但散在两处** | **来自同一份脚本**，不会出现两份不一致 |

**最关键的一条**：改前 HR 看到的 prompt 和 lobster 内部用的 prompt 是**两份**行内 Python、各自拼——Lobster 跑过 / 不跑过 / 何时跑，HR 一无所知。改后**两份 prompt 来自同一份脚本**（`build-approval-prompt.py`），HR 看的预览 = lobster 内部用的，不会出现「预览和实际批准的内容不一致」。

## §13 prompt 加时间戳：让 HR 看见"时间维度的当下"

§12 解决了"prompt 是当下 stub 状态的投影"——但**只解决了内容维度**。HR 看到 prompt 时**不知道**：

- 这份材料是**何时**准备好的（是今早刚准备，还是 5 天前 stub 落盘的）？
- 这份材料**何时被改过**（是 stub 一次性写的，还是 halt 之后又被 IT 系统改过）？
- 这道门**等了多久**（刚停下来等人批，还是已经停了 3 天没人接）？

本节引入**时间字段**——把"内容维度的当下"升级为"内容 + 时间两个维度的当下"。**实现最简、价值最大**——比 §12 的方案更往前走一步，但改动量更小。

### 1. 设计要点

**stub 落盘时写两个时间字段**：

- `prepared_at` —— stub 第一次写 JSON 的时间（ISO 8601 UTC 字符串）。**只写一次，永不变**。
- `updated_at` —— stub 最后一次被改的时间。**stub 自己写时取 now；外部系统改 stub 时由改方维护**。

**`build-approval-prompt.py` 在 prompt 文本里追加"准备于 X，Y 前"**——把 ISO 时间转人话（"5 分钟前"/"2 小时前"/"3 天前"），HR 一眼能读。

**`record-pending-approval.py` 落盘 `pending-approvals/<pinyin>-<gate>.json` 时多存三个时间字段**：

- `stub_prepared_at` / `stub_updated_at` —— 从 stub JSON 读出来
- `halted_at` —— 落盘瞬间的时间（也就是这道门 halt 的时间）

**`querying-onboarding-status` Skill 输出 `stub_changed_after_halt` boolean**——算 `stub_updated_at > halted_at`，明确告诉 HR"halt 之后 stub 被改过"。这是这套设计**最灵魂**的一行——把"是否变化"从 HR 靠记忆判断变成机器明确告知。

### 2. stub JSON 加时间字段

5 个 stub 全部加 `prepared_at` / `updated_at` 两个字段。下面以 `contract.sh` / `it-account.sh` 为例（其它 3 个 stub 同理）：

```bash

{"system":"合同文件","candidate":"${NAME}","role":"${ROLE}","salary":"${SALARY}","contract":"劳动合同已起草","files":"岗位说明书/保密协议/员工手册确认书 已备齐","probation":"6个月","status":"待审批","prepared_at":"${NOW}","updated_at":"${NOW}"}
```

```bash
# scripts/it-account.sh（节选）
```

**设计要点**：

- **用 `date -u +%Y-%m-%dT%H:%M:%SZ`**——UTC 避免时区歧义，ISO 8601 格式方便 Agent / 前端解析。
- **`prepared_at` 写入时是 now，之后永不变**——除非 stub 被删重写。`updated_at` 写入时也是 now，但**未来加"外部系统改 stub"接口时由改方更新**（目前所有 stub 都是自己一次性写，prepared_at == updated_at）。
- **5 个 stub 同步改**——`device.sh` / `training.sh` / `buddy.sh` 同样加两个字段。prep 阶段它们一起跑、一起写、一起带时间戳。

### 3. `build-approval-prompt.py` 在 prompt 文本里追加"准备于 X，Y 前"

在 §12 已有的脚本里**加一个 `_humanize_age(iso)` 工具函数 + 在 prompt 末尾追加一行**：

```python
#!/usr/bin/env python3
"""
build-approval-prompt.py —— 入职审批门 prompt 构建器

§13 升级：在 prompt 文本里追加 stub 准备时间 + 人话等待时长，
让 HR 看见"时间维度的当下"——知道这份材料何时准备、是否刚准备。
"""
import datetime as dt
import json, os, sys


def _read_state(path):
    if not os.path.exists(path):
        sys.stderr.write(
            f"[build-approval-prompt] 缺少状态文件：{path}\n"
            "——通常因为 4 路并行准备没跑完、或被人手动删了。"
            "请重新执行 run-onboarding.sh start ... 让 prep 步骤重写 stub-state。\n"
        )
        sys.exit(2)
    with open(path, encoding="utf-8") as f:
        return json.load(f)


def _parse_iso(s):
    """解析 ISO 8601 UTC 字符串（Z 后缀）"""
    if not s:
        return None
    try:
        return dt.datetime.strptime(s, "%Y-%m-%dT%H:%M:%SZ").replace(tzinfo=dt.timezone.utc)
    except ValueError:
        return None


def _humanize_age(iso):
    """把 ISO 时间转人话：'5 分钟前' / '2 小时前' / '3 天前'"""
    t = _parse_iso(iso)
    if not t:
        return "时间未知"
    now = dt.datetime.now(dt.timezone.utc)
    delta = now - t
    seconds = int(delta.total_seconds())
    if seconds < 0:
        return "刚刚"   # stub 时间在未来（时钟漂移）
    if seconds < 60:
        return f"{seconds} 秒前"
    if seconds < 3600:
        return f"{seconds // 60} 分钟前"
    if seconds < 86400:
        return f"{seconds // 3600} 小时前"
    return f"{seconds // 86400} 天前"


def _append_age_clause(prompt, prepared_at):
    """在 prompt 末尾追加 '（材料准备于 X，Y 前）' 一行"""
    age = _humanize_age(prepared_at)
    return f"{prompt}\n\n（材料准备于 {prepared_at}，{age}）"


def build_contract_prompt(state_dir):
    c = _read_state(os.path.join(state_dir, "contract.json"))
    prompt = (
        f'HR 主管，请审批 {c["candidate"]} 的劳动合同：'
        f'岗位 {c["role"]} / 薪资 {c["salary"]} / 试用期 {c["probation"]}。'
        f'是否批准进入签约？'
    )
    if "prepared_at" in c:
        prompt = _append_age_clause(prompt, c["prepared_at"])
    return {"prompt": prompt, "items": [c]}


def build_account_prompt(state_dir):
    a = _read_state(os.path.join(state_dir, "account.json"))
    prompt = (
        f'IT 安全负责人，请审批 {a["candidate"]} 的账号权限范围（'
        f'工号 {a["workno"]} / 邮箱 {a["email"]} / 企业微信 + 内网访问）。'
        f'是否批准开通？'
    )
    if "prepared_at" in a:
        prompt = _append_age_clause(prompt, a["prepared_at"])
    return {"prompt": prompt, "items": [a]}


def main():
    if len(sys.argv) < 2:
        sys.stderr.write("usage: build-approval-prompt.py <contract|account>\n")
        sys.exit(1)
    gate = sys.argv[1]
    state_dir = os.environ.get("STATE")
    if not state_dir:
        sys.stderr.write("[build-approval-prompt] 缺少 $STATE 环境变量。\n")
        sys.exit(2)
    if gate == "contract":
        payload = build_contract_prompt(state_dir)
    elif gate == "account":
        payload = build_account_prompt(state_dir)
    else:
        sys.stderr.write(f"[build-approval-prompt] 未知 gate: {gate}\n")
        sys.exit(1)
    print(json.dumps(payload, ensure_ascii=False))


if __name__ == "__main__":
    main()
```

**设计要点**：

- **`_humanize_age` 是纯函数**——不依赖 stub 内容，只依赖当前时间。无副作用、好测试。
- **追加在 prompt 末尾、`\n\n` 分段**——保留主 prompt 单行（lobster 期望），新段落只补充事实（"材料准备于 X，Y 前"）。**不替 HR 决策**，只是陈述。
- **`if "prepared_at" in c` 兜底**——如果 stub 没写时间字段（旧版本兼容），不追加该子句而不是报错。
- **`items` 仍整段透传**——lobster 渲染的 items 是审批人看清依据的关键，整段传过去；时间字段在 items 里也能看到（`items[0].prepared_at`），prompt 是文本化表述，items 是结构化数据。

### 4. `record-pending-approval.py` 落盘 `pending-approvals/` 时多存时间字段

这是 §4.5 / §2.5 兜底 2（halt 时落盘）的入口脚本。**每个 `approval: true` 步骤的 run 在拼完 prompt 后同时调它**——`build-approval-prompt.py` 拼 prompt 给 lobster 用，`record-pending-approval.py` 落盘给 HR/查询 Skill 用。两者解耦，互补。

```python
#!/usr/bin/env python3
"""
record-pending-approval.py —— halt 时落盘待审批状态

由 hr-onboarding.lobster 的两个 approval: true 步骤的 run 调用：
    run: |
      python3 $STUB/build-approval-prompt.py contract > /dev/null
      python3 $STUB/record-pending-approval.py contract

落盘到 $PENDING_DIR/<pinyin>-<gate>.json，字段：
  candidate / pinyin / gate / halted_at / waiting_days
  stub_prepared_at / stub_updated_at
  resume_token / current_prompt / stub_snapshot

§13 升级：多存三个时间字段（stub_prepared_at / stub_updated_at / halted_at），
未来 querying-onboarding-status Skill 用 stub_updated_at > halted_at 算
stub_changed_after_halt boolean。
"""
import datetime as dt
import json, os, sys, time

GATE_LABEL = {
    "contract": "合同审批（HR 主管）",
    "account":  "账号权限审批（IT 安全负责人）",
}


def _read_state(path):
    if not os.path.exists(path):
        sys.stderr.write(f"[record-pending-approval] 缺少状态文件：{path}\n")
        sys.exit(2)
    with open(path, encoding="utf-8") as f:
        return json.load(f)


def main():
    if len(sys.argv) < 2:
        sys.stderr.write("usage: record-pending-approval.py <contract|account>\n")
        sys.exit(1)
    gate = sys.argv[1]
    state_dir = os.environ.get("STATE")
    pending_dir = os.environ.get("PENDING_DIR",
        os.path.join(os.path.dirname(state_dir or ""), "pending-approvals"))
    if not state_dir:
        sys.stderr.write("[record-pending-approval] 缺少 $STATE 环境变量。\n")
        sys.exit(2)
    os.makedirs(pending_dir, exist_ok=True)

    # 读 stub JSON（contract.json / account.json）
    state = _read_state(os.path.join(state_dir, f"{gate}.json"))
    pinyin = state.get("pinyin", "unknown")
    candidate = state.get("candidate", "未知候选人")

    # 拼当前 prompt（复用 §12 的 build-approval-prompt.py，不重复实现）
    import subprocess
    proc = subprocess.run(
        ["python3", os.path.join(os.path.dirname(__file__),
                                 "build-approval-prompt.py"), gate],
        env={**os.environ}, capture_output=True, text=True
    )
    if proc.returncode != 0:
        sys.stderr.write(f"[record-pending-approval] build-approval-prompt.py 失败：{proc.stderr}\n")
        sys.exit(proc.returncode)
    prompt_payload = json.loads(proc.stdout)

    # 落盘
    now = dt.datetime.now(dt.timezone.utc).isoformat()
    record = {
        "candidate": candidate,
        "pinyin": pinyin,
        "gate": gate,
        "gate_label": GATE_LABEL.get(gate, gate),
        "halted_at": now,
        "waiting_days": 0,
        "stub_prepared_at": state.get("prepared_at"),
        "stub_updated_at": state.get("updated_at"),
        "resume_token": "<由 lobster 在 halt 返回 JSON 时生成，Skill 写入>",
        "current_prompt": prompt_payload["prompt"],
        "stub_snapshot": state,
    }
    out_path = os.path.join(pending_dir, f"{pinyin}-{gate}.json")
    with open(out_path, "w", encoding="utf-8") as f:
        json.dump(record, f, ensure_ascii=False, indent=2)
    print(f"[record-pending-approval] 已落盘：{out_path}")


if __name__ == "__main__":
    main()
```

> **lobster 怎么把 token 写进 JSON**：`resumeToken` 是 lobster 在 halt 时返回的，不是 run 步骤能拿到的。实际工程化做法是——`build-approval-prompt.py` / `record-pending-approval.py` 跑在 lobster run 步骤里，run 步骤只能往 stdout 写 lobster 解析的 JSON（含 prompt）。lobster halt 时**外部脚本**（`run-onboarding.sh`）会拿到 JSON 里的 resumeToken，再**回填**到 `pending-approvals/*.json` 里。这是一处细节，留待生产化时由 `run-onboarding.sh` 配合回填（先记 stub_snapshot 占位、halt 时回填 token）。

### 5. `querying-onboarding-status` Skill 输出流程快照

这是 §4.5 / §2.5 兜底 3——专门回答"X 的入职流程到哪了"的查询 Skill。本节升级其输出形态，加上时间字段和 `stub_changed_after_halt` 标记：

```bash
bash skills/querying-onboarding-status/scripts/query-onboarding-status.sh 张磊
```

```json
{
  "candidate": "张磊",
  "pinyin": "zhanglei",
  "halted_at_gate": "contract_gate",
  "gate_label": "合同审批（HR 主管）",
  "halted_at": "2026-07-12T10:30:00+08:00",
  "halted_at_humanize": "3 天前",
  "waiting_days": 3,
  "stub_prepared_at": "2026-07-10T15:00:00+08:00",
  "stub_prepared_humanize": "5 天前",
  "stub_updated_at": "2026-07-12T09:45:00+08:00",
  "stub_updated_humanize": "3 天前",
  "stub_changed_after_halt": true,
  "resume_token": "<base64>",
  "current_prompt": "HR 主管，请审批 张磊 的劳动合同：岗位 后端工程师 / 薪资 40K (终面调整) / 试用期 6个月。是否批准进入签约？\n\n（材料准备于 2026-07-10T15:00:00+08:00，5 天前）",
  "stub_snapshot": { "candidate":"张磊", "role":"后端工程师", "salary":"40K (终面调整)", "prepared_at":"2026-07-10T15:00:00+08:00", "updated_at":"2026-07-12T09:45:00+08:00" }
}
```

**`stub_changed_after_halt: true` 是这套设计的灵魂**——明确告诉 HR"你 halt 之后 stub 被改过，需要看一下是不是新数据"。判断逻辑：

```python
stub_changed_after_halt = (
    stub_updated_at is not None
    and halted_at is not None
    and stub_updated_at > halted_at
)
```

**查询 Skill 的 SKILL.md 硬规则（与 §4.5 兜底 3 一致）**：

> **本 Skill 只负责查询，不负责批准 / 拒绝。** 拿到 token 之后，HR 仍须用 `running-onboarding-workflow/scripts/run-onboarding.sh resume <token> yes|no` 走人工确认路径。审批决策权始终在人，不在本 Skill。`stub_changed_after_halt` 是事实陈述，不是建议。

### 6. 三个时间字段的因果链

```
stub 落盘（prep 阶段）
  ↓ prepared_at = now
  ↓ updated_at = now
  ↓
lobster run 步骤（contract_gate / account_gate）
  ↓ 调 build-approval-prompt.py → 拼 prompt（含 "准备于 X，Y 前"）
  ↓ 调 record-pending-approval.py → 落盘 pending-approvals/<pinyin>-<gate>.json
  ↓   ├── stub_prepared_at ← stub 字段
  ↓   ├── stub_updated_at  ← stub 字段
  ↓   └── halted_at        = now
  ↓
lobster halt
  ↓ 启动器（run-onboarding.sh）拿到 resumeToken
  ↓ 回填到 pending-approvals/<pinyin>-<gate>.json 的 resume_token 字段
  ↓
HR 查询（querying-onboarding-status Skill）
  ↓ 读 pending-approvals/<pinyin>-<gate>.json
  ↓ 算 stub_changed_after_halt = (stub_updated_at > halted_at)
  ↓ 算 _humanize_age(stub_prepared_at) / _humanize_age(halted_at)
  ↓ 输出 JSON 给 HR
```

**核心信息流**：stub 写时间 → lobster 拿时间 → 落盘存时间 → 查询读时间 → 算"是否变化"。

### 7. 改造量与档位选择

| 档 | 做什么 | 改动量 | 价值 |
|---|---|---|---|
| **轻** | stub 加 `prepared_at` / `updated_at` + `build-approval-prompt.py` 拼"准备于 X，Y 前" | 5 个 stub 各加 1 行 + 1 个 python 改 | HR 看到 prompt 多了"准备于 X"——基础 |
| **中**（推荐） | 轻 + `record-pending-approval.py` 落盘时间字段 | + 1 个新脚本 + lobster run 步骤多调一次 | `pending-approvals/` 存时间——查询 Skill 可读 |
| **重** | 中 + 查询 Skill 输出 `stub_changed_after_halt` boolean | + 查询 Skill 升级 | **HR 一眼看到"halt 之后 stub 变过"** |

**推荐走"中"档落地**——重档只是查询 Skill 加一行 `stub_changed_after_halt`，但它依赖中档先做（没有 `pending-approvals/` 里存的时间字段就没法算）。等中档跑通，再加 1 行算 boolean 即可升级到重档。

### 8. 这次升级在 §4.5 三问题因果链里的位置

回到 §4.5 列出的三个工程问题：

- **问题 1 · prompt 是否当下**——
  - §12 解决**内容维度**：prompt 跟 stub 走，不跟 halt 时刻的快照走
  - §13（本节）解决**时间维度**：prompt 显式告诉 HR stub 何时准备 / 何时被改 / 门等多久
- **问题 2 · token 易丢**——本节顺手为兜底 2 提供时间字段基础（`halted_at` 是 halt 落盘的天然时间锚）
- **问题 3 · 查询 Skill**——本节升级其输出形态，加 `stub_prepared_humanize` / `waiting_days` / `stub_changed_after_halt` 等字段

也就是说 §13 不是另起炉灶——**它是 §12 / 兜底 2 / 兜底 3 三个落地方案的"时间维度"升级**。三个落地方案独立存在时各只解决"内容当下"；加了 §13 的时间字段后，"内容当下"升级为"内容 + 时间双维度的当下"。

> **本节的教学价值**：用最少改动（5 个 stub 各加 1 行 + 1 个 python 改）让 HR 从 prompt 里**多看见两件事**——材料何时准备、门等多久——这是 stub 数据自身的扩展，不引入新 Skill、不改工作流节点。**先做轻、立刻可见效果**；中档重档按 §4.5 兜底推进时同步升级即可。

## 附录 B：术语速查表


| 术语                            | 含义                                                                                                   |
| ----------------------------- | ---------------------------------------------------------------------------------------------------- |
| **Lobster**                   | OpenClaw 内置的工作流引擎插件，用 `.lobster` 文件定义多步、有状态、带审批门的流程                                                  |
| `.lobster` **文件**             | Lobster 工作流定义文件，分 `args` / `env` / `steps` 三大块                                                       |
| **HiTL**                      | Human-in-the-Loop，人工介入——关键节点必须停下等真人点头，靠引擎级 halt/resume 实现，不靠 prompt 措辞                               |
| **halt**                      | 工作流跑到审批门（`approval: true`）时暂停，把流程状态落盘、控制权交还给人                                                        |
| **resume**                    | 用 `resumeToken` 恢复一个 halt 住的流程，`--approve yes`/`no` 批准或拒绝                                            |
| `resumeToken`                 | 恢复流程的唯一钥匙，base64 编码，内含一个指向磁盘流程状态的 `stateKey` 指针；每次 halt 生成新的，不能用 `approvalId` 顶替                     |
| `approvalId`                  | 一次审批请求的短标识，**不能**用来 resume 流程                                                                        |
| `stateKey`                    | 找到磁盘上流程状态（`~/.lobster/state/`）的钥匙，形如 `workflow_resume_<UUID>`                                        |
| `approval: true`              | 把一个步骤标记成审批门；该字段不做 `${...}` 模板替换                                                                      |
| `when`                        | 步骤执行条件，条件为假就跳过；是声明式依赖，不是阻断机制本身                                                                       |
| `--args-json`                 | 调用工作流时传参数 JSON，覆盖 `args` 默认值，让一个文件服务所有新员工                                                            |
| **stub**                      | 桩，模拟真实企业系统行为的占位脚本，产出结构化 JSON 状态；真实上线换成调企业接口，工作流文件不动                                                  |
| **Cron**                      | OpenClaw 内置定时调度子系统，`--at` 一次性 / `--cron` 周期 / `--every` 每隔固定时长                                       |
| `--no-deliver`                | Cron 任务参数，关掉结果投递；HR 隔离 profile 没配 channel 时必须带，否则投递失败被判出错                                            |
| `--keep-after-run`            | Cron 任务跑完后保留任务定义和执行历史，便于审计回溯                                                                         |
| **工作流型 Skill**                | 封装一条多步有状态流程的 Skill，SKILL.md 讲"流程生命周期"（如 `running-onboarding-workflow`）                               |
| **脚本型 Skill**                 | 封装一段一次跑完代码的 Skill，SKILL.md 讲"输入→输出"（如 `running-onboarding-review`、`generating-onboarding-dashboard`） |
| **stub-state / review-state** | workspace 根的共享状态目录——三个入职 Skill 协作的"状态真相源"；现行结构为 `stub-state/<pinyin>/`（候选人隔离） |
| **workflow.json**             | 候选人目录下的流程扭转落盘（`status` / `current_step` / events）；看板角标与查询 Skill 的定性依据                         |
| **待审批 / 已通过**               | 审批门 stub 状态约定：进门「待审批」（灰），过门「已通过」（绿，兼容旧文案「已审批」）                                      |
