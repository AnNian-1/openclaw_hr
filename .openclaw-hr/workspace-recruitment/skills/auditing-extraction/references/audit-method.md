## 1. 核对的对象与目的

核对的对象：`parsing-resumes` 抽取产出的候选人 JSON（`parsed/<简历名>.json`）。

核对的目的：把 JSON 里的每个字段值，回溯到简历原文，确认它**真来自简历、不是 LLM 补出来的**。

为什么必须有这一步：LLM 抽取结构化数据时有「补全」倾向——原文某字段缺失或模糊时，它会倾向填一个看起来合理的值。`parsing-resumes` 的指令写了「不要编造」，能压低这种倾向但压不到零。简历解析产出是招聘子 Agent 整条链的地基，地基有假数据，评分、画像、人才库会一路错下去。所以解析之后必须有一道**事后核对闸**——这就是真实性核对。

这件事和 `parsing-resumes` 内置的 `validate_profile.js` 不同：

| | `validate_profile.js` | `audit_extraction.js`（本 Skill） |
|---|---|---|
| 核对维度 | schema / 合规**结构** | 抽取值**逐字段回溯原文** |
| 回答的问题 | 形状对不对 | 内容真不真 |
| 抓得出的错 | 缺字段组、混进 `age`、`job_count` 对不上段数 | 抽取值与原文对不上、软推断字段漏标注 |

两道闸都要过：先 `validate_profile.js`（形状），再 `audit_extraction.js`（内容）。

## 2. 三类字段，三套核对标准

抽取产出的字段不是一种东西，可信度来源不同，核对标准必须分开——这是 §2.4 最核心的一条。

| 字段类型 | 典型字段 | 核对标准 |
|---------|---------|---------|
| 硬提取 | name / phone / email / target_position / expected_salary / expected_city / available_date / school / major / degree / company / position / start_date / end_date | 值必须能在简历原文里**逐字符找到出处** |
| 软推断 | `industry`（从公司名推断行业） | 不核对原文出处（原文本就没有）；核对**是否带 `_inferred` 标志** + 推断依据是否成立 |
| 派生 | `total_experience_years` / `job_count` | 不回溯原文；核对**计算依据**（`work_experience` 各段）是否成立 |

## 3. 硬提取字段——逐字符回溯

硬提取字段的值，简历原文里有明确出处。核对标准是**逐字符比对**：把抽取值拿到原文里去找，找得到 = 可追溯，找不到 = 疑似编造/笔误/张冠李戴，必须人工核实。

核对时做了文本归一化（去空白、统一全角半角括号、统一连字符、统一大小写）——简历原文常有换行截断（一句话被拆成两行）、全角符号，归一化后再比对，避免「值确实来自原文、只是排版不同」被误判。

带括号补充说明的值（如 `算法工程师（推荐 / NLP / 大模型应用方向）`）：先看整串是否命中，不命中就核对**主体部分**（去掉括号后的核心值，如 `算法工程师`）。**括号里的补充项不能单独让整个值通过**——比如 `expected_salary` 被改成 `30K-40K（月薪）`，「月薪」二字在原文里有，但核心值 `30K-40K` 是编造的，整个字段照样判不可追溯。

起止时间（`start_date` / `end_date`）单独处理：抽取规则把它规范成了 `YYYY-MM`，但原文可能写 `2021.07` / `2021/07` / `2021年7月`。核对时年份必须命中，有月份则月份也要命中（容忍 `7` / `07` 两种写法）。`至今` 单独判。

## 4. 软推断字段——核对标注，不核对出处

软推断字段（典型是 `industry`）原文没有直接出处——简历不会写「我所在的行业是 SaaS」，是 Agent 看公司名「某 SaaS 创业公司」推出来的。对它做「逐字回溯原文」没有意义。

软推断字段的核对标准是两条：

1. **必须带 `<字段>_inferred: true` 标志**。`work_experience` 里某段产出了 `industry`，就必须同时有 `industry_inferred: true`。漏标注 = 把「AI 的判断」混成「简历事实」，下游评分、合规审计分不清——这是必须报的问题。
2. **推断依据要成立**。`industry` 的推断依据是公司名，那公司名本身要能在原文找到。依据都不在原文，推断就是无源之水。

## 5. 派生字段——核对计算依据

派生字段（`total_experience_years` / `job_count`）不是从原文抄的，是按 `work_experience` 算的。核对它不回溯原文，只确认**计算依据成立**——`work_experience` 数组在场、非空即可。

> 派生字段的值算得对不对（如 `total_experience_years` 是否等于各段起止时间之和），是 `validate_profile.js` 的职责（它会按起止时间累加比对）。本 Skill 只核对「这个派生字段有没有计算依据」，不重复做数值校验。

## 6. 可追溯率怎么算

```
硬提取字段可追溯率 = 可逐字回溯的硬字段数 / 硬字段总数
```

这个比率是简历解析这一步交出的「真实性体检结果」。L2-1 §2.4 的实验里，候选人A 13 字段 + 候选人B 8 字段，19 个硬提取字段 100% 可逐字回溯——可追溯率 100%，说明这批解析产出可信。

软推断字段不计入可追溯率（它本就无原文出处），单独统计「已合规标注的比例」。

## 7. 核对发现问题后怎么办

`audit_extraction.js` 退出码 1，说明有字段对不上。按报出的字段类型分别处理：

- **硬提取字段对不上原文**：回到 `parsing-resumes` 重新抽取这个字段，或人工核对简历原文确认正确值。不要直接改 JSON 蒙混过关——对不上就是对不上。
- **软推断字段漏标注**：给该段 `work_experience` 补 `industry_inferred: true`。
- 修正后重跑 `audit_extraction.js`，直到核对通过。

核对报告（`audited/<简历名>.audit.json`）留存逐字段核对结果，可审计、可复查。
