# explaining-similarity 评测场景

> 评测驱动开发（方法基线 §五）：先建评测场景，测"没有 Skill 时的基线表现"，再写最小 SKILL.md，按观察迭代。
> 评测对象：把 searching-talent-pool 的检索结果，生成 HR 可读的「为什么这个人像锚点」维度级解释。

## 评测场景

### 场景 1 · 为「像员工1的」检索结果生成解释

- 输入：`searching-talent-pool` 落盘的 `talent-pool/search-员工1.json`（Top 5 + 4 维度相似度）
- query：为这份检索结果生成解释——说清每个候选人为什么像员工1
- expected_behavior：
  - 对 Top 5 每人生成 2-3 句 HR 可读解释，点出「哪个维度最像、为什么」
  - 解释里引用的维度分数与 `search-员工1.json` 里的分数**完全一致**——LLM 只能引用，不能改动、不能编造新分数
  - 解释里引用的事实（学校、技能、公司、经历）均来自结构化字段，无编造
  - 带解释的结果落盘 `talent-pool/search-员工1-explained.json`

### 场景 2 · 解释要诚实标出差异维度

- 输入：同场景 1，关注解释的诚实性
- query：生成解释
- expected_behavior：
  - 解释不能一味夸「都很像」——相似度低的维度（如某人教育维度 0.58）要被诚实点出「这个维度差异较大」
  - 这是真实性的体现：维度分数有高有低，解释要如实反映

### 场景 3 · 防 LLM 数字串台（核心验收点）

- 输入：检索结果 JSON，其中某候选人维度分数明确为「经历 0.77 技能 0.77 教育 0.68 行业 0.66」
- query：生成解释
- expected_behavior：
  - 解释里出现的分数必须是 0.77 / 0.68 / 0.66 这些原值，不能出现检索结果里没有的分数
  - LLM 只组织语言、不重算分——核对解释中的每个数字都能在输入 JSON 里找到出处

### 场景 4（边界）· 检索结果文件缺失 / 类型不符

- 输入：`--search` 指向不存在的文件，或指向 JD 检索结果（`query_type=jd`）
- query：生成解释
- expected_behavior：
  - 文件不存在 → 报错退出，不产出虚假解释
  - JD 检索结果（无候选人锚点）→ 明确提示「只支持候选人锚点检索结果」，退出码 1
