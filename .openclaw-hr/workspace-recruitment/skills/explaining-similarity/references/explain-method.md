## 1. 解释要解决什么问题

`searching-talent-pool` 检索出来的结果是「排名 + 分数」——王浩然综合相似度 0.6761，经历 0.772、技能 0.769。但光给排名和分数，HR 还是不知道「凭什么说像」。这个 Skill 把检索结果翻译成 HR 能读懂的话：「两人都在互联网核心业务线长期深耕，技能栈高度重叠……教育背景差异略大」。

## 2. 输入与输出

- 输入：`searching-talent-pool` 落盘的检索结果 JSON（`talent-pool/search-<锚点>.json`），里面有 Top N 候选人和各自的 4 维度相似度分数。
- 输出：带解释的检索结果 JSON（`talent-pool/search-<锚点>-explained.json`），在原检索结果上为每个候选人加一段 `explanation` 解释文字。同时在终端打印每个候选人的解释。

CLI：`python3 explain_similarity.py --search talent-pool/search-<锚点>.json`

## 3. 核心设计：LLM 只组织语言，不重新算分

这个 Skill 必然要调 LLM——把数字翻译成人话是 LLM 擅长的事。但调 LLM 就有「数字串台」的风险：LLM 可能在生成解释时把分数改掉、或编一个检索结果里根本没有的分数。

防串台的设计有三条硬约束，全部写进了脚本的 prompt：

1. **维度相似度分数由 `searching-talent-pool` 真实算出，原样传给 LLM，prompt 明令「只能引用，不能改动、不能编造新分数」。**
2. **解释里引用的所有事实（学校、技能、公司、经历年限）必须来自传入的结构化字段，不得编造。**
3. **不让 LLM 自由发挥**——给定锚点和候选人的真实字段、真实分数，只让它「对比说人话」。

LLM 在这里只负责「解释组织」，不负责「算分」「排名」。算分排名是 `searching-talent-pool` 用余弦相似度做掉的确定性工作。

## 4. 解释的质量标准

一段合格的相似度解释：

- 点出「哪个维度最像、为什么」——结合具体事实（同样的技能栈、同样的行业赛道）。
- 也点出「哪个维度差异较大」——不一味夸「都很像」。维度分数有高有低，解释要如实反映。
- 引用的分数与检索结果 JSON 里的完全一致。
- 引用的事实都能在候选人结构化字段里找到。
- 2-3 句话，不分点编号，HR 能直接读。

## 5. 为什么这样防数字串台

招聘子 Agent 在评分阶段踩过「数字串台」的坑——LLM 给评分时把维度分数和总分算得对不上。相似度解释如果让 LLM 自由发挥，同样的坑会再踩一次：HR 看到的解释里写「经历相似度 0.9」，但检索结果其实是 0.77。

把「算分」和「解释」彻底分开——分数是脚本用余弦相似度算死的、原样传入、prompt 禁止改动，LLM 只做「对比说人话」——这就是这个 Skill 防数字串台的根本办法。解释质量好（引用真实事实、诚实标差异）的功劳在「约束 LLM 只组织语言」，不在「让 LLM 自由发挥」。
