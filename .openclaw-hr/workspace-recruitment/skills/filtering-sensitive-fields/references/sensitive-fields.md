## 1. 为什么要物理删除（不是叮嘱大模型）

几乎所有人第一反应都是在评分 prompt 里加一句"请不要根据年龄、性别评分"，然后把整份简历丢给大模型。这个做法的问题不在于话写得不够诚恳，而在于它**无法被证明**——大模型在 prompt 里看得到出生年月和性别，没有任何办法证明它打分时没受影响。招聘是要向监管和候选人解释的场景，一句 prompt 里的"请不要"说明不了任何事。

合规过滤层的设计原则是一句话：**不是求大模型别用敏感特征，是让它根本看不到。** 在数据进入评分模型之前，把敏感字段从结构化数据里物理删除——评分模型收到的 prompt 里根本不存在年龄、性别、院校层次。

业界已有真实代价：iTutorGroup 因直接用年龄做筛选特征被起诉、36.5 万美元和解；亚马逊招聘 AI 从历史简历学会给含"women's"字样的简历和女子学院毕业生降分，性别从未被直接使用却通过间接特征渗入，整个项目被下线。把敏感特征喂给评分模型，间接歧视是必然后果。

## 2. 敏感字段黑名单

`filter_sensitive.js` 的 `FORBIDDEN_KEYS` 维护这份黑名单，中英文键名都覆盖：

| 类别 | 字段 |
|------|------|
| 年龄 / 出生日期 | 出生年月、出生日期、年龄、生日、age、birth_date、birth_year、date_of_birth 等 |
| 性别 | 性别、gender、sex |
| 婚育 | 婚育、婚姻状况、生育、marital_status、marriage、children |
| 户籍 / 籍贯 / 出生地 | 籍贯、户籍、出生地、户口、hometown、household、domicile、native_place 等 |
| 民族 | 民族、ethnicity、nation、race |
| 健康 / 残疾 | 健康状况、残疾、health、disability |
| 院校层次 | 院校层次、院校排名、第一学历、school_tier、school_rank |
| 政治面貌 | 政治面貌、political_status |

中英文都列入的原因：评分模型看到英文键 `age` 一样会用它打分，不能因为键名是英文就放过。

## 3. 两类字段的法律强度差异

黑名单里的字段，合规分量分两类。两类都要物理删除，但到了合规论证时，法律分量不一样：

- **法定受保护特征**——年龄/出生日期、性别、民族、户籍籍贯、婚育、健康/残疾。《就业促进法》为其中一部分设了专条：性别（第 27 条）、民族（第 28 条）、残疾（第 29 条）、传染病病原携带（第 30 条）；年龄、户籍籍贯、婚育没有专条，由第 26 条"不得实施就业歧视"一般性条款覆盖。无论有没有专条，把这些当评分依据都是法律不允许的。
- **政策强烈反对、非法定受保护特征**——院校层次（"第一学历""985/211 门槛"）。教育部、人社部多次发文不鼓励校招设院校门槛，必须剥离，但定性是"避免间接歧视与政策风险"，不是"违反某条具体法律"。
- **政治面貌**——未被《个人信息保护法》第 28 条明文列举，但第 28 条对敏感个人信息用"等"字非穷尽列举，政治面貌属于应从严保护的敏感个人信息，一并剥离。

## 4. 递归扫描：敏感字段不只在顶层

敏感字段不只出现在数据顶层——**院校层次嵌在 `education` 子层里**。`filter_sensitive.js` 的剥离用递归扫描，所有层级（顶层、education 子对象、work_experience 数组里的每一段）都扫。

只扫顶层是合规漏洞的常见来源：顶层的出生年月、性别剥掉了，藏在 `education.school_tier` 里的院校层次没动，`985` 这个标签照样进评分模型。

## 5. 合规自检：不可绕过的关卡

剥离之后，`filter_sensitive.js` 做一道合规自检——递归重扫脱敏后的数据，用词干匹配找任何残留的疑似敏感 key。自检发现残留即退出码 1，绝不放行。

自检的词干匹配（`FORBIDDEN_STEMS`）是黑名单的兜底：黑名单逐字列写法时总有漏网的变体（如 `birthYear` 驼峰、`applicantBirthInfo` 这种合成键名），词干匹配把小写去分隔符后含 `birth`/`gender`/`schooltier` 等词干的 key 都兜住。

合规自检通过（剩余敏感字段 = 0）这一行，是写进日志的**合规证据**——可审计、可追溯。当候选人或监管来问"评分用没用年龄"，答案不是一句空洞承诺，而是一条可查的日志记录。
