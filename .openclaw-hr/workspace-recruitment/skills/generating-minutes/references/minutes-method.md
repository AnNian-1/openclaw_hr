## 1. 纪要生成做的三件事

`gen_minutes.py` 把转写稿变成纪要，分三步：

**step1 重组转写稿**——转写稿是按时间排的片段序列，同一个人可能连说好几段。脚本把连续的同说话人片段合并，得到"面试官: …… / 候选人: ……"的对话稿。这一步是确定性的字符串处理。

**step2 大模型生成结构化纪要**——把对话稿交给 DeepSeek V4，用 `response_format: json_object` 强制 JSON 输出。大模型产出：关键问答（qa）、优势（strengths）、待考察点（concerns）、高亮时刻（highlights）、评分建议（recommendation），以及候选人口述的项目数字（mentioned_numbers）。这一步是非确定性的大模型调用，脚本对它做 3 次重试；多次重试仍失败就显式报错退出码 1，绝不返回空纪要冒充成功。

**step3 数字回核**——见 §3。

## 2. 说话人标签映射：speaker_A/B 怎么变成面试官/候选人

`transcribing-interviews` 的 CAM++ 凝聚聚类只能告诉你"录音里有 N 个人"，它把他们标成 `speaker_A` / `speaker_B` / `speaker_C`……但 CAM++ 不知道谁是面试官、谁是候选人。

把标签映射成角色，靠 `--interviewer` 参数：它指定哪个标签是面试官，其他就是候选人。默认 `speaker_A` 是面试官——依据是面试录音里通常面试官先开口（开场、自我介绍引导），但 `speaker_A` 在 CAM++ 聚类里只是"第一个被聚出的 cluster"，和"先开口"没有必然关系，所以这只是一个**默认假设**，不是保证。

判断默认对不对：看生成的纪要里"面试官说的话"和"候选人说的话"有没有反。如果"面试官"在回答技术问题、"候选人"在提问，就是反了——把 `--interviewer` 换成 `speaker_B` 重跑。

为什么不让脚本自动判断谁是面试官：自动判断要么靠"谁先说话"（不可靠），要么靠大模型读内容判断（又引入一次非确定性调用）。把它做成一个显式参数 + 一条"反了就换"的简单规则，比藏一个不可靠的自动判断更稳。

## 3. 数字回核：大模型提取、脚本判真伪

数字回核要解决的问题：大模型生成纪要的自由文本时，会把候选人口述的数字记错——可能数字写错，可能把别处的数字安到这里。纪要里引用的项目数据（TPS、降幅、规模）是 HR 判断候选人能力的依据，错一个数字就误导一次决策。

回核的分工是关键：

- **大模型只负责"提取"**——它从转写稿里把候选人口述的数字挑出来，放进 `mentioned_numbers`，每项记 `claim`（原话数字）+ `context`（什么场景）。大模型不判断这个数字是真是假。
- **脚本负责"判真伪"**——`gen_minutes.py` 把每个 `claim` 里的数字 token 抽出来，在候选人原简历里查。数字 token 全部能在简历里找到 → 标"可追溯到原简历"；找不到 → 标"简历中未找到，需人工核实"。

为什么这样分工：判断"数字真不真"是一件确定性的事——要么简历里有，要么没有。确定性的事不该交给大模型（它会概率性犯错），交给脚本做字符串匹配。大模型擅长的是"从一段对话里认出哪些是项目数字"这种需要语义理解的事，让它只做这部分。

回核基准只能是候选人的**原简历**，不能是岗位 JD。JD 里的数字看起来"相关"，但它属于岗位、不属于候选人——拿 JD 做基准会把 JD 的数字误判成"候选人口述属实"。

## 4. 数字回核的已知局限：中文数字表述

回核脚本抽数字用的是阿拉伯数字正则（`\d+`）。候选人口述里的**中文数字表述**抓不到：

- "超卖率从千分之三降到十万分之二"——"千分之三""十万分之二"是中文数字，正则抽不出阿拉伯数字 token。

这种情况回核会标"无阿拉伯数字（中文数字表述，回核脚本未覆盖）"。要点是：这**不是漏判成"虚构"**，也不是判成"属实"——它诚实地标成"脚本没覆盖、这一项需人工看"。把"没核到"和"核过没问题"分开，是回核诚实性的底线。

实测核心的关键数字——80 万行、23 个服务、12.8 万 TPS、45 分钟降到 6 分钟——都是阿拉伯数字表述，回核都能覆盖。中文数字表述漏检的多是比率类（千分之、百分之）。生产环境改进方向：在回核前做一遍中文数字归一化（"千分之三"→ 0.003），把中文数字也纳入匹配。

## 5. ASR 误识的纠错由大模型承担

转写稿里仍可能有 ASR 误识的错字（FunASR Paraformer-zh 比旧版 faster-whisper 稳，但仍有少量错——"扣减"偶发听成"扣检"、低频人名偶发听错）。

纪要生成的 system prompt 里有一条明确要求：依据上下文纠正 ASR 误识的人名/术语错字。大模型在"后端架构师候选人"的语境里，能从上下文还原。

但大模型纠错不是 100%——专业术语错字可能漏网。这是链路的真实局限：转写有误差、纠错不彻底。生产环境如果对术语零容错，应在转写后加术语校正词表，而不是指望大模型全兜住。

## 6. 为什么评分建议只能是建议

纪要给的 `recommendation` 是"通过/待定/不通过"建议 + 理由。它是**建议**，不是决定：

- 候选人是否进入下一轮、是否录用，由人工面试官决定。这是《个人信息保护法》第 24 条对自动化决策的要求——涉及个人重大权益的决定不能完全由自动化做出，要保留人工干预（Human-in-the-Loop）。
- 纪要 Markdown 末尾固定带一条合规说明，把这条边界写明给看纪要的人。

纪要可以把候选人摆清楚——优势、短板、高亮时刻一目了然，帮 HR 判断得更快更准；但"判断"这个动作本身留给人。
