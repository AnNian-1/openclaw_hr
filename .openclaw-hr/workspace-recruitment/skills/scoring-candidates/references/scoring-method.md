8 维度评分方法

scoring-candidates Skill 的评分逻辑细则。SKILL.md 在需要时引用本文件。

== 1. 为什么不是一个总分 ==

一个综合总分丢掉了 HR 最需要的信息——这个分是怎么来的。两位都拿 60 分的候选人：第一位方向对口但各维度中规中矩，第二位某些维度突出但方向不对——这是处置完全不同的两种人，一个总分把他们混成一样。

把评分拆成 8 个维度、每维度配一句理由，ranking 才可解释：HR 看到的不是孤零零一个数字，而是能力结构。这也是个保法第 24 条对自动化决策"可解释"的硬要求——候选人有权要求说明评分依据。

== 2. 8 个固定维度 ==

8 个维度来自 candidate-profile-schema.md §8——基于 HR 业界面试评估标准、且能从简历判断的维度。维度清单固定写在 score_candidate.js 的 DIMENSIONS 常量里，不靠 LLM 临场记。

| 维度 | 简历阶段的评分依据 |
|------|------------------|
| 专业技能 | 技能清单、项目用到的技术、证书 |
| 经验匹配 | 行业、职级、职责与目标岗位的相关性 |
| 逻辑能力 | 业绩描述的逻辑性、项目复盘的深度 |
| 学习力 | 技能更新、转型经历、学历进修 |
| 沟通能力 | 简历表述的清晰度、是否有跨团队协作经历 |
| 协作能力 | 团队角色、跨部门项目 |
| 抗压能力 | 高强度项目经历、稳定性 |
| 价值观 | 职业选择的一致性、自我评价 |

每个维度 1-5 分。

== 3. 综合匹配分不是维度分的算术加权 ==

综合匹配分不是"8 个维度分按权重加权再映射到 0-100"。一个反例：一位候选人 8 维度全打 5 分，综合分也未必是 100——综合分里还含 8 维度之外的因素。

综合匹配分的真实含义，是评分模型对"这位候选人 × 这个岗位"整体匹配度的判断，综合了两部分：

- 8 维度的能力表现——候选人本身的能力画像；
- 岗位 fit 因素——薪资期望与岗位预算是否匹配、期望城市是否一致、经验年限与岗位要求是否错配（过低，或过高即 overqualified）。这些不在 8 维度里，但实打实影响"这个人来这个岗位合不合适"。

8 维度是结构化的能力画像，综合分是含 fit 的总匹配度——两样东西。一位能力强但 fit 差的候选人，8 维度分高、综合分却可能不高。

维度权重：评分 prompt 引导模型以"专业技能""经验匹配"这两个对口度维度为最重——方向不对口的候选人，在这两个高权重维度拿不到分，综合分自然低。权重是写进 prompt 的判断指引，不是事后乘的算术系数。

== 4. 评级切分 ==

综合匹配分 → A/B/C/D 评级，由 score_candidate.js 的 ratingOf() 固定切分，不靠 LLM 临场判：

| 评级 | 综合分区间 | 含义 |
|------|-----------|------|
| A | ≥ 85 | 强烈推荐 |
| B | 75-84 | 推荐 |
| C | 60-74 | 待定 |
| D | < 60 | 不匹配 |

岗位初筛基线是 60 分。注意：评级大类才是决策依据，1-2 分之差不抠——综合分本身有非确定性波动（同一份简历多次评分有正负几分浮动）。拿到 ranking 后看评级大类 + 评分理由，不要纠结精确分值。

== 5. concerns 与 hard_issues 的边界 ==

评分产出里 concerns（顾虑）和 hard_issues（硬伤）是两个边界严格的字段，不能混：

- concerns（顾虑）：岗位匹配度相关的担忧。期望薪资超岗位带宽、期望城市不符、方向不对口、overqualified、跳槽频繁、就业空窗期——这些都进 concerns。
- hard_issues（硬伤）：简历本身的真实性/可信度问题。只有三类算硬伤：
  ① 工作经历时间矛盾（两段全职经历时间区间重叠）
  ② 学历存疑（学历与岗位硬性门槛不符，或学历信息自相矛盾）
  ③ 简历内容自相矛盾（如工作年限与经历明显对不上）

为什么要分清：硬伤会触发"复核简历真实性"这种更严重的处置建议。一个简历完全真实、只是薪资期望偏高的候选人，不该被打"硬伤"标签。薪资高、城市不符是匹配度问题不是真实性问题，跳槽频繁、空窗期是稳定性信号不是真实性问题——都归 concerns。

抓出硬伤之后，评分 Skill 不淘汰候选人——把硬伤如实标进 hard_issues，建议动作写"建议人工复核简历硬伤后再定"，判断交还给人。这是个保法 24 条 + Workday Mobley 判例的要求：对个人有重大影响的决策不能完全交给算法。

== 6. 批量评分与排序 ==

batch_rank.js 对一个 JD、一个目录下的多份脱敏候选人 JSON 评分，按综合匹配分降序排序。同目录下的 `score-*.json` / `ranking-*.json` 不会被当成候选人。

增量缓存：`clean-<stem>.json` → `score-<stem>.json`，文件内 `cache.scorer_version`、`cache.jd_sha256`、`cache.clean_sha256`。三者与当前 JD 正文、当前 clean 文件、`SCORER_VERSION` 一致才 skip LLM。同人更新简历（clean 变了）或改 JD 正文会自动重评。改 8 维/prompt 时 bump `SCORER_VERSION`，全员变脏；用 `--stale-only --limit N` 分片重打，`--merge-only` 合并当前版本分数。混 version 的分数不得当作终榜。

`--force` 忽略缓存；与 `--limit` / `--max-seconds` 同时用时，一次进程仍只啃一块。OpenClaw exec `timeout` 过短会 SIGKILL（实测 120 秒、8 人、评到第 5 份被杀），分片时把 timeout 设到能盖住本批墙钟。

关键纪律——LLM 输出非确定性，批量任务偶发失败是常态（LLM 偶发返回非法 JSON、网络中断）。每份候选人最多评 3 次，3 次全失败显式标记"待人工处理"，绝不静默丢弃。招聘场景漏掉一个候选人是事故，宁可重试不可漏人。

每个候选人标"建议动作"（建议优先面试 / 建议进入面试候选名单 / 建议人工复核），不标"淘汰/通过"——AI 只给评分排序建议，最终决定由人工 HR 做。
