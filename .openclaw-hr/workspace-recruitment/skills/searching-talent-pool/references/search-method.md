## 1. 检索要解决什么问题

人才库建好之后，业务部门那句「上次招的张磊不错，再找几个像他的」就能回答了。检索要做的是：拿一个已知的人（或一份 JD），去人才库里捞「语义上相似」的候选人——这正是关键词搜索做不好的事。

## 2. 两种检索入口：按候选人 / 按 JD

`search_talent_pool.py` 支持两种 query：

- `--like <姓名>` —— 按候选人检索。锚点是库里已有的某个候选人，找出和他最相似的其他人。对应「再来一个像张三的」。
- `--jd <JD文件路径>` —— 按职位描述检索。锚点是一段 JD 文本，现算它的向量，找出最匹配的候选人。

`--topn N` 控制返回数量（默认 5）。`--compare-keyword` 额外跑一遍关键词检索做对照。

## 3. 向量语义检索怎么算

检索全程不经 LLM 排名：

1. 取 query 向量——按候选人检索时直接用库内已有的整体向量；按 JD 检索时现算 JD 文本的向量。
2. 与库内每名候选人的整体向量逐一算余弦相似度 `cos()`。
3. 按相似度从高到低排序，取 Top N。

相似度是真实的向量余弦计算，**不是 LLM 编出来的名次**——这是检索结果可信的根本。

## 4. 维度级相似度分解

按候选人检索时，除了综合相似度，还会用 4 个维度向量分别算相似度：

- `education`（教育）、`experience`（经历）、`skills`（技能）、`industry`（行业）

每名 Top N 候选人都会给出 4 个维度的相似度，按高到低排。这样检索结果不是一个黑盒分数——能说清「这个人主要是经历和技能像，教育差一些」。维度分解依赖入库时每人存的 4 个维度向量（见 `ingesting-talent-pool`）。

按 JD 检索时锚点是一段文本、没有维度向量，维度分解为空，但综合相似度排序正常。

## 5. 关键词检索对照组

`--compare-keyword` 会额外跑一遍关键词检索作为对照：

- 分词：英文按词、中文按 2-gram（相邻两字）。
- 打分：query 的词在候选人文本里命中的比例（词重叠率）。
- 按词重叠率排 Top N。

这是 BM25 式的朴素关键词检索，只看「字面是否一样」。

## 6. 向量检索 vs 关键词检索：差别在哪

`--compare-keyword` 跑完会打印差异分析——「只有向量召回的人」「只有关键词召回的人」。

关键词检索的硬伤：它只看字面重叠，看不懂语义。「Java 后端架构师」和「Android 移动端开发」字面词重叠少、但都是写代码的技术人；「后端架构师」和「财务经理」可能都写了「负责团队」「5 年以上经验」，字面重叠反而不低。结果就是关键词检索会把财务经理、运营总监这类语义完全不相干的人，仅凭通用词面重叠排进「像后端架构师」的结果里。

HR 人才库要找「相似的人」，靠的必须是理解语义的向量检索。`--compare-keyword` 的作用就是把这个差别摆在台面上。

## 7. 检索结果产物

检索结果落盘 `talent-pool/search-<tag>.json`（`tag` 是锚点姓名或 `jd`），含：

- `query` / `query_type`（candidate / jd）/ `topn`
- `results`：Top N 数组，每项含 `rank` / `id` / `name` / `category` / `target_position` / `similarity`（综合相似度）/ `dim_similarity`（4 维度相似度）

这份结果是 `explaining-similarity` Skill 的输入——它读这份 JSON 来生成维度级解释。
