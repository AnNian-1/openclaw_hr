# 字段抽取规则

> parsing-resumes Skill 的字段级抽取细则。SKILL.md 在需要时引用本文件。
> 字段标准对齐 `candidate-profile-schema.md`（招聘子 Agent 数据资产）。

## 目录

- 1. 输出 JSON 结构
- 2. 基础信息字段
- 3. 教育背景字段
- 4. 工作经历字段
- 5. 技能字段
- 6. 派生字段（计算字段）
- 7. 硬提取 vs 软推断
- 8. 合规红线（绝不进入输出）

## 1. 输出 JSON 结构

抽取产出一个 JSON 对象，五个字段组：

```json
{
  "name": "...",
  "phone": "...",
  "email": "...",
  "target_position": "...",
  "expected_salary": "...",
  "expected_city": "...",
  "available_date": "...",
  "education": { "school": "...", "major": "...", "degree": "...", "graduation_year": "..." },
  "work_experience": [
    { "company": "...", "position": "...", "start_date": "...", "end_date": "...", "industry": "...", "industry_inferred": true }
  ],
  "total_experience_years": 0,
  "job_count": 0,
  "skills": ["...", "..."]
}
```

## 2. 基础信息字段

| 字段 | 抽取规则 |
|------|---------|
| `name` | 姓名，逐字照抄。简历里若标了"(男)/(女)"，括号内不要带进 name |
| `phone` | 联系电话，**保持原文脱敏形态**（如 `137**8845`），不还原、不补全 |
| `email` | 邮箱，同上保持脱敏形态 |
| `target_position` | 求职意向/目标岗位，逐字照抄 |
| `expected_salary` | 期望薪资，逐字照抄（含"月薪/13薪"等说明） |
| `expected_city` | 期望城市 |
| `available_date` | 到岗时间 |

## 3. 教育背景字段

- 简历常列多段学历。`education` 只取**最高学历**那一段。
- 例：候选人A有某某大学3硕士 + 某某大学4本科 → 取硕士。
- `graduation_year`：从起止时间的结束年取，如 `2017.09 - 2018.11` → `2018`。
- `school` 照抄学校全名（含括号里的英文名也保留）。

## 4. 工作经历字段

- `work_experience` 是数组，每段独立工作经历一条。
- 每条必含 `company` / `position` / `start_date` / `end_date`。
- `start_date` / `end_date` 统一成 `YYYY-MM` 格式。在职写 `"至今"`。
- `industry`（行业）是**软推断字段**——见 §7。

## 5. 技能字段

- `skills` 是字符串数组，对应简历的"专业技能/技能清单"段。
- 逐项照抄，不归并、不改写。

## 6. 派生字段（计算字段）

派生字段不是从原文某处抄来，而是按工作经历**算**出来的：

| 字段 | 计算方式 |
|------|---------|
| `total_experience_years` | 各段工作经历时长之和（年）。简历若有"工作年限"栏，以**起止时间算出的值**为准，自述值只作参照 |
| `job_count` | `work_experience` 数组长度 |

> 为什么以计算值为准：求职者自述年限可能笔误或有意写长。schema 约定派生字段一律以可计算的客观数据为准。

## 7. 硬提取 vs 软推断

抽取产出的字段分两类，可信度来源不同：

- **硬提取字段**：值在简历原文有明确出处（name / salary / school / 起止时间）。逐字照抄。
- **软推断字段**：原文没直接写，靠上下文推导。典型是 `industry`——简历不会写"我所在的行业是内容社区"，是看公司名"某内容社区平台"推出来的。

软推断字段**必须显式标注**。约定：`work_experience` 里每段若产出了推断的 `industry`，同时加一个 `"industry_inferred": true` 标志。这样下游评分、合规审计能一眼看出哪些是 AI 判断、哪些是简历事实。

## 8. 合规红线（绝不进入输出）

下列字段简历里可能有，但**绝对不能出现在抽取产出的 JSON 里**（schema §9，依据个保法 24 条 / 就业促进法 26-31 条）：

- 年龄 / 出生日期
- 性别
- 婚育状况
- 户籍 / 籍贯 / 出生地
- 民族
- 健康状况 / 残疾

这些字段进了结构化数据，下游评分就可能拿它当依据，构成就业歧视风险。抽取时直接跳过它们——既不抄中文键、也不译成英文键。`validate_profile.js` 会做最后一道拦截，但抽取阶段就该主动排除。
