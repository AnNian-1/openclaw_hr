## §0 一句话主旨：把 1-2 天的体力活压到约 30 分钟

周一下午两点，业务部门找上门：公司要给新入职员工办一期入职培训，业务讲师需要 HR 协助，把整套培训物料备齐——PPT 大纲、讲师手册、学员手册、随堂测试题。**讲师手头只有一个培训主题，整套物料从零做起，人工要一两天。**

这是入职之外的另一种工作模式：**从一个主题出发，一层层生成出多份内容，前一份决定后一份的形态，最后汇成一整套物料。** 培训子 Agent 要做的，就是把这条生成链固化成 Agent 自己会用的标准能力。

> **AI 的价值定位要说准，免得理解偏**：AI 的价值不在"质量碾压人工讲师"，在"**把 1-2 天的体力活压到约 30 分钟**"。一位有经验的讲师，单论某一页讲解的打磨，仍可能比 AI 写得更好。但讲师的时间贵在判断和经验，不该耗在排版、凑题、逐页写控场要点上。Pipeline 把这套机械劳动接走（且**不生成逐字稿**，避免无效长文），讲师拿到的是一份完成度很高的初稿，把精力留给"审核、校正、按现场调整"——这才是这条 Pipeline 的真实定位。

> **一条底线**：AI 生成的培训物料是讲师的**辅助，不是可以直接对外的权威材料**。物料必须经讲师审核后才能交付，每个文件都应标注"AI 辅助生成、讲师审核后交付"。这条合规红线 §10 展开。

**本轮实操真实产出**：以"星桥科技新员工入职培训"为主题（公司已有现成真实 HR 文档可作素材，产出能逐句追溯到真实制度），端到端约 30 分钟，产出 **8 个 Markdown 文件、共 3010 行、约 6.9 万字**（现行交付不含配图）。

## §1 生成 Pipeline vs 流程编排：培训为什么不用 Lobster

**编排范式**指"把一个复杂任务拆成多个步骤、再把这些步骤组织起来跑"的方式。Lesson 2-2 用到两种：

| 维度 | 流程编排型 | 生成 Pipeline 型 |
|---|---|---|
| 代表 | 入职子 Agent、Lobster 工作流 | **培训子 Agent、ADDIE Pipeline** |
| 步骤的性质 | 混合——shell 命令、脚本、真人审批 | **同质——每一步都是 LLM 生成任务** |
| 步骤间的关系 | 有强先后依赖，有的还要等审批 | 有上下游，前一步产出喂给后一步 |
| 要不要等人 | 要——关键节点停下等真人点头 | **不要——从头到尾一次跑完** |
| 要不要按时间触发 | 要 | **不要——一次性生成** |
| 工程上要解决的核心问题 | 流程能停得住、接得回、拒得掉 | **阶段间的数据契约严丝合缝** |

> **术语澄清**："Pipeline"（流水线）指的是同一类思想：把任务拆成首尾相接的阶段，前一阶段的产出是后一阶段的输入。招聘子 Agent 的"评分 Pipeline"、本集的 ADDIE 都是 Pipeline。而流程编排型不叫 Pipeline，因为它的步骤不只是"数据流动"，还夹着审批、夹着等待——它是"流程"，不是单纯的"流水线"。

### 反例：把培训物料生成做成 Lobster 工作流

培训物料生成的若干步骤——分析需求、设计大纲、写讲师手册、出测试题——确实有上下游顺序，但它们之间**没有"强依赖"那种硬约束**：没有哪一步要停下等人审批，也没有哪一步要等到某个时点才能跑。

> **硬套 Lobster 工作流，你要为它单独写一个工作流文件、配置每个步骤、处理审批字段——而这些机制一个都用不上。工作流文件凭空多出一层复杂度，却没换来任何东西。** 这种活，一条直白的生成 Pipeline 脚本（本集是一条 prompt 链）就够了。选错范式，不该有的复杂度会凭空冒出来。

### 关键：生成 Pipeline 的强约束不在引擎里，在 prompt 设计里

本集的 ADDIE Pipeline，**没有一个 `addie-pipeline.py` 之类的编排脚本**。它的真实形态是：5 个阶段、多次 `openclaw agent --local --agent training -m "..."` 调用（生成 8 份文本物料），prompt 内联在 `-m` 参数里。阶段之间的交接，靠文件落盘 + prompt 指定读哪些文件。

> **为什么不写个编排脚本？因为这个范式不需要。** 生成 Pipeline 型编排的强约束，不在引擎里、不在脚本里，**就在 prompt 设计里**。只要每一次调用的 prompt 都写清"读什么、产出什么"，这条 Pipeline 就成立。这正好和入职用的 Lobster 工作流形成对照：Lobster 需要工作流文件和引擎来做 halt、resume、审批门，而 ADDIE 这种"步骤间没有审批、没有时间触发、全是 LLM 生成任务"的 Pipeline，套一个工作流引擎只会徒增复杂度。

## §2 一套培训物料到底包含什么

业务部门一句"明天上午给新人做场培训"，落到 HR 头上不是一句话，是一摞活。一套真正能用的培训物料，至少包含**八类文件**：

| 物料 | 作用 |
|---|---|
| 需求分析 | 培训教给谁、要解决什么痛点、达成什么目标 |
| 课程设计 | 课程结构、模块划分、时长分配、教学方式 |
| PPT 大纲 | 逐页的标题与要点，是讲台上放映的主体 |
| 讲师手册 | 给讲师的逐页讲解要点、互动引导、控场提示（**不含逐字稿**） |
| 学员手册 | 发给学员、培训后能带走当工具书查的材料 |
| 课后测试题 | 检验学员到底学到没有 |
| 交付指南 | 一份说明，告诉没参与设计的讲师怎么把这套物料落地 |
| 评估反馈表 | 培训结束后让学员匿名填，收集"培训本身好不好"的反馈 |

**这八类不是平摊并列的，它们之间有先后**——必须先想清楚"教给谁、教什么"，才能排课程结构，才能逐页写 PPT、写讲义。这条先后顺序，正是 ADDIE Pipeline 要落实的东西。

人工做这件事的三个痛点：
- **耗时**。一套完整物料一名讲师要花一到两个工作日。大量时间不是花在"想内容"上，是花在排版、凑测试题、写控场提示这类机械劳动上——典型的"知道怎么做，但就是耗时间"。
- **不成体系**。很多讲师凭经验做，跳过需求分析直接动手写 PPT，结果培训目标和实际讲的内容对不上。
- **物料不齐**。时间一紧往往只来得及做 PPT，讲师手册、测试题缺位——培训讲完了，没人能说清效果到底如何。

## §3 ADDIE：培训设计的五阶段框架

ADDIE 不是本课发明的，它是培训设计领域沿用了数十年的标准方法论，五个字母是五个阶段的首字母：

| 阶段 | 中文 | 本课落地 | 产出物 |
|---|---|---|---|
| **A**nalysis | 需求分析 | 分析受众、培训目标、痛点、约束条件 | `01-needs-analysis.md` |
| **D**esign | 课程设计 | 课程结构、模块划分、时长分配、教学方式 | `02-course-design.md` |
| **D**evelopment | 物料开发 | 据课程设计逐项生成全套物料 | `03` PPT 大纲 / `04` 讲师手册 / `05` 学员手册 / `06` 测试题 |
| **I**mplementation | 实施 | 把物料组织成讲师能落地的培训包 | `07-delivery-guide.md` |
| **E**valuation | 评估反馈 | 课后测试题 + 培训反馈表 | `06` 测试题 / `08-evaluation-form.md` |

> **ADDIE 之所以是"框架"而不只是"步骤清单"，关键在它强制了一个顺序**：先分析、再设计、再开发，最后评估。人工做培训最常犯的错——跳过需求分析直接写 PPT——在 ADDIE 里被结构性地堵住了：**没有需求分析的产出，设计阶段就没有输入。** 这个"上一阶段没产出、下一阶段就没法开工"的硬约束，正是生成 Pipeline 型编排的本质。

## §4 Pipeline 的本质：前阶段输出严格定义后阶段输入

把多个步骤串起来这件事本身不难。难的是让它们"**严格承接**"——不是松散地"prompt 接 prompt"，而是**后一阶段的输入由前一阶段的输出严格定义**。这是 ADDIE Pipeline 和"随便排个顺序"的分水岭。

### 承接靠两样东西落实

1. **文件落盘做交接介质。** 每个阶段的产出都是一个写进 `training-materials/` 目录的真实文件。下一阶段开工前，先把上一阶段的文件读进来。交接介质是磁盘上的文件，不是 LLM 上下文里飘着的一段话——**文件可审计、可复查、可单独重跑**。
   > 还有一个更底层的工程理由：8 份物料近 7 万字，若全程留在 LLM 上下文里跨 7 次调用累积，会把上下文窗口撑爆、把注意力稀释。**文件落盘相当于给 Pipeline 加了一层外部记忆**——每次调用只从磁盘读进这一步需要的那几个文件，拿到的是一个有界的、干净的新鲜上下文。

2. **prompt 明确指定读哪些文件、吃哪些字段。** 每一次调用，prompt 里都写死"先读 XX 和 YY，再据此产出 ZZ"。Agent 不是自由发挥，是被 prompt 钉在"承接前一阶段"这件事上。

### 承接做到位的最直接证据：对应矩阵

课程设计文件 `02-course-design.md` 的最后一节标题是"**模块与培训目标对应矩阵**"。这一节把课程设计的每个模块，和需求分析里定下的每个培训目标，显式地一一对应起来。它的意义是：课程设计不是 Agent 凭感觉排的，每一个模块都能反查到 `01-needs-analysis.md` 里的某一条培训目标。**这张矩阵，就是"前阶段输出严格定义后阶段输入"落到文件里的样子。**

### 八类物料的承接链

| 物料 | 输入来自 | 承接的关键字段 |
|---|---|---|
| 01 需求分析 | `source-docs/` 三份真实 HR 文档 | 公司简介、培训通道、入职流程 |
| 02 课程设计 | 01 需求分析 | 5 项培训目标 T1-T5、6 条受众痛点 |
| 03 PPT 大纲 | 02 课程设计 | 5 个课程模块的结构与时长 |
| 04 讲师手册 | 03 PPT 大纲 | 21 页页码、标题、要点 |
| 05 学员手册 | 03 PPT 大纲 | 5 模块划分、各模块知识点 |
| 06 测试题 | 01 需求分析 + 05 学员手册 | T1-T5 培训目标、手册考点 |
| 07 交付指南 | 全部物料清单 | 8 文件清单、实施流程 |
| 08 评估反馈表 | （相对独立，是培训后的即时反馈表） | — |

### 单一内容源：一致性的关键设计

这条链里有个细节值得点出：**04 讲师手册和 05 学员手册都吃 03 PPT 大纲，而不是各自重新去读 source-docs。** 这是有意的设计——让 PPT 大纲当"**单一内容源**"。三份物料（PPT、讲师手册、学员手册）共用一个源头，就不会出现"PPT 说五大中心、讲师手册说六大中心"这种自相矛盾。

> **一致性靠单一内容源约束，比让三份物料各读各的素材稳得多。** 这正是"AI 一键生成"最容易翻车的地方——PPT 说五大中心、讲师手册说六大中心，测试题考的考点学员手册里根本没讲。ADDIE Pipeline 用单一内容源把这种自相矛盾从结构上堵住。

> **一条边界，免得把"单一内容源"理解过头**："单一内容源"保证的是几份物料彼此口径一致，**不等于每句话都能精确回溯到 source-docs**。03 PPT 大纲本身可追溯源文档，但 04 讲师手册的讲解要点扩写、05 学员手册的速查 Q&A，是 LLM 在 03 的 bullet 基础上写出来的——离源文档隔了两三跳。所以讲师审核时，对 04 / 05 里扩写出的具体制度表述（数字、名称、流程细节），仍要回查 source-docs 核对，不能因为"都从 PPT 大纲来"就默认它们一定准。

## §5 两个最关键的 prompt 设计：讲师手册与测试题

八份 prompt 里，讲师手册和测试题这两份的设计最见功夫——它们决定了产出是"能用"还是"看着齐全但用不了"。

### 讲师手册：核心要求是"讲解要点 + 控场"，**不要逐字稿**

早期实验曾要求每页写可照念的长篇逐字稿——生成慢、难审、实际授课时讲师也很少照念。现行流程已删除逐字稿：每页只要 **讲解要点（3～6 条 bullet）+ 互动引导 +【讲师提示】**（如"这页容易讲超时"）。讲师按要点自己组织话术即可。

> **取舍**：手册要帮新讲师"知道这页讲什么、怎么控场"，不必替他把每句话写死。省掉逐字稿后，步骤 3 耗时与审稿成本显著下降，物料仍够用。

### 测试题：核心要求三条

1. **每道题标注【对应培训目标】**，确保 T1-T5 五个目标都有题覆盖——这是 **ADDIE 闭环的关键**：需求分析定下的目标，最后必须由评估回头检验。
2. **难度分梯度**（基础、中等、应用），全是基础记忆题区分不出"真懂"和"背下来了"。
3. **每道题必须有"答案详解"**，解释为什么对、为什么其他选项错——只给答案字母，学员做错了也不知道错在哪；有了详解，测试题才从"考试工具"升级成"复习工具"。

## §6 核心 Skill：markdown 指令型（materials）

把 ADDIE 这条 prompt 链从"靠人每次手敲多次调用"重构成 Agent 自己会用的标准能力——封装成 **一个** Skill：

| Skill | 形态 | 封装对象 |
|---|---|---|
| `generating-training-materials` | **markdown 指令型 Skill** | ADDIE 五阶段 prompt 链——SKILL.md 正文编排工作流，prompt 模板放 `references/` |

> **现行交付只有这一个 Skill。** 早期实验另做过 `generating-training-figures`（matplotlib 配图），已裁撤，见 §7。招聘侧常见的「脚本型 Skill」（如 `validate_*.js`）仍可作为对照形态理解，但培训子 Agent 本身不依赖配图脚本。

### 新形态：Skill 也能封一条 prompt 链

`generating-training-materials` 展示了一个关键形态：**Skill 不只能封一段可执行脚本，也能封一条 prompt 链、一整套工作流。** Lesson 2-1 的 `parsing-resumes`、`auditing-extraction` 都是脚本型（有校验脚本做确定性校验）。ADDIE Pipeline 没有确定性脚本可封（它没有 `addie-pipeline.py`，它的"确定性"在 prompt 设计本身）。这种情况，Skill 化要做的不是"给它一个脚本"，是"**把这条 prompt 链固化成一份 Agent 能照着一步步走的标准工作流文档**"。这就是 markdown 指令型 Skill。

### markdown 指令型：确定性靠"写死的步骤结构"兜，不靠代码兜

脚本型 Skill 把确定性收进代码（校验脚本一跑，对错有定论）；markdown 指令型的**阶段生成**没有脚本主体，确定性主要靠 SKILL.md 正文结构来兜。具体是四件事：

1. **写死的步骤清单。** ADDIE 是抽象框架，正文要把它翻译成编号步骤 0→7（生成）+ **步骤 8（交付前自检）**，Agent 照着走就行。**把方法论翻译成可执行 checklist，是 markdown 指令型 Skill 的核心手艺。**
2. **写死的文件名承接。** 每个步骤明确写出输入文件名、输出文件名——"步骤 2 读 01 和 02、产出 03"。
3. **可自检的完成判据。** 每步判据必须具体（"两份文件落盘""末尾有对应矩阵"），不能写"产出质量良好"。
4. **评测说明书进工作流。** `evals/eval-cases.md` 不是只给作者看的旁注——Agent 交付前必须对照；可机器化部分用 `scripts/self_check.py` 当轻量裁判，判断项仍按 `expected_behavior` 人工核。

> **形态补充**：ADDIE 阶段生成仍是「正文当裁判」；交付验收可叠一层结构自检脚本，堵住「只生产不验收」。判据与 eval-cases 写得含糊，Skill 仍兜不住确定性。

### 在 `skills info` 上看得见的形态

`generating-training-materials` 主体仍是 markdown 指令型（生成靠 `group:fs`）；现行为 `self_check.py` 声明 `requires.bins: [python3]`，`skills info` 应能看到对应 Requirements。

### 换主题复用的红利，要在正文里讲清

把 prompt 链固化成 Skill 之后，多出来一个裸做法没有的红利——**换主题复用**。换一个培训主题，只改步骤 1【模板 1】里对素材和受众的描述，后面 6 步一个字都不用动（它们吃的是前阶段产出文件，主题会自动顺着流水线往下传）。

> 但这条红利不会自己发生——**必须在 SKILL.md 正文里把它当成一条规则写明**，Agent 才会这么用。这就是"把 prompt 链封成 Skill"相对"每次手敲 prompt"的核心增量价值：手敲做法换主题要重发整条 prompt 链，Skill 化做法换主题只改一处。

## §7 配图能力已裁撤：为什么不再做 figures Skill

**现行结论：培训子 Agent 不做配图交付；`generating-training-figures` 不纳入标准能力。**

早期实验曾把 matplotlib 结构图封成脚本型 Skill，并讨论「需求同期标注【建议配图】、产出后置批量画图」。实践下来，这条支线对「一套能上的培训物料」帮助有限，反而抬高维护成本，因此裁撤。

### 为什么砍掉

1. **核心价值在文本 Pipeline，不在 PNG。** 讲师真正缺的是 PPT 大纲、讲师手册（讲解要点/控场）、学员手册、测试题与评估闭环；结构图可有可无，不应绑架交付完整性。
2. **图与源文档脱节。** `gen_figures.py` 把职级、节点、安全流程等**写死在绘图函数里**，运行时并不解析 `source-docs/` 或 PPT 大纲——源文档一变，图不会自动变，还要人改代码再重跑，和「忠实于素材」的纪律拧着。
3. **旁路与校验成本高。** Agent 可能跑到 workspace 里同名旧脚本；退出码 0 也不等于图画对，必须逐张 Read 肉眼核事实标注——投入大、收益不稳定。
4. **与 ADDIE 主 Skill 抢注意力。** 第二个 Skill、`python3`/`runtime`/`media` 权限、字体回退链、路径反推……都是为配图单独养的一套工程，稀释了「一个 materials Skill 换主题复用」的主线。

### 现行做法

- Pipeline **只产 8 份 Markdown**；PPT 大纲里不必再强制【建议配图】清单作为交付门槛。
- 若某次课务实在需要插图：由**讲师 / 设计师**按品牌规范另做，或临时使用平台图像工具——**不属于培训子 Agent 的标准 Skill 闭环**。
- workspace 里若仍残留 `skills/generating-training-figures/` 或 `training-materials/figures/`，视为历史实验产物，**Agent 不应主动触发**。

## §8 双 Claude 迭代：真跑 → 观察 → 改 Skill

**双 Claude 迭代**：让装上 Skill 的 Agent **真跑任务**，观察它哪里卡、哪里漏，带着具体观察回去 **改 Skill**（执行侧 Agent + 作者侧改文档，常构成「双 Claude」闭环）。

配图 Skill 虽已裁撤，但迭代方法仍适用于 `generating-training-materials`：

| 观察（真跑撞到的坑） | 加固动作（写回 SKILL.md） |
|---|---|
| 跳过需求分析直接写 PPT | 步骤顺序写死 A→D→I→E，完成判据要求 01/02 先落盘 |
| 讲师/学员手册各读各的 source-docs，口径打架 | 写死单一内容源：04/05 只吃 `03-ppt-outline.md` |
| Agent 幻觉「文件已存在」偷懒不生成 | prompt / 任务声明「该文件目前不存在，不要假设已存在」 |
| 换主题时 Agent 想改后几步模板 | 正文规则：只改步骤 1【模板 1】，后 6 步不动 |

> 方法论原则不变——**任务越脆弱、越要一致，就给越具体、越低自由度的指令。** 配图时代的教训（「别自己写脚本」还不够，还要写死跑哪条路径）同样适用于文本 Pipeline：关键约束必须写进步骤与硬规则，不能靠 Agent 临场发挥。

## §9 4 维度范式判断准则

培训（ADDIE）和入职（Lobster）两种范式都跑透之后，回头给出判断准则。一句话：**纯 LLM 生成 → Pipeline；混合命令、脚本、审批 → Lobster。**

| 判断维度 | 新员工入职审批 | 培训物料生成 | 报销 / 调薪审批 | Offer 发放 |
|---|---|---|---|---|
| ② **审批门**（硬指标） | 有（合同 + 账号 2 门） | **无** | 有（主管 / 财务审批） | 有（发放前审批） |
| ① **强先后依赖**（运行时条件控制） | 有（reject 终止后续节点） | **无（五阶段纯线性）** | 有（超额自动加签上级） | 部分 |
| ④ **纯 LLM 任务** | 否（脚本 + 审批 + 条件） | **是（每步都是生成）** | 否（金额校验 + 打款） | 混合 |
| **→ 范式判断** | Lobster | **Pipeline** | Lobster | 拆分 |
| ③ 是否叠加 Cron（正交，不参与范式判断） | 是（7/30/60/90 review） | **否（单次跑）** | 否（提交即触发） | 否 |

> **培训物料生成命中三个"Pipeline 特征"**：无审批门、无强先后依赖（五阶段纯线性）、每步都是纯 LLM 生成任务。这三个特征叠加，就是"生成 Pipeline 型"的判据——套 Lobster 工作流引擎只会徒增复杂度（§1 反例）。这套判断力不锁定 HR，可推广到任何 Agent 系统设计。

## §10 合规红线：培训物料 AI 辅助标注

### 红线：AI 生成的培训物料，必须标注"AI 辅助生成、讲师审核后交付"

培训物料和入职审批不一样——它不直接定法律责任，但它**会教人**。一套 AI 生成的物料里，讲师手册含逐页讲解要点、测试题带标准答案，学员会照着学、照着考。问题是：**AI 一键生成，不等于一次就对。**

> **一个真实的反面例子**：AI 生成的测试题或讲师手册要点里，制度数字、职级对应可能写错——例如把「P8↔M4」写成「P8≈M5 VP」。错误藏在长文本里，从 Agent 的「已完成」回报看不出来，必须对着 `source-docs/` 逐条核对。如果物料不加「AI 辅助、须讲师审核」标注就直接上课，错误会原样传给学员。

标注的作用有两层：**一是知情**——讲师和学员有权知道手里是 AI 生成的初稿，不是专家定稿；**二是定责**——把"必须有人校验"这个动作明确钉进物料，它不是免责声明，是流程要求。

> **监管背景**：《生成式人工智能服务管理暂行办法》（2023.08.15 施行）要求生成式 AI 的输出内容合规，AI 生成的培训内容进入正式交付前要有把关环节。

### 怎么落实：写进 Pipeline 的物料模板，不靠 AI 自觉

落实只有一处，但必须做死：ADDIE Pipeline 产出的 8 个物料文件，每个文件 header 固定加一行标注——

```
> 本物料由 AI 辅助生成，讲师 / 培训负责人审核后交付。
```

> **这一步要作为 Pipeline 的固定输出环节，不能靠 AI 自觉。** §5 的实验里能看到 Agent 确实有一定边界意识——PPT 大纲末尾它自己加了"PPT 具体视觉呈现由设计师按品牌规范完成"的说明。但 **Agent 的自觉不稳定，这次加了下次未必加**。把标注写进 Pipeline 的物料模板、每个文件强制带上，才是可靠的落实。

### 诚实的局限：合规边界会变

合规边界不是固定的，它随法律演变（《个人信息保护合规审计管理办法》2025.05.01 施行；EU AI Act 高风险义务时间表一直在调整）。**本集教的不是一套"一次写好永远合规"的代码，而是一种把合规红线工程化落实的方法**——把红线拆成可落地的工程措施、落在流程里看得见的位置（一行文件 header 标注）。法律变了措施要调，但"红线必须落到看得见的工程位置、不能停留在态度"这个方法不变。

## §11 业界对位：基线 / 差异化 / 营销陷阱

把培训子 Agent 放回真实世界，和市面上的 AI 课件生成工具摆在一起比。

### 第一层：基线——不做就被淘汰

"用 AI 生成一份 PPT 大纲"早已不是新鲜事，是入场券。小慧在基线上做到的是 §5 ADDIE 开发阶段产出 21 页 PPT 大纲——"也有，且做扎实了"。

### 第二层：差异化——头部才做的事

| 差异化点 | 通行做法 | 小慧的做法 |
|---|---|---|
| 培训物料完整度 | 给一份 PPT，讲义和测试题靠讲师自己补 | §5 ADDIE 五阶段一次出 8 类文本物料——PPT 大纲 + 讲师手册 + 学员手册 + 测试题 + 交付指南 + 评估表，近 7 万字 |
| 一致性 | 各份物料各说各话，容易自相矛盾 | 单一内容源约束——讲师/学员手册都基于 03 PPT 大纲，口径一致（§4） |
| 可控性 | 商业工具的生成逻辑是黑盒 | Pipeline 调用、物料 prompt 全部看得见、改得动，换主题只改一处 |

### 第三层：营销陷阱——"AI 一键出 PPT 就是一键出培训"

AI 课件生成工具普遍宣传"一键生成培训课件"。问题在于"**课件**"这个词被偷换了——多数工具一键出的只是 PPT 幻灯片。但一场培训真正要的物料远不止 PPT：讲师需要逐页讲解要点与控场提示（讲师手册），学员需要带得走的工具书（学员手册），培训效果要靠测试题来评估，新讲师还需要一份交付指南才知道这套物料怎么用。

> **讲师拿到一份只有幻灯片、没有任何授课指引的 PPT，培训当天仍难把控节奏。** §5 的 ADDIE Pipeline 一次出的是 8 类物料（讲师手册为讲解要点版，不含逐字稿）——这才是"一套能上的培训物料"，不是 5 页 PPT。营销陷阱的共同点：把"做了一部分"包装成"全做完了"。省掉的环节往往正是工业级和 demo 级的分界线。

### 什么时候用商业工具，什么时候自己做

- 要开箱即用、有 SLA 保障 → 买商业工具 / SaaS。
- 要完全可控、能按自己业务深度定制、能嵌进自己工作流的培训物料生成 → 本课这套方案就是骨架。它的价值不在"功能比商业工具多"，在"每一处都是你自己的，看得见、改得动"。

> **诚实的局限**：培训子 Agent 产出的是 AI 辅助生成的初稿，不是专家定稿。任何培训物料对外交付前必须经讲师审核、带"AI 辅助生成、讲师审核后交付"标注——这是合规红线，不是可选项。
