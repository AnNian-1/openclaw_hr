## §1 工业四步操作模板（通用）

在 OpenClaw 里给一个 Agent 加一项能力，标准流程是四步，缺一不可：

1. **建 Skill**——写 `SKILL.md`（合法 frontmatter），按渐进式披露把脚本放进 `scripts/`、详细文档放进 `references/`、评测放进 `evals/`。
2. **改核心 md 文档**——在 persona 文档里告诉 Agent"你现在有这个能力了、它嵌在工作流哪一步、什么时候该调"。`TOOLS.md` 写"你手上有什么、怎么用"，`AGENTS.md` 写"你做什么、怎么做"，`SOUL.md` 写"你是谁"和硬边界。
3. **改配置**——检查工具权限组、Skill 启用表（allowlist）是否到位。**即使确认"无需改动"也要主动 `config get` 确认，这一步不能省。**
4. **调用测试**——先 `skills info` 验证 Skill 已被 Agent 加载，再发真实自然任务做端到端测试，看 Skill 有没有被 Agent 自己选中、脚本有没有真跑、产出对不对。

> **脚本型 Skill 多一道纪律**：脚本写完，先不经 Agent、直接用 `python3` 跑评测场景（评测先于文档），把"脚本"这个变量锁定为"已知正确"；之后 Agent 调用再出问题，就能确定问题在 Agent 一侧。这道隔离验证省不掉。

## §2 raw/ 数据准备与裸做法基线

### 放好 7 份 360 反馈数据

每份反馈表是一个 JSON——含 `scores`（5 个维度各打 1-5 分）、`comments`（5 个维度文字评语，带具体事例）、`strengths`、`improvements`。结构统一，规范写在 `_schema.md`：

```
~/.openclaw-hr/workspace-performance/feedback-360/raw/
├── _schema.md       数据规范（评估对象、7 份来源、5 维度、JSON 结构）
├── manager.json     上级
├── peer-01.json     平级 · 同组后端
├── peer-02.json     平级 · 风控组跨组对接
├── peer-03.json     平级 · 前端组接口对接
├── report-01.json   下属
├── report-02.json   下属
└── self.json        自评
```

### 用最朴素的方式跑一遍机械聚合

Lesson 1 阶段的裸做法，是 HR 在消息里直接编排一串命令——先校验、再聚合：

```bash
cd ~/.openclaw-hr/workspace-performance/feedback-360
python3 check_feedback.py   # 数据校验：7 份 JSON 是否合法、结构是否统一
python3 aggregate.py        # 机械聚合：分组算分、标记疑似分歧
```

这条裸路能跑通，但基线的真实痛点不在"这一次能不能跑通"，在它的**不可靠**：

- **调用顺序靠人记**：必须先校验再聚合。漏了校验，脏数据直接进聚合，算出的平均分/极差不可信，而且没人会发现（聚合脚本不会因数据脏就报错）。
- **脚本和数据耦死**：两个脚本都用 `os.path.dirname(__file__)` 推 `raw/` 目录，脚本和数据耦死在 `feedback-360/` 一个目录里。换评估对象、换数据目录就得改脚本。
- **关键设计判断散落在文档之外**：`"聚合层用脚本不用 LLM"` 这条核心判断散在课程叙述里，不在任何 Agent 能读到的地方。换个人来做，很可能让大模型直接算聚合分。
- **Agent 自己不知道有这个能力**：performance 的 persona 文档里压根没有"我有 360 聚合能力、该怎么用"——只能靠人在消息里 `exec` 硬调。

这些"靠人记的顺序 + 耦死的路径 + 散落的设计判断 + 缺失的能力描述"，就是 `aggregating-360-feedback` Skill 该装进去的东西。

## §3 aggregating-360-feedback（第一层 · 脚本型 Skill）

### 目录布局

```
aggregating-360-feedback/
├── SKILL.md                       标准 frontmatter + 渐进式披露正文（约 75 行）
├── scripts/
│   ├── check_feedback.py          数据前置校验器（参数化路径）
│   └── aggregate.py               机械聚合器（参数化路径）
├── references/
│   └── aggregation-method.md      聚合细则（SKILL.md 一层引用）
└── evals/
    └── eval-cases.md              4 个评测场景
```

### 第一步 · 建 Skill

**frontmatter 三个要点**（对照 L2-1 规范）：

```yaml
---
name: aggregating-360-feedback
description: Aggregate multiple 360-degree performance feedback forms into a
  single perspective-grouped dataset. Use this skill whenever a set of 360
  feedback JSON files (from manager, peers, direct reports, and self) needs to
  be mechanically rolled up by reviewer perspective... It only aggregates; it
  never produces a performance rating.
metadata:
  openclaw:
    requires:
      bins: ["python3"]
---
```

- `name` 用**动名词**形式 `aggregating-360-feedback`，不是 `feedback-aggregator`。
- `description` 第三人称、写给 AI 看，含 what（把多份 360 反馈机械聚合成按视角分组的数据集）和 when（拿到一组 360 反馈 JSON、需按视角汇总时）。末尾那句 **`It only aggregates; it never produces a performance rating`** 把合规边界写进了 Agent 选 Skill 的依据里——让 Agent 在"要不要用这个 Skill"这一刻就知道能力的边界。
- `requires.bins: ["python3"]` 显式声明依赖，缺失时优雅降级。

**正文渐进式披露**（约 75 行）：只当"目录"——第一层定位、"为什么聚合层用脚本不用 LLM"的核心判断、两步工作流（校验 → 聚合）、几条关键规则，字段级细则引到 `references/aggregation-method.md`。正文里写死的关键规则：

1. 聚合前必须先过校验，校验不通过的数据不聚合。
2. `aggregated-data.json` 是唯一数据基准，下游一律从它取数，绝不让大模型重新算分。
3. 极差 ≥ 1.0 是机械信号、不是最终结论，只"触发关注"，最终共识/分歧由第二层语义分析定。
4. 这个 Skill 只做机械聚合，绝不输出 S/A/B/C/D 绩效评级。

**脚本参数化改造（裸脚本变 Skill 的关键动作）**：原脚本用 `os.path.dirname(__file__)` 推 `raw/` 目录，Skill 化后脚本搬进 `skills/aggregating-360-feedback/scripts/`，物理位置变了、相对路径假设不成立。所以两个脚本都改成 CLI 接受参数：

```bash
python3 check_feedback.py <raw_dir>
python3 aggregate.py <raw_dir> [out_json_path]   # out_json_path 缺省输出到 raw_dir 同级
```

退出码约定 `0 / 1 / 2`：成功 / 数据问题 / 用法错误。

**校验脚本要"解决问题"不是"甩锅"**：`check_feedback.py` 真去校验——每个 JSON 能否解析、必需字段（`reviewer_relation` / `scores` / `comments`）齐不齐、`reviewer_relation` 取值是否为 manager/peer/report/self 之一、5 维度齐不齐且评分是否 1-5 整数、是否至少有 1 份 manager + 1 份 self（360 反馈视角完整性的下限，缺上级或自评这份 360 就不成立）。

**聚合脚本的合理增强**：新 `aggregate.py` 新增 `divergence` 段——把原版只在终端打印的"疑似分歧机械标记"结构化写进 `aggregated-data.json`，下游看板可直接读、不用各自重算极差。阈值 1.0 在注释里写明依据（5 分制的 20%、保守的关注门槛），不是来历不明的魔数。

**脚本先单独验证**（隔离变量）：脚本写完先不经 Agent，用 `python3` 跑 4 个评测场景（见附录 A）。

- 场景 1 正常路径：7 份全合法，聚合产出四视角对照。维度离散度逐项核对——目标达成极差 0.00、专业能力 0.33 标**共识**；协作沟通 1.50、责任心 1.00、学习成长 2.00 标**分歧**。责任心极差正好 1.00 踩在阈值上被机械标分歧，所以标出的是**三个**疑似分歧维度（它最终算不算分歧要等第二层读评语，最终被归入共识）。
- 场景 2 脏数据：故意造评分越界（出现 7 分）+ 缺维度，校验脚本精确抓出两个问题、退出码 1、脏数据挡在聚合之前。
- 场景 3、4：缺 self 反馈抓"缺自评视角"退出码 1、空目录/目录不存在报错退出。4 个场景全过，脚本本身可用。

**建完立即验证 Skill 被识别**：

```bash
$OPENCLAW_HR_BIN skills info aggregating-360-feedback --agent performance
```

看到 `✓ Ready`、`Source: openclaw-workspace`、`Visible to model: yes`、`Binaries: ✓ python3`。`skills check --agent performance` 的 Skill 总数从 52 变 53。标准一层布局 + 合法 frontmatter 当场被识别、无需重启 gateway。

### 第二步 · 改核心 md 文档

此刻 performance 还不知道"我有 360 聚合能力"。这一步把能力写进三份文档：

- **`TOOLS.md`**——加"绩效子 Agent 的工具与 Skill 清单"。原本是默认模板（Local Notes / Cameras / SSH 占位），整体替换为按三层 Pipeline 组织的能力清单，每个能力列"做什么 / 什么时候用 / 调用要点"。`aggregating-360-feedback` 的调用要点写明：聚合前必须先跑 `check_feedback.py`、产出是后两层的唯一数据基准、跑脚本需 `group:runtime` 权限。
- **`AGENTS.md`**——加"绩效业务工作流"段。原本完全是默认模板（group chat 礼仪、heartbeat）。顶部插入"绩效业务工作流"：360 反馈聚合三层 Pipeline 链，定死四条硬规定——机械聚合是后两层前提、聚合前先过校验、"数字归脚本、语义归我"、极差 ≥ 1.0 只是机械信号不是分歧结论。**同时把第二层 LLM 综合分析的方法论写进去**：工作流段明确第二层章法"读 7 份反馈评语 + `aggregated-data.json`，逐维度对照，把疑似分歧坐实为共识/分歧，给归因 + 面谈建议，产出 `aggregated-report.md`"。
- **`SOUL.md`**——补硬边界。此前已有"只聚合不定级"红线，这一步补细成五条硬边界：绝不给最终评级（依据个保法第 24 条 + 制度第五条）、产出定位为面谈输入材料、数字不自己算（交脚本，可复现可审计）、分析用发展性描述不写评判式定级式的话、模拟数据说明。

> **Note · 改法**：先 `Read` 看清当前内容，再用精确字符串替换插入新段落，**不整文件覆盖**——`AGENTS.md` 默认模板里有大量 group chat / heartbeat 内容要原样保留；`TOOLS.md` 篇幅小、原本全是占位说明，可整体替换。

### 第三步 · 改配置

```bash
$OPENCLAW_HR_BIN config get 'agents.list[4].id'      # 确认 [4] 确实是 performance
$OPENCLAW_HR_BIN config get 'agents.list[4].tools'   # performance 的工具权限
$OPENCLAW_HR_BIN skills check --agent performance     # skill allowlist 状态
```

> `agents.list` 顺序：0=main、1=recruitment、2=onboarding、3=training、**4=performance**、5=er-admin、6=router。

两点确认，本步无需改配置：① `tools.allow` 已含 `group:runtime`（脚本型 Skill 调 `exec` 跑脚本所需，早期搭骨架时配好）；② `skills check` 显示 `Total: 53`、`Blocked by allowlist: 0`，workspace 来源的 Skill 默认被接受。**但"确认"不能省——必须主动 `config get`，不是默认它没问题。**

### 第四步 · 调用测试

- **测试 A · 验证加载**：见第一步。
- **测试 B · 发自然任务，验证 Agent 自己触发 Skill**：发一个不提 Skill 名的自然任务。发任务前先**备份并删除现有的 `aggregated-data.json`**（防 Agent 幻觉"文件已存在、不用做了"），任务里显式声明文件不存在、要求把脚本输出原样贴回：

```bash
$OPENCLAW_HR_BIN agent --local --agent performance \
  -m "feedback-360/aggregated-data.json 这个文件目前不存在，不要假设它已存在。
请你现在把 feedback-360/raw/ 下张磊的 360 反馈表聚合一下，把你跑的命令和
脚本的完整输出原样贴给我。"
```

Agent 自己选中 `aggregating-360-feedback`，按 SKILL.md 工作流先跑 `check_feedback.py`（7 份全合法）再跑 `aggregate.py`，把两条命令和完整输出原样贴回——**调用顺序不再靠人交代，是 Agent 自己读 SKILL.md 工作流照着先校验后聚合。**

- **测试 C · 核验文件真落盘、数据正确**：不信 Agent 的文字汇报，事后独立核验三件事——① `ls aggregated-data.json` 确认真落盘（6276 字节）；② `perspectives` 段所有视角平均分、`overall` 段与 Skill 化之前裸脚本基线**逐项完全一致**（证明换实现方式没改动功能）；③ 新产出多了 `divergence` 段（协作沟通 `perspective_range: 1.5 / suspected_split: true`、责任心 `1.0 / true`、学习成长 `2.0 / true`、目标达成 `0.0 / false`、专业能力 `0.33 / false`）。

> **Note · md5 不同不要慌**：新产出 `aggregated-data.json` 的 md5 与基线不同（内容多了 `divergence` 段）。"功能不变"要核对到**数据级**——逐项比对 `perspectives` / `overall` 段核心数字一致才算对齐，新增字段属合理增强、不属于功能偏差。

## §4 generating-360-dashboard（第三层 · 脚本型 Skill）

### 功能与目录

第三层从 `aggregated-data.json` 取数，渲染一张 HTML 看板——核心是四视角雷达图，加五维度对照表、共识/分歧卡片、顶部合规声明 banner。

```
generating-360-dashboard/
├── SKILL.md                     标准 frontmatter + 渐进式披露正文（约 70 行）
├── scripts/
│   └── build_dashboard.py       看板生成器（参数化路径）
├── references/
│   └── dashboard-method.md      看板生成细则
└── evals/
    └── eval-cases.md            4 个评测场景
```

### 第一步 · 建 Skill

**frontmatter**：

```yaml
---
name: generating-360-dashboard
description: Generate a single-file HTML dashboard from aggregated 360-degree
  feedback data. Use this skill whenever an aggregated-data.json produced by 360
  feedback aggregation needs to become a visual review board... The dashboard
  reads every score straight from the aggregated data and never recomputes — it
  is a presentation layer, not a rating tool, and never outputs a performance
  grade.
metadata:
  openclaw:
    requires:
      bins: ["python3"]
---
```

`name` 与 `aggregating-360-feedback` 同一套命名风格（有意的）。末尾 `it is a presentation layer, not a rating tool, and never outputs a performance grade` 把合规边界写进选 Skill 依据。

**正文**（约 70 行）：第三层定位、"为什么要做这张看板"（雷达图价值）、两步工作流、几条关键规则（数字只取不算、看板单文件自包含、共识/分歧判定以综合分析层为准、绝不输出绩效评级），渲染细节和判定口径引到 `references/dashboard-method.md`。

**脚本参数化**：

```bash
python3 build_dashboard.py <aggregated_json> [out_html] [verdict_json]
# out_html 缺省为数据文件同目录的 report.html
```

脚本还做数据完整性检查（缺 `perspectives` 段或视角不全直接报错退出，不产残缺看板），并记录数据源 md5 打进看板页脚。matplotlib 渲染中文的两个坑——三条独立字体渲染路径、极坐标图不能用 `tight_layout`——在注释里写明，用 `FontProperties` 显式传字体、`set_position` 手动留白处理掉。

**脚本先单独验证——这一步抓出了一个真实的坑**：跑场景 1 时立刻撞上——第一版图省事把"维度分类"改成直读 `aggregated-data.json` 的 `divergence` 机械标记，结果分歧维度算出 3 个（协作沟通、责任心、学习成长），而原实验应是 **2 个分歧 + 3 个共识**。

> 根因：责任心极差正好 1.00 踩阈值被机械标 `suspected_split = true`，但原 `build_dashboard.py` 有一个 `REPORT_VERDICT` 表把责任心硬定为 `consensus`（第二层综合分析读完评语判它是共识——各视角评分都 ≥ 4，上级给 4 分是"留成长空间"）。直读机械信号，等于把"机械信号触发关注、结论交给语义分析"这条核心设计丢掉了。
>
> **修正**：恢复 `REPORT_VERDICT` 语义覆盖机制——看板最终共识/分歧判定以 `REPORT_VERDICT`（综合分析层判定）为准，机械极差只在对照表"极差"列照实展示；同时支持第三个 CLI 参数 `verdict_json` 覆盖默认表，让看板跟随不同评估对象的综合分析结论。修正后分歧维度回到 2 个（协作沟通、学习成长），与原实验对齐。

**建完立即验证**：`✓ Ready`、`Binaries: ✓ python3`，`skills check` 总数从 53 变 54（两个 Skill 都已加载）。

## §5 看板解读：三段看懂交付物

`report.html` 是这条 Pipeline 真正的交付物。浏览器打开分三段读：

- **顶部 · 合规声明与四视角雷达图**：最上方橙色块是合规 banner（"供绩效面谈与校准会 review"、"AI 不进行绩效评级"、"最终评级由三级人工流程确定"）——这是 §6 合规落实二。下方四视角雷达图：五个维度五个轴，四条折线叠在一张图。目标达成、专业能力两轴上四条线几乎重合（共识）；学习成长轴上明显张口、自评线远凸出（分歧）。抽象的"极差 1.50/2.00"在这张图上变成肉眼可见的张口。

- **中段 · 五维度对照表与共识点**：**平级内部明细表**特别重要——对照表里平级协作沟通平均分 3.00，但这个数是同组 4 分、风控 2 分、前端 3 分平均出来的，掩盖了"对内 4 分、对外 2-3 分"的真实结构。明细表专门把三个分数摊开——**分析颗粒度要下沉到"单个评估人"，不能停在"视角平均分"**。下方三张绿卡是共识点（目标达成、专业能力、责任心）。
  > 责任心机械极差正好 1.00 踩阈值被标 `suspected_split`，但看板把它归进共识（绿卡）——因为第二层读完评语判定上级给的相对低分是"留成长空间"、各视角核心叙事一致。看板归类不照搬机械阈值，而对齐第二层判定——这正是 `REPORT_VERDICT` 语义覆盖机制在看板上的体现。

- **底部 · 分歧点卡片与综合结论**：两张橙卡是第二层识别的两个分歧点——协作沟通"对内暖、对外硬"、学习成长"成长定义不一致"，每张带四视角分数和分歧原因，卡片下方小字"聚合分析只负责把分歧摆出来、给出原因假设，不下结论"。底部综合结论列 3 长板、2 瓶颈和面谈聚焦建议，最后一行印章式标注"本看板为面谈输入材料 · 最终绩效定级由人工三级流程确定 · AI 不出评级"。**看板从头到尾没有任何一处给张磊一个 S/A/B/C/D 等级。**

## 附录 B：踩坑速查表

| # | 注意事项 | 为什么 |
|---|---|---|
| 1 | 裸脚本 Skill 化必须做"路径参数化" | 脚本搬进 `scripts/` 后，原来耦死的相对路径假设会崩 |
| 2 | 散落的设计判断收进 `SKILL.md` 正文 | 正文 Agent 一定读；`references/` 按需加载、可能不读 |
| 3 | 脚本写完先单独 `python3` 跑评测，再接 Agent | 隔离变量——后面出问题能锁定在 Agent 一侧 |
| 4 | Agent 测试要显式声明"文件不存在" + 要求贴回脚本输出 | Agent 会因"觉得做过了"偷懒幻觉，要堵掉前提、要可核验产物 |
| 5 | "功能不变"要核对到数据级 | md5 变不要紧，核心数字逐项一致才算对齐，新增字段属增强 |
| 6 | "换实现方式"不要想当然简化原实现 | 原实现里看着冗余的设计（如 `REPORT_VERDICT`）往往承载核心设计意图 |
| 7 | "会随评估对象变化"的东西改成 CLI 参数 | 写死就会重新耦死，参数化才能换对象不改脚本 |
| 8 | 脚本型 Skill 装进 workspace ≠ Agent 能调它 | `exec` 属 `group:runtime`，文件装好、权限没给够照样报错 |
