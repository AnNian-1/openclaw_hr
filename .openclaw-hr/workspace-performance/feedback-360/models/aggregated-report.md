**视角极差恰好 1.0，触发机械层的 `suspected_split` 信号。但读完全部评语后判定为共识。**

**归因分析**：所有评语在同一方向上，没有相互矛盾的叙事——每个人都认为员工1对自己的职责范围高度负责。评分的梯度（下属 5.0 → 自评 5.0 → 平级 4.33 → 上级 4.0）反映的是「责任制的宽度差异」而非「是否负责」的争议：

- **下属（5.0 满分）** 体验的是他带教端的极致投入：下属2提到员工1 review 代码时发现了隐藏 bug「帮我避免了一次线上事故」，下属1提到员工1「每周专门留时间和我过一遍进展」。
- **上级（4.0）** 的评语「对自己负责的模块很上心」完全正面，4 分更可能是上级在 5 分制上习惯性留成长空间，以及希望他将责任范围从「自己的模块」扩展到更宽的领域——这与成长维度的关切一脉相承。
- **平级（4.33）** 中唯一 4 分的来自跨组对接人（同事1：「对他自己模块的事很负责这一点我不否认」、同事2：「接口文档维护及时，挺负责的」），措辞均无保留。

> 判定规则：视角极差恰好 1.0 且所有评语方向一致 = 正常打分尺度差异，归为共识。

**面谈提示**：全场认可靠谱，可作为发展对话的安全基础。可顺势衔接成长维度——「大家都觉得你负责，现在的问题是：负责的范围能不能再大一圈？」

### ⚠️ 分歧点 1：协作沟通（collaboration）

| 视角 | 均分 | 评分区间 |
|------|:----:|:--------:|
| 上级 | 3.00 | [3] |
| 平级 | 3.00 | [4, 2, 3] |
| 下属 | 4.50 | [5, 4] |
| 自评 | 4.00 | [4] |

**视角极差 1.50，判定为真分歧。**

#### 分歧格局

```
组内视角（平级-同组 + 下属 + 自评）         跨组视角（平级-跨组 + 上级）
─────────────────────────────────────────────────────────────
同事3 4：乐于分享、主动整理文档        同事1 2：三次接口评审僵持，
下属全员 4-5：耐心、真心带人                               方案确认拖一两周
自评 4：组内协作做得不错                    同事2 3：偏技术导向，先质疑
                                            上级 3：收到风控组反馈，
                                                   已单独和他谈过
```

#### 分歧归因

这不是随机的评分噪声，而是一个**方向性分歧**——分歧点不在「员工1是不是一个好合作的人」，而在于 **「员工1对内部、对下属、对跨组同事，展现的是同一面吗？」**。

**内部关系端**（全部好评）：
- 同事3打 4：「组里同事很好，我有问题随时找他。主动把限流方案整理成文档分享给我们」
- 下属2打 5：「我刚来什么都不懂，问再基础的问题他都耐心解答，从不让我觉得难堪」
- 下属1打 4：「只要他有空就一定会认真帮我」

**跨组关系端**（形成一致的低分信号）：
- 同事1打 2——这是全 7 份反馈中唯一出现的 2 分。「每次评审员工1都很坚持自己的设计，对风控这边提的字段需求和改动诉求接受度比较低，几次会都开得有点僵，方案确认拖了一两周」
- 同事2打 3：「从体验角度提的接口调整，他会先质疑必要性，需要解释半天他才接受」
- 上级打分 3 并提供独立交叉验证：「跨组配合上我收到过风控组的反馈，说他在接口方案讨论时比较坚持自己的意见」

**自评的认知偏差值得关注**：员工1自评打 4，且评语中他明确意识到了这个问题：「我在风控和前端的方案讨论里确实坚持得多一些——但我是基于支付系统稳定性的硬要求，支付出问题是要赔钱的，我不能为了配合就放松底线。我认为我的坚持是对的。」——他将「坚持己见」归因为「技术正确性」，没有意识到这种坚持的方式本身（而非内容）已经是协作障碍。

#### 分歧本质

这不是「他有没有协作能力」的问题，他显然有（组内关系、带教能力充分证明）。核心问题是：

> **当协作场景需要他让渡一部分技术控制权、或在技术正确性之外考虑协作效率时，他的协作弹性不足。**

跨组协作者体验到的不是「他技术不对」，而是「他不听对方说完就给出判断」「评审会上气场压人」「非要 leader 出面才能推动」。风控的评语里说得很明白：「我理解他是从支付侧稳定性考虑，但跨组协作不能只站自己这边。」

#### 面谈建议

这是一个发展型分歧，不是评价型问题。建议面谈时注意三点：

1. **先认可，再扩展**。先确认组内协作和带教的好评是真实的、被广泛看到的——他不是不可合作的人，他有协作能力。问题出在特定场景。
2. **帮助他区分「技术方案的正确性」与「协作形式的正确性」**。跨组评审中，让对方感觉被倾听、被理解，本身就是推动方案落地的手段——这和坚持技术标准不矛盾。可以这样引入话头：「你的限流方案技术上是好的，但如果评审会上风控同事觉得你根本没听进去他们的诉求，就算方案是对的，他们也会抗拒。」
3. **给具体的改进锚点**。比如：下次跨组评审，先让对方说完再回应；遇到对方诉求在技术上不可行时，不只说「不行」，而是给替代方案再解释为什么。「不要从『你的方案有问题』走到对方的方案，要从『我理解你的诉求』走到双方都能接受的方案。」

### ⚠️ 分歧点 2：学习成长（growth）

| 视角 | 均分 | 评分区间 |
|------|:----:|:--------:|
| 上级 | 3.00 | [3] |
| 平级 | 3.33 | [4, 3, 3] |
| 下属 | 4.50 | [4, 5] |
| 自评 | 5.00 | [5] |

**视角极差 2.00，是全表最大的分歧维度。判定为真分歧。**

#### 分歧格局

```
高分组（下属 + 自评）              低分组（上级 + 跨组平级）
─────────────────────────────────────────────────────
下属：在他身上学到很多，          上级：技术在精进但偏「把
他从让我做难一点的事到            手头的事做深」，希望跳出
帮我兜底                          纯执行，多带人、多沉淀
                                  可复用成果
自评 5.0：技术深度、新中间件、    跨组平级：没看到明显变化
带教能力都有很大提升              ——或只看到技术变强但沟通
                                  方式没变
```

#### 分歧归因

这个分歧的本质不是「他有没有成长」，而是**「成长」的定义权在谁手上**。

**「自评 + 下属」定义下的成长**（5.0 / 4.5）：
- 员工1本人：「技术深度、新中间件、带教能力都有提升」——他把「成长」等同于「在已有赛道上越做越好 + 开始带人」
- 两位下属：用他从带教中获得的能力提升来衡量他的成长——这没问题，但「带教效果」和「带教者本人的成长」不完全等同

**「上级」定义下的成长**（3.0）：
- 上级期望的成长是**能力域宽度的扩张**，而非能力深度的延深：「我希望他下半年能跳出纯执行，多带一带新人、多沉淀一些组内可复用的东西。他自己觉得成长很快，我的观察是还偏被动。」——上级看的是「员工1对组织的辐射面」有没有变大，而非「员工1的手艺」有没有变精。
- 上级给出 3 分（符合预期）恰恰说明上级不否定他的技术深化，只是认为在这个岗位和资历上，技术深化属于「应该做到」而非「超出预期」。

**跨组平级**在此维度上打分低（3.0-3.0），主要因为接触面有限，看不到全貌：「接触不算多，不太好评价」（同事1）、「和他对接半年，感觉是个稳定输出的人，没看到特别明显的变化」（同事2）。这部分低分属于信息不足导致的保守打分，而非对成长的实质性否定。

#### 分歧本质

> **员工1定义成长 = 技术变强 + 带新人起步；上级定义成长 = 影响面变宽 + 从个人贡献者走向技术组织者。**

这和协作维度有深层关联——员工1的技术深度的确在增加，但他的**影响范围**（上级眼里的「成长」）被协作弹性的不足限制了。他打磨自己的技术、带眼前的两个新人足够了，但如果他想往「支付平台整体设计靠」（自评里的改进方向），就需要能驱动跨组的方案——而这恰好是他当前协作的弱项。

#### 面谈建议

1. **对齐「成长」的定义**。明确告诉员工1：你的技术深度和带教能力，上级看到了，也认可。但在这个职级上，「成长」的定义要从「个人能力精进」迁移到「对组织技术方向的影响」——不是技术更精 10%，而是让小组少依赖你个人 10%、跨组评审因为你一个人在场就快 10%。
2. **发展路径对应协作短板**。他的自评「想下半年在系统架构层面再往上走一走，从模块负责人往支付平台的整体设计靠」这个方向完全对——但这条路径需要他先打通跨组协作的弹性。一个影响支付平台整体设计的工程师，不可能每次跨组讨论都把对方推回去等 leader 出面。
3. **给出抓手**。具体建议：下半年尝试主导至少一次跨组评审（而不是被评审推着走）、沉淀至少一项不在他直接负责模块内的技术方案文档、正式或非正式带至少一个新人之外的人（比如给同组同事做 code review 分享体系化的经验）。

## 四、跨维度关联观察

协作和成长两个分歧维度存在**深层因果关联**，不应孤立看待：

> 员工1的技术深度的边际价值，被跨组协作弹性的不足上锁了。他能把支付网关做到 P99 180ms，但要让风控、前端、产品都顺畅地接住并放大这个成果，他目前的协作模式不够。这直接影响上级对他的成长判断——他的硬实力已经准备好往「支付平台整体设计」走，但软实力（跨组推动力）还没到这个水位。

面谈时如果有共识基础，可以尝试把这个因果链讲出来——不用妄下结论，而是作为思考邀请：「你觉得你的技术往整个支付平台架构走的路上，协作模式会是助力还是阻力？」

## 五、面谈建议路线图

建议按以下顺序展开绩效面谈，由共识入分歧：

1. **开场锚点**（5 分钟）：从目标达成和专业技术两个全场共识开始，给面谈一个建设性基调。可以说「上半年的网关重构，七个人全给了好评，这是我们对话的起点」。
2. **安全确认**（3 分钟）：快速走过责任心维度，确认「你的靠谱大家有目共睹」。
3. **核心对话——协作**（15 分钟）：这是本年度最大的发展杠杆点。用「同组同事和下属对跟你合作评价很高」作为桥接，再引入跨组视角。不指摘本人，而是呈现「同样一个你，不同人看到的侧面不一样」的现象，邀请本人共同解读。
4. **核心对话——成长对齐**（10 分钟）：基于协作对话的铺垫，讨论「成长」从个人维度到组织维度的迁移。与他自评中「想往整体设计靠」的发展方向对齐路径。
5. **收尾共识**（5 分钟）：确认下半年 1-2 个可观察的发展动作（如主导跨组评审、沉淀组内可复用资产），明确上级可提供的支持。

- **不包含绩效评级（S/A/B/C/D）**。绩效定级由「直接主管初评 → 隔级主管复核 → 校准会确认」三级人工流程确定，依据《个人信息保护法》第 24 条自动化决策条款、公司绩效管理制度第五条。
- 报告内所有评分数据源自 `aggregated-data.json`（由 `aggregate.py` 确定性脚本计算），所有评语引文源自 `feedback-360/source_feedback/<被评估人>/` 下反馈原文，未做复述漂移。
- 分歧分析以「摆出各方说法 + 给原因假设」为原则，用发展性描述，不写评判式、定级式结论。结论由主管在面谈中与本人对齐。
