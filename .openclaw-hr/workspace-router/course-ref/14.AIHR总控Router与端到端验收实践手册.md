## §1 写总控 Router 的 SOUL.md

Router 的路由逻辑 100% 写在 `~/.openclaw-hr/workspace-router/SOUL.md` 里。它不长，四个关键块，每块对应一个真实的工程考量。

### 第一块「我是谁」

```markdown
## 我是谁

我是 HR 数字员工"小慧"的**总控 Router**，是用户面对的**唯一统一入口**。

公司里的招聘、入职、培训、绩效、行政五摊 HR 业务，背后各有一个专门的子 Agent 在处理。
但用户不需要知道这些——用户只跟我说话，我负责听懂需求、找到对的人、把结果带回来。
对用户来说，我就是"小慧"这一个人。
```

### 第二块「我负责什么」（三项职责写死）

```markdown
## 我负责什么

我**只做三件事**：判断领域、分发请求、汇总结果。我不直接干 HR 业务。

1. **判断领域**——接收用户请求，判断它属于哪个 HR 业务领域（招聘 / 入职 / 培训 / 绩效 / 行政）。
2. **分发请求**——用 `sessions_spawn` 工具，把请求转给对应的业务子 Agent。
3. **汇总结果**——拿到子 Agent 的处理结果后，整理成对用户友好的回复。
```

> **一个沿用的旧叫法**：早期版本这里写的是"用 `agent_to_agent` 工具"。**OpenClaw 里并没有一个真叫 `agent_to_agent` 的工具**——Router 转发请求实际用的是 `sessions_spawn`。`agentToAgent` 是**配置项**的名字，管的是另一个工具（§2 步骤 2 讲清）。本仓 `workspace-router/SOUL.md` 第 14 行目前仍是旧叫法，**改造时建议同步订正为 `sessions_spawn`**（第 36 节"怎么分发"一段已是正确写法）。

### 第三块「五子 Agent 路由表」

```markdown
| 子 Agent ID | 业务领域 | 负责什么（典型请求） |
|---|---|---|
| `recruitment` | 招聘 | 简历批量解析/评分排序、人才库检索（"再找几个像张三的"）、面试录音转纪要、JD 文案生成 |
| `onboarding` | 入职 | 新员工入职流程编排、Lobster 入职审批工作流、30/60/90 天入职 review 跟进 |
| `training` | 培训 | 一键生成全套培训物料（PPT 大纲 / 讲师手册 / 学员手册 / 课后测试题）、培训配图 |
| `performance` | 绩效 | 360 度反馈多源聚合、季度绩效评估调度、绩效数据可视化 |
| `er-admin` | 行政 / 员工关系 | HR 政策问答（年假/病假/报销/社保公积金）、会议纪要、HR 月报 |
```

大模型判断领域，就是拿用户请求和这张表做**语义匹配**。**表写得越具体，匹配越准**——所以"再找几个像张三的"这种真实话术直接写进了表里。

> **Caution**：表里的子 Agent ID 必须和 OpenClaw 里实际注册的 Agent ID **逐字一致**。写 `SOUL.md` 前先核对一遍：
>
> ```bash
> $OC agents list
> ```

### 第四块「路由判断规则」+「边界红线」

```markdown
## 路由判断规则

1. **抓业务动作 + 业务对象**——"筛简历""出 JD" → 招聘；"启动入职流程" → 入职；
   "做培训""出 PPT" → 培训；"汇总 360 反馈" → 绩效；"年假怎么休""报销规定" → 行政。
2. **一个请求只路由到一个子 Agent**——判断出来立即分发，不要拆给多个子 Agent。
3. **跨领域请求**——先路由到主领域子 Agent，在汇总回复里说明还涉及哪个领域。
4. **领域不明确就问，不要猜**——直接问用户澄清，不随意分发。

## 怎么分发（sessions_spawn 工具）

- **分发新请求一律用 `sessions_spawn`**——不要先试 `sessions_send`（那是往已在跑的 session
  里追发消息的，新请求场景用它会报 "No session found"）。
- `agentId` 参数填路由表里的子 Agent ID，`task` 参数填用户的完整需求。
- `sessions_spawn` 是异步的——spawn 之后**不要**再调 `sessions_list` / `sessions_history` 轮询。

## 我的边界（红线）

- **我只做调度与分发，绝不直接回答 HR 业务问题**——这是我最重要的红线。
  - 哪怕用户问的是"年假有几天"这种我"好像知道答案"的简单问题，也**必须** `sessions_spawn`
    转给对应子 Agent，**不许自己用通用知识作答**。
  - 判断标准：**只要请求落在五个业务领域里，就必须路由出去，没有例外。**
```

> 第四块的红线是 §3 越界自答修复后的版本。**新写 `SOUL.md` 时直接照这个强度写**，不要写成"原则上不直接执行业务"——模糊措辞会被大模型解读出例外。

**`SOUL.md` 是工作区文件，改完下一次对话即时生效，不需要重启。**

## §2 配通跨 Agent 路由白名单（5 步）

`SOUL.md` 写好只是"逻辑就位"，路由还跑不通——Router 判断出"该转给 `recruitment`"之后，还得真的有权限把请求转过去。

> **本仓已配好**：`agents.list[6].subagents.allowAgents` 已经是五个业务子 Agent。你照着跑步骤 1 会直接成功、看不到 `forbidden`，这是正常的。**这一节的价值在于讲清"当初为什么会卡、怎么排查"**——换环境重建时你会原样撞上。

### 步骤 1：探测——Router 用什么工具转发请求

直接问 Router 自己：

```bash
$OPENCLAW_HR_BIN agent --agent router -m "你能调用哪些工具来把请求转给其他 agent？"
```

> 第一次运行 `openclaw agent`，终端会先刷一行黄色警告 `[plugins] plugins.allow is empty; ...`——它提示插件白名单没显式配置，本课环境下**可以忽略**。后面每条 `openclaw agent` 命令都会带这行，下文不再重复。

Router 会报出 `sessions_*` 这一组：`sessions_spawn` / `sessions_send` / `sessions_yield`。**真正用来分发请求的是 `sessions_spawn`**（"spawn" = 新起一个子 Agent 运行，相当于业界多 Agent 框架里的 handoff / 任务委派）。

> Router 具体一次报几个工具、措辞如何，每次回答会略有不同——它是 LLM Agent，输出本就不完全稳定。**关键不在数量，而在 `sessions_spawn` 在不在。**

让 Router 真的用它调一次 `recruitment`：

```bash
$OPENCLAW_HR_BIN agent --agent router -m "用 sessions_spawn 把请求转给 recruitment 子 Agent，让它做个自我介绍"
```

**白名单没配时会报**：

```
status: forbidden
error: agentId is not allowed for sessions_spawn (allowed: router)
```

### 步骤 2：排查——路由白名单是 subagents.allowAgents

报错里的 `allowed: router` 是关键：`sessions_spawn` 现在**只允许 spawn 给 `router` 自己**。

顺着线索查配置（`openclaw config schema` 能打印每个配置项的官方说明），会发现一组名字相近、却管着不同事情的配置：

| 配置项 | 管哪个工具 |
|---|---|
| `tools.agentToAgent`（`enabled` + `allow`） | `sessions_send`（跨 Agent 直接消息）——**不是路由关卡** |
| `agents.list[<n>].subagents.allowAgents` | `sessions_spawn`——**Router 路由用的就是它** |

**`subagents.allowAgents` 不配时，默认只允许 spawn 自己**，这就是 `allowed: router` 的来源。

### 步骤 3：给 Router 配 subagents.allowAgents

```bash
# 改配置是敏感操作，先备份一份（config set 也会自动备份，多留一份更稳妥）
cp ~/.openclaw-hr/config/openclaw.yaml /tmp/openclaw-hr-g1-backup.yaml

# 给 router（agents.list[6]）配 subagents.allowAgents，列入 5 个业务子 Agent
$OPENCLAW_HR_BIN config set 'agents.list[6].subagents.allowAgents' \
  '["recruitment","onboarding","training","performance","er-admin"]' --strict-json
```

**三个细节**：

1. **为什么用 `agents.list[6]` 这个带下标的路径**——要改的是数组里 Router 这一个元素。用下标精确定位，只动这一个。**用整体替换数组的写法（如 `config patch` 覆盖整个 `agents.list`）会把其他六个 Agent 的配置一起冲掉。**
2. **为什么列表里只有 5 个 ID、不含 `router`**——`allowAgents` 是"Router 能 spawn 到的目标"，它不需要 spawn 自己。
3. **`--strict-json` 是什么**——要求 `config set` 把后面那段值按严格 JSON 解析。给数组这种结构化的值赋值时，严格解析能第一时间暴露括号、引号写错的问题。

> **Caution · macOS / zsh 必看**：配置路径 `agents.list[6].subagents.allowAgents` **必须用单引号包起来**。zsh 会把 `[6]` 当成文件名通配符去匹配当前目录，匹配不到就整条命令报 `(eval):1: no matches found: agents.list[6]...`，命令根本到不了 openclaw。加单引号后 zsh 就不解释方括号。bash 环境不报这个错，但**统一加引号最省心**——`config set`、`config get` 都一样。

> **关于 `Restart the gateway to apply` 提示**：本课的 Gateway 不是常驻服务——每次执行 `openclaw agent` 时会临时拉起一个内嵌 Gateway，读的就是最新的配置文件。**配完直接用 `openclaw agent` 验证即可生效。**

### 步骤 4：验证白名单就位

```bash
# 路由的关卡：Router 的 sessions_spawn 目标白名单（带 [6]，加单引号）
$OPENCLAW_HR_BIN config get 'agents.list[6].subagents.allowAgents'

# 一并看一眼 tools.agentToAgent——它管的是 sessions_send、不是路由，这里只是确认它的状态
$OPENCLAW_HR_BIN config get tools.agentToAgent
```

`tools.agentToAgent` 这个路径里没有方括号，不用加引号；带 `[6]` 的那条要加。

再跑一遍步骤 1 的那条 `sessions_spawn` 命令，原来 `forbidden` 的那条路应当通了——`recruitment` 会真实产出一段自我介绍。

### 步骤 5：实测五个领域的路由分发

通路打通只证明了"能 spawn 出去"，还没证明**判断领域准不准**。发五条覆盖五个领域的**真实业务话术**请求，每条用独立 `--session-id` 方便事后核对：

```bash
$OPENCLAW_HR_BIN agent --agent router --session-id g1-route-1 -m "帮我筛一下这周收到的简历"
$OPENCLAW_HR_BIN agent --agent router --session-id g1-route-2 -m "新员工张三下周一入职，帮忙启动入职流程"
$OPENCLAW_HR_BIN agent --agent router --session-id g1-route-3 -m "下午要给业务部门做一场 AI 应用培训，帮我准备培训物料"
$OPENCLAW_HR_BIN agent --agent router --session-id g1-route-4 -m "帮我汇总一下李娜的 360 度反馈"
$OPENCLAW_HR_BIN agent --agent router --session-id g1-route-5 -m "员工想问一下年假到底怎么休"
```

> **每条耗时约 20–45 秒**——Router 要走完一个完整回合：加载工作区、组装系统提示词、调大模型判断领域、调 `sessions_spawn`、再让出回合等子 Agent 回流。**终端"卡住"几十秒是正常的。** 另外：Router 这一轮的可见回复通常是"已把请求转给××处理"这类确认语，有时甚至没有可见文字——这都正常。

**怎么核对路由对不对**：不能只看 Router 嘴上说"已交给招聘专员处理"，那只是它自称。硬证据在 `sessions_spawn` 返回的 `childSessionKey`（形如 `agent:<目标agent>:...`）里：

```bash
# 只挑出关键信息（-o 让 grep 只打印匹配到的那一小段）
grep -o '"childSessionKey":"[^"]*"' ~/.openclaw-hr/agents/router/sessions/g1-route-*.jsonl | sort -u
```

> 不加 `-o` 直接 `grep '"childSessionKey"'` 会刷出一大屏 JSON——每条匹配是一整行完整会话记录。这正常，不是你敲错了。

**预期结果**："筛简历"→ `recruitment`、"启动入职流程"→ `onboarding`、"准备培训物料"→ `training`、"汇总 360 反馈"→ `performance`、"年假怎么休"→ `er-admin`。**5 条请求，5/5 路由判断正确。**

> **为什么用真实话术**：五个领域各一条、用"帮我筛一下这周收到的简历"这种真实说法，而不是"测试 recruitment"这种作弊式提示——**才能验证 Router 是真的有领域分辨能力，不是碰巧。**

### 这个坑，记住三件事

1. 跨 Agent 路由（`sessions_spawn`）的白名单是**调度方 Agent 的 `subagents.allowAgents`**——不配就 `forbidden`，报错里的 `allowed: <自己的 ID>` 就是默认值在说话。
2. **别被 `tools.agentToAgent` 的名字骗了**——它管的是 `sessions_send`。只配它、不配 `subagents.allowAgents`，路由照样 `forbidden`；反过来把它关掉、只留 `subagents.allowAgents`，路由照样能通（已实测对照验证）。
3. **建议只给调度中心（Router）配 `subagents.allowAgents`**，业务子 Agent 都不配——天然形成星型路由拓扑。生产上更稳的写法见 §2.5（`defaults` 全禁 + 叶子显式 `[]`）。

## §2.5 星型拓扑硬化 + delegationMode prefer（本仓已落地）

§2 把「Router 能 spawn 五个业务子 Agent」配通了。本节补上生产级拓扑与委派加固——对齐 `openclaw_part_7` 的多 Agent 安全默认，并给 Router 叠一层 `delegationMode: prefer`。**本仓 `openclaw-hr/config/openclaw.yaml` 已写入；换环境重建时按下面命令重做。**

### 2.5.1 星型拓扑硬化：defaults 全禁 + 叶子显式 `[]` + requireAgentId

目标形态：

```yaml
agents:
  defaults:
    subagents:
      allowAgents: []          # 默认全禁——谁要 spawn 必须 per-agent 显式开
      requireAgentId: true     # spawn 必须显式带目标 agentId
  list:
    - id: main
      subagents: { allowAgents: [] }
    - id: recruitment
      subagents: { allowAgents: [] }
    - id: onboarding
      subagents: { allowAgents: [] }
    - id: training
      subagents: { allowAgents: [] }
    - id: performance
      subagents: { allowAgents: [] }
    - id: er-admin
      subagents: { allowAgents: [] }
    - id: router                 # 唯一调度中心
      subagents:
        delegationMode: prefer   # 见 2.5.2
        allowAgents: [recruitment, onboarding, training, performance, er-admin]
```

写入命令（改前先备份）：

```bash

$OC config set 'agents.defaults.subagents.requireAgentId' 'true' --strict-json

# ② 叶子显式禁 spawn（索引 0=main … 5=er-admin；router 是 6，不要动错）
for i in 0 1 2 3 4 5; do
  $OC config set "agents.list[$i].subagents.allowAgents" '[]' --strict-json
done

$OC config validate
$OC config get 'agents.defaults.subagents'
# 抽查一个叶子 + router
$OC config get 'agents.list[5].subagents'
$OC config get 'agents.list[6].subagents'
```

**核对预期**：

| 路径 | 期望 |
|---|---|
| `agents.defaults.subagents` | `{"allowAgents":[],"requireAgentId":true}` |
| `agents.list[0..5].subagents.allowAgents` | 各为 `[]` |
| `agents.list[6].subagents.allowAgents` | 仍为五个业务 ID（**不要被冲掉**） |

> **为什么叶子要显式写 `[]`？** 不配时默认「只能 spawn 自己」，和显式 `[]`（谁都不能 spawn）多数场景接近；但显式空数组是**可审计的安全声明**，也不会被误读成「忘了配」。`defaults.allowAgents: []` 则堵住「新加 Agent 却忘了收权」——新 Agent 默认不能 spawn 任何人。

> **仓库副本也要同步**：`config set` 写的是运行时 `~/.openclaw-hr/config/openclaw.yaml`；本仓 git 跟踪的是 `hr_claw_hub/openclaw-hr/config/openclaw.yaml`，两份文件不是 symlink，**改完运行时后记得把同样字段写回仓库副本**。

| 值 | 含义 |
|---|---|

### 3.4 附带修一个工具选择的试错

回看 §2 步骤 5 第 5 条请求（`g1-route-5`），路由判断是对的，但工具调用统计里有 `failures: 1`：Router 先调了 `sessions_send`（往一个已在跑的 `er-admin` 会话发消息），此刻没有活跃会话，返回 `No session found: er-admin`；再调 `sessions_list` 确认，然后才改用 `sessions_spawn`。

**这不是路由错**，是分发工具选错走了弯路。修复同样是改 `SOUL.md` 的「怎么分发」段，写明：

```markdown
- **分发新请求一律用 `sessions_spawn`**——不要先试 `sessions_send`。

```

**优化后**：同一条请求，工具调用降到 `sessions_spawn` → `sessions_yield` 两个，`failures: 0`，一步到位。

### 3.5 SOUL 调优的工作节奏与纪律

> **与 §2.5 的关系**：`delegationMode: prefer` 已在配置层加压，但**挡不住** `TOOLS: None` 直答。本节 SOUL「没有例外」硬红线仍是防越界的主防线；两者叠加见理论篇 §3.8。

> **纪律**：**persona 调优要针对实测发现的具体问题，不要顺手大改已经正确的部分。** 领域判断已经 5/5 全对，这两次调优都没动「路由判断规则」那一段，只动了「边界红线」和「怎么分发」。**哪里出问题改哪里**——不要因为"正好在改 `SOUL.md`"就把对的地方也重写一遍。

## §4 Per-Sender 三档权限：配置与 16/7/3/0 实测

### 4.0 本仓当前落地 vs 完整三档模板

| 范围 | `tools.toolsBySender` |
|---|---|
| **本仓当前**（演示向） | 仅 `id:ou_REPLACE_EMPLOYEE` + `*`（`allow:["*"]`）。Web / TUI / 未登记发送者走 `*`，可直接演示 IMA 答疑 |
| **完整三档模板**（生产建议） | 下表三档 `id:ou_*` + `*` 改为 `deny:["*"]` |

> **不要用 `name:<角色>`。** WebChat / Control UI / TUI **不注入 `SenderName`**，`name:HR主管` 永远命不中；正式分档只认飞书 `open_id`（`id:ou_xxx`）。消息正文里写「我是 HR 主管」也改不了 sender key。

> **普通员工查的是 IMA 知识库，不是 Builtin Memory。** 链路是 `router` → `sessions_spawn(er-admin)` → `exec search_ima_policies.cjs`。因此低权限档必须放行 `sessions_spawn` / `sessions_yield` / `exec` / `read`，且**不能** `deny group:runtime`（否则 `exec` 被挡死）。旧版「只给 `group:memory`」已废弃。

### 4.1 三档 + 兜底的配置内容（完整模板）

| sender key | allow | deny |
|---|---|---|
| `id:ou_REPLACE_HR_LEAD` | `["*"]` | —（全放行） |
| `id:ou_REPLACE_BIZ_LEAD` | `["group:web","read","sessions_list","sessions_history","sessions_spawn","sessions_yield","exec"]` | `["write","edit","apply_patch","browser","cron"]` |
| `id:ou_REPLACE_EMPLOYEE` | `["sessions_spawn","sessions_yield","exec","read"]` | `["write","edit","apply_patch","browser","cron","group:fs"]` |
| `*`（生产） | — | `["*"]` |
| `*`（比赛演示，本仓当前） | `["*"]` | — |

> **窄白名单里的 `deny` 是纵深防御，不是主拦截。** `deny` 列的危险工具本来就不在 `allow` 内——删掉 `deny` 实测结果往往一样。留着是防止日后有人放宽 `allow`、或 profile 基线叠回危险工具时还有第二道闸。**`deny` 优先于 `allow`。**

拿到真实 `ou_xxx`：用该飞书账号给小慧发一条消息 → `openclaw pairing list feishu` 或 Gateway 日志里的 `open_id` → 把 `REPLACE_*` 换成真实值（保留 `id:` 前缀）。

```javascript
#!/usr/bin/env node
// g2-verify-persender.mjs —— Per-Sender 三档 + 兜底：16 / 7 / 3 / 0
import { existsSync, readdirSync } from 'node:fs';
import { execSync } from 'node:child_process';
import { join, resolve } from 'node:path';
import { pathToFileURL } from 'node:url';

const HR_HOME = process.env.HOME + '/.openclaw-hr';
const CONFIG_PATH = process.env.OPENCLAW_CONFIG_PATH || `${HR_HOME}/config/openclaw.yaml`;

async function findPolicyFn() {
  const dist = join(HR_HOME, 'install/node_modules/openclaw/dist');
  const candidates = [join(dist, 'agents/pi-embedded-runner/effective-tool-policy.js')];
  for (const f of readdirSync(dist)) {
    if (f.startsWith('effective-tool-policy-') && f.endsWith('.js')) candidates.push(join(dist, f));
  }
  for (const p of candidates) {
    if (!existsSync(p)) continue;
    try {
      const mod = await import(pathToFileURL(resolve(p)).href);
      if (mod.applyFinalEffectiveToolPolicy) return mod.applyFinalEffectiveToolPolicy;
    } catch { /* next */ }
  }
  throw new Error('找不到 applyFinalEffectiveToolPolicy');
}

const PROBES = [
  'read', 'write', 'edit', 'apply_patch', 'browser',
  'exec', 'process', 'code_execution',
  'memory_search', 'memory_get',
  'web_search', 'web_fetch',
  'sessions_spawn', 'sessions_list', 'sessions_history',
  'image_generate',
].map((name) => ({ name }));

// 完整三档写入后：用 senderId（对应 id:ou_xxx），不要用 senderName / name:
const SENDERS = [
  { label: 'HR 主管',         senderId: 'ou_REPLACE_HR_LEAD',  expect: 16 },

  { label: '未知身份（兜底）', senderId: undefined,             expect: 0  }, // 生产 * = deny
];

const config = JSON.parse(execSync(
  `python3 -c 'import json; print(json.dumps(json.load(open(${JSON.stringify(CONFIG_PATH)}))))'`,
  { encoding: 'utf8' },
));

const applyPolicy = await findPolicyFn();
for (const s of SENDERS) {
  const eff = applyPolicy({
    bundledTools: PROBES,
    config,
    agentId: 'router',
    senderId: s.senderId,
    warn: () => {},
  });
  const got = Array.isArray(eff) ? eff.length : 0;
  const mark = got === s.expect ? '✅' : '❌';
  console.log(`${mark} ${s.label.padEnd(12)} -> ${got} 个有效工具（期望 ${s.expect}）`);
}
```

| HR 主管 | `id:ou_REPLACE_HR_LEAD` | **16** | 可用 | 可用 | 可用 |
| 业务部门负责人 | `id:ou_REPLACE_BIZ_LEAD` | **7** | 可用 | 拦截 | 可用（可 spawn） |
| 普通员工 | `id:ou_REPLACE_EMPLOYEE` | **3** | 可用 | 拦截 | 可用（spawn + exec + read） |
| 未知身份（兜底） | （无身份） | **0** | 拦截 | 拦截 | 拦截 |

- **普通员工 = 3**：探针集命中 `read` / `exec` / `sessions_spawn`（`sessions_yield` 若不在探针里则不计数）。这是 IMA 答疑最小工具面，**不是**旧的 `memory_search`×2。
- **未知身份 = 0**：仅当 `*` 为 `deny:["*"]`。本仓演示期 `*` 为 `allow:["*"]` 时，未知身份也会拿到全套工具——赛后务必改回 deny。

> **这四个数在 `router` 入口上算**——router 的 Per-Agent 是 `allow:["*"]`，故 16/7/3/0 隔离的是 Per-Sender 单层效果。

> **⚠️ PITFALL 1：探针集别放 profile 门控工具**（如 `cron` / `gateway`），否则会把「没注册」误判成「被分权拦了」。

### 4.4 运行时对照：生产兜底 vs 演示兜底 / 飞书真身份

**生产模型**（`* = deny`）：`openclaw agent --local` / TUI **不带飞书 `senderId`，必然命中 `*`**，预期 `No callable tools remain after resolving explicit tool allowlist`。

**本仓演示模型**（`* = allow`）：同一命令可直接跑通 IMA / `exec`，便于比赛演示；**赛后改回 deny**。

验普通员工档的可靠做法：飞书真实账号私聊小慧（sender key = `id:ou_xxx`），或临时把 `*` 设成与 `id:ou_REPLACE_EMPLOYEE` 相同的 allow/deny，验完恢复：

```bash
# 临时：* = 普通员工档（模拟飞书员工身份）
$OC config set 'tools.toolsBySender.*' \
  '{"allow":["sessions_spawn","sessions_yield","exec","read"],"deny":["write","edit","apply_patch","browser","cron","group:fs"]}' \
  --strict-json
# 重启 Gateway 后跑政策问答，确认走 er-admin + search_ima_policies.cjs
# 演示结束：
#   比赛继续演示 → $OC config set 'tools.toolsBySender.*' '{"allow":["*"]}' --strict-json
#   生产收紧     → $OC config set 'tools.toolsBySender.*' '{"deny":["*"]}' --strict-json
```

> **⚠️ PITFALL 2：演示期 `allow:["*"]` 等于未登记身份全放行。** 赛后 / 上线前必须改回 `deny:["*"]`，否则权限分级漏底。

### 4.5 toolsBySender 语法速查

| 字段 | 形态 | 含义 |
|---|---|---|
| `allow` | `["*"]` / `["sessions_spawn","exec","read"]` | 独立白名单（替换 profile 基线） |
| `alsoAllow` | `["group:web"]` | 在基线 / allow 上叠加（本课三档不用） |
| `deny` | `["write","group:fs"]` | 禁止的工具 |

**sender key 六类**（从精确到宽松，先命中先用）：

| sender key | 形态 | 匹配精度 |
|---|---|---|
| `channel:<channelId>:<senderId>` | 某渠道里的某个具体人 | 1 · 最精确 |
| `id:<id>` | **本课三档采用**：飞书 `id:ou_xxx` | 2 |
| `e164:<手机号>` | 国际格式手机号 | 3 |
| `username:<用户名>` | 平台用户名 | 4 |
| `name:<显示名>` | 显示名 · **可伪造；本仓已弃用** | 5 |
| `*` | 兜底 | 6 · 最宽松 |

**三条规则**：① `deny` 优先于 `allow`；② key 从精确到宽松先命中先用；③ 未匹配登记 key 的发送者走 `*`。

## §5 Cron 总调度：7 任务全景与超时故障修复

### 5.1 第一步：cron list 看原始输出

```bash
$OC cron list
```

7 行任务，每行有 ID、Name、Schedule、Next、Last、Status 等列。**终端宽度不够时整行会被折成两行，长任务名还会被截断**——原始表格适合快速扫一眼"有哪些任务"。

> 看到的 `Status` 不一定全是 `idle`。`weekly-recruitment-summary` 是每周一 09:00——如果你跑的当天正好是周一且已过 09:00，它可能已被自动触发过一次，`Last` 有值、`Status` 是 `ok`。**这是正常的，不是故障。**

### 5.2 第二步：cron list --json 出结构化全景

要按"周期 / 一次性"分类、按子 Agent 归类，得走 `--json` 拿完整字段再用脚本编排：

```bash
$OC cron list --json | python3 g2-cron-landscape.py
```

`g2-cron-landscape.py`（吃 stdin 的 JSON，按 `schedule.kind` 分两类、按子 Agent 归类）：

```python
#!/usr/bin/env python3
"""g2-cron-landscape.py —— 吃 `openclaw cron list --json`，输出 Cron 总调度全景。

用法：openclaw cron list --json | python3 g2-cron-landscape.py

局限：只识别 cron（周期）/ at（一次性）两类。用 --every 注册的任务
schedule.kind 是 every，会被漏掉——需要自行扩展。
"""
import json
import sys
from collections import defaultdict

data = json.load(sys.stdin)
jobs = data if isinstance(data, list) else data.get("jobs", data.get("entries", []))

buckets = {"cron": [], "at": [], "other": []}
for job in jobs:
    kind = (job.get("schedule") or {}).get("kind", "other")
    buckets.get(kind, buckets["other"]).append(job)


def describe(job):
    sched = job.get("schedule") or {}
    if sched.get("kind") == "cron":
        expr = f"{sched.get('expr')}  @{sched.get('tz', '宿主机时区')}"
    else:
        expr = sched.get("at", "-")
    payload = job.get("payload") or {}
    agent = payload.get("agentId") or job.get("agentId") or "-"
    state = job.get("state") or {}
    return job.get("name", "-"), expr, agent, state.get("lastStatus", "idle")


for title, kind in (("周期任务（cron）", "cron"), ("一次性任务（at）", "at"), ("其他", "other")):
    group = buckets[kind]
    if not group:
        continue
    print(f"\n== {title} · {len(group)} 个 ==")
    for job in group:
        name, expr, agent, status = describe(job)
        print(f"  {name:<32} {expr:<34} {agent:<12} {status}")

by_agent = defaultdict(int)
for job in jobs:
    payload = job.get("payload") or {}
    by_agent[payload.get("agentId") or job.get("agentId") or "-"] += 1
print(f"\n== 覆盖 {len(by_agent)} 个子 Agent，共 {len(jobs)} 个任务 ==")
for agent, count in sorted(by_agent.items()):
    print(f"  {agent:<14} {count} 个")
```

**预期全景**：3 个周期任务（周招聘汇总 / 月薪资提醒 / 月末报表）+ 4 个一次性入职 review 节点，覆盖 `onboarding`、`er-admin`、`recruitment`、`performance` 四个子 Agent。

> **关键不是那个排版脚本，是 `cron list --json`。** 原始 `cron list` 给的是人看的表格，`--json` 给的是带完整字段的结构化数据。**任何想对 Cron 任务做分组、统计、二次加工的需求，入口都是 `--json`。**

### 5.3 7 任务总调度一览

| 任务名 | schedule | 子 Agent | 类型 |
|---|---|---|---|
| `weekly-recruitment-summary` | `cron 0 9 * * 1` @Asia/Shanghai | recruitment | 周期 |
| `monthly-payroll-reminder` | `cron 0 10 25 * *` @Asia/Shanghai | performance | 周期 |
| `hr-monthly-report` | `cron 59 23 28-31 * *` @Asia/Shanghai | er-admin | 周期 |
| `onboard-review-zhanglei-day7` | `at 2026-05-23 02:00Z` | onboarding | 一次性 |
| `onboard-review-zhanglei-day30` | `at 2026-06-15 02:00Z` | onboarding | 一次性 |
| `onboard-review-zhanglei-day60` | `at 2026-07-15 02:00Z` | onboarding | 一次性 |
| `onboard-review-zhanglei-day90` | `at 2026-08-14 02:00Z` | onboarding | 一次性 |

> `at` 那一列的 `2026-05-23 02:00Z`（日期与时间之间是空格）是 `cron list` 的**显示格式**，不是注册时的输入格式。注册 `--at` 要用合法 ISO 8601（`2026-05-23T02:00:00Z`）。

### 5.4 第三到五步：cron error 排查与修复（回放）

> **回放说明**：这个 cron 超时故障在实验当时就已修好。你现在环境里 `weekly-recruitment-summary` 的 `timeoutSeconds` 已经是 600、最近几次运行是 `ok`——**你不会"自己跑出"一个新的 error**。但 Cron 执行历史是持久化的，当时那条失败记录（`run :2`，`status=error`）一直留在历史里，**排查对象是它**。

**第三步 · 从执行历史里发现并定位**

```bash
# 手动触发一次（ID 是位置参数，从 cron list 的 ID 列查）
$OC cron run 48e76591-5346-4deb-a042-b069afa0fcf5
```

输出是一小段 JSON：`{"ok": true, "enqueued": true, "runId": "manual:48e76591-...:N"}`。**`"enqueued": true` 是关键——`cron run` 是异步入队，命令立刻返回，任务在后台真正跑完要约 2–3 分钟。敲完别马上去看结果。**

```bash
$OC cron runs --id 48e76591-5346-4deb-a042-b069afa0fcf5 2>&1 | head -20
```

`cron runs` 输出一个 `entries` 数组，每个元素是一次运行。关键字段两个：

```
"status": "error"
"error":  "cron: job execution timed out (last phase: model-call-started)"
```

**这个错误信号很明确**：不是工具权限被拦（那会报 `No callable tools remain`），也不是配置语法错——**是任务跑得太慢、撞到了超时上限。**

**接着用 `cron get` 定位为什么超时**

```bash
$OC cron get 48e76591-5346-4deb-a042-b069afa0fcf5
```

修复前的两个关键字段：

```json
{
  "payload": { "timeoutSeconds": 180 },
  "state":   { "lastDurationMs": 180250, "lastStatus": "error" }
}
```

**两个数字几乎相等**——任务跑到 180 秒整、撞上上限被强制中断。再看任务在做什么：让招聘子 Agent 盘点收件箱、评分、人才库三个目录，生成本周招聘进度简报——这是一个"多次读目录 + 让大模型综合成报告"的**复合任务**，本身就偏重。**180 秒对它定得太紧了。**

**第四步 · cron edit 把超时从 180 调到 600**

```bash
# 改任务前先备份它的当前定义——cron 任务存在调度器的任务库里、不在 openclaw.yaml，
# 所以备份对象是任务定义本身，用 cron get 导出
$OC cron get 48e76591-5346-4deb-a042-b069afa0fcf5 > /tmp/job-pre-edit.json

# 把执行超时调到 600 秒（10 分钟），给复合任务足够余量
$OC cron edit 48e76591-5346-4deb-a042-b069afa0fcf5 --timeout-seconds 600
```

> **两个点要交代**：
> ① **备份对象**——Cron 任务不存在于 `openclaw.yaml` 里（任务是 `cron add` 注册进调度器任务库的），**备份 `openclaw.yaml` 是没用的**，要用 `cron get <id> > 文件` 导出任务定义本身。
> ② **两个 timeout 别改错**——`--timeout <ms>` 是 **CLI 等 Gateway 响应**的超时（默认 30000ms），跟任务跑多久无关；`--timeout-seconds <n>` 才是 **agent job 自己的执行超时**，对应 `payload.timeoutSeconds`。
> 调到 600 而不是刚够用的 200，是**留余量**——简历目录会继续增长、大模型响应时间也有波动。

**第五步 · 重新触发验证**

```bash
# 手动重新触发（--expect-final 等任务跑到终态，--timeout 给足 CLI 等待时间，单位毫秒）
$OC cron run 48e76591-5346-4deb-a042-b069afa0fcf5 --expect-final --timeout 620000

# 跑完后查执行历史
$OC cron runs --id 48e76591-5346-4deb-a042-b069afa0fcf5
```

修复前后对比（`runId` 结尾的 `:N` 是同一任务历次运行的序号）：

| run | status | durationMs | 说明 |
|---|---|---|---|
| `:2` | `error` | 180250 | 修复前：撞 180 秒上限超时 |
| `:3` | `ok` | 122897 | 修复后：122.9 秒跑完 |

**`run :3` 的 122897ms 是这次诊断的硬证据**——任务真实需要约 123 秒。它落在原来的 180 秒上限和新设的 600 秒之间，说明 180 秒离真实耗时太近（再算上加载工作区、组装 prompt 的开销，撞 180 秒完全合理），**调到 600 秒后留出了三倍以上余量**。

这一次任务真跑通了——招聘子 Agent 读完三个目录，生成出一份完整的本周招聘进度简报（`cron runs` 的 `summary` 字段里能看到全文）。

> **另一类真实故障（L2-3 月报）**：Cron 把行政子 Agent 唤醒了，但它的 `deny` 列表拦掉了 `group:runtime`——月报脚本要用的 `exec` 正属于这一组。子 Agent"手被绑住"，在工具权限解析这一步**秒退（997 毫秒）**，报 `No callable tools remain`。**这就是为什么本仓 `er-admin` 的 deny 里没有 `group:runtime`。**

### 5.5 cron add 参数速查

| 参数 | 取值示例 | 作用 |
|---|---|---|
| `--name` | `weekly-recruitment-summary` | 任务名，后续在 `cron list` 里靠它认领 |
| `--cron` | `"0 9 * * 1"` | 周期触发，crontab 表达式（5 或 6 字段） |
| `--at` | `"2026-05-23T02:00:00Z"` | 一次性触发，ISO 8601 时刻（`T` 分隔日期与时间） |
| `--every` | `"6h"` | 周期触发，每隔固定时长跑一次 |
| `--tz` | `"Asia/Shanghai"` | 时区。**周期任务务必显式带** |
| `--agent` | `recruitment` | 到点唤醒哪个子 Agent |
| `--message` | 一句指令 | 唤醒子 Agent 后交给它的任务指令 |
| `--session` | `isolated` | 任务在独立会话里跑，不污染主对话 |
| `--tools` | `exec` | 按最小权限限定这个任务能用的工具 |
| `--timeout-seconds` | `600` | agent job 的执行超时上限 |
| `--keep-after-run` | （无值） | 一次性任务跑完不自动删除，保留可审计 |

> **重试不是 `cron add` 的参数。** OpenClaw Cron 的重试是全局配置（`retryOn`，默认对 `rate_limit` / `overloaded` / `network` / `server_error` 这几类瞬时故障做带退避的重试）——**它对治的是网络抖动、限流这类瞬时错误，不是超时**。

### 5.6 schedule 表达式与任务状态速查

| 形式 | 写法 | 含义 |
|---|---|---|
| cron 字段 | `分 时 日 月 周`（5 字段）或 `秒 分 时 日 月 周`（6 字段） | OpenClaw 由 Croner 解析，两种都支持 |
| 每周一 09:00 | `0 9 * * 1` | 周字段 `1` 代表周一 |
| 每月 25 日 10:00 | `0 10 25 * *` | 日字段固定 25 |
| 每月末 23:59 | `59 23 28-31 * *` | 28–31 日各触发一次，**配合脚本"月末守卫"只在真月末跑** |
| 一次性 | `--at "2026-05-23T02:00:00Z"` | ISO 8601，`T` 分隔，末尾 `Z` 表示 UTC |

| status | 含义 |
|---|---|
| `idle` | 已注册、等待下次触发，从未跑过或上次未产生终态 |
| `ok` | 上次运行成功 |
| `error` | 上次运行失败（看 `cron runs` 的 `error` 字段定位原因） |
| `skipped` / `lost` / `timeout` | 跳过 / 丢失 / 超时等更细的状态，`cron runs` 历史里会记 |

> **Caution · 时区**：`--at` 时间戳不带时区偏移时按 **UTC** 解释；`--cron` 不带 `--tz` 时按 **Gateway 宿主机本地时区**解释。宿主机时区不可控——本机 Mac 常是 `Asia/Shanghai`，云服务器上常是 UTC。**周期任务一律显式带 `--tz "Asia/Shanghai"`。**
>
> **Caution · croner 的 OR 语义**：cron 表达式里"日"和"周"两个字段同时非通配时，croner 按"**任一匹配即触发**"（OR）。想要"每月 15 号且周一"，写 `0 9 15 * 1` 会变成"15 号**或**任意周一都跑"。本课三条表达式周字段要么是 `*`、要么日字段是 `*`，没踩这个坑——**你自己写时要留意。**

### 5.7 cron error 排查 checklist

1. `cron runs --id <id>` 看执行历史——有没有触发记录、`status` 是什么。
2. **没有触发记录** → 第一段链路（调度）问题，查 schedule、时区、任务是否 enabled。
3. **有记录但 `error`** → 第二段链路（被唤醒方）问题，看 `error` 字段：
   - `No callable tools remain` → **工具权限问题**，给子 Agent 补任务所需工具的权限。
   - `... timed out` → **执行超时**，`cron get` 看 `timeoutSeconds` 和 `lastDurationMs`，用 `cron edit --timeout-seconds` 调大。
4. **注意子命令参数风格**：`cron runs` 用 `--id`，`cron get` / `cron run` / `cron edit` / `cron remove` 用**位置参数** `<id>`。

> **⚠️ PITFALL：cron 子命令的 ID 参数风格不统一。** 给 `cron get` 传 `--id` 会报 `OpenClaw does not recognize option "--id"`。不同版本、不同教程对参数名也有出入——**每个 cron 子命令第一次用，先 `openclaw cron <子命令> --help` 确认当前版本的真实参数**，这比照搬别处的写法靠谱。

> **两处正常现象别当故障**：① 转写阶段会刷出几行红色 `RuntimeWarning ... matmul`（`divide by zero` / `overflow` / `invalid value`），这是 faster-whisper 处理静音帧时的**已知无害告警**，转写仍正常完成。② 纪要生成是**非确定性**的——结构固定（关键问答 / 优势 / 待考察点 / 评分建议四部分），但每部分条数每次跑都会浮动，**你跑出的条数和课件不完全一样是正常的**。

> **两处真实的能力边界要点出来**：① **ASR 转写有误识**——small 模型对中文专业术语和人名有误识（把"张磊"听成"张蕾"、"80 万行"听成"80 万型"），下游大模型能从上下文纠正回来；要更高准确率得换 medium 或 large-v3。② **说话人分离有适用边界**——基频聚类在本场景成立，靠的是面试官和候选人音色差异明显、且只有 2 个人；**换成 3 人以上或同性别音色相近的场景会失效**，要换 pyannote。

**三场景对照三检验**：

| 场景 | 真实业务 | 有价值的技术 | 真实价值 |
|---|---|---|---|
| 1 批量筛简历 + 画像 | HR 真做简历初筛 | office 解析 + 合规过滤 + 8 维评分 + HTML 画像 | 批量排序 + 每人一张画像（人工初筛根本不做画像） |
| 2 人才库语义检索 | 业务部门真会说"再找几个像他的" | 通义 embedding + 手写余弦语义检索 + 维度级可解释 | 88 毫秒出 Top 5 |
| 4 面试纪要生成 | 面试后真要写纪要 | faster-whisper 转写 + 基频聚类分离 + LLM 结构化 | 按发言人组织成稿 + 数字回核 |

> **一个不显眼但不能抽掉的环节——数字回核。** 场景 1 的"7 人全部 0 虚构"、场景 4 的纪要回核都是它在工作：**把每个数字反查一遍原始数据，防止大模型把数字记错、串台。** 它不产出任何亮眼的东西，但正是这种环节决定了链路是"能上线的工业级"还是"看着能跑的 demo"。

```bash
$OC config get 'agents.defaults.subagents'            # 应含 allowAgents: [] + requireAgentId: true
$OC config get tools.agentToAgent

$OC config set 'agents.defaults.subagents.requireAgentId' 'true' --strict-json
for i in 0 1 2 3 4 5; do
  $OC config set "agents.list[$i].subagents.allowAgents" '[]' --strict-json
done
$OC config set 'agents.list[6].subagents.delegationMode' '"prefer"' --strict-json
# 注意：上面 for 循环不要碰 list[6]；router 的 allowAgents 白名单应已在 §2 配好

$OC cron runs --id <id>                               # 注意：runs 用 --id
$OC cron run <id> --expect-final --timeout 620000     # --timeout 单位毫秒
```

| 命令 | 参数 | 单位 | 含义 |
|---|---|---|---|

| `cron edit` | `--timeout-seconds` | **秒** | agent job 自己的执行超时（`payload.timeoutSeconds`） |

| # | 现象 | 根因 | 解法 |
|---|---|---|---|
| 1 | `status: forbidden` / `agentId is not allowed for sessions_spawn (allowed: router)` | `subagents.allowAgents` 没配，默认只允许 spawn 自己 | `config set 'agents.list[6].subagents.allowAgents' '[...]' --strict-json` |

| 4 | 改完白名单其他 Agent 配置没了 | 用了整体替换数组的写法 | 用带下标的 `config set`，**不要 patch 数组** |
| 5 | Router 直接回答了业务问题，还不报错 | **越界自答**——`SOUL.md` 边界写得太软 | 查 `TOOLS: None` / `agentId` 出现 0 次；按 §3.2 三件事强化红线 |
| 6 | 工具调用统计里 `failures: 1`，路由却是对的 | Router 先试了 `sessions_send`，目标没有活跃会话 | `SOUL.md` 分发指引写明"新请求一律用 `sessions_spawn`" |
| 7 | `allow:["*"]` 的 HR 主管，`cron` 也显示被拦 | `cron` / `gateway` 带 **profile 注册门控**，压根没进过滤管线 | 探针集里剔掉这类工具 |
| 8 | `--local` / TUI 报 `No callable tools remain` | 不带飞书 `senderId`，命中 `* deny` | 生产预期；验员工档可临时把 `*` 设成员工 allow/deny，或用飞书真账号；**验完按环境恢复** |
| 9 | 满屏红黄噪声 + 非零退出码 | 兜底锁死后模型回退重试留下的 | 只找关键行 `No callable tools remain after resolving explicit tool allowlist` |
| 10 | `config set` 的值被当成字符串塞进去 | 忘了 `--strict-json` | JSON 值一律加 `--strict-json` |
| 11 | Cron 报 `job execution timed out` | `timeoutSeconds` 定得太紧（复合任务真实耗时更长） | `cron get` 看 `lastDurationMs`，`cron edit --timeout-seconds` 调到真实耗时的 2–3 倍 |
| 12 | Cron 报 `No callable tools remain`，997 毫秒秒退 | 子 Agent 的 `deny` 拦掉了任务要用的工具组（如月报要的 `exec` 属 `group:runtime`） | 给子 Agent 补上任务所需工具的权限 |

| 15 | 写 `0 9 15 * 1` 想要"每月 15 号且周一"，结果天天在跑 | croner 对"日 + 周"同时非通配按 **OR** 语义 | 日、周两个字段至少留一个 `*` |
| 16 | `cron run` 敲完立刻查历史，什么都没有 | `cron run` 是**异步入队**，后台真正跑完要 2–3 分钟 | 等任务跑完，或用 `--expect-final` + 足够的 `--timeout` |
| 17 | 备份了 `openclaw.yaml`，改坏 Cron 任务却回滚不了 | Cron 任务**不在 yaml 里**，在调度器任务库 | 改任务前 `cron get <id> > 文件` 导出任务定义 |
| 18 | 配了 `name:HR主管` 但 Web/TUI 永远命中 `*` | WebChat / Control UI / TUI **不注入 SenderName** | **只用飞书 `id:ou_xxx`**；本仓已弃用 `name:` |
| 18b | 普通员工能 spawn 但查不到 IMA / `exec` 被拦 | 低权限档只放了 `group:memory`，或 `deny` 了 `group:runtime` | 员工档放行 `sessions_spawn`/`sessions_yield`/`exec`/`read`，且不要 deny `group:runtime` |
| 18c | 演示期谁都能用全套工具 | `*` 停在 `allow:["*"]` | 赛后改回 `deny:["*"]` |
| 19 | `agent` 命令等了两分钟没反应，以为卡死 | 一个完整 turn 要加载工作区、组装 prompt、调大模型 | 正常，**别按 Ctrl+C**；Router 路由一条请求约 20–45 秒，`--local` 完整任务 1–3 分钟 |
| 20 | 面试纪要每次跑出的条数都不一样 | 大模型生成是**非确定性**的 | 结构固定即可（四部分），条数浮动正常 |
| 21 | 开了 `delegationMode: prefer`，Router 仍对「年假有几天」直答（`TOOLS: None`） | `prefer` 是 **Prompt-only**，注入文案仍允许「已知短答」直回 | **不能替代** §3 SOUL「没有例外」硬红线；查会话里有没有 `sessions_spawn` |
| 22 | 业务子 Agent 也开始乱 `sessions_spawn` | 把 `delegationMode: prefer` 写进了 `agents.defaults` | **只给 router** 开 prefer；叶子保持 `allowAgents: []` |
| 23 | 新建了一个 Agent，它莫名其妙能 spawn 别人 | `defaults.allowAgents` 不是 `[]`，或新叶子没写显式 `[]` | 按 §2.5.1 把 defaults 全禁 + 新叶子显式 `[]`；只有 router 开白名单 |
| 24 | 运行时 yaml 改对了，git 里还是旧配置 | `config set` 写的是 `~/.openclaw-hr/config/openclaw.yaml`，与仓库 `openclaw-hr/config/openclaw.yaml` **不是同一份** | 改完运行时后同步写回仓库副本再提交 |
