## §0 一句话主旨：五个子 Agent 不等于一个数字员工

### 周一上午的三个请求

设想某某公司周一上午的半小时，三个人几乎同时找 HR 数字员工「小慧」办事：

| 谁 | 请求 | 数据敏感度 |
|---|---|---|
| HR 主管 | 导出全公司花名册（含薪资、考勤、绩效） | 最高权限才该碰 |
| 业务部门负责人 | 看本部门这个月的招聘进度 | 能看自己部门，不该看别的部门，更不该看全公司花名册 |
| 普通员工小王 | 年假到年底没休完会不会清零 | 谁都能问 |

三个请求来自三个权限不同的人，分属两个业务领域（导花名册、问年假 → 行政；看招聘进度 → 招聘）。**手上那五个子 Agent 接不住这半小时**，原因有两条：

1. **它们是五个独立入口**——用户得自己知道"筛简历找招聘子 Agent、问政策找行政子 Agent"，得自己在命令行里指定 `--agent`。真实用户不会这么用：HR 主管不关心后台有几个 Agent，他只想说一句"导出花名册"。
2. **它们现在谁来调都一样**——普通员工小王只要会敲命令，照样能让行政子 Agent 去导出全公司花名册。

### 编排要解决的三件事

把五个子 Agent 拼成一个「小慧」，不是把五个文件挪进同一个文件夹。它要解决三件在"单看子 Agent"时根本不存在的事：

- **统一入口**——用户只跟一个对象说话，由系统判断该把请求交给哪个子 Agent。
- **按身份隔离**——同一个「小慧」，面对 HR 主管和普通员工，能给出的能力必须不一样。这不是子 Agent 自己的事，是编排层的事。
- **自动化总调度**——除用户主动提的请求外，还有一批定时任务（入职跟进、月报）要无人值守按时跑；散在各子 Agent 里没法统一管。

> **为什么"编排"值得单独一集**：五个子 Agent 单独跑通，证明的是每个 Agent 的**业务能力**没问题。但"能不能上线"考的是另一组问题——用户不知道该找谁怎么办？高权限数据被低权限的人请求到怎么办？某个定时任务漏跑了谁来发现？这些问题单独看任何一个子 Agent 都不会暴露，只在"五个子 Agent 要合成一个对外的数字员工"时才出现。**工业级数字员工和 demo 级数字员工的差别，几乎全在这一层。**

## §1 编排层四件套：各管一层，且有依赖顺序

| 部分 | 核心对象 | 解决什么 |
|---|---|---|
| §2 | 总控 Router | 五个子 Agent 的统一入口——判断领域、分发请求 |
| §3 | Per-Sender 三档权限 | 按飞书 `id:ou_xxx` 隔离权限——HR 主管 / 业务负责人 / 普通员工各有边界（弃用 `name:`） |
| §4 | Cron 总调度 | 七个定时任务跨四个子 Agent，无人值守自动跑 |
| §5 | 端到端 8 场景验收 | 用一套可复核的方法，验「小慧」到底能不能上线 |

**这四层不是并列的功能清单，是有依赖顺序的**：

- **Router 是地基**——没有统一入口，权限隔离和总调度都无从谈起。
- **Per-Sender 架在 Router 之上**——请求先进 Router，Router 才知道该按什么权限往下分发。
- **Cron 是另一条线**——它不经过用户，直接按时间触发子 Agent。
- **端到端验收是最后一层**——它检验前三层合起来到底成不成。

### 一个请求走一遍「小慧」

以普通员工小王问"年假到年底没休完会不会清零"为例：

1. **请求进 Router**——小王的消息先到总控 Router。Router 不直接回答，它的职责是调度，不是答题。
2. **Router 判领域**——"年假怎么休"是 HR 政策问题，属行政领域，对应 `er-admin`。
3. **分发**——Router 用工具把请求转给 `er-admin`，并带上发送者的身份（普通员工档）。
4. **子 Agent 在权限内处理**——`er-admin` 检索公司政策，引用原文回答。同样是问 `er-admin`，HR 主管的请求能让它导出花名册，小王的请求不能——**决定差异的不是子 Agent，是发送者的权限档**。
5. **结果回流**——`er-admin` 把答复交回 Router，Router 转述给小王。整个过程小王只看到「小慧」一个对象。

## §2 总控 Router：只调度不办事

### 2.1 Router 是什么

Router 是业务请求的总入口。它对外只有一个身份——「小慧」；对内**只做三件事**：判断领域、分发请求、汇总结果。

注意这三件事里**没有一件是"办业务"**。Router 不筛简历、不答政策、不聚合绩效——那是五个业务子 Agent 各自的活。

> **术语校准**：业界（如 LangGraph）有时把"只做分类分发、分完就完"的那一步称为 **Router**，把"还要汇总结果、做多轮编排"的称为 **Supervisor / Orchestrator**。本课的"总控 Router"职责上同时含分发与汇总，按这个区分**更接近 Supervisor 模式**。沿用"Router"取的是"总控分发"这个通俗叫法，学过 LangGraph / OpenAI Agents SDK 的读者留意术语差异即可。

### 2.2 为什么必须"只调度不办事"

这条原则听起来像自我设限——Router 明明是个能力很强的 LLM，为什么不让它顺手把简单的活也干了？

**因为业务子 Agent 不是简单的问答机器人，它们各有专业机制。** 行政子 Agent 答一个政策问题，背后是一整套设计：检索公司自己的 14 份政策文件、引用政策原文出处、遇到法律纠纷或个人数据问题硬性转人工。招聘子 Agent 评简历，背后有合规过滤层和数字回核。

如果 Router 觉得"年假有几天"是个简单问题、自己用通用知识答了——它绕过了行政子 Agent 那一整套机制。它给出的"年假 5/10/15 天"是**国家法定标准，不是这家公司的政策**（公司完全可能有更优安排）。**Router 越界自答一次，就把"公司政策咨询"悄悄降级成了"通用常识问答"，还不报错。**

> **类比：Router 是总机，不是专家。** 多 Agent 教程常用"前台总机""医院分诊台"打比方，但多数比方只讲到"把请求转对"为止。本课要多讲一层：**转错之外，总机还有另一种更隐蔽的犯错方式——"热心过头"**。一个总机觉得报销标准自己也知道，就直接答了；答错了，来电的人还以为得到了官方答复。Router 的设计目标，就是做一个**克制的总机**：判断准、转得对、不抢答。

### 2.3 路由逻辑写在 SOUL.md 里，没有 routing-config.yaml

做过传统后端的人会以为路由该有一份配置文件——比如 `routing-config.yaml`，里面列着"招聘关键词 → recruitment"这样的对照表，再配优先级。

**Router 没有这样的文件。它的路由逻辑，全部写在 `router` 子 Agent 的 `SOUL.md` 里。**

理由要回到一个判断：**Router 是一个 LLM Agent，不是路由代码。** 既然路由判断是大模型在运行时做的，那"怎么判断"就只能用大模型读得懂的方式来写——自然语言，写进 persona。

> **补充**：严格说 OpenClaw 子 Agent 的 persona 是一组文件——`SOUL.md`（人格、职责、边界）、`IDENTITY.md`（身份与能力信息）、`USER.md`、`AGENTS.md` 等，启动时一起注入系统提示词。本课把五领域路由表也放进 `SOUL.md`，是一个**有意的简化**：路由表本质是"能力清单"、更贴近 `IDENTITY.md` 的定位，但集中在 `SOUL.md` 里、改一个文件就够了。

Router 的"路由能力"是三样东西组合出来的：

| 构成 | 是什么 | 谁提供 |
|---|---|---|
| persona（`SOUL.md`） | Router 这个 LLM Agent 的人设 + 路由指令 | 自己写 |
| `sessions_spawn` 工具 | 运行时把请求转给别的子 Agent 的工具 | OpenClaw 提供（需配白名单） |
| 大模型的判断力 | 读懂用户请求、判断属于哪个领域 | LLM Provider（本课 DeepSeek V4 Pro） |

### 2.4 SOUL.md 的四个关键块

1. **「我是谁」**——把 Router 定位成"用户面对的唯一统一入口"。对用户来说你就是「小慧」，后台有五个子 Agent 是用户不需要知道的。
2. **「我负责什么」**——把三项职责写死："我只做三件事：判断领域、分发请求、汇总结果。我不直接干 HR 业务。"不写死它，大模型很可能"热心过头"。
3. **「我能调度的五个业务子 Agent」**——一张五行路由表，每行列出子 Agent ID、业务领域、典型请求。**表写得越具体，匹配越准**——所以"再找几个像张三的"这种真实话术直接写进了表里。
4. **「路由判断规则」**——给大模型一套判断方法论，不是让它凭感觉：
   1. **抓业务动作 + 业务对象**——请求里的核心动词和名词决定领域。动词加名词，是最稳的判据。
   2. **一个请求只路由到一个子 Agent**——绝大多数请求归属唯一领域，判断出来立即分发。
   3. **跨领域请求**——先路由到主领域子 Agent，在汇总回复里说明还涉及哪个领域。
   4. **领域不明确就问，不要猜**——直接问用户澄清，不随意分发。

> **Caution**：路由表里的子 Agent ID（`recruitment`、`onboarding` 等）**必须和 OpenClaw 里实际注册的 Agent ID 逐字一致**。写成 `recruit`、实际注册的是 `recruitment`，Router 就会去调一个不存在的 Agent，路由直接失败。

**路由判断是语义匹配，不是关键词硬匹配。** 规则里举的"筛简历""出 JD"是例子，不是穷举词表。用户说"这周收到的简历帮我过一遍"，句子里没有"筛"字，大模型照样能判断出这是招聘领域——这正是用 LLM Agent 做路由的价值。

### 2.5 为什么不用别的做法：四种路由方案取舍

| 做法 | 怎么做 | 取舍 |
|---|---|---|
| **单 Agent 全包** | 不分子 Agent，一个 Agent 把五个领域全干了 | persona 巨长——五套指令、五套合规红线堆进一个 `SOUL.md`，注意力被稀释；维护难——改招聘逻辑可能波及行政表述；**无法分级权限**——一个 Agent 没办法对不同领域开不同权限 |
| **客户端硬编码路由** | 在调用方写死 `if 含"简历" then 调 recruitment` | 不灵活——自然语言说法无穷，关键词表永远覆盖不全；改一次路由就要改一次代码、重新发布 |
| **意图分类器路由** | 用小分类模型 / embedding 相似度判定领域再转发（业界的 semantic router / intent classification） | 延迟低（毫秒级）、成本低、判断稳定；但要单独训练维护分类器，新增领域往往要重新标注、重训 |
| **总控 Router（本课）** | 一个 LLM Agent 读 `SOUL.md` 做语义路由，分发给五个独立子 Agent | 灵活——自然语言怎么说都能懂；子 Agent 各自独立、persona 精简、可分别配权限；改路由只改 `SOUL.md`。**代价**：每个请求多一跳 LLM 调用（实测每条请求 20–45 秒 + token 成本）；路由准不准依赖语义判断，不是 100% 确定 |

**这里要诚实说清代价，不能只夸不提。** 选 LLM Router，是用"延迟和成本"换"灵活性和可分级权限"。HR 场景里这笔交换划算——请求量不大、领域语言多变、权限分级是硬需求；但换一个高并发、领域固定的场景，意图分类器可能更合适。

四种做法里最值得说的是**"无法分级权限"**这一条：单 Agent 全包模式下，Router 和业务逻辑揉在一起，你没办法说"这个领域只给 HR 主管用"。而五个子 Agent + Router 的结构，天然为 Per-Sender 三档权限留好了位置。**编排结构的选择，直接决定了后面权限设计有没有空间。**

### 2.6 两个名字相近的配置：路由的关卡只有一个

配通 Router 的分发通路时会撞上第一个工业级坑——它跟一个名字相近的配置有关：

| 配置项 | 官方定位 | 管哪个工具 |
|---|---|---|
| `tools.agentToAgent`（`enabled` + `allow`） | 跨 Agent **直接消息**的开关与白名单 | `sessions_send`，**不是** `sessions_spawn` |
| `agents.list[<n>].subagents.allowAgents` | 某个 Agent 用 `sessions_spawn` 时能 spawn 到哪些目标 Agent 的白名单 | `sessions_spawn`（**Router 路由用的就是它**） |

**坑的根子**：Router 做路由用的是 `sessions_spawn`，而 `sessions_spawn` 的目标白名单是 `subagents.allowAgents`——不是 `tools.agentToAgent`。后者名字看起来像"允许 Agent 之间通信"，很容易让人以为配了它路由就通了。

`subagents.allowAgents` 不配时，**默认只允许 Agent spawn 自己**——报错里的 `allowed: router` 就是这个默认值在说话。

> **实测对照（不是从文档推的）**：在 `subagents.allowAgents` 已配好的前提下，把 `tools.agentToAgent.enabled` 关成 `false`，再让 Router 路由一条招聘请求——**路由照常成功**，`sessions_spawn` 正常 spawn 到了 `recruitment`。这证明跨 Agent 路由只认 `subagents.allowAgents` 这一套白名单。

**星型路由拓扑**：`subagents.allowAgents` 是按 Agent 分别配的——只给 Router 配，让它能 spawn 五个业务子 Agent；业务子 Agent 侧不配（或显式 `[]`），它们就调不动别人。这样整个系统形成一个干净的**星型路由拓扑**：所有调度都从 Router 出发，业务子 Agent 之间不会互相乱调。**这是最小权限原则在多 Agent 编排上的落地。**生产上更稳的「三层写死」见 §2.7。

### 2.7 星型拓扑的硬化写法（本仓已落地）

课程原文的写法是「业务子 Agent **不配** `allowAgents`」。生产上更稳的做法（对齐本仓库 `openclaw_part_7` 多 Agent 实战配置）是**三层写死**，而不是依赖「不配 = 默认只能 spawn 自己」这种隐式行为：

| 层 | 配置 | 本仓取值 | 作用 |
|---|---|---|---|
| **默认基线** | `agents.defaults.subagents.allowAgents` | `[]` | 默认全禁——谁要 spawn，必须在 per-agent 显式开 |
| **强制带 ID** | `agents.defaults.subagents.requireAgentId` | `true` | spawn 时必须显式传目标 `agentId`，不允许隐式默认 |
| **叶子显式禁** | `main` / `recruitment` / `onboarding` / `training` / `performance` / `er-admin` 的 `subagents.allowAgents` | 各为 `[]` | 写进配置文件，审计时一眼能看出「叶子不能互调」 |
| **调度中心** | `agents.list[6]`（router）的 `subagents.allowAgents` | 五个业务子 Agent ID | **唯一**能向外 spawn 的节点 |

> **为什么叶子要显式写 `[]`，而不是继续「不配」？** `allowAgents` 不配时的默认是「只能 spawn 自己」，和显式 `[]`（谁都不能 spawn）在多数场景效果接近，但**显式空数组是可审计的安全声明**——配置评审、对照 `openclaw_part_7` 的生产兜底配置时，不会被误读成「忘了配」。`defaults.allowAgents: []` 则把「新加一个 Agent 却忘了收权」的风险堵住：新 Agent 默认不能 spawn 任何人，除非你主动给它开白名单。

## §3 越界自答：一个不报错的坑，与 SOUL 调优

### 3.1 现象与危害

给 Router 发一条 HR 政策咨询请求："员工咨询：年假一年有几天？请给出明确答复。"——观察 Router 是规规矩矩转给行政子 Agent，还是自己就答了。

**实验结果是后者。** 强化修复前的会话记录里，Router 这一轮对话的工具调用统计是 `TOOLS: None`——**一个工具都没调**，`agentId` 字段出现 0 次。Router 直接用大模型的通用知识，自己输出了一大段"年假天数取决于累计工作年限：5/10/15 天"的答复。

**这个坑的可怕之处在于：它不报错。** 跨 Agent 白名单那个坑至少会甩一个 `forbidden` 出来提醒你；越界自答什么都不甩——路由"看起来"还在正常工作，Router 也给了用户一个像模像样的答复。不专门去查工具调用字段，根本发现不了。

> **硬信号**：判断 Router 有没有越界自答，有一个客观标准——会话统计里的 `TOOLS` 字段。总控 Router 的正常对话回合，**一定有 `sessions_spawn` 工具调用**。如果某一轮 `TOOLS: None`，就说明 Router 这一轮没路由、自己把活干了。**验收多 Agent 系统时，这个字段要专门查。**

### 3.2 为什么会越界自答

根子还是那句话：**Router 是一个 LLM Agent，不是路由代码。**

实验里反复观察到：模型判断出"这是个政策问题"之后并不总是老实转发——遇到"年假有几天"这种它"觉得自己也知道答案"的简单问题，它倾向于直接答。这背后是大模型一个常见倾向：**在"严格走流程"和"尽快把用户的问题解决掉"之间，模型往往偏向后者。**

第一版 `SOUL.md` 其实写了边界——"我只做调度与分发，不直接执行具体 HR 业务"。但这句话不够强硬，大模型把它解读出了一个例外空间："复杂的业务才转，'年假有几天'这种简单问题我答一下应该不算'执行业务'吧。"——**模糊的措辞，会被大模型解读出例外。**

### 3.3 修复：把红线写到不留余地

修复办法不是改 OpenClaw 的代码，是改 `SOUL.md`。强化后的边界段做了三件事：

1. **堵死"简单问题"这个借口**——"绝不直接回答 HR 业务问题——哪怕用户问的是'年假有几天'这种我'好像知道答案'的简单问题，也必须用 `sessions_spawn` 转给对应子 Agent。"**直接点名"看起来简单"的问题**，不让大模型钻空子。
2. **给一个无例外的判断标准**——"只要请求落在五个业务领域里，就必须路由出去，**没有例外**。"用"没有例外"四个字，把模糊的"原则上""一般情况下"彻底删掉。
3. **解释清楚为什么**——把"绕过子 Agent 的公司政策检索 = 用通用常识冒充公司政策"写进去。**让大模型理解这条红线的分量，而不只是记住一条禁令。理解了分量的约束，比单纯的禁令更稳。**

### 3.4 另一个调优案例：工具选择的试错

五条实测请求里，"年假怎么休"→ `er-admin` 的路由判断是对的，但工具调用统计里有 `failures: 1`。读会话文件能看到：Router 先调了 `sessions_send`（往一个已经在跑的 `er-admin` 会话发消息），但此刻 `er-admin` 没有正在运行的会话，返回 `No session found`；Router 接着调 `sessions_list` 确认，然后才改用 `sessions_spawn`。

**这不是路由错**，目标判断从一开始就对。它是 Router 在"用哪个工具分发"上多走了一步弯路：

| 工具 | 用途 | 什么时候用 |
|---|---|---|
| `sessions_spawn` | 新起一个子 Agent 运行来处理任务 | 用户新提一个需求时 |
| `sessions_send` | 往一个已存在的活跃会话里追发消息 | 续接一段已有对话时 |

修复同样是改 `SOUL.md`——在分发指引里写明"分发新请求一律用 `sessions_spawn`，不要先试 `sessions_send`"，并把两个工具的适用边界写进去。优化后工具调用降到两个，`failures: 0`。

### 3.5 SOUL 调优是 LLM Agent 开发的常规工作

把这两个修复放在一起看，能总结出一个重要的工作模式：**两个问题的修复，一行 OpenClaw 代码都没改，改的都是 `SOUL.md`。**

原因还是那句话：Router 的路由行为不是写死的代码，是大模型读 `SOUL.md` 之后的"理解执行"。它的行为偏差，不能靠改代码拦，只能靠把指引写得更清楚。

**所以 LLM Agent 的"调试"，很大一部分是在调 `SOUL.md` 这份 persona 文档，而不是在调代码。** 标准节奏是一个循环：**实测 → 发现行为偏差 → 改 persona 指引 → 再测**。`SOUL.md` 是工作区文件，改完下一次对话即时生效，不需要重启——这让循环转得很快。

> **一条纪律**：**persona 调优要针对实测发现的具体问题，不要顺手大改已经正确的部分。** 领域判断已经 5/5 全对，两次调优都没动"路由判断规则"那一段，只动了"边界红线"和"分发指引"。哪里出问题改哪里——不要因为"正好在改 `SOUL.md`"就把对的地方也重写一遍，那样很容易把已经稳定的行为改坏。

### 3.6 为什么不让 Router 自己判断要不要答

可能有人会想：与其把红线写得这么死，为什么不信任大模型、让 Router 运行时自己判断？

**因为那样不可控。** 判断标准全靠模型临场发挥——同一个"年假有几天"，这次判"该转"，下次可能就判"我能答"。更麻烦的是会被用户追问带偏：用户说"你就直接告诉我嘛，别转来转去的"，模型很可能就顺着突破了边界。`SOUL.md` 里"没有例外"那条硬约束，做的恰恰是把"要不要路由"从**模型自由发挥**变成**明文守则**——守则不参与临场判断，它就是规则本身。

### 3.7 这套修复的局限（三条要诚实讲）

1. **"没有例外"管的是"落在领域内别自答"，不是"什么都不许答"。** 它没有禁止 Router 回应不属于任何 HR 领域的话——用户打招呼、问"你能帮我做什么"，Router 可以直接回应，也可以按规则 4 反问澄清。红线约束的是"业务问题别自己答"，不是"把 Router 变成哑巴"。
2. **"算不算落在领域内"仍是模型的语义判断。** 硬约束把"必须路由"变成了明文守则，但具体某条请求算不算落在五个领域里，仍要经过语义理解——这一步不是 100% 确定性的。**红线降低了越界的概率，没有把它降到零。**
3. **本课的修复是"概率性约束 + 事后检测"，不是结构性预防。** 写硬红线降低越界概率、检测 `TOOLS: None` 是事后告警，两者都不能从根上让越界"不可能发生"。可叠加的加固见 §3.8——其中 `delegationMode: prefer` 与星型拓扑硬化**本仓已落地**；forced tool call 仍取决于运行时是否暴露控制，**当前版本未用到**。

### 3.8 生产加固：delegationMode prefer（本仓已落地）

在 SOUL 硬红线之上，本仓给 Router 叠了一层 OpenClaw 原生的委派强度配置：

```yaml
# 只写在 router 上，不要写到 agents.defaults（业务子 Agent 不该 prefer spawn）
agents.list[6].subagents:
  delegationMode: prefer
  allowAgents: [recruitment, onboarding, training, performance, er-admin]
```

| 值 | 含义 |
|---|---|
| `suggest`（OpenClaw 默认） | 普通引导：较大的活「可以用」`sessions_spawn` |
| `prefer`（本仓 Router） | **强引导**：在 system prompt 注入「你是协调者；凡比直接回复更复杂的事，优先 `sessions_spawn`」 |

**它是什么 / 不是什么**：

- ✅ **是** Prompt-only 加固——运行时把委派偏好写进系统提示词，降低「懒得转、自己答」的概率，与 SOUL 红线方向一致。
- ❌ **不是** 工具权限（管不了能不能 spawn——那是 `allowAgents`）。
- ❌ **不是** forced tool call——**挡不住**模型完全不调工具、用通用常识直接回答。
- ⚠️ `prefer` 的注入文案仍允许「寒暄 / 澄清 / 当前上下文里已有短答」直回——这正好是「年假有几天」那类越界的借口空间，所以 **`prefer` 只能叠加，不能替代 SOUL「没有例外」硬红线**。

与 §2.7 的星型拓扑硬化合在一起，本仓编排层当前的防越界栈是：

| 层 | 手段 | 性质 | 本仓状态 |
|---|---|---|---|
| L0 | SOUL「落在五领域必须路由、没有例外」 | 概率性约束 | ✅ 已有 |
| L1 | `router.subagents.delegationMode: prefer` | Prompt 加压 | ✅ **已落地** |
| L2 | `defaults.allowAgents: []` + 叶子显式 `[]` + `requireAgentId: true` | 拓扑结构 | ✅ **已落地**（§2.7） |
| L3 | Router 工具白名单从 `*` 收窄到 sessions_* | 工具结构 | 📋 后续 |
| L4 | 业务问句回合无 `sessions_spawn` → 告警 / 拒发 | 事后门禁 | 📋 后续 |
| L5 | forced tool call（`tool_choice` 类） | 真结构强制 | 📋 上游未暴露，暂缓 |

> **落点**：**Router 的克制，比 Router 的能力更重要。** 一个会越界自答的 Router，哪怕领域判断 5/5 全对、路由能力再强，也不能上线——因为它会悄悄架空整个多 Agent 系统的专业性。**验收一个多 Agent 系统，不能只验"它能不能干活"，必须专门验"它会不会越界干不该它干的活"。**

## §4 双层权限模型：Per-Sender + Per-Agent

### 4.1 为什么权限必须分级

统一入口带来一个新问题——所有人都从同一扇门进来找小慧，而这扇门后面，不同的人能让小慧做的事绝不该一样。

回到周一上午的三个请求：导花名册要在服务器上跑命令、读写 HR 数据文件（重操作）；看部门进度只是查看；问年假只需检索政策库。如果三个人用同一套工具权限，结局只有两种：**要么放到最宽**，普通员工也能导出全公司花名册（越权）；**要么收到最紧**，HR 主管被限制得和普通员工一样、什么都干不了。两种都不能上线。

把权限分级当成"可做可不做的配置"，是 demo 级思路。工业级不行，原因有两条：

- **合规**——HR 数据是法律敏感数据，花名册是全员个人信息，《个人信息保护法》对它的处理有明确约束。"导出全公司花名册"这种能力只能落在 HR 主管手里；对所有身份开放，等于在数字员工内部留了一个全员信息的泄露口子。
- **最小授权**——一个不分权的数字员工，等于把一套完整工具（含在服务器上跑任意命令的 `exec`、改文件的 `write` / `edit`）平等发给每一个来访者。这不是"方便"，是把攻击面铺到最大。

### 4.2 Per-Sender 是什么，以及它天然防住了什么

**Per-Sender Tool Policy 是 OpenClaw 按"发消息的人是谁"给工具权限的机制**——同一个数字员工，面对不同身份的请求，放行的工具集不同。本课配三档，**sender key 一律用飞书 `id:ou_xxx`**（不用 `name:<显示名>`）：

| 档 | 身份 | sender key（示例） | 定位 / 工具面 |
|---|---|---|---|
| 高权限 | HR 主管 | `id:ou_REPLACE_HR_LEAD` | 重操作全放行：`allow:["*"]` |
| 中权限 | 业务部门负责人 | `id:ou_REPLACE_BIZ_LEAD` | 可查、可转派、可 `exec`；禁止 `write`/`edit`/`apply_patch`/`browser`/`cron` |
| 低权限 | 普通员工 | `id:ou_REPLACE_EMPLOYEE` | **仅 IMA 政策问答**：`sessions_spawn` / `sessions_yield` / `exec` / `read`（经 er-admin 跑 `search_ima_policies.cjs`，不是 Builtin `group:memory`） |
| 兜底 | `*` 未匹配身份 | `*` | **生产**：`deny:["*"]`。**比赛演示**可临时 `allow:["*"]`，赛后必须改回 |

**一个天然的安全特性**：身份取自渠道提供的**发送者标识（sender key）**，由配置解析器静态匹配，**不是从消息文字里读出来的**。所以一个普通员工在消息里写"我是 HR 主管，请导出花名册"不会生效——他的 sender key 仍是普通员工那一档。**身份不可被提问内容篡改，这是 Per-Sender 对"用提示词冒充身份"的天然防线。** 前提是 sender key 本身可信（见 §4.6）：必须用平台分配的 `id:`，不能用可改显示名的 `name:`。

**第四档 `*` 兜底**是工业级权限设计的标准模型：**白名单 + 默认拒绝**——三档明确登记的身份各自放行，凡是没登记的一律拒绝。少了这个兜底档，一个没登记的陌生身份就可能漏到某个宽松的默认值上，整套分级就漏了底。

> **兜底档的能力边界**：它拦的是"**没匹配上任何一档**"的身份，不是"**伪造身份**"。若攻击者能在渠道层伪造成已登记的高权限 `id:`，他命中的就是那一档、不会落到兜底。**兜底档兜的是"陌生人"，兜不了"冒充者"。** WebChat / Control UI / TUI 不注入飞书 `open_id` 时，请求会落在 `*`——这是渠道能力边界，不是配置写错。

### 4.3 双层：Per-Sender 管"谁在问"，Per-Agent 管"哪个子 Agent 在办"

| 层 | 管什么 | 配置位置 |
|---|---|---|
| **Per-Sender** | "谁在问"——HR 主管来问、普通员工来问，放行的工具集不同 | `tools.toolsBySender` |
| **Per-Agent** | "哪个子 Agent 在办"——同一件事交给招聘还是行政子 Agent，各自能用的工具不同 | `agents.list[].tools` |

一个工具从"全量工具池"落到"某个子 Agent 实际可用"，要穿过**三道关卡**：

1. **profile 注册门控**——这个工具有没有被注册进当前环境（受 profile、插件启用状态控制）。没注册进来，后面两层根本看不到它。
2. **Per-Sender 过滤**——按发消息的人的身份决定放行哪些。
3. **Per-Agent 过滤**——按办事的子 Agent 决定放行哪些。

**Per-Sender 和 Per-Agent 叠加生效：一个工具要落到子 Agent 手里，必须两层都放行，任意一层挡掉就用不了。**

> **关卡顺序**：教学图里把 Per-Sender 画在 Per-Agent 前面（先"谁在问"、再"哪个 Agent 办"）；OpenClaw 内部 tool-policy 管线的真实顺序是 **Per-Agent 在前、Per-Sender 在后**。但这两层都是纯过滤（对工具集取交集），先后不影响最终结果——记住"**两层叠加取交集**"这个本质即可。

### 4.4 为什么要两层，不是一层

- **只配 Per-Sender 不行**——只管住了"谁在问"，没管住"哪个子 Agent 在办"。HR 主管是高权限档，他要是让行政子 Agent 去服务器上跑命令——行政子 Agent 本职是员工关系答疑，根本不该有 `exec` 这种能力。这正是业界说的"**多 Agent 跨调用导致权限级联放大**"风险：一个 Agent 的高权限顺着调用链传染给本不该有此权限的另一个 Agent，Per-Agent 层就是给它设的闸。
- **只配 Per-Agent 不行**——所有来访者对同一个子 Agent 权限相同。普通员工和 HR 主管都能驱动招聘子 Agent 批量跑简历，这显然不对。
- **vs 把权限写死在调用方**——硬编码在客户端代码里，换一个入口（飞书、API、命令行）就要重写一遍，而且数字员工本身没有防线：客户端被绕过，权限就形同虚设。**Per-Sender + Per-Agent 配置在数字员工这一侧，不管请求从哪个入口进来都拦得住。**

**"两层都放行才通"落到数字上就是取交集**：一个 HR 主管（Per-Sender `allow:["*"]`）的请求落到 `er-admin`（Per-Agent deny `write`/`edit`/`apply_patch`/`browser`，但**保留 `exec`** 供月报与 IMA）——他在 er-admin 会话里仍干不了改文件，却能跑检索脚本。**高权限的人，经由一个受限的子 Agent，重操作面被收窄。**

### 4.5 deny 是纵深防御，不是主拦截（诚实讲清）

有一条贯穿 OpenClaw 工具权限的规则：**同一个工具同时落在 `allow` 和 `deny` 里时，`deny` 永远赢。**

业务负责人 / 普通员工档的 `allow` 是**窄白名单**——没列进 `allow` 的工具天然拿不到。因此这两档 `deny` 里的 `write`、`browser` 等，**多数本就不在 allow 内**；`deny` 主要是**纵深防御**，防止日后放宽 `allow` 或 profile 叠回危险工具。

但有一条必须单独说清：**普通员工档不能 deny `group:runtime`。** IMA 答疑依赖 `exec`；deny runtime 等于把知识库检索掐死。旧课「员工只给 `group:memory` + deny runtime」与现行 IMA 链路不兼容，已废弃。

所以要分清：

- **HR 主管档（`allow:["*"]` 宽档）**——若加 `deny`，是在宽 allow 上精确扣工具。
- **业务负责人 / 普通员工档（窄白名单档）**——主拦截是 `allow`；`deny` 是冗余加固。**员工档的 `allow` 必须包含 `exec`（及 spawn/yield/read）。**

补充字段：`tools.toolsBySender` 每条支持 `allow` / `alsoAllow` / `deny`。**本课三档统一用 `allow` 定义独立白名单。**

### 4.6 sender key 六类：本课三档用 `id:`，弃用 `name:`

OpenClaw 的 sender key 从精确到宽松六类，匹配时**先命中先用**：

| sender key | 形态 | 匹配精度 |
|---|---|---|
| `channel:<channelId>:<senderId>` | 某渠道里的某个具体人 | 1 · 最精确 |
| `id:<id>` | **本课三档采用**：飞书 `id:ou_xxx` | 2 |
| `e164:<手机号>` | 国际格式手机号 | 3 |
| `username:<用户名>` | 平台用户名 | 4 |
| `name:<显示名>` | 显示名 · **可伪造；本仓已弃用** | 5 |
| `*` | 兜底 | 6 · 最宽松 |

**为什么不用 `name:`**：① 显示名可改、可重名，攻击者改成「HR主管」就能命中高权限档；② WebChat / Control UI / TUI **根本不注入 `SenderName`**，`name:` 键在这些入口上永远匹配不到。**飞书接入后应直接写 `id:ou_xxx`，不要再经 `name:` 过渡。**

### 4.7 这套模型的五条局限

1. **profile 注册门控是隐藏的第三层。** `cron`、`gateway` 等带 profile 门控的工具，没注册进池子就不进 Per-Sender/Per-Agent 过滤。验证时要绕开，避免把「没注册」误判成「被分权拦了」。
2. **完整端到端验证依赖真实飞书身份。** 三种真实 `ou_xxx` 各发一条、各自命中对应档，才算端到端；静态脚本可证明 16/7/3/0，TUI/`--local` 只能验 `*` 档行为。
3. **本地嵌入式 / TUI 不带飞书 `senderId`。** 必然命中 `*`。生产下 `* = deny` 会看到 `No callable tools remain`；演示期若 `* = allow` 则可直接跑通——赛后必须改回 deny。
4. **`name:` 已弃用**（见 §4.6）；勿再把它当无渠道权宜方案。
5. **Per-Sender / Per-Agent 都是工具层分权，不是数据层分权。** 「只看本部门数据」要另做数据视图过滤，不在 Per-Sender 范围内。

## §5 Cron 总调度：无人值守是两段式链路

### 5.1 什么是 Cron 总调度

前面讲的是"有人发话时小慧怎么响应"。工业级数字员工还有另一半：**没人发话的时候，小慧自己在干什么。**

Cron 是 OpenClaw 内置的定时调度子系统——**它到点自动唤醒指定的子 Agent 去执行任务，把"什么时候该做什么"交给系统，而不是交给人的记忆。** "总调度"指的是把散落在各个子 Agent 上的定时任务收拢成一张统一的调度地图。

收拢加补配之后，「小慧」挂着 **7 个 Cron 任务、跨 4 个子 Agent**：

| 任务名 | 子 Agent | 调度 | 含义 |
|---|---|---|---|
| `weekly-recruitment-summary` | recruitment | `cron 0 9 * * 1` @Asia/Shanghai | 每周一 09:00 盘点招聘进度 |
| `monthly-payroll-reminder` | performance | `cron 0 10 25 * *` @Asia/Shanghai | 每月 25 日 10:00 发薪资提醒 |
| `hr-monthly-report` | er-admin | `cron 59 23 28-31 * *` @Asia/Shanghai | 每月末 23:59 出 HR 月报 |
| `onboard-review-zhanglei-day7/30/60/90` | onboarding | `at` 四个具体日期 | 入职后 7/30/60/90 天回访 |

来源清楚：入职 review 4 个（Lesson 2-2）+ HR 月报 1 个（Lesson 2-3）+ 本集补配的周招聘汇总和月薪资提醒 2 个。

### 5.2 为什么要"总调度"，不是各管各的

任务一多，分散就出问题，主要两点：

- **不可观测**——定时任务散在各子 Agent 配置里，没有一个地方能一眼看全"这个数字员工挂着多少个自动任务、下次什么时候触发、上次跑成功没有"。哪个任务悄悄失效了，没人会发现，直到该出的报表没出来。
- **难维护**——要调触发时间、要排查报错，得先知道它在哪个子 Agent 名下。任务越多，"先找到它"的成本越高。

**可观测，是定时任务从"能跑"走向"工业级可靠"的前提。**

### 5.3 真无人值守，是一条两段式的链路

"无人值守"听起来是一件事，其实是**两段独立的链路**接起来的：

1. **定时触发**——调度器到点，把指定的子 Agent 唤醒。
2. **被唤醒的子 Agent 真能干完活**——子 Agent 醒来后，有权限、有时间、有正确的环境，把任务执行到终态。

**Cron 触发成功，不等于子 Agent 能干完活。** 这是 Lesson 2 三集 Cron 实践里反复出现的一句话。

### 5.4 第二段链路的故障地图：权限 vs 超时

Lesson 2 三集的 Cron 实践，一起拼出了第二段链路完整的故障地图：

| 故障类型 | error 信号 | 失败速度 | 修复方向 |
|---|---|---|---|
| **工具权限不对**（L2-3 月报） | `No callable tools remain after resolving explicit tool allowlist` | 立刻失败，`durationMs` 极小（实测 997 毫秒） | 给子 Agent 补上任务所需工具的权限 |
| **执行超时**（L2-4 周招聘汇总） | `... timed out` | 视超时类型而定 | 按真实耗时把 `timeoutSeconds` 调够 |

- **L2-3 月报栽在权限**：Cron 确实把行政子 Agent 唤醒了，但这个子 Agent 的 `deny` 列表拦掉了 `group:runtime`——而月报脚本要用的 `exec` 正属于这一组。**子 Agent 被叫醒了，却"手被绑住"、没有可调用的工具**，于是在工具权限解析这一步秒退。
- **L2-4 周招聘汇总栽在超时**：Cron 触发了、子 Agent 也醒了、工具权限齐全，但任务是个"读几十个文件 + 调一次大模型综合成报告"的复合任务，180 秒的超时上限定得太紧，撞线被强制中断。真实耗时约 123 秒，修复是把 `timeoutSeconds` 调到 600 秒。

**超时还要再细分**（判定一律以 `error` 字符串为准，`durationMs` 量级只能辅助）：

- **整体预算超时**（`job execution timed out`）——任务跑满 `timeoutSeconds` 才失败，`durationMs ≈ timeoutSeconds × 1000`。
- **阶段看门狗超时**（如 `setup timed out before runner start`）——在 runner 启动前或首次模型调用前就快速失败，`durationMs` 很小、并不会跑满预算。

> **别看到"`durationMs` 很小"就断定是权限问题**，它也可能是阶段看门狗超时。

### 5.5 超时估法与重试的适用边界

**超时怎么估**：让任务先真跑一次，看 `state.lastDurationMs` 或历史耗时，**按真实耗时的 2–3 倍设上限**。复合任务（读多个文件 + 调大模型综合）光大模型那一次调用就可能上百秒，`timeoutSeconds` 不能拍脑袋给小值。调到 600 而不是刚够用的 200，是**留余量**——数据目录会继续增长、大模型响应时间也有波动。

**重试治什么、不治什么**：OpenClaw Cron 有一套全局重试机制（`retryOn`，默认对 `rate_limit` / `overloaded` / `network` / `server_error` 这几类瞬时故障做带退避的重试）。但要分清——**重试对治的是"瞬时抖动型"故障**（限流、网络波动、服务端临时错误），重试一次很可能就过了；**超时型故障无脑重试只会再超时一次，治标不治本**。什么故障用什么对策，得分清。

### 5.6 时区与 croner 的两个坑

- **`--at` 和 `--cron` 的默认时区不一样，别混**：`--at` 时间戳不带时区偏移时按 **UTC** 解释；`--cron` 表达式不带 `--tz` 时，按 **Gateway 宿主机的本地时区**解释（不是 UTC）。宿主机时区不可控——本机 Mac 常是 `Asia/Shanghai`，云服务器 / VPS 上常是 UTC。**所以周期任务一律显式带 `--tz "Asia/Shanghai"`，理由是消除对宿主机时区的隐式依赖，让任务换台机器跑也不会偏。**
- **croner 的 OR 语义**：cron 表达式里"日（day-of-month）"和"周（day-of-week）"两个字段同时非通配时，croner 按"**任一匹配即触发**"（OR），不是"两个都匹配"（AND）。想要"每月 15 号且周一"，写 `0 9 15 * 1` 会变成"15 号**或**任意周一都跑"。

## §6 端到端验收：三检验方法论

### 6.1 验收一个数字员工，验的是什么

配置层面"配好了"，不等于产品层面"能上线"。「小慧」最终面对的不是配置项，是 HR 的真实工作场景。这门课从立项起锁定了 **10 个 HR 应用场景**，验收就是逐个场景去查：**它到底有没有创造真实的价值。**

判断一个场景"有价值"不能凭感觉。本课用一套固定的检验——**三检验**。一个场景要算合格，必须**同时**过三道关：

| 检验 | 问什么 | 不过会怎样 |
|---|---|---|
| **真实业务** | HR 真的会做这件事吗？它对应岗位上真实存在的痛点，不是为展示技术编出来的需求 | 这个场景是**伪需求** |
| **有价值的技术** | 解决它用的是有特色的能力吗？——而不是把一段话丢给通用大模型、套个壳就交差 | 这个场景只是**技术摆设** |
| **真实价值** | 相比人工，有能感知、能说清的提升吗？——落到具体的时间、质量或覆盖面，不是"AI 加持"这种空话 | 这个场景是**自嗨** |

**关键在"同时"两个字。** 三条里缺任意一条，这个场景就不算合格——这种情况称为**技术自嗨**：看着热闹，落地没用。

> **像一场转正答辩**：一个新员工能不能转正，看的不是简历多漂亮、入职时学了多少新工具，而是他在真实岗位上交付了什么。三检验就是答辩桌上的三个必答题——你做的是不是岗位上真实的活、你的手艺是不是真有门道、你的产出是不是真的有人用。三题全过，才算转正。

**反例：简历颜值评分。** 用视觉模型给候选人照片打分——技术上跑得通，但 HR 根本不会、也不该按长相筛人（真实业务过不去）；这个分数对招聘决策也没有任何正当价值（真实价值立不住）。这就是典型的技术自嗨：为了证明"我会用 AI"，做了一件没人要、甚至不该做的事。**工业级验收要做的，恰恰是把这类场景挡在门外。**

### 6.2 8 场景达标 + 2 场景受限

10 个场景逐个对照三检验，结论是：**8 个完整场景（1、2、4、6、7、8、9、10）三检验全过；2 个受限场景（3、5）诚实标注，不计入本集收敛标准。**

八个达标场景的"有价值的技术"和"真实价值"落到实处：

| 场景 | 用了什么有特色的技术 | 相比人工的真实提升 |
|---|---|---|
| 1 批量简历初筛 + 画像 | office 文档解析 + 敏感字段合规过滤层 + 8 维加权评分 + HTML 画像 | 批量排序把对口的人筛出来；每人一张可视化画像——画像是人工初筛根本不做的事 |
| 2 人才库语义检索 | 通义 embedding 向量化 + 手写向量（余弦）语义检索 + 维度级可解释 | 88 毫秒出 Top 5 相似候选人——"找相似的人"是关键词搜索做不到的能力 |
| 4 面试纪要自动生成 | faster-whisper 转写 + 基频聚类说话人分离 + LLM 结构化 + 数字回核 | 录音自动转成按发言人组织的纪要；人工逐句整理要 1–2 小时 |
| 6 新员工入职全流程跟进 | Lobster HiTL 工作流 + 多路并行 + Cron 定时 review | 多部门准备并行不漏；30/60/90 天 review 靠 Cron 自动触发、不靠人记 |
| 7 培训物料一键生成 | LLM task + ADDIE 五阶段 Pipeline 编排 | 一次跑完产出 8 类物料全套；人工备一套要 1–2 天 |
| 8 绩效 360 反馈聚合 | 多源聚合 + LLM 区分共识与分歧 + HTML 雷达可视化 | 多视角反馈自动聚合、共识分歧分开摆；人工汇总做图表几小时起步 |
| 9 HR Helpdesk 智能答疑 | 政策知识库检索（本仓现行为腾讯 IMA；课程版本为 Memory RAG）+ HiTL 升级 | 7×24 即时答疑、引用政策原文出处可追溯；复杂敏感问题升级真人 |
| 10 HR 月报自动生成 | Cron 定时触发 + pandas 算指标 + HTML 图文 + 数字回核 | 月底自动生成图文月报、每个数字可追溯到源数据；人工拉数据做月报要半天到一天 |

**每一行的技术列都不是"调了个大模型"**——是体系里有特色的能力（Lobster HiTL 工作流、知识库检索、Cron、说话人分离、合规过滤层）；**每一行的价值列都落到了具体的动作和对比**，不是"效率提升 X 倍"这种话术。

> **两个场景的价值边界要特别留意**：场景 1 的评分、场景 8 的绩效聚合，**AI 都只给建议、不做决定**——评分给"建议进入面试名单"不给"录用 / 淘汰"，绩效聚合给面谈输入材料不给 S/A/B/C/D 评级。这不是能力不够，是合规红线（《个人信息保护法》第 24 条）。所以这两个场景的"真实价值"体现在"**把功课做到极致**"（筛得准、聚合得全），而不是"替 HR 拍板"。**一个越过这条线的场景，哪怕技术再漂亮，三检验里也过不了——它创造的不是真实价值，是法律风险。**

### 6.3 受限场景：诚实标注 vs 凑数

场景 3（面试安排协调）和场景 5（候选人 7×24 对话答疑），**真实业务这一关是过的**，卡住的是后两关：

- **场景 3**：核心价值在于查多个面试官和候选人的忙闲、自动约会议，这要接真实的日历系统。本集没接，做不出这个价值。
- **场景 5**：核心价值在于候选人能随时找到一个对话入口，这要接一个面向候选人的 channel。本集没接，候选人无从触达。

把它们做成达标，技术上有个很省事的办法——用本地脚本造一段假的"忙闲数据"、假的"候选人对话"，让脚本跑通，评级表上凑两个绿，10 个场景全绿。**本集没有这么做。**

| | 凑数 | 诚实标注 |
|---|---|---|
| 做法 | 用假数据让受限场景跑通，评级凑成达标 | 受限场景如实标"受限"，写明卡在哪、留哪集 |
| 验收表 | 10 个全绿，好看 | 8 绿 2 黄，不好看 |
| 拿去用 | 照搭发现跑不通，被误导 | 知道哪些现在能用、哪些要等下集 |
| 本质 | 把"演示"包装成"落地" | 区分清楚"已落地"和"待落地" |

**理由是：凑出来的绿会误导使用者。** 验收表的价值在于它说真话；说一次假话，整张表就不能信了。诚实标注吃亏在验收表不好看，但**工业级和"演示级"的本质区别恰恰在这里**：演示级的目标是让人当场觉得"哇全做完了"；工业级的目标是让人能照着把系统真的搭起来、用起来。后者要求每一个状态标注都说真话——**包括如实承认"这两个还没做完"。诚实标注受限场景，是工业级的一条真实纪律，不是认怂。**

### 6.4 三检验 vs 技术质量评估：互补，不是替代

验收一个 Agent 系统，三检验不是唯一思路。先看两个偷懒的方法：

- **数功能数量法**——"我做了 10 个功能"。**数量不等于价值**，10 个技术自嗨场景数出来也是 10。
- **"能跑就算"法**——脚本跑通不报错就算过。**跑通不等于有价值**，"简历颜值评分"的脚本也能跑得通。

市面上真正主流的是第三种——**技术质量评估**：构造测试集，算任务成功率、准确率、召回率、响应延迟，再做轨迹分析、红队测试。业界成熟的 Agent 评估框架大多围绕这套指标展开，它是严肃、有用的方法。那为什么还要三检验？

| | 技术质量评估 | 三检验 |
|---|---|---|
| 回答的问题 | 这个场景**做得好不好**（准不准、快不快、稳不稳） | 这个场景**该不该做**、对 HR 有没有价值 |
| 前提假设 | 默认这个场景值得做 | 不预设——"真实业务"这一关专门质疑它 |
| 挡得住技术自嗨吗 | 挡不住——"简历颜值评分"的准确率也可能很漂亮 | 挡得住——它在"真实业务""真实价值"两关上现形 |

**一个完整的 Agent 验收，应该是三检验先筛掉自嗨场景，技术质量评估再把留下的场景做到位——两者各管一段。**

### 6.5 收敛达标与四条边界

达标的同时，有几条边界要诚实交代，避免误判「小慧」现在的能力：

1. **三检验是定性框架，不是定量打分。** 它判"过 / 不过"，不给"打几分""提效百分之多少"。这是有意的——价值很难精确量化，硬塞一个百分比本身就是另一种自嗨。**能说清"具体快在哪、好在哪、覆盖到了什么"，比一个虚的百分比可信。**
2. **8 场景达标是"本地化范围内"达标。** 真实渠道接入、与真实 IT / 日历 / 薪资系统对接、生产环境的故障演练和监控告警，都留到下一阶段。
3. **部分场景用的是构造数据。** 绩效 360 用模拟反馈、月报用构造的 6 个月 CSV——验证的是 Pipeline 和能力本身，真实生产要换成企业自己的历史数据。
4. **受限场景的完整价值要到下集验收。**

## §7 业界对位三层：编排库 vs 运行时平台

### 7.1 第一层：基线——多 Agent 编排能力本身

把一个请求分发给多个 Agent、让它们协作，这个能力到 2026 年**已经是多 Agent 框架的入场券，不是亮点**：

- **OpenAI Agents SDK**——OpenAI 2024 年 10 月发布过实验性框架 Swarm（README 明确标注"不用于生产"），2025 年 3 月用 Agents SDK 取代；截至 2026 年 5 月是 production-ready 的活跃项目（Python 与 TypeScript 双版本）。多 Agent 编排核心是 **handoffs**——一个 Agent 把控制权交接给另一个。
- **LangGraph**——LangChain 团队的编排框架，2026 年已到 1.x。把多 Agent 系统建模成一张图（StateGraph）：节点是 Agent 或函数，边定义数据怎么流动，内置 checkpointing、`interrupt()` 人工介入、并行 fan-out。
- **Microsoft Agent Framework**——微软把 AutoGen 和 Semantic Kernel 合并的产物，2026 年 4 月发布 1.0（AutoGen 已转入维护模式）。提供图结构工作流编排加 middleware 管线。

**这一层要诚实：多 Agent 编排不是 OpenClaw 的独创，上面三个框架都做到了。基线必须扎实，否则后面谈差异化没有意义。**

### 7.2 第二层：差异化——编排库 vs 运行时平台

真正拉开差距的不是"有没有多 Agent 编排"，是**它以什么形态存在**。上面三个框架都是**编排库**——你把它装进自己的工程，自己负责运行环境。OpenClaw 是一个**运行时平台**——编排只是它的一部分，权限、调度、Channel 接入这些运行时能力是平台自带的。

| 维度 | OpenAI Agents SDK | LangGraph | Microsoft Agent Framework | 小慧（OpenClaw） |
|---|---|---|---|---|
| 形态 | 编排库（Python / TS） | 编排库（Python / JS） | 编排库（.NET / Python） | **运行时平台** |
| 多 Agent 编排 | handoffs 交接控制权 | StateGraph 图：节点 + 边 | 图结构工作流 + middleware | Multi-Agent Routing：LLM 判断 + `sessions_spawn` |
| 运行时 HiTL | guardrails + 审批回调 | `interrupt()` 暂停 / resume | middleware + 审批 | Lobster 审批门 halt / resume |
| **按身份分权（Per-Sender）** | 框架不内置，自行实现 | 框架不内置，自行实现 | 框架不内置，自行实现 | **运行时原生 `tools.toolsBySender`** |
| **定时调度** | 不含，配外部 scheduler | 库不含，依赖 LangGraph Platform | 不含，配外部 scheduler | **运行时原生 `openclaw cron`** |

**差异化集中在下半部两行。** 按发送者身份分档的工具权限，是 OpenClaw 运行时原生的一项配置；在编排库里要做出等价能力，得自己在 Agent 外面包一层身份鉴权 + 工具门控，没有现成开关。定时调度同理。

**所以小慧的差异化是定位上的**：不是"编排做得比 LangGraph 好"，而是"它是一个把编排 + 权限分级 + 定时调度 + Channel 接入装在一起的运行时平台"。

> **把话说全**：运行时平台这一类并不只有 OpenClaw——IBM watsonx Orchestrate、n8n 等也是平台形态。OpenClaw 在这一类里的具体位置是——**自托管、开源、面向企业内部数字员工**：编排逻辑、权限策略、Cron 配置全在自己手里，可改、可审计，这是商业托管平台给不了的。

### 7.3 第三层：要警惕的两类营销话术

| 话术 | 它许诺什么 | 真实情况 | 对位本集哪个设计 |
|---|---|---|---|
| **"一个 Agent 跨领域全包"** | 一个超级 Agent 把招聘、入职、绩效、答疑全包了，不用搞多 Agent 那么复杂 | 多职能塞进一个 Agent，persona 越写越长、领域边界互相干扰、难维护，更没法按领域分级权限。**Router 越界自答，本质就是"一个 Agent 想多管"的副产物** | §2 把五个领域拆成五个子 Agent，router 只调度不办事——拆开才管得住 |
| **"AI Agent 全自动"** | Agent 端到端全自动跑完，人完全不用管 | 工业级 HR 场景里，绩效定级、Offer 发放、合同解除必须有人在回路；不同身份能用的能力必须分级；每个决策必须留审计日志。**"全自动"省掉的每一步，上线后都要还** | §4 三档权限隔离、Lobster 审批门、§8 合规叠加，都是"不全自动"的工程落实 |

> **第一类要特别说清一层，免得对位失准："单 Agent 架构"本身不是话术。** 它是 2026 年 AI 工程界一场严肃架构辩论的一方——Cognition 团队 2025 年的《Don't Build Multi-Agents》就有扎实的工程理由主张默认用单 Agent（上下文共享、更易调试；多 Agent 在传递上下文时容易丢信息），Anthropic 则用研究型任务为多 Agent 辩护。**要警惕的话术是更具体的一句——"一个 Agent 就能把招聘、入职、绩效、答疑这些领域全包了"。** 单 Agent 适合边界清晰、上下文需紧密共享的任务；而 HR 这五个领域边界各异、persona 互相干扰，硬塞进一个 Agent 正是越界自答的同类病根。

### 7.4 实用建议：什么时候用编排库，什么时候用运行时平台

- **要把多 Agent 编排嵌进一个已有的服务、需要跨多个 LLM provider、看重生态与社区规模**——选**编排库**。LangGraph 是 2026 年行业落地最广的一个，图结构的确定性、checkpointing、可视化调试都很成熟。
- **要的是一个企业内部的数字员工——要按员工身份分级、要定时无人值守、后面还要接 IM Channel**——**运行时平台**更省事。本集的 Router + Per-Sender + Cron + 端到端验收，就是这条路线的完整骨架。

> **诚实的局限**：其一，OpenClaw 的路由是 **LLM 判断**——越界自答正是要付的代价，必须靠 `SOUL.md` 调优去兜（这个权衡与 OpenAI Agents SDK 的 handoffs 共有；真正提供"确定性"这一额外选项的是 LangGraph 的**静态图边**）。其二，OpenClaw 的生态与社区规模不及 LangGraph 这类已被行业广泛采用的框架。其三，本集只做到本地编排，Channel 接入、故障演练、监控告警、灰度发布留到下一阶段。**把 OpenClaw 说成"全面优于编排库"是不诚实的。**

## §8 编排层的合规叠加：四个复验点

### 8.1 一条容易被忽略的原则：编排层是新的合规风险面

**编排层的合规，不是各子 Agent 合规的简单相加。**

直觉上会觉得——五个子 Agent 每个都验过合规了，用 Router 串起来合规自然也就齐了。但 §3 已经给过一个明确的反例：**Router 会越界自答。** 员工问"年假一年有几天"，Router 用通用知识自己答了，根本没路由给 `er-admin`。这意味着——`er-admin` 辛苦做的政策检索、引用出处、HiTL 升级红线，**被 Router 这一层悄悄绕过了**。子 Agent 那一层的合规设计还在，但**请求根本没走到它**。

这就是编排层的特殊性：**它在五个子 Agent 之上引入了一个新的决策点（Router），也就引入了一个新的合规风险面。** 所以本集的合规不是"再讲一遍前三集"，而是一次**端到端的合规复验**——把前三集分散落实的合规措施，在编排完成之后整体走一遍，确认编排层没有把它们漏掉。

### 8.2 四大合规叠加

**叠加一 · 审计日志全链路落盘。** 诊断插件采集指标与链路，bundled hooks 中的 `command-logger` 记录命令日志。每条审计记录回答五个问题：**谁、何时、做了什么、依据什么、结果是什么**。编排层要确认的是：请求从 Router 分发到子 Agent 再回流，这条**跨 Agent 的链路全程在日志里**——核对路由对不对靠的就是 router session 文件里 `sessions_spawn` 调用的 `agentId` 和 `childSessionKey`，这些底层记录本身就是审计链路的一部分。**为什么不能省**：《个人信息保护法》第 24 条要求自动化决策可追溯、可解释，没有全链路审计日志，「小慧」就回答不了"这个结果是怎么来的"。

**叠加二 · HiTL 端到端实测可用。** HiTL 在前三集每一集都验过：招聘评分只给"建议动作"、最终淘汰人工定；入职 Lobster 有合同、账号两道审批门；绩效 360 不出评级；HR Helpdesk 敏感问题升级人工。编排层要确认的是：**经过 Router 分发之后，这些审批门、升级红线还停得住**——Router 不能因为"想快一点"就跳过子 Agent 的审批环节。

> **一个有技术背景的人会追问的边界**：Router 正确路由之后，HiTL 卡点为什么必然守得住？**因为 Lobster 审批门（halt / resume）写死在子 Agent 的工作流文件里、`SOUL.md` 的升级红线也是写死的明文守则；Router 通过 `sessions_spawn` 传给子 Agent 的是用户的原始需求，它无权改写子 Agent 的流程定义。** 所以只要请求落到子 Agent，卡点就由子 Agent 自己的工作流保证。叠加二由此闭环——既验"请求别被 Router 拦在半路"，也确认"请求落地后卡点仍在"。

**叠加三 · 三档权限端到端隔离。** 按身份分级不是功能优化，**是数据最小化原则的落地**。为什么这条在编排层才算数：单个子 Agent 上配权限意义有限，**只有当五个子 Agent 都收在一个 Router 入口后面、权限在这个统一入口上分档，"按身份隔离"才真正覆盖整个数字员工**。

**叠加四 · 受限场景诚实标注。** 把它列进合规叠加，是因为"**不掩盖能力边界**"也是工业级真实纪律的一部分：把"还没做到"包装成"已经做到"，本质上是一种对使用方的误导。**一个会对自己边界诚实的数字员工，比一个什么都说"能"的数字员工更可信。**

### 8.3 为什么不能省：两种替代做法的漏洞

**替代做法 A：合规完全交给各子 Agent，编排层不管。** 漏洞有两个，都不在任何单个子 Agent 内部、只在编排层暴露：其一，Router 越界自答会绕过子 Agent 的全部合规设计，而 Router 不管合规就发现不了；其二，Per-Sender 的 `*` 兜底如果配错（实验记录里就撞到过兜底一度停在 `allow:["*"]`），意味着任何未登记的陌生身份都能拿到全套工具，整个权限分级漏了底。**编排层不复验，它们就没人管。**

**替代做法 B：编排层加一道框架级 guardrail 统一拦。** 这一层有用，但**框架级 guardrail 是通用校验，拦不住领域级问题**——它拦不住"360 报告某个章节标题写成'绩效结论'导致定位漂移"，也拦不住"Router 用通用知识把公司年假政策答错"。**领域级的合规问题，只有领域级的工程落实能拦。**

**本集的做法**：编排层做一次端到端的合规叠加复验。它**不替代**子 Agent 各自的合规设计，而是在它们之上补一道"**编排没把它们漏掉**"的确认。

### 8.4 法律依据

| 法律 / 案例 | 与编排层合规的关系 |
|---|---|
| 《个人信息保护法》第 24 条 | 通过自动化决策方式作出对个人权益有重大影响的决定，个人有权要求说明、并有权拒绝仅由算法作出的决定。「小慧」处理简历、绩效、薪资咨询，全程不替人做定级 / 淘汰 / 裁断——**叠加二、叠加三正是这一条的工程落实** |
| 《互联网信息服务算法推荐管理规定》（2022 年 3 月施行） | 要求算法决策透明、用户对算法有拒绝权。**需要界定清楚**：这部规定主要规制面向公众提供互联网信息服务的算法推荐，企业内部 HR 系统是否落入其规制范围要视具体形态而定——直接套到企业内部 HR Agent 上属于**过度引用**。但其"算法透明、可拒绝"原则已被个保法第 24 条吸收，作为设计准则同样成立 |
| 《就业促进法》 | 明确禁止基于民族、种族、性别、宗教信仰的就业歧视；地域、年龄等也是反就业歧视政策持续关注的方向。招聘子 Agent 的合规过滤层剥离敏感字段、评分不下淘汰决定，对接的就是这条 |
| Mobley v. Workday（美国 AI 招聘歧视案） | 2024 年 7 月法院驳回 Workday 的撤案动议，认定 AI 招聘工具的提供方可能作为"代理人"承担反歧视责任；2025 年 5 月法院批准该案以 ADEA 集体诉讼形式推进，基于"差别性影响"理论，覆盖 40 岁以上经该平台被拒的求职者。**它印证的是：AI 招聘 / 评估工具一旦对受保护群体产生系统性不利影响，提供方与使用方都要担责**——这正是"AI 只建议、人来定夺"必须守住的现实原因 |

### 8.5 诚实的局限：合规边界会变

一个正在发生的例子：欧盟《人工智能法案》把招聘、绩效评估、晋升 / 解雇等就业类 AI 列为**高风险系统**，强制要求人工监督、透明、可追溯日志。这套高风险义务原定 2026 年 8 月生效，又经 2026 年 5 月的"Digital Omnibus"政治协议推迟到 2027 年 12 月（该推迟为欧盟理事会与议会达成的临时协议，尚待两院正式表决）——一年多里时间表反复变动。国内这边，修订后的《网络安全法》2026 年 1 月施行、新增了人工智能专门条款，工信部等十部门也印发了《人工智能科技伦理审查与服务办法（试行）》。

**这意味着：本集教的不是一套"一次写好永远合规"的代码，是一种把合规红线工程化、并在编排层端到端复验的方法。法律怎么变，"编排层要重新验一遍子 Agent 的合规有没有被漏掉"这个动作不变。**

## 附录 A：贯穿编排层的工程纪律

1. **Router 只调度不办事**——判断准、转得对、不抢答。克制比能力更重要。
2. **ID 逐字一致**——路由表里的子 Agent ID 必须和实际注册的 Agent ID 完全一致，写 `SOUL.md` 前先用 `agents list` 核对。
3. **配路由认准 `subagents.allowAgents`**——别被 `tools.agentToAgent` 的名字骗了。
4. **星型拓扑要写死三层**——`defaults.allowAgents: []` + 叶子显式 `[]` + 只给 Router 开业务白名单；并开 `requireAgentId: true`（§2.7）。
5. **`delegationMode: prefer` 只给 Router**——不要写进 `agents.defaults`，否则业务子 Agent 会被推着乱 spawn（§3.8）。
6. **`prefer` 不能替代 SOUL 硬红线**——它是 Prompt-only，仍挡不住无工具直答。
7. **验收要专门验"会不会越界"**——查 `TOOLS` 字段，`TOOLS: None` 就是越界自答的硬信号。
8. **persona 调优针对具体问题**——哪里出问题改哪里，不要顺手大改已经正确的部分。
9. **白名单 + 默认拒绝**——生产上 `*` 兜底必须是 `deny:["*"]`（比赛演示可临时 `allow:["*"]`，赛后改回）。三档 sender key 用飞书 `id:ou_xxx`，不用 `name:`。
10. **为验证临时放开的安全配置，做完必须立即收回**——验证命令和恢复命令要绑在一起写。
11. **改配置前先备份**——数组元素用带下标的路径精确写入，不要整体替换数组（会冲掉其他 Agent 的配置）。
12. **Cron 超时按真实耗时的 2–3 倍设**——先真跑一次看 `lastDurationMs`，不要拍脑袋。
13. **周期任务一律显式带 `--tz`**——消除对宿主机时区的隐式依赖。
14. **故障判定以 `error` 字符串为准**——`durationMs` 量级只能辅助。
15. **受限场景诚实标注，不用假数据凑绿**——验收表说一次假话，整张表就不能信。
16. **能力边界要写清楚**——工具层分权不等于数据层分权；分档只用飞书 `id:`，不用可伪造的 `name:`。

## 附录 B：术语速查表

| 术语 | 含义 |
|---|---|
| **总控 Router** | 五个业务子 Agent 的统一入口，只做判断领域 / 分发请求 / 汇总结果三件事。职责上更接近业界的 Supervisor 模式 |
| **`sessions_spawn`** | 新起一个子 Agent 运行来处理任务的工具，Router 分发请求用的就是它。相当于业界多 Agent 框架里的 handoff / 任务委派 |
| **`sessions_send`** | 往一个已存在的活跃会话里追发消息的工具，续接已有对话时用 |
| **`subagents.allowAgents`** | 某个 Agent 用 `sessions_spawn` 时能 spawn 到哪些目标 Agent 的白名单。**跨 Agent 路由唯一的关卡**；不配时默认只允许 spawn 自己；显式 `[]` = 谁都不能 spawn |
| **`subagents.delegationMode`** | 委派强度：`suggest`（默认）/ `prefer`（强引导 spawn）。**Prompt-only**，不是工具权限，也不是 forced tool call。本仓仅 Router 设为 `prefer` |
| **`requireAgentId`** | `agents.defaults.subagents` 下的开关；`true` 时 spawn 必须显式带目标 Agent ID，不允许隐式默认 |
| **`tools.agentToAgent`** | 跨 Agent 直接消息（`sessions_send`）的开关与白名单。名字相近，**不是路由关卡** |
| **星型路由拓扑** | `defaults.allowAgents: []` + 叶子显式 `[]` + 只给 Router 开业务白名单——所有调度从 Router 出发，子 Agent 之间不互调 |
| **越界自答** | Router 绕过子 Agent、用大模型通用知识直接回答业务问题。**不报错**，硬信号是会话统计里的 `TOOLS: None` |
| **SOUL 调优** | LLM Agent 的"调试"方式：实测 → 发现行为偏差 → 改 persona 指引 → 再测。改的是 `SOUL.md`，不是代码 |
| **Per-Sender Tool Policy** | 按"发消息的人是谁"给工具权限的机制，配置在 `tools.toolsBySender` |
| **Per-Agent policy** | 按"哪个子 Agent 在办"给工具权限，配置在 `agents.list[].tools` |
| **sender key** | 发送者标识，六类从精确到宽松：`channel:` / `id:` / `e164:` / `username:` / `name:` / `*`。本课三档用 `id:ou_xxx`。先命中先用 |
| **兜底档（`*`）** | 匹配不到任何登记 key 的身份走这一档；生产必须 `deny:["*"]`（演示可临时 allow）。**兜的是"陌生人"，兜不了"冒充者"** |
| **飞书 `id:ou_xxx`** | 本课三档采用的 sender key；平台分配、不可靠改显示名伪造。Web/TUI 不注入时落 `*` |
| **纵深防御（defense-in-depth）** | 窄白名单档里的 `deny` 是冗余加固，防止日后 allow 被放宽时还有第二道闸 |
| **profile 注册门控** | 双层权限模型之外的隐藏第三层——工具有没有被注册进当前环境。验证分权时要绕开这类工具 |
| **两段式链路** | 无人值守 = 定时触发（第一段）+ 被唤醒的子 Agent 真能干完活（第二段）。**触发成功 ≠ 能干完活** |
| **整体预算超时 / 阶段看门狗超时** | 前者跑满 `timeoutSeconds` 才失败；后者在 runner 启动前就快速失败、`durationMs` 很小 |
| **三检验** | 真实业务 / 有价值的技术 / 真实价值，**必须同时过**。缺任意一条即"技术自嗨" |
| **技术自嗨** | 看着热闹、落地没用的场景。典型反例：简历颜值评分 |
| **受限场景诚实标注** | 卡在依赖上的场景如实标"受限"、写清卡在哪，不用假数据凑成达标 |
| **编排层合规叠加** | 编排完成后对四个合规点（审计日志 / HiTL / 权限隔离 / 诚实标注）做一次端到端复验 |
