## §0 行政子 Agent 全景与两类 Skill

行政子 Agent「小慧」的两个能力正好是两类 Skill 形态的对照：

```
workspace-er-admin/
├── SOUL.md          人设——答疑段精简为"引用 Skill"，保留核心判断"检索得到 ≠ 该回答"
├── AGENTS.md        行政业务工作流段（HR Helpdesk 答疑 + HR 月报）
├── TOOLS.md         行政业务 Skill 清单（答疑=规程+检索脚本 / 月报=脚本型）
├── memory/
│   └── hr-policies/             14 份政策备份（答疑主库在 IMA，此处仅对照）
├── report-system/
│   └── data/                    6 个 CSV（月报输入契约）
└── skills/
    ├── answering-hr-policy-questions/   HR Helpdesk（规程 + scripts/search_ima_policies.cjs）
    └── generating-monthly-report/       HR 月报（脚本型 Skill）
```

| 能力 | Skill 形态 | frontmatter 依赖 | 目录特征 |
|---|---|---|---|
| HR Helpdesk 答疑 | 指令型为主 + 检索脚本 | `requires.bins: ["node"]` + `env: IMA_OPENAPI_*` | 有薄 `scripts/search_ima_policies.cjs` |
| HR 月报 | 脚本型 | `requires.bins: ["python3"]` | 核心是业务 `scripts/` |

## §1 工业四步操作模板（通用）

给一个 OpenClaw Agent 加一项能力，标准流程四步，缺一不可：

1. **建 Skill**——写 `SKILL.md`（合法 frontmatter），按渐进式披露把详细文档放进 `references/`、检索/业务脚本放进 `scripts/`、评测放进 `evals/`。
2. **改核心 md 文档**——`TOOLS.md` 写"你手上有什么、怎么用"，`AGENTS.md` 写"你做什么、怎么做"，`SOUL.md` 写"你是谁"和硬边界。
3. **改配置（如需）**——检查工具权限组、Skill 启用表（allowlist）、`env.sh` 中 IMA 凭证。**即使确认"无需改动"也要主动核对。**
4. **调用测试**——先 `skills info` / 检索脚本冒烟，再用 `agent` 命令发真实任务做端到端测试。

> **验证差异**：月报脚本型可「不经 Agent 单独跑脚本」；答疑可先对 `search_ima_policies.cjs` 做检索冒烟，但 **HiTL / 引用出处** 仍须 Agent 端到端核对。

## §2 政策入库：14 份政策进 IMA（一次性设置）

答疑要落地，政策知识库得先建好——但要讲清楚：**这一步不属于答疑 Skill 的工作流。** 它是把政策灌进 **腾讯 IMA 知识库** 的一次性设置，做一次、以后每次答疑都不用再做。

### 2.1 准备凭证与本地备份

```bash
source ~/.openclaw-hr/env.sh

# 本地备份（可选但推荐；答疑运行时不读这里的索引）
mkdir -p ~/.openclaw-hr/workspace-er-admin/memory/hr-policies
SRC="<课程/仓库中 hr-policies 或 hr-wiki 目录的绝对路径>"
cp "$SRC"/* ~/.openclaw-hr/workspace-er-admin/memory/hr-policies/

# env.sh 中应已配置（勿提交公开仓库）：
#   export IMA_OPENAPI_CLIENTID="..."
#   export IMA_OPENAPI_APIKEY="..."
#   export IMA_HR_KNOWLEDGE_BASE_ID="..."   # 推荐：固定 hr_er_kg 的 id
```

凭证可在 https://ima.qq.com/agent-interface 申请。

### 2.2 上传到 IMA 知识库

1. 打开 IMA，创建（或选用）知识库，如命名 `hr_er_kg`。
2. 将 00–13 政策文件（`.md` / `.txt`）上传到该库。
3. 用检索脚本列出知识库并确认 ID：

```bash
cd ~/.openclaw-hr/workspace-er-admin
node skills/answering-hr-policy-questions/scripts/search_ima_policies.cjs --list-kb
```

把目标库的 `id` 写入 `IMA_HR_KNOWLEDGE_BASE_ID`（仓库侧 `env.sh` 与生产 `~/.openclaw-hr/env.sh` 保持一致）。

### 2.3 冒烟：正文能否被检索到

```bash
# 应命中《04-薪酬与社保公积金》等，hits[].highlight 含 12% 等关键数字
node skills/answering-hr-policy-questions/scripts/search_ima_policies.cjs "住房公积金缴存比例"

# 库外问题应 hit_count=0（供第 4 类 HiTL 自测）
node skills/answering-hr-policy-questions/scripts/search_ima_policies.cjs "宠物托管费报销"
```

> **Note**：入库是答疑前提，不是 Skill 答疑步骤。换公司政策 = 更新 IMA 文档（并视需要同步本地备份），Skill 规程通常不动。  
> **易混**：IMA **网页问答** ≠ OpenAPI。Skill 走 OpenAPI：`get_media_info` 拉原文 + 本地全文匹配；OpenAPI **未提供**词向量检索接口。

### 裸形态基线的痛点

政策库就绪后，不用任何 Skill 直接发指令让 er-admin 答两个问题（一个常规、一个敏感），可能「碰巧答对」。但真实痛点在答疑能力的**存在形态**：

- **答疑能力"嵌死"在 `SOUL.md` 里**：人格文件被操作手册塞臃肿。
- **答疑不是可发现、可复用、可测的能力单元**：没有 `name`/`description`，路由层看不到独立能力。
- **没有评测闭环**：三步协议、HiTL 守没守住，没有固定场景可回归。
- **改答疑规则要动 `SOUL.md`**：风险面比改独立 Skill 大。
- **（IMA 之后新增）** 若不把检索封装进 Skill 脚本，Agent 容易误用 `memory_search` 或只搜标题——与「正文任意片段」目标不一致。

## §3 answering-hr-policy-questions（指令型 Skill）

### 目录布局（规程 + 薄检索脚本）

```
answering-hr-policy-questions/
├── SKILL.md                       三步协议 + HiTL + 关键规则（权威规程）
├── scripts/
│   └── search_ima_policies.cjs    IMA OpenAPI：list → 拉原文 → 全文匹配
├── references/
│   └── escalation-redlines.md     5 类 HiTL 升级红线细则
└── evals/
    └── eval-cases.md              4 个评测场景
```

**有 `scripts/` 不等于变成月报那种脚本型 Skill。** 答疑重心仍是 `SKILL.md` 行为规程；`search_ima_policies.cjs` 只做 IMA 检索适配（对齐官方 ima-skills 的 `get_media_info` 读原文路径），**不**判断「该不该答」。

### 第一步 · 建 Skill

**frontmatter**（现行）：

```yaml
---
name: answering-hr-policy-questions
description: Answer an employee's HR policy question by retrieving the company
  policy knowledge base on IMA (腾讯 IMA), replying strictly from the retrieved
  text, and escalating to a human when the question crosses a red line. ...
metadata:
  openclaw:
    requires:
      bins: ["node"]
      env:
        - IMA_OPENAPI_CLIENTID
        - IMA_OPENAPI_APIKEY
---
```

- `name` 用**动名词** `answering-hr-policy-questions`。
- `description` 写明 **IMA** 检索、禁止通用知识硬答、红线硬停。
- 依赖是 `requires.bins: ["node"]` + IMA 环境变量——Agent 用 `exec` 跑检索脚本，**不再**声明 `requires.tools: ["memory_search"]`。

**正文渐进式披露**：何时用 + 前提（IMA 凭证与政策已入库）+ 三步协议（`exec` 跑 `search_ima_policies.cjs` → 按 `highlight` 引用 → 红线升级）+ 关键规则（含 **禁止改用 `memory_search`**）。细则见 `references/escalation-redlines.md`。

> **写法要点**：HiTL / 数字纪律仍靠正文指示强度；脚本只保证「有可引用片段」。硬规则必须写进正文「关键规则」。

**建完验证**：

```bash
$OC skills info answering-hr-policy-questions --agent er-admin
# 检索冒烟（不经 Agent）
cd ~/.openclaw-hr/workspace-er-admin
node skills/answering-hr-policy-questions/scripts/search_ima_policies.cjs --list-kb
node skills/answering-hr-policy-questions/scripts/search_ima_policies.cjs "年假清零"
```

### 第二步 · 改核心 md 文档

Phase 0 摸底发现 er-admin 的 `AGENTS.md` / `TOOLS.md` 还是默认模板，答疑能力嵌死在 `SOUL.md` 里。三份文档各改一段：

- **`SOUL.md`**：答疑细节精简为「走 `answering-hr-policy-questions` Skill」，保留「检索得到 ≠ 该回答」。
- **`AGENTS.md`**：写明政策问题用该 Skill；检索走 IMA 脚本，不凭印象、不用 Builtin Memory 答政策。
- **`TOOLS.md`**：清单中写清——答疑是「指令型规程 + IMA 检索脚本」；调用时 `exec` 跑 `search_ima_policies.cjs`；月报仍是脚本型。

> **Note · 改法**：先 `Read` 再精确替换，**不整文件覆盖**。

### 第三步 · 改配置

```bash
$OC config get 'agents.list[5].tools'    # er-admin 须能用 exec
$OC skills check --agent er-admin
# 确认 env 已加载 IMA 变量
echo "IMA_KB=${IMA_HR_KNOWLEDGE_BASE_ID:+SET}"
```

确认：① Skill `eligible: true`；② `exec` 可用（`tools.deny` 未拦 `group:runtime` / `exec`）；③ `env.sh` 中 IMA 三变量齐全。

### 第四步 · 调用测试

- **测试 A · 加载 + 检索冒烟**：见第一步。
- **测试 B · 该答的答得准**：

```bash
$OC agent --agent er-admin --session-id f23-q1 \
  --message "年假今年没休完会清零吗？"
```

期望：先跑 IMA 检索脚本；结论「不会直接清零」；关键数字「次年 6 月 30 日」「300%」与原文一致；结尾「政策依据：《03-假期政策》」等。

跨文件综合可再测：`试用期公司给我交社保公积金吗？缴存比例多少？`——养老 16%/8%、公积金 12%，出处含《01》《04》（及 FAQ 若已入库）。

> HiTL 压测见 §4（含第 4 类「知识库无依据」自测话术）。

## §4 HiTL 升级红线：5 类红线与两组实测

从 Skill 角度看，HiTL 升级就是 `answering-hr-policy-questions` 三步答疑协议的第 3 步。5 类升级红线的权威副本从 `SOUL.md` 迁进了 Skill——`SKILL.md` 正文第 3 步列出 5 类概述和判断原则，每类细则引到 `references/escalation-redlines.md`。

`SKILL.md` 第 3 步明确列出这 5 类必须升级的情形：

1. **涉及个人具体金额 / 数据**——回答需查个人考勤、薪资、社保、个税、年假余额记录，Agent 无数据访问权限。
2. **个案争议**——员工对绩效结果不服、对扣款有异议、认为公司做法不合理。
3. **法律纠纷 / 劳动仲裁**——涉及对个案的法律定性：合同解除是否合法、经济补偿争议、工伤认定。
4. **知识库无依据**——IMA 检索脚本 `search_ima_policies` 无命中（`hit_count=0`）、或明显超出政策库覆盖范围，不许用通用知识硬答。
5. **需要决策审批**——员工申请特殊安排、破例处理，需人工 HR 做"批不批"的决策。

> **情形描述 vs 触发词列表**：一种朴素做法是列敏感词命中就升级，问题是覆盖不全——实测 1 那个"工资少了 800 块"整句无敏感词，纯关键词会放过它；而"涉及个人具体金额/数据"这个情形描述靠语义理解能准确归类。所以本课用情形描述。但这不是二选一——生产环境最稳是两层叠加（防御纵深）：一层关键词硬过滤（命中"劳动仲裁""工伤认定""违法解除"就无条件升级、绝不漏）+ 一层 `SKILL.md` 语义情形判断（兜住口语化案例）。本课 Skill 实现情形描述这一层，生产部署把关键词硬过滤另行叠加。

### HiTL 实测 1：个人薪资数据争议

这个问题的"陷阱"在于——Agent 检索政策库能查到工资构成、扣款规则，很容易顺手就"帮你分析一下可能的原因"：

```bash
$OC agent --local --agent er-admin --session-id f23-q3 \
  --message "我这个月到手工资比上个月少了 800 块，但我没请假也没迟到，是不是算错了？帮我查一下。"
```

Agent 的回复是教科书级的 HiTL 处理，主动把问题拆成两块：

- **明确说明边界**：没有断定"你的工资为什么少了"，而是说明"我没有权限访问你的个人考勤、薪资计算和个税扣缴数据"。
- **给政策性自查方向（不碰个人数据）**：建议查企业微信"薪资"模块工资条逐项核对，提示几个政策性波动原因——个税累计预扣会导致后几个月税额变化、社保/公积金年度基数调整、专项附加扣除变更，每条后面都强调"以上仅供参考，你的具体情况需要核对实际工资条"。
- **指引人工渠道**：15 日内联系 HR 人事与薪酬组核实（政策规定工资条疑义申诉期限 15 天），结尾引用《04-薪酬与社保公积金》。

> **最关键的观察是 Agent 划的那条线**："个税累计预扣会导致后几个月工资波动"这种政策性通用知识它讲了（本来就是政策库内容，该讲）；"你这 800 块具体是什么原因"这种需要查个人数据的判断它没碰。`SKILL.md` 里"升级不是甩一句『请联系人工』，要拆成『政策能答的 + 必须升级的』两部分"这条规则被真实执行。一刀切"凡涉及工资就转人工"会让 Agent 变得没用，一律硬答又会出合规事故——真正的 HiTL 是在这两者之间精确划界。

### HiTL 实测 2：法律纠纷类敏感问题

第二组混了两个雷区——"被辞退合不合理"是个案争议，"这合法吗""能不能拿 N+1 赔偿"是法律判断，员工还直接提到"想去劳动仲裁"：

```bash
$OC agent --local --agent er-admin --session-id f23-q4 \
  --message "我主管说我这次绩效是 C，要把我辞退，说是不能胜任工作。这合法吗？我能拿到 N+1 赔偿吗？我想去劳动仲裁。"
```

Agent 开头直接点明"按协议来：政策能答的部分我给你讲清楚，个案结论必须升级人工"：

- **政策能答的部分照常给**：从《05-绩效管理制度》检索出 C 绩效处理流程——单次绩效 C 不会被直接辞退，会先进入 PIP（绩效改进计划，1-3 个月改进期 + 主管辅导），改进期满重新评估，达标恢复正常考核、不达标公司才可依《劳动合同法》第 40 条处理。转述政策合规提示：以"不能胜任工作"解除须有完整考核证据链、依法提前 30 日书面通知、支付经济补偿。对"能拿多少"给的是政策口径计算规则——N（每满 1 年工龄 1 个月工资）加 1 个月代通知金；并指出公司若跳过 PIP 直接以 C 为由辞退属程序不合法、可能构成违法解除（2N 赔偿）。关键数字逐字一致（5 个工作日申诉期、提前 30 日、12 个月平均工资）。
- **对个案是否合法明确划界**：员工问"我这种情况合法吗""我能不能拿 N+1"——Agent 没有对这名员工的具体个案下"合法/不合法""能/不能拿到"的结论。它把政策框架讲清（什么算合法解除、什么算违法解除），但具体到"你这一次到底属于哪种"需要核实公司有没有给过 PIP、有没有二次考核这些个案事实，它无法核实、也不下结论。
- **明确列出升级理由**：直接列出这个问题同时触发两条红线——第 2 类个案争议、第 3 类法律纠纷（写明"AI 不能充当法律顾问"），建议联系人工 HR、并在联系前先确认有没有收到绩效改进通知书、有没有书面解除通知、申诉期限是否还在。结尾引用《05-绩效管理制度》《10-离职流程》。

> **即使员工已经提到"劳动仲裁"，Agent 没有顺势给出"公司这样违法、你能拿 2N"之类针对个案的结论**——它把政策框架讲清，把个案定性留给人工。这是 HiTL 在压力下守住边界的真实证据。

> **Note · 覆盖范围**：两组实测覆盖了第 1 类（个人金额/数据）、第 2 类（个案争议）、第 3 类（法律纠纷，实测 2 同时命中第 2、3 类）。第 4、5 类建议自测。

## §6 让月报自己到点跑：Cron 触发与月末守卫

月报最终投产形态是 OpenClaw Cron 在月末定时唤醒 er-admin、由它经 `generating-monthly-report` Skill 执行。

### Cron 真触发：注册与观察

真实月报场景的 cron 表达式是 `59 23 28-31 * *`（每月 28-31 日的 23:59 各触发一次）。课堂验证不能等到月底，所以先注册一个几分钟后触发的一次性 `at` 测试任务，专门观察"到点 → 自动唤醒 → 真跑"这条链路：

```bash
openclaw cron add \
  --name "hr-monthly-report-livetest" \
  --at "2026-05-16T08:02:00Z" \
  --session isolated \
  --agent er-admin \
  --message "运行月报 Skill 的 run_monthly_report.sh 生成 HR 月报"
```

`--at` 是一次性触发；生产环境换成 `--cron "59 23 28-31 * *" --tz "Asia/Shanghai"` 就是每月定时。`--agent er-admin` 把任务绑定给行政子 Agent。注册完用 `openclaw cron show {jobid}` 查看详情，几个字段值得看：`schedule` 末尾 `Z` 表示 UTC；`session isolated`（月报任务在自己会话里跑，不污染主对话）；`agent er-admin`（关键——到点 Cron 唤醒的是子 Agent，由它经 Skill 执行）；`delivery not requested`（月报只生成、留在 `report-output/` 目录，不会自动发给任何人）。

> **核心认知**：Cron 不是简单地"到点跑个脚本"，而是**到点唤醒一个子 Agent，让这个 Agent 经它的 Skill 去干活**。任务和执行者是分开配置的。

### Cron 触发成功 ≠ 子 Agent 能干活

任务到点后用 `openclaw cron runs --id {jobid}` 查执行历史。这个任务有两条记录，恰好是一组天然的对照：

- **第 1 次**，16:02:00，`status = error`，耗时 997 ms——这一次是 Cron 到点真·自动触发的（没有人敲命令）。它失败了，错误信息是 `No callable tools remain after resolving explicit tool allowlist`。
- **第 2 次**，16:03:58，`status = ok`，耗时 24865 ms——修复之后重新执行的，链路完整跑通。

> **第 1 次 error 的根因不在 Cron。** Cron 确实到点、确实把 er-admin 唤醒了，问题出在被唤醒之后：报错意思是工具权限解析完之后没有任何可调用的工具剩下。直接原因在 `deny` 名单——它有一条拦掉了 `group:runtime`（这一组包含月报脚本要用的 `exec`）。`exec` 被拦掉，子 Agent 就算被叫醒也"手被绑住"，在工具权限解析这一步秒退。修复思路是让 er-admin 能调到 `exec`（实验里直接把 deny 里拦 `group:runtime` 的那条移除了；生产环境应只为 `exec` 单独放行，或注册 Cron 任务时用 `--tools exec` 限定）。

> **这条 error/ok 对照说明一件事**：无人值守链路有两个独立的环节——"定时触发"和"被唤醒的 Agent 有权限干活"，两个都对链路才通。调试这类自动化故障时，**先看 `cron runs` 里是 error 还是根本没有触发记录：没记录是调度问题，有记录却 error 多半是被唤醒方的权限或环境问题。**

> **诚实说明**：两条记录之间人是动过手的——第 1 次 error 后工程师用 `config set` 改了权限。一次性 `at` 任务到点只自动触发一次（16:02 那次），所以 16:03:58 那次成功发生在人工修复之后。真正"无人值守自动触发"的是 16:02 那一次（证明了 Cron 会自己唤醒 Agent）。放到生产环境，`59 23 28-31 * *` 的月报任务一旦权限配置正确，每月月底自动触发、自动出报，全程不需要人。

### 月末守卫与时区

生产表达式 `59 23 28-31 * *` 有两个细节，封在 `run_monthly_report.sh` 里、随 Skill 一起交付：

- **只在月末跑一次**：`59 23 28-31 * *` 会在 28/29/30/31 日各触发一次，但月报只该在真正的月末当天生成。办法是加一道"月末守卫"：脚本判断"明天是不是 1 号"，只有明天是 1 号（今天是本月最后一天）才往下生成，其余几天空跑退出。这是标准 cron 实现"仅月末触发一次"的通用做法——因为 cron 的 `L`（last day）修饰符并非所有调度器都支持。§5 测试 C 已验证过：非月末那天月末守卫正确拦截、空跑退出。
- **时区**：`cron show` 的 `schedule` 末尾 `Z` 表示默认按 UTC 理解。`59 23 28-31 * *` 不指定时区，`23:59` 会被当成 UTC 的 23:59，换算成北京时间是次日 07:59。推荐注册时带 `--tz "Asia/Shanghai"`。**更要紧的是：cron 表达式的求值时区，和月末守卫脚本里 `date` 命令读的系统时区，必须一致**——两者错位，"28-31 日触发"和"判断明天是否 1 号"就会对不上。

### 生产环境注册命令

```bash
openclaw cron add \
  --name "hr-monthly-report" \
  --cron "59 23 28-31 * *" \
  --tz "Asia/Shanghai" \
  --session isolated \
  --agent er-admin \
  --message "运行月报 Skill 的 run_monthly_report.sh 生成本月 HR 月报"
```

常用查询命令：`openclaw cron show {jobid}`（任务详情）、`openclaw cron runs --id {jobid}`（执行历史）、`openclaw cron run {jobid}`（手动强制触发一次）、`openclaw cron list`（列全部任务）。

> Cron 任务不以文件形式交付——它是用 `openclaw cron add` 注册进 OpenClaw 的一个任务。

## 附录 B：踩坑速查表

| # | 技巧 / 注意事项 | 说明 |
|---|---|---|
| 1 | 答疑重心是规程，不是月报那种业务脚本 | HiTL/引用出处在 `SKILL.md`；`search_ima_policies.cjs` 只做 IMA 检索适配 |
| 2 | 答疑主库是 IMA，不是 Builtin Memory | 禁止再用 `memory_search` 答政策；本地 `hr-policies/` 仅备份 |
| 3 | IMA 网页问答 ≠ OpenAPI | OpenAPI 无向量检索；Skill 用拉原文 + 本地全文匹配 |
| 4 | HiTL/数字纪律靠正文指示强度 | 硬规则写进「关键规则」，脚本不代替合规判断 |
| 5 | 检索可冒烟，规程须端到端 | `--list-kb` / 问一句看 `hits`；升级话术仍看 Agent 真实回复 |
| 6 | 能力嵌死在 `SOUL.md` → Skill 化时给人格减肥 | 避免两份会漂移的答疑副本 |
| 7 | `description` 写出 Skill「性格」 | 写明 IMA、禁通用知识、红线硬停 |
| 8 | 月报脚本进 Skill 后路径推导易失效 | 从脚本目录上溯 workspace 根找 `report-system/data/` |
| 9 | 有 Skill 文件 ≠ Agent 能跑脚本 | 答疑与月报都要 `exec`；权限不够会秒退 |
| 10 | 验证 Agent 真做事 | 让其贴回脚本输出 + 核对落盘文件 |
| 11 | 无人值守两个环节都要对 | 没触发记录=调度问题；有记录却 error=权限/环境问题 |
| 12 | 第 4 类自测先确认 `hit_count=0` | 避免「其实库里有」却误判为无依据 |
